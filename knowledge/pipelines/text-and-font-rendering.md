## 0. 方向变更记录：本文档在写作过程中被推翻重写过一次

**必须先读这一节，否则后面的结论会显得前后矛盾。**

本次调研最初的任务方向是「离线预烘焙像素点阵字体到图集，运行时零字体依赖」，候选字体全部是像素点阵字体（Fusion Pixel Font 等）。调研过程中，项目所有者推翻了这个方向，理由是：

> 12px 像素字体渲染汉字实际不可读——笔画多的字（「鑫」「囊」「攀」）在 12×12 里会糊成一团，中文像素字体要到 16px 才勉强，而那个尺寸已经不成其为像素风了。「像素风字体 + 中文」本身是个别扭组合。

新方向：**优先可读性与 i18n 排版能力**，字体从「像素点阵」改为「开源无衬线 CJK 字体」（思源黑体 / Noto Sans CJK 一类），渲染架构从「离线预烘焙图集」改为「运行时用 `cosmic-text` + `glyphon` 排版栅格化」。本文档从第 1 节开始按新方向写；旧方向的产出（像素字体调研）已作废，不再收录在正文里，只在「与规格的出入」一节里提一句避免后来者去找一份不存在的旧稿。

**这之后又有两轮范围收窄，同样写进正文而不是另开一节**：一轮追加了「美观」判定项（拉丁/CJK 协调、与美术方向是否冲突、字重是否够、小字号可读性，见第 4.1、4.2 节）；紧接着又把范围收窄成「只用一套字体家族、不做展示字体」（见第 2.5 节），把"字重覆盖"的优先级从美观四项之一提升为与许可证同级的否决线，把"字形性格"的优先级下调到可读性之后。**这两轮修订发生在同一次调研会话里，前一轮的判断（比如"字形性格"曾经被要求重点评估）被后一轮部分推翻，本文档只保留最终结论，前一轮被推翻的具体措辞不再收录，避免读者拿着已经作废的中间结论去用。**

## 1. 核心架构：两条渲染通道，各管各的分辨率

### 1.1 世界层：已经存在、已经验证的整数缩放管线

`ll-render` 现有的世界渲染管线（`crates/ll-render/src/target.rs`）已经是「低分辨率画布 + 整数倍放大」的结构，**不是新设计，是既有代码**：

- `LOGICAL_WIDTH = 640`、`LOGICAL_HEIGHT = 360`（`target.rs` 第 10、13 行）
- `fit_viewport` 按窗口尺寸算 `scale: u32`，取宽高两个方向能撑满的整数倍中较小的那个，`RenderTarget::blit_to` 按这个整数倍把 640×360 的画布放大贴到窗口 surface 上
- 测试直接锁了这个行为（`target.rs` 第 372–419 行）：窗口恰好两倍尺寸时 `scale == 2`；非整数倍时**向下取整**而不是拉伸变形（「非整数倍缩放会让相邻像素被放大成宽窄不一的方块，是像素美术最刺眼的瑕疵，宁可留黑边」，原注释原话）；窗口比逻辑分辨率还小时兜底取 `scale == 1`

**修正一处过度引用**：交接材料里曾提到「实测 scale=2/4」，本次实读代码只找到 `scale == 1` 与 `scale == 2` 两档的直接断言（`fit_viewport(2560, 720)` 那条测试概念上能推出 4 倍会被高度那边的 2 倍限流，但**没有一条测试直接断言过 `scale == 4`**）。这条不算错，但「4」这个具体数字**未核实**，写文档时不应当成已验证的既有事实转述。

这条管线是**像素画的家**：世界瓦片、精灵、UI 的九宫格边框，都应该走这条路径，因为整数缩放是保住像素网格不糊的唯一办法。

### 1.2 UI/文本层：原生分辨率，不参与整数缩放，本文档新定的规则

文本（尤其是 CJK）**不走上面这条管线**。理由分两层：

**技术理由**：640×360 逻辑分辨率下，一个汉字撑死给到 12×12 像素的方框，前面第 0 节引用的判断已经说明这个尺寸下笔画多的汉字会糊成一团。把文字栅格化到低分辨率画布再整数放大，糊的问题不会因为放大而改善——放大只是把糊了的像素等比例放大，观感上等于用更大的模糊色块显示模糊字形。**要让汉字清晰，栅格化这一步本身就必须发生在足够高的分辨率下**，也就是必须绕开 640×360 这个画布，直接在窗口原生分辨率（或至少比 640×360 高得多的中间分辨率）上栅格化文字。

**架构理由**：`cosmic-text` 处理变宽字体的真实字体度量（前进宽度、行高、CJK 断行点）本来就是按字体的原始设计尺寸计算的，如果之后再整数缩放，度量结果与视觉呈现会脱节——比如按整数缩放前的坐标算出的断行点，缩放后未必仍然落在同一个视觉位置（取决于取整方式），容易在极端窗口尺寸下产生一像素级的错位。原生分辨率渲染没有这个中间转换，度量即所见。

**两条通道不冲突**：世界是像素画，UI 文字清晰，各自服务各自的视觉目标，这本身是像素游戏里常见的分层做法——**但本文档没有去核实某一款具体游戏的具体实现细节，这句话只是描述这个模式本身的合理性，不是拿某个产品案例背书**，避免把未核实的旁证当依据。

### 1.3 与确定性纪律的关系：这条新增的运行时字体依赖不会污染世界状态

[ADR 0002](../decisions/0002-integer-only-world-state.md) 定的规矩是「浮点只允许出现在渲染层与音频层，且结果绝不得回流入世界状态」。`cosmic-text` 的排版结果（断行位置、字形前进宽度）本质上是浮点/依赖字体库版本的产物——同一段文字在不同 `cosmic-text` 版本、不同字体版本下，栅格化出来的具体像素可能有一位之差。这**完全落在 ADR 0002 划定的允许范围内**：文本排版结果只用于当前帧的屏幕绘制，不写入存档、不参与确定性重放校验、不影响任何 `Effect`/`apply` 路径。真正需要保持确定性的是"这段文字的语义内容是什么"（来自 Fluent 翻译键 + 变量插值，这部分本来就是确定性的字符串拼接），"这段文字画出来长什么样"从来不需要跨平台逐位一致。

## 2. 为什么现在需要一套完整文本栈（推翻了先前"不需要"的判断）

先前的判断是「中文等宽、拉丁文只需每字一个前进宽度，不需要 HarfBuzz 级别的文本栈」——这个判断建立在「字体是固定尺寸像素点阵、每格一个字符」的前提上。前提没了：**改用矢量 CJK 字体后，变宽排版、真实字体度量、CJK 断行规则（不能在词中间断、标点悬挂规则）都需要一套真正的文本层来处理**，这正是新方向里「优先 i18n 排版」这个诉求本身要求的能力。

**边界仍然要划清楚**：真正需要 HarfBuzz 级别复杂整形（阿拉伯语连字变体、印地语等复杂文字的字形替换、双向文本 BiDi）的语言，本项目当前范围（简中、繁中、英文、日语预留空包）**都不需要**。中文是逐字等宽概念（每个汉字一个前进宽度，不需要连字），拉丁文/日文假名需要真实字体度量但不需要复杂整形。**如果将来要支持阿拉伯语、印地语、乌尔都语等需要连字/变体/双向的语言，这条简化就不成立**，届时需要引入 HarfBuzz 本身（或 `rustybuzz`，HarfBuzz 的 Rust 移植）做字形整形，`cosmic-text` 目前的整形能力不到这个级别（见下节维护状态核对，`cosmic-text` 用的是自带的简化整形，不是完整 HarfBuzz）。

### 2.1 Rust 文本栈候选核对结果

| crate | 用途 | 许可证（`crates.io` API 实测） | 最新版本与发布时间（`crates.io` API 实测） | 备注 |
|---|---|---|---|---|

**推荐**：`cosmic-text`（排版）+ `glyphon`（wgpu 渲染）。四项许可证全部落在本项目 `deny.toml` 现有白名单（MIT / Apache-2.0 / Zlib 均已在白名单里，见 [P0 扫描](../licenses/2026-08-16-p0-scan.md)），不需要改白名单。四个 crate 最近一次发布都在近一年内，维护状态健康。`glyphon` 就是 `cosmic-text` 官方配套的 wgpu 渲染器，与本项目 `wgpu` 渲染栈完全对口，**规格 §3/§5 原来选 `cosmic-text` 这件事本身是对的**（此前判断它"过重"是基于像素字体前提，前提已经变了）；缺的是 `glyphon` 这块渲染适配层，规格里没有点名它，本文档补上。

**`fontdue`/`ab_glyph` 的定位**：两者都只做字形栅格化，不做排版整形，如果 `glyphon` 在某个具体需求上不够用（比如需要极致的栅格化性能、或者需要绕开 `cosmic-text` 自己写排版逻辑），可以退回到它们做底层栅格化，但断行、CJK 处理、双向文本都得自己实现，不建议作为默认选择。

## 2.5 只用一套字体家族，不做展示字体

**调研过程中又有一轮范围收窄**：不做艺术字体/展示字体，游戏标题、菜单大标题、章节标题、正文全部用同一个字体家族，层次感完全靠**字号与字重**拉开，不靠换字体。这条约束直接决定了第 4 节候选评估的权重分配：

- **字重覆盖的重要性上升到与许可证同级**——没有展示字体兜底，缺字重时渲染层只能做伪粗体（描边或位移叠加），中文笔画本来就密，伪粗体会直接糊成一团。**至少要有常规 + 粗体两档真实字重，且 CJK 部分必须和拉丁部分字重数量对等**——如果拉丁字重齐全、CJK 只有一两档，中文标题没法用真粗体，这是否决级缺陷，不是「差一点」的问题。
- **字形性格的权重下降**。正文要连续读几万字，性格强烈的字体（丸ゴシック一类）读久了容易疲劳，本节改为优先"清晰、中性、耐读"，性格是否贴合美术方向放在可读性满足之后再看。**可读性 > 性格**。

## 3. 硬约束：字体一律非衬线，中文取黑体系，不设例外

**这条约束不因为放弃像素字体而放松，反而更需要明文写死。**

### 为什么

技术理由：像素尺寸下宋体/明体的三角装饰笔画（衬线）会退化成一颗孤立的亮点，看起来像脏点而不是笔形——这是像素字体阶段就成立的判断，**在原生分辨率渲染下依然部分成立**：UI 小字号（8/10/12px 对应的实际渲染尺寸区间）下，抗锯齿会把宋体纤细的衬线笔画糊成一团模糊的灰色，可读性反而不如黑体的粗壮笔画在同样小的尺寸下清晰。**这条要求与可读性是一致的，不是纯风格偏好**——这也是为什么方向从像素字体改成矢量字体之后，这条约束没有被一并推翻。

风格理由：游戏整体是像素美术基调，即便 UI 文字层走原生分辨率不参与整数缩放，字重与字形的视觉语言仍然需要和世界层的像素风保持同一个基调，黑体系的几何感比宋体的书法笔触更贴近这个基调。

### 例外口子锁死在哪：将来最可能破例的地方

**古籍、卷轴、碑文这类想要古意的文本**是将来最可能有人想用宋体/明体的地方（世界历史生成里的史书、碑刻、家族族谱这类内容，见 [世界历史生成](../design/world-history.md)）。**这里明文要求：任何想为这类内容引入衬线字体的人，必须先修改本文档这一条规则，而不是在某个 UI 组件里顺手换一个字体、绕开这条规则本身。** 目的是让"破例"这件事必须经过一次显式的文档变更和评审，而不是悄悄发生。

### 推荐结论

**推荐思源黑体 Source Han Sans（Adobe 发行版），OFL-1.1。**

核实方式：直接抓取 `github.com/adobe-fonts/source-han-sans` 仓库的 `release` 分支 `LICENSE.txt` 原文（确认是 SIL OFL 1.1，且保留名明确写的是「Source」而不是整个字体族名，不影响我们把字形烘焙/打包进游戏资产），用 GitHub REST API（`api.github.com/repos/.../contents/...`）直接读取 `SubsetOTF/CN` 目录下各字重文件的字节数（不是道听途说的"大概几 MB"，是接口直接返回的 `size` 字段），以及 `releases` 页面确认最近一次发布是 2025-06-18。

**否决了谁，为什么**：

- **Zpix（最像素）**：先前候选清单里的一项，实测其官方仓库页面写明**商业用途单个产品收费 RMB 7000 或 USD 1000**，个人/教育项目才免费——直接撞上"不接受付费"这条硬标准，出局。这条是本次核实过程中一个容易被想当然的地方（不少中文资料把它笼统称为"免费像素字体"，但没提到收费的商用条款），值得单独强调。
- **HarmonyOS Sans**：许可证原文明确禁止修改字体文件本身，这与本项目要对字体做子集化/打包处理直接冲突；且不是标准 SPDX 许可证，不落在 `deny.toml` 现有白名单的任何一类里，即便愿意手工特批也要先补一条白名单例外，成本不划算。
- **阿里巴巴普惠体**：同样的问题，许可证原文列了一串禁止行为，包含"拆分"（可以理解为覆盖子集化这类操作）。字数声称覆盖广（116,895 字），但许可证本身就堵死了我们要做的子集化操作，覆盖再广也用不上。
- **Noto Sans CJK（Google 版）**：不是被否决，是作为等价备选记录在案——与思源黑体本质是同一套字形（Adobe 与 Google 联合开发，分别按各自品牌名 Source Han / Noto 发行，字形几乎完全相同，仅版权与命名不同，这条关系是本次调研通过多篇独立二手资料交叉印证的，**不是单一信源直接原文核实的**，标注核实强度低于许可证条款本身），但实测同一档字重（简中，Regular）的 OTF 文件体积 Adobe 版 8.04MB vs Google 版 16.4MB，几乎两倍差距（原因未核实，可能是打包时的字符集范围或 hinting 数据量不同），且 Google 侧字重更新明显慢于 Adobe 侧。两个理由都指向选 Adobe 发行版更划算。

### 4.1 美观四项评估（与许可证同级的判定项）

**要求只用一套字体家族、不做展示字体，层次全靠字号与字重**（见第 2.5 节）之后，「美观」的判定标准收窄成四项：拉丁/CJK 是否协调、是否与美术方向冲突、字重是否够、小字号是否可读。逐项评估思源黑体：

**① 拉丁与 CJK 是否协调**：是。思源黑体本身就是拉丁 + CJK 一体设计的字体，不是「配一款 CJK 字体再另配一款拉丁字体」——`SourceHanSansCN-Regular.otf` 这一个文件里同时含拉丁字母、数字、标点和汉字字形，二者出自同一套设计系统，笔画粗细、字面率天然对齐，不存在"两套字形拼起来违和"的风险。这一点直接满足了"最稳做法是用同一个超级家族"的要求，且不需要额外配一款拉丁字体——**Inter 这类拉丁文补充候选因此不再需要**，思源黑体自带的拉丁字形已经够用，第 4 节表格里列 Inter 只是调研过程的记录，最终方案不采用它。

**② 与美术方向（日式动漫像素画）是否冲突**：**这是本文档没有查到可靠一手资料、只能给判断而非结论的一项，如实标注。** 思源黑体属于中性、偏系统风的黑体，不是丸ゴシック那类带圆润性格的字形——如果单看"是否像贴上去的"，中性字体确实有这个风险。但第 2.5 节的范围收窄已经把判断标准从"字形性格是否贴合美术方向"改成了"可读性优先，在满足可读性的前提下再看是否冲突"，思源黑体在这个新标准下是合格的：它不带任何会读久了疲劳的强烈性格，笔画结构规整，作为长文本正文字体是安全选择。真正决定"会不会显得像贴上去的"，很大程度上取决于 UI 周边元素（九宫格边框、图标、配色）与文字之间的整体协调，不完全是字体本身的问题——**这一判断没有实际视觉打样验证，标注为推断，不是核实结论**。

**③ 字重是否够**：是，且是本次调研里核实强度最高的一项。前面第 5.1 节用 GitHub REST API 直接列出的 `SubsetOTF/CN` 目录文件清单本身就是证据：`SourceHanSansCN-{ExtraLight,Light,Normal,Regular,Medium,Bold,Heavy}.otf` 七个独立文件，**每个文件都是含拉丁+CJK 完整字形的单一 OTF，不是"拉丁七档、CJK 一两档"的拼凑**——因为思源黑体从设计上就是每个字重出一个统一文件，不存在拉丁和 CJK 分开发布不同字重数量的情况。这直接满足"CJK 部分必须也有对应字重"这条否决级标准，且七档字重远超"常规+粗体"的下限要求，中文标题可以用真粗体而不是伪粗体描边。

**④ 小字号（12–16px）下的可读性**：**未核实**。本次调研没有拿到思源黑体在 12–16px 屏幕渲染下的实际渲染截图或第三方可读性测试数据，只核实到它是黑体系、x 高度按黑体字重设计通常较大（这是黑体字形的一般结构特征，不是针对思源黑体的专项测量），中文笔画在小字号下是否粘连需要实际渲染出来看。**这一项建议在拿到真实渲染管线（`cosmic-text` + `glyphon`）之后用实机截图验证，不应该只凭字体设计理念判断。**

### 4.2 清晰矢量文本与像素画世界并置：是否会打架

这是本文档被明确要求正面回答、但**没有查到可靠一手资料的一项**。搜索到的资料大多是笼统的像素游戏 UI 设计博客（如讨论"像素字体在 8K 时代为什么还流行"一类的营销向文章），没有找到具体某款日式像素风游戏"UI 用清晰矢量字、世界用像素画"的实机案例分析或开发者访谈作为证据。**如实标注：这个具体问题未核实到可靠案例，不编造。**

本文档给出的是基于第 1.2 节架构推理的判断，不是案例佐证：两条通道视觉目标不同（世界服务于像素美术的网格感，UI 服务于文字的清晰可读），只要不让 UI 的清晰矢量字直接贴在世界像素网格的边界上产生视觉对比过于剧烈的观感（比如可以让文字所在的 UI 面板本身带一层像素风的九宫格边框，形成一个"画框"把两种渲染方式的边界含糊掉，这条也是推断，不是核实），理论上是可以共存的。**这一条建议列为 P6 UI 层落地时的一项视觉验收点（实机截图比对），而不是本文档能单凭调研解决的问题。**

### 4.3 字体许可与「操作系统字体风格」的区分

项目所有者提到希望用「操作系统那种字体」，这里核实清楚：**这指的是视觉风格（中性黑体、系统 UI 常见的那种气质），不是真的要打包或调用系统字体本身**——原因如下，三条许可证结论均已实际核实：

| 字体 | 许可证结论 | 核实来源 | 是否可随游戏分发 |
|---|---|---|---|
| **微软雅黑（Microsoft YaHei）** | 版权由北大方正持有，微软向方正付费获得的是「在 Windows 系统内嵌使用」的授权，不含向第三方软件/游戏分发的权利；要把字体文件打包进游戏分发给用户，需要另向 Monotype（微软字体商用授权的代理方）购买扩展授权 | Microsoft 官方 Q&A 论坛帖子交叉印证多篇中文行业资讯（`learn.microsoft.com/zh-cn/answers/...`），核实强度中——找到的是社区问答与二手资讯的交叉印证，不是微软官方一手 EULA 文本原文 | **不可**，除非额外付费购买扩展授权，与"不接受付费"的硬标准冲突 |
| **苹方 PingFang** | Apple 的字体 EULA 明确把字体使用范围限定在"运行 Apple 软件的兼容设备上显示/打印内容"，禁止提取、修改、反编译字体文件，禁止任何形式的再分发；仅当具体字体文件的内嵌规则允许时才能内嵌到内容里（需要在 macOS 的字体信息面板逐字体核实内嵌权限） | Apple 开发者论坛与用户社区讨论帖交叉印证，**未直接核实到 PingFang 具体这一款字体的内嵌权限位标记**，核实强度中 | **不可**（默认推定，除非逐字体核实内嵌权限位后另有结论，本次未做这一步） |
| **思源黑体 Source Han Sans / Noto Sans CJK** | `OFL-1.1`，第 4 节已用一手 `LICENSE.txt` 原文核实，允许自由分发、修改、嵌入 | 见第 4 节 | **可以**，这正是选它而不是"操作系统那种字体"字面意思本身的原因 |

**实现约束（写进本文档，供后续实现参考）**：游戏必须打包自带字体文件，**绝不能依赖运行环境已安装的系统字体**——一是许可证不允许（上表已核实），二是技术风险：没装对应字体的机器上会直接显示缺字方块（tofu），这条风险不需要额外核实，是字体渲染的常识性行为。

### 4.4 CJK 字重覆盖情况汇总（回应"是否够用"）

在「只靠字号字重构建视觉层次」这个新要求下，思源黑体的七档字重（ExtraLight/Light/Normal/Regular/Medium/Bold/Heavy，且每档都是拉丁+CJK 统一的单一文件）**是够用的**——从标题（Heavy/Bold）到正文（Regular/Normal）到弱化文本（Light/ExtraLight）可以覆盖常见 UI 层次需求的绝大部分场景，且不存在"中文缺档只能伪粗体"的问题。唯一的未知数是第 4.1 节④提到的小字号可读性，**这一项仍待实机验证**。

## 5. 体积核算与子集化

### 5.1 实测体积（不是估算）

用 GitHub REST API 直接读取文件字节数（`api.github.com/repos/adobe-fonts/source-han-sans/contents/SubsetOTF/CN`）：

| 字重 | 文件 | 体积 |
|---|---|---|
| Regular | `SourceHanSansCN-Regular.otf` | 8,429,224 字节 ≈ **8.04 MB** |
| Bold | `SourceHanSansCN-Bold.otf` | 8,569,308 字节 ≈ **8.17 MB** |
| （对照）Noto Sans CJK SC Regular | `NotoSansCJKsc-Regular.otf` | 16,437,364 字节 ≈ **15.7 MB** |
| （对照）Noto Sans CJK SC Bold | `NotoSansCJKsc-Bold.otf` | 17,002,248 字节 ≈ **16.2 MB** |

**这个数字本身推翻了任务下达时"完整 CJK 字体每字重可能十几 MB"这个假设的严重性**：思源黑体（Adobe 版）简中子集，Regular + Bold 两档字重加起来约 **16.2 MB**，跟"十几 MB"这个假设里单一字重的量级相当，而不是两倍。以现代游戏资产的体积量级看，16MB 完全在合理范围内，**不构成必须做子集化的强理由**。

**七档字重全带上的体积**：第 4.4 节提到"多几档更好"，如果不只带 Regular/Bold 两档，而是把全部七档字重（ExtraLight/Light/Normal/Regular/Medium/Bold/Heavy）都打包，实测七个文件字节数分别为 7,612,056 / 8,416,432 / 8,434,332 / 8,429,224 / 8,406,556 / 8,569,308 / 8,808,068，**加总约 56 MB**（GitHub API 返回的字节数直接相加换算，不是估算）。56MB 对应七档完整字重、每档都含拉丁+CJK 统一字形，仍然在现代游戏资产的合理量级内，**没有必要为了省这几十 MB 去砍字重档位**——毕竟字重不够是第 2.5 节定的否决级标准，体积换字重覆盖率是划算的。是否真的七档全带，还是先上 3–4 档（比如 Light/Regular/Medium/Bold 覆盖弱化文本到标题的常见层次），留给资产预算最终敲定时决定，本文档给出的是体积上限不构成阻碍这个结论。

需要说明：这里的 `SourceHanSansCN`（`CN` 后缀）本身就已经是"简体中文地区子集"，不是覆盖全部 CJK 甚至全部 Unicode 的"超集"版本（超集版本如 `Super OTC` 实测 91.4MB，明显更大，这次调研没有采用它）。也就是说我们不需要在这个"地区子集"的基础上再做一次子集化——它本身已经是一个合理粒度的子集。

### 5.2 是否还需要进一步子集化

**结论：不建议做进一步子集化，理由是任务里点出的那个真问题——玩家自定义名字、mod 文本会用到未预料的字，子集化会不会把它们切掉。**

正面回答这个问题：

- 如果进一步子集化（比如只保留"通用规范汉字表一级"约 3500 字），能再省几 MB，但风险是**任何不在这个子集里的字（生僻姓氏用字、mod 作者自定义的地名/人名用字）在运行时会查不到字形**，渲染层要么显示缺字方块（tofu），要么静默跳过——这与本项目现有纪律（`p2_acceptance::GpuResources::lookup` 查不到图集条目时静默跳过，见 `p3_acceptance/font.rs` 文档注释里引用的同一条纪律）一致，但对玩家来说体验很差：自己给角色起的名字里有个字变成方块。
- 16MB 这个体积换来的是"CN 地区子集本身覆盖的字符范围已经相当宽"（该子集是 Adobe/Google 面向中国大陆通用场景设计的，覆盖国标字符集的绝大部分常用字），**用体积换覆盖率是划算的**，没有必要为了省几 MB 冒着让玩家改名功能出现缺字方块的风险再去做二次子集化。
- 明确不建议的做法：**运行时"按需从更大字体动态抽取字形"的动态子集化**。这类方案工程复杂（需要在运行时持有一份更大的字体源文件、按需做字形提取与二次打包），且与本项目"资产在打包阶段确定、运行期只做查找"的一贯思路（[总纲规格](../../docs/superpowers/specs/2026-08-16-lostland-design.md) §11.1 资产元数据 JSON 源→打包为二进制、运行期不解析文本的分工原则）相悖，不采用。
- **推荐做法**：直接打包 `SourceHanSansCN` 的 Regular + Bold 两档字重（约 16MB），不做进一步子集化。对于确实落在这个子集之外的字符（理论上存在，但本次调研没有拿到"CN 子集具体覆盖多少字、缺哪些字"的精确清单，**这一点未核实**，需要后续实际跑一次覆盖率检查），运行期走"缺字提示"路径：`cosmic-text` 本身支持字形回退（fallback）机制，可以配置一个覆盖更广的备用字体（比如引入 Noto Sans CJK 的超集版本作为纯粹的运行时回退，不参与打包体积核算，只在极端情况下触发），或者更简单地在 `tools/ll-pack` 里做一次静态检查：mod/存档里出现的自定义文本如果包含子集外字符，打包时警告而不是运行时才发现。**这个静态检查怎么做、要不要做，本文档只提出方向，不展开设计**，留给 `tools/ll-pack` 具体实现时决定。

## 6. 归属与阶段

### 6.0 规格自身的排期矛盾：P4 已经依赖文本渲染，不是 P6 才需要

**反向核对规格**（按 [审计报告](../audit/2026-08-17-doc-code-audit.md) 定的纪律：不只问"实现是否满足规格"，还要问"规格内部是否自相矛盾"）发现一处规格自身的排期矛盾，**不是本文档偏离规格，是规格原文两处互相打架**：

- 规格 §15（第 471 行）把「加载管理界面」列进 **P4**（脚本层与 Mod 框架）的交付物，且规格 §10.6（第 309–316 行）写明它的具体内容：「即 mod 管理器与脚本错误控制台的合体」，需要「结果分组显示：已加载/有警告/失败；可展开查看含文件名与行号的详细错误」——这是一个信息密度很高的文本界面，文件名、行号、错误信息都是变长文本，不是能用几个固定字符集/数字拼出来的东西。
- 规格 §15（第 473 行）同时把「UI 层：像素 UI 控件库、游戏内菜单、设置界面、i18n」整体排在 **P6**。

**这两条放在一起就是矛盾**：P4 交付物本身就需要渲染变长的、内容不可预知的文本（mod 作者写的任意文件名、Steel 脚本报出的任意错误信息），但完整的文本渲染能力（`ll-text`：`cosmic-text` + `glyphon` + `Fluent` i18n，本文档第 1、2 节描述的架构）规格却排在两个阶段之后的 P6 才交付。P4 阶段如果没有文本渲染管线，「加载管理界面」这个交付物实际上做不出来，或者只能像 P3 demo 那样用一套极简点阵字体应付（而第 7 节已经说明点阵字体连拉丁字母都撑不住可读性下限，何况要显示任意 mod 文件名和错误堆栈）。

**由此得出的结论**：文本渲染的地基（`cosmic-text`/`glyphon` 排版与栅格化管线本身，不是完整的像素 UI 控件库）应当提前到 P4 就位，完整控件库（九宫格边框、焦点导航、菜单/设置这些真正意义上的"UI 层"）继续留在 P6。这不是要求把整个 P6 提前，只是把"文本能不能画出来"这一层地基从 P6 挪到 P4，与 mod 框架同批交付——**这条结论本文档只负责指出矛盾和给出方向，不代为修改规格排期表，规格文件不在本次任务可写范围内**。

### 6.1 `ll-text` 与 `tools/ll-pack` 的职责划分

规格 §5 规划的是 `ll-text`（`cosmic-text` + Fusion Pixel Font + Fluent i18n）与 `tools/ll-pack`（资产打包）。本文档确认：

- **`cosmic-text` 的选择本身是对的**，不需要改；需要补的是它的 wgpu 渲染适配层 `glyphon`，规格原文没有点这个名字，应当在规格修订时补上。
- **字体从 Fusion Pixel Font 改为思源黑体 Source Han Sans（OFL-1.1）**，这是本文档记录的一处**明确的规格变更**，不是本文档自己的臆断——规格原文（§3 第 75 行、§14 第 38 行、§11.3 第 341 行）三处都写的是 Fusion Pixel Font，**这三处都需要在规格文档里同步修订**，但规格文件（`docs/superpowers/specs/2026-08-16-lostland-design.md`）不在本次任务的可写目录范围内，本文档只负责记录这处出入，不代为修改规格原文。
- **烘焙工具归 `tools/ll-pack`**：不再是"把像素点阵字形栅格化进图集"，而是"把思源黑体的 Regular/Bold 两个 OTF 文件作为资产收录进打包产物"——因为现在不做离线预烘焙，`tools/ll-pack` 在字体这块的职责收窄成"资产收录 + 前面第 5.2 节提到的静态覆盖率检查"，不再需要做栅格化。
- **运行时查找与排版归 `ll-text`**：`cosmic-text`（排版整形）+ `glyphon`（wgpu 栅格化渲染）+ `fluent`（i18n 文本键值与变量插值）三者组合，**这与规格 §5 对 `ll-text` 的描述（"cosmic-text 排版 + Fusion Pixel Font + Fluent i18n"）字面上只差一个字体名**，不像先前（像素字体阶段）判断的那样存在"完整文本栈 vs 字形图集查找"的路线分歧——**这一处此前判断的分歧因为方向变更已经不成立，如实记录：规格原描述基本正确，只有字体本身这一个具体名词需要替换**。

## 7. 记录一条当前的现实：P3 验收 demo 的 4×6 点阵字体

P3 验收 demo 目前用的是手写 **4×6** 像素点阵字体（`crates/ll-sim/examples/p3_acceptance/font.rs`，**本文档只读未改**）。已读过该文件：`GLYPH_COLS = 4`、`GLYPH_ROWS = 6`，字符集 `CHARSET = "0123456789ABCDEGIKLMNOQRSTUVZ "`（27 个大写拉丁字母/数字/空格，只覆盖 demo 实际会拼出来的字符），栅格化方式是把字形手绘位图拼进图集图片下方新增的一整行，走既有的图集条目查找路径。

4×6 在拉丁字母的可读性下限以下——`M`/`N`、`U`/`L`、`G`/`C` 这类字形在 4×6 的分辨率下无法区分，实机截图里名字确实认不出来。这是**已知的临时占位**，不是缺陷。

**替换时机**：不是"等做出一套更大的像素点阵字体"（这条路线已经被第 0 节记录的方向变更否掉了），而是**等 `cosmic-text` + `glyphon` 这套运行时文本管线（本文档第 1、2 节描述的架构）真正落地**。在那之前，P3 demo 继续用这套 4×6 占位字体不需要额外动作。

**必须显式记录的一条依赖**：[命名、改名与本地化](../design/naming-and-localization.md) 定的命名与本地化方案要求中文字形渲染（音素表切换到中文版时用汉字/拼音音节，见该文档「三、i18n 的坑与解法」一节），而 **4×6 点阵永远不可能渲染汉字**——汉字在任何点阵字体方案下至少需要 12×12 才有基本可读性，4×6 连拉丁字母都撑不住。这条依赖此前的任务指令里已经提过一次，方向变更之后依然成立，且更加成立：现在不只是"点阵字体太小"的问题，而是"整套运行时文本管线（`cosmic-text`/`glyphon`）都还没有落地"的问题——**真做 i18n 测试（首发简中+英文双语并行开发，规格 §11.3 要求"双语并行开发以尽早暴露硬编码字符串与长文本下的 UI 排版溢出"）之前，文本渲染管线必须先就位，否则这条要求执行不了**。这条阻塞关系应当写进后续阶段交接清单（`knowledge/handoff/`，本文档无权直接写，只在这里提示）。

## 8. 已知风险与未验证项

| 项 | 状态 |
|---|---|
| `cosmic-text` + `glyphon` 与本项目现有 `wgpu` 管线（`ll-render` 的 `GpuContext`/`RenderTarget`）具体怎么接、要不要独立一个 `RenderTarget` 或复用世界层的、原生分辨率的渲染目标怎么和窗口 surface 对齐 | **完全未实现、未验证**，本文档只定了"两条通道"的原则，没有给出具体接入代码路径 |
| `SourceHanSansCN`（简中地区子集）具体覆盖多少字、和"通用规范汉字表"或 GB18030 的覆盖率差异 | **未核实**，需要后续实际跑一次字符覆盖率检查 |
| Noto Sans CJK 的 `LICENSE` 文件里是否有显式的「Reserved Font Name: Noto」声明 | **未核实**，抓取到的 `LICENSE` 文件本身没有版权声明那一行的具体文字，只核实到许可证类型是 OFL-1.1 |
| 思源黑体（Adobe）与 Noto Sans CJK（Google）字形"几乎完全相同"这条关系 | 多篇二手中文资料交叉印证，**不是通过逐字形比对等一手方式核实的**，体积差一倍的原因也未查明 |
| 阿里巴巴普惠体的具体字数（116,895 字）、字重数量 | 来自中文字体资讯站的二手转述，**未找到官方一手来源核实**（该字体没有找到官方 GitHub 仓库） |
| `fit_viewport` 是否真的支持到 4 倍整数缩放 | 代码逻辑上支持任意整数倍，但测试只直接断言到 2 倍，4 倍**未见直接测试用例** |
| 思源黑体在 12–16px 实际渲染下是否粘连、可读 | **未核实**，需要 `cosmic-text`/`glyphon` 管线落地后用实机截图验证，见第 4.1 节④ |
| 清晰矢量文本与像素画世界并置是否违和、其他像素游戏怎么处理 | **未核实到可靠一手案例**，只查到笼统的设计博客，见第 4.2 节；本文档给出的是架构推理，不是案例佐证 |
| PingFang 具体字体文件的内嵌权限位（Font Book 面板标记） | **未核实**，本次调研未拿到 macOS 实机去查这个标记，默认按"不可分发"处理，见第 4.3 节 |
| 微软雅黑許可條款的官方一手 EULA 原文 | **未直接核实**，本次结论来自 Microsoft 官方 Q&A 论坛帖子与中文行业资讯的交叉印证，不是逐字读官方 EULA 文本得出的，见第 4.3 节 |
