# P2 → P3 交接清单

**冻结于** 2026-08-17，P2 世界与地形层结束时。
**读者**：P3（回合与战斗层 `ll-sim`）的规划者与实现者。

---

## 一、P3 会立刻撞上的三处潜伏缺陷

这三处现在都不表现为错误，因为 P2 的世界里只有地形、没有实体。**P3 引入实体的那一刻它们全部转为可见缺陷。**

### 1. `DrawOrder.foot_y` 在环面上不成立

> **[2026-08-17 doc-code-audit 更新] 已修复**，修复于提交 `c0768af`（`fix: DrawOrder 的排序键改用屏幕纵坐标`）。`DrawOrder::new` 的文档现已明确要求传屏幕纵坐标，`crates/ll-world/examples/p2_acceptance/main.rs` 的 `push_terrain`/`push_player` 均先经 `camera.world_to_screen` 换算再构造 `DrawOrder`。详见 `knowledge/audit/2026-08-17-doc-code-audit.md` 的 H-2。以下原文保留供追溯问题的历史背景。

`ll-render::sprite` 把 `foot_y` 定义为「**世界**纵坐标」，P2 的 demo 传的也是世界 y。

但在环面世界里，`y = 319` 与 `y = 0` 在屏幕上相邻却相差 319——**跨南北接缝的 Y 排序会反转**，站在接缝北侧的单位会被南侧的错误遮挡。

P1 用 `TorusSize::delta` 解决了跨接缝的**位置**，但**排序键没跟上**。P2 只有一个实体、地形又平铺，所以看不出来。

**P3 必须在引入第二个实体之前处理**：`foot_y` 应当用**相机相对的屏幕纵坐标**，而不是世界纵坐标。

### 2. `entry.footprint` 被 demo 焊死为 1×1

P2 的 demo 在 `push_player` 里硬编码 `Footprint { width: 1, height: 1 }`，而 `AtlasEntry.footprint` 是公开字段、就在手边。

hero 恰好是 1×1 所以看不出来，但规格 §12.1 明确写着「footprint 与视觉尺寸必须是两个独立概念」且**不得延后**。换成 32×48 的重点目标立刻错位。

P3 加入敌人与随从时，请从图集条目读 footprint，不要重复这个焊死。

### 3. 存档的不可信输入校验还有邻居没修

P2 修了三处（裁定 P2-6 的 `TorusSize`、P2-8 的 `WorldState` 交叉校验、P2-9 的 `TerrainKind`），但这是**同一类缺陷在同一个阶段里出现三次**。

**规律**：凡是「私有字段 + 返回 `Option`/`Result` 的构造函数」的类型，加 serde 派生时都会被 serde 从背后绕过构造校验。P3 往 `WorldState` 里加实体、时间轴、技能冷却时，**每加一个这样的类型都要问一次**：反序列化能不能造出非法值？

用 `#[serde(try_from = "…Repr")]` 中转类型强制走校验，P2 里有三处现成范例。

## 二、P2 已就绪的能力（P3 可直接用）

| 能力 | 入口 |
|---|---|
| 世界状态 | `state::WorldState { seed, clock, size, terrain }`，`new`/`advance`/`hash`，可完整序列化 |
| 地形查询 | `chunk::ChunkGrid::{terrain_at, set_terrain}` |
| 地形属性 | `TerrainKind::{blocks_sight, blocks_move, move_cost}`——**`move_cost` 是分级的**（草 100 / 浅水 200 / 山 400 / 不可通行 `u32::MAX`），供寻路直接用 |
| 视野 | `fov::compute_fov(&ChunkGrid, TorusPos, u32) -> VisibleSet`，**对称**（属性测试守护） |
| 光照与视野半径 | `ll_core::light` 的曲线 + `ll_world::light::{season_light_scale, sight_radius_at}` |
| 地形生成 | `generate::{GenParams, generate_terrain}`，四边无缝、有大陆尺度 |
| 地图数据 | `overview::{minimap, continent_map}`——只读视图，不缓存 |

## 三、必须知道的三条既有取舍

### 1. FOV 的墙可见性（裁定 P2-5）

墙与地板共用「中心落在扇区内」规则，代价是**某些边界墙格不会被标记可见**（约 97% 的随机场景中至少有一个）。

**这是刻意的**：改成「墙被扫描到即可见」会破坏对称性（实测 1500 组随机地图中 12 例不对称），而对称性破坏是玩法缺陷（被自己看不见的敌人攻击），边缘墙不可见只是视觉瑕疵。

**掩盖机制是探索记忆**——玩家上次看到那面墙时已记入记忆，这一帧没被实时标记不会让它凭空消失。探索记忆在 P5 落地（规格 §15 P5 行有债务条目），**在那之前这个瑕疵是可见的**。

### 2. 世界尺寸的两条硬约束

- 任一维度**必须 > 43×25 格**，否则 `Camera::visible_tiles` 产出重复坐标、地形填不满留黑块。`ChunkGrid::new` 在构造点拒绝。
- 宽高**必须是 16（`CELL_SIZE`）的整数倍**，否则噪声接缝不连续。`generate_terrain` 在入口返回 `WorldNotTileable`。

推荐尺寸 **512×320**（已实测地形分布合理）。

### 3. 白昼只有一个真相源

日出日落曲线在 **`ll-core::light`**，`Tick::is_daylight()` 由曲线阈值（中点 550）派生，`ll-world::light` 只做季节缩放。

**不要在别处另立昼夜边界**——P2 修的正是这个问题（两处定义每天有 4 小时结论相反）。

18:00 的光照恰好等于阈值 550，这是「阈值取曲线中点 + 窗口对称」的结构性必然，不是巧合，已有测试钉死具体数值。

## 四、规格里尚无人认领的三项

P2 收尾做了一次「反向核对规格」（查规格是否已被实现淘汰，而非查实现是否满足规格）。除已修的之外，还有三项**规格写了但从未实现、且没有任何阶段认领**：

| 规格处 | 内容 | 状态 |
|---|---|---|
| §7.3 | 「瓦片地形携带…**光照透过率**等属性」 | `TerrainKind` 无此属性，无阶段认领 |
| §7.1 | 「**气候为周期性条带**：两条赤道 + 两条极圈」 | 全仓零实现，无阶段认领 |
| §7.2 | 「季节更替是**时间轴上的一个定时事件**，其 `Effect` 修改各城镇生产速率…」 | P2 用纯函数派生，无事件无 Effect |

**第三项与 P3 直接相关**——P3 要建时间轴调度器，届时必须决定：季节到底是纯函数派生（当前实现）还是时间轴事件（规格原文）？**两者不能都留着。**

> **[2026-08-17 doc-code-audit 更新]** 核实：光照透过率、气候条带两项仍零实现（未变化）。季节一项有新进展需要关注——`ll-sim::Effect` 枚举已经落地（`MoveTo`/`Damage`/`Kill`/`ScheduleNext`/`SetTerrain`/`AdjustWallet` 六个变体），但仍不含任何季节相关变体，`ll-world::light::season_light_scale` 仍是纯函数。时间轴基础设施已就位却仍未回应这个决策点，改造成本正在上升。已升级为独立审计发现 H-3，并产出工单 `knowledge/audit/worklist.md` 的 W-03，需要 P3 实现者/架构决策者裁定二选一。

## 五、规格声称存在但实际不存在的 CI 门禁

反向核对还发现规格 §14.7 列了 9 项门禁，而 `.github/workflows/ci.yml` 只有 5 项。**缺失的 4 项**：

- `cargo-llvm-cov` 覆盖率
- 无硬编码用户可见字符串检查
- 无手写欧氏距离检查（§7.1 明确写着「此项由 CI 静态检查强制」）
- 无死代码与过时文档检查

规格用的措辞是「任一项失败即阻断」。**目前这四条阻断是不存在的。** P3 应当要么补上，要么把规格措辞改成实情——两者留着不一致，本身就违反 §13。

### 顺带发现：`cargo doc` 从来不在门禁里

P2 收尾时顺手跑了一次 `cargo doc --workspace --no-deps`，发现 **1 处真正的断链**（`ll-render/src/batch.rs` 的文档链到了一个测试函数）与 **8 处「公开文档链到私有项」**警告。

这类问题 `clippy` 与 `cargo test` 都不检查，所以**积累了整个项目周期无人发现**。规格 §13 要求「文档与代码不一致即视为缺陷」，而失效的文档链接正是此类。

P3 建议把 `cargo doc --workspace --no-deps` 加进门禁（可先只对真正断链失败，私有项链接降级为警告）。

## 六、方法论：本阶段新立的一条纪律

**每个阶段收尾必须反向核对一次规格**——不是查实现有没有满足规格，而是查**规格有没有被实现淘汰**。

来由：P1 阶段规格里「精灵批处理需支持最多 4 份偏移副本」这条**错了整整一个阶段、五轮评审无一发现**。因为评审的问法始终是「实现是否满足规格」，从来不问反过来的问题。于是规格里躺了一整个阶段的错误指导。

P2 靠这条纪律修了三处（噪声方案、跨接缝绘制、阶段表措辞），并发现了上面第四、五节的六项。
