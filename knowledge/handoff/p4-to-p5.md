## 二、A. 存档格式是 P5 的核心，而它有一串前置债务

- **`ContentIndex` 不可持久化，存档必须写字符串 ID**——`ll-mod::Registry` 已提供 `snapshot()`/`rebuild_from()`（`crates/ll-mod/src/registry.rs`，Task 7），保证「按 `ContentIndex` 顺序导出/按顺序重新 `intern`」这条往返关系在内存里成立。**但快照的序列化格式（大概率 `Vec<String>`）、写入存档头的具体字段位置、读档失败时的错误路径怎么对接规格 §10.4「缺失 mod 不得崩溃」，这些接线一律未做**——`task-6-9-report.md` 第五节已明确写下这条边界，不是遗漏，是本阶段职责之外的事，P5 必须在冻结存档格式时把它做完整。
- **多处 `#[serde(skip)]` 待还**（[已还清 2026-08-19，见下方说明]）：`WorldState::population`（`ThinPopulation`）、`WorldState::actors`（`Arena<Agent>`）——P3 遗留债务；P4 本阶段又新增一处同类字段：**`WorldState::terrain_table`（`TerrainTable`）同样标了 `#[serde(skip)]`**（`crates/ll-world/src/state.rs`，Task 8 引入）。三处债务同一个模式：依赖注册期上下文的类型无法脱离该上下文反序列化，读档后默认为空。

  > **[已过时 2026-08-19]** 三处债务已在 P5 批次全部处理完毕，处理方式不完全相同，逐条说明：`population`/`actors` 两处已按本条原文设想的「真正的往返实现」摘掉 `#[serde(skip)]`，现在参与序列化（提交 `e9d0940`「`Registry::snapshot/rebuild_from` 真正接入存档头映射表」一带，`crates/ll-world/src/state.rs` 字段文档明确写着「参与序列化，见本类型文档『`population`/`actors` 现在参与序列化』一节」）。`terrain_table` 走的是本条目下一段建议的另一条路——**没有**摘掉 `#[serde(skip)]`，而是补了下一段建议的显式校验点（见下方说明），这也是当时"建议"文本本身预判的两种可能解法之一，不是遗漏。
- **`terrain_table` 读档后为空，且目前没有「是否已重新灌入」的显式校验点**（[已落地 2026-08-19，见下方说明]）——Task 8 报告（`.superpowers/sdd/2026-08-18-p4-script-and-mod/task-8-report.md` 第八节）明确写下这条：若 P5 落地存档读写时忘了显式重新灌入 `TerrainTable`，世界会安静地把所有地形当成「可通行且透明」处理——不报错，表现诡异，且没有任何警告。**建议**：P5 落地存档读写时，把「读档后 `terrain_table` 是否已被替换为非空表」做成一个显式的前置校验，失败即拒绝进入游戏而不是带着空表继续跑。

  > **[已过时 2026-08-19]** 本条建议已按原样落地：`WorldState::assert_terrain_table_loaded`（`crates/ll-world/src/state.rs`，提交 `fd8a908`「`terrain_table` 读档后补显式校验点，核实 `surface_profile` 不适用同款检查」）在 `terrain_table` 为空时返回 `Err`，`crates/ll-world/src/lib.rs` 有对应的加载期调用点。该提交同时核实了 `surface_profile` 字段**不适用**同款校验（`ContentIndex` 用魔法值 0 表示"未设置"，与 `terrain_table` 靠 `Vec::is_empty()` 判定的方式不对称），已如实记录为独立的后续开放项，不是本条债务的一部分。
- **存档必须分开记录「生成期 mod 集合」与「当前 mod 集合」**（`knowledge/design/identity-and-ids.md` 六、存档与 mod 集合）：只存当前的话，玩家中途装个 mod，那个世界就再也复现不出来——**种子分享、缺陷复现、回归测试全部失效**。P4 已经做了类型层面的区分（`ll-mod::mod_set::{GenerationModSet, CurrentModSet}`，Task 9，裁定 P4-3），编译期阻止两者混用，但**没有接任何真实存档读写**，也没有真正的「世界生成」事件可以绑定「生成期」这个时刻（P7 才有世界生成器，[2026-08-18 规格修订] 原 P6 顺移为 P7）。P5 冻结存档格式时必须把这两个类型真正写进存档头两个独立字段，不能图省事合并成一份。
- **存内容哈希而非仅版本号**——`Registry::content_hash_of(namespace)`（Task 7）已经提供了这个能力（异或折叠，`crates/ll-mod/src/registry.rs`），但同样**没有接进存档头**。mod 作者改内容不改版本号是常态，P5 必须真正把这个哈希写进存档头,不能只满足于「有这个函数存在」。
- **缺失 mod 的降级策略按内容类型分别定义**（`identity-and-ids.md` 六之②）：物品可丢弃、NPC 种族可降级占位、**玩家角色的种族不能降级**（降级意味着玩家失去自己的角色，是所有处理方式里唯一不可接受的一种）。**该文档建议再加一档只读模式**——允许打开存档查看、导出角色/物品但不能继续游玩，这好过现在「凑合丢数据继续玩」与「直接拒绝打开」的二选一。P4 完全没有触碰这部分（P4 计划「有意留给后续阶段的缺口」一节已明确列出），P5 必须正面设计这套降级策略，不能等玩家真的撞上缺失 mod 才临时决定怎么处理。
- **脚本状态存储（`knowledge/design/script-state-storage.md`，本会话新定）同样是 P5 存档格式的一部分，应与 `ContentIndex` 映射层、mod 集合双记录同批落地**——三者共享同一类问题（"某种运行期/加载期才能确定的数据，怎么落进存档并在读档后正确复原"）：`ContentIndex` 依赖 mod 加载顺序需要字符串映射表回填，mod 集合需要生成期/当前两份独立记录，脚本状态存储的键本身用的又是同一套 `NamespacedId` 命名空间隔离规则。**脚本状态存储额外多一条别的两者都没有的依赖**：文档 3.3 节「能不能存实体引用」的结论（允许存，但只限厚层 `Arena<Agent>`）依赖 `WorldState::actors` 补齐 serde——这正是本节第二条「多处 `#[serde(skip)]` 待还」提到的同一处 P3 遗留债务，P5 若安排脚本状态存储接入存档，必须同时确认 `Arena<Agent>` 序列化往返能保持槽位下标与世代号逐位不变，否则会出现「存档时脚本状态里的实体引用还能查到，读档后却查不到」这类看似诡异、实则是 3.4 节既有失效检测约定的合法结果——容易被误判成新缺陷，值得在 P5 实现说明里提前写明。
- **脚本状态存储还依赖两项本会话新定的配套决定,一并同批考虑**：[ADR 0019](../decisions/0019-denied-capability-needs-substitute-or-justification.md)（被禁能力必须有替代品或写明理由的通则,附带把现有拒绝清单与八条 mod 作者需求逐项核实过一遍,其中「整数几何工具」「每 mod 独立随机流」两条已核实是当前真实存在的缺口，优先级最高）与 [ADR 0020](../decisions/0020-scripts-may-use-floats-internally-boundary-type-gated.md)（脚本内部允许浮点，安全边界收拢到 `register_fn` 类型签名，部分取代 ADR 0002 的适用范围——`WorldState` 本身仍然零浮点不变）。三份文档同批产出、互相引用，P5 规划脚本相关任务时应当一并阅读，不要只挑其中一份。

## 三、B. 坐标系变更会影响存档格式，且必须在 P5 冻结前定形

`knowledge/design/coordinate-system-and-layers.md`（本会话新定）第十四节明确写着：**「坐标系形状必须在 P5 冻结存档格式之前定」**——这不是一条建议，是该文档存在的直接理由。

对 P2 成果的影响范围（该文档第十四节「诚实评估」，已在本次收尾核实过）：

- **必须重写、且必须先于存档格式定形的三处**：`ll_world::state::WorldState`（`terrain: ChunkGrid` 字段本身与两级坐标系前提直接冲突）、`ll_world::chunk::ChunkGrid`（要么重新设计「区块 → 存储块」索引层，要么按丙案整体替换，见该文档第十节）、`ll_world::generate::generate_terrain`（调用方式要从「一次性生成整张图」改成「按区块窗口生成」，核心算法 `terrain_at_coord`/`build_noise` 不用动）。
- **算法可平移、但需要补一个非环绕姊妹类型的两处**：`ll_world::fov::compute_fov`（算法零改动，但 `Interior` 的有界局部地图不能直接套用 `ChunkGrid` 内建的 `TorusSize::wrap`，否则视野半径接近地图尺寸一半时会「隔着地下城两端却相互看得见」）、`ll_render::camera::Camera`（`world_to_screen`/`visible_tiles` 换算逻辑不变，但需要一个基于有界坐标的等价「世界」上下文）。
- **完全不受影响的四处**：`ll_core::torus`（`TorusSize`/`TorusPos`）、`ll_world::noise`（`TileableNoise`）、`ll_world::light`（`ambient_light`/`sight_radius_at`，只需新增调用方判断——地下空间必须先查 `SpaceProfile.exposed_to_sky` 再决定要不要调用 `ambient_light(tick)`，否则地下城正午会满光照）、`ll_render::sprite`（`Layer`/`DrawOrder`，与本次的 `Space`/Z 完全是两个不同概念，只是碰巧都叫「层」，命名巧合容易混淆）。

**为什么这不是「加个字段」量级的改动**：`WorldState.terrain: ChunkGrid` 这个「整个世界一张图」的字段本身要被替换成区块索引 + 流式加载的结构，`WorldState` 的序列化纪律（ADR 0011 的 `try_from` 交叉校验模式）要延续，但校验对象要跟着新结构变——这意味着 P5 不能把「先冻结存档格式，坐标系细节以后再说」当成可行路径，必须先完成 `WorldState`/`ChunkGrid`/`generate_terrain` 三处的结构重写（数值——区块边长 128、常驻上限 256 等——可以之后再调），再谈存档格式冻结。**这条依赖关系是单向的，反过来行不通**：若先冻结了按旧模型设计的存档格式，之后再补两级坐标系，就是一次追不回旧档的存档迁移。

## 四、C. P4 期间发现的两条「本体特权」，以及它们说明什么

Task 8（`TerrainKind` 迁入注册表）迁移过程中撞出两处 API 洞，均已在本批修掉（详见 `task-8-report.md` 第六节）：

1. **`ll-sim::resolve` 硬编码 `terrain == TerrainKind::DOOR_CLOSED`——「撞门即开」只有本体能做，mod 表达不出来**。旧版 `resolve_move`/`resolve_open_door` 直接对地形做恒等比较，命中就把该格改写成开门状态；任何 mod 想注册一种「撞入即开」的地形（活板门、栅栏）都没有公开 API 能表达同样的行为，只能去改 `ll-sim` 源码。已改为 `TerrainDef`/`TerrainAttrs` 加 `opens_into: Option<...>` 通用属性，`resolve` 相应地把恒等比较换成查表。
2. **`TerrainAttrs` 写成模块私有，导致公开函数 `TerrainTable::define` 事实上外部不可调用**——编译能过，但任何模块外的调用方（包括 `ll-mod` 的 mod 地形注册函数）拿不到构造 `TerrainAttrs` 的入口。这是本批自己在草稿阶段引入又自己撞见的洞，写「本体地形与 mod 地形走同一条路径」的验收测试时直接撞见。

**结论要写明**：这两条都是「本体即 Mod」（规格 §10.3，ADR 0016 的守门规则）作为检验手段抓出来的，不是代码评审或类型检查抓出来的——若不是坚持「本体必须走与 mod 完全相同的注册路径」这条纪律，这两处会作为「本体的合理特殊处理」长期存在，直到某个 mod 作者真的想做一扇活板门才会暴露。**P5 要加职业、技能树、任务图——每一类新内容都要重复这个检验**，否则特权路径会重新长出来。具体来说：P5 设计技能效果的 `Intent`/`Effect` 产出路径时，若发现某个技能效果（例如「击退」「击晕」这类需要直接操作 `WorldState` 局部状态的效果）本体实现里抄了近路（直接改字段而不是走脚本 API 能表达的通用属性），要按 ADR 0016 的守门规则处理：**这是 API 缺陷，不是特性，必须修 API，不允许开后门**。

## 五、D. 端到端仍是最有效的缺陷发现手段

P4 的验收 demo（Task 12，`crates/ll-ui/examples/p4_acceptance/`）用真实窗口 + 真实按键驱动跑起来，又抓出两个只有真跑才暴露的缺陷（`task-11-12-report.md` 第四节），性质与 P3 交接清单第一节记录的两个缺陷（`resolve` 从不读敏捷、玩家死亡后主循环空转）相同——**单元测试全绿完全没测出来**：

| 缺陷 | 现象 | 对照 `docs/qa/04-覆盖率与缺失测试层.md` L4–L8 空白盘点，落在哪一层 |
|---|---|---|
| P3-1：`resolve` 从不读敏捷 | 时间轴排期时刻不受 `agent.stats.dexterity` 影响，「敏捷不同→出手频率不同」这条手感在结算层根本不成立 | **L6 端到端**——`04` 文档原文：单元测试各自测「这一段代码在给定输入下行为对不对」，没有测试问「敏捷字段真的从 `Agent` 流到了排期时刻吗」；这是跨模块的连线断了，不是单个函数错了 |
| P3-2：玩家死亡后主循环空转 | `advance_ai` 只在循环入口检查玩家存活，玩家在循环内部死亡时会继续对其余敌人反复空转直到耗尽步数上限 | **L6 端到端**——同上，`Effect::Kill` 把玩家移除后循环条件没有跟着更新，是「一段脚本化输入序列跑够多步、断言若干步之后关键状态」这类测试才会揭示的问题 |
| P4-1：熔岩地板被深水隔断，玩家走不过去 | mod 注册的熔岩地板最初铺在出生点东偏移 3~6 格处，中间隔着一段深水，真实窗口里连续按方向键玩家纹丝不动 | **L6 端到端**——这同样是「一串移动 Intent 依次结算后，玩家是否真的到达了目标格」这个跨越多个 tick 的连通性问题，不是任何单个 `resolve_move` 调用的正确性问题（`resolve_move` 本身对每一步输入的判定都是对的，问题出在地形摆放导致整条路径不连通）；已补一条回归测试锁住「出生点到 mod 地形之间不得有不可通行的阻隔」这条约束 |
| P4-2：加载管理界面文字面板换行错位 | 展开失败详情时，较长的错误消息/绝对路径在面板宽度内被 `cosmic-text` 自动换行，压住下一行文字，肉眼看不清 | **L7 视觉回归**——这是渲染像素层面的问题，`cosmic-text` 的排版 API 调用本身没有报错，问题是排版结果与面板宽度的组合在视觉上不可读；`04` 文档写 L7「有基准生成机制，没有自动比对」，本次仍然只能靠真人截图肉眼发现。**顺带一条**：`04` 文档写 L4 快照测试的「UI 布局」子项当时因为 `ll-ui` 还不存在而「无从谈起」——**现在 `ll-ui` 已经落地**，若当时有一层 `insta::assert_snapshot!` 快照 `TextRun` 的具体坐标/宽度，这类溢出/重叠本可以在不跑真实窗口的情况下被自动发现，成本远低于「跑起来、截图、肉眼看」这条路径 |

**给 P5 的建议，按性价比排序**：

1. **L6 端到端测试应该真正建起来，不能再拖**——三轮交接清单（P2→P3 第一节引 `04` 文档、P3→P4 第一节、本轮）都在重复同一条建议，P4 阶段本该起步（`p3-to-p4.md` 已经明确要求「P4 计划落地时应当把『起步 L6 端到端测试』列为前置任务」）但实际没有做，仍然只有手动跑 demo + 肉眼看。P5 引入技能树/任务图后，跨模块的连线只会更多（脚本产出 `Intent` → 结算 → 效果 → 下一轮时间轴调度这条链现在还要叠一层任务状态机），继续靠「手动跑一次验收 demo」发现缺陷，发现窗口会越来越晚、修复成本越来越高。
2. **`ll-ui` 已经存在，L4 UI 布局快照测试现在成本很低、收益明确**——针对 `TextRun`/面板布局结果做 `insta` 快照（不是像素级，是排版结果的坐标/宽度数据），P4-2 这类溢出/重叠缺陷本可以被这一层拦住，且不需要真实窗口或 GPU。
3. **P5 的存档反序列化是 L5 模糊测试新的最高优先级目标**——`04` 文档第 5 节已经指出「存档反序列化的 fuzz target 现在就可以补，因为存档格式已经存在」，但那时候（P3 冻结）的存档格式只是 `WorldState` 的裸 serde 往返，P5 才会有真正需要面对玩家真实文件的存档格式（含 mod 集合、内容哈希、schema 迁移）。畸形/截断的存档文件是玩家会真的遇到的输入，P5 必须在存档读取路径接入之前就规划好模糊测试覆盖，不要重复 P4「格式已存在但没人为它写 fuzz target」这个模式。

## 六、E. 工程流程：两条已确认的教训

### 1. 并行代理必须各自独立的 git worktree

`p3-to-p4.md` 第六节已经记录过一次真实的三次提交撞车教训（P3 收尾评审与另一个并行代理共享同一个 git 工作树）。P4 期间这个问题**升级**了，不再只是提交撞车这么温和：Task 6/7/9（`ll-mod`）与 Task 10（`ll-text`）两条并行线各自新建了一个 crate，而 workspace 用 `crates/*` 通配成员——`task-6-9-report.md` 第三节明确写着「按包验证（开发过程中使用，规避与 `ll-text` 并行编辑造成的间歇性工作区解析失败）」，这不是猜测，是实际撞见的现象：**其中一个正在编辑中的 `Cargo.toml`（半写状态）会让所有人的 `cargo` 命令一起挂**，因为工作区级命令要解析全部成员的 `Cargo.toml`。

**领地分开（各自只碰自己的 crate 目录）挡得住文件内容冲突，挡不住共享构建状态**——`cargo fmt --all --check`/`cargo test --workspace` 这类工作区级命令没有「只看我关心的那部分」这个选项，任何一个成员的 `Cargo.toml` 处于无法解析的中间状态，会让所有并行代理的工作区级验证同时失败。P5 若继续按 crate 边界拆分并行任务（规格「并行切分」一节本就鼓励这么做），**必须先把 worktree 隔离作为并行开发的前提条件写进计划**，尤其是任何涉及「新建 crate」的任务——这是比「共享工作树下精确 `git add`」更根本的问题，worktree 隔离能同时解决两者。

### 2. 裁定必须及时提升为 ADR

ADR 0013（`knowledge/decisions/0013-ledger-vs-adr-discipline.md`）记录了这条教训的由来：本项目从 P0 到 P4，阶段执行期的裁定一直写在 `.superpowers/sdd/<日期-阶段名>/progress.md` 这份账本里，而这份账本从诞生起就被 `.gitignore` 排除，**从未进过版本库**。P4 期间，一个子代理需要引用裁定「P4-4」时，在版本库能看到的范围内找不到任何对应记录——**它没有编造一个听起来合理的解释去填补空白，而是如实报告了这处引用缺失**，这次如实报告是本次「账本抢救」任务（提升 ADR 0014–0017）存在的直接原因。

现已确立的纪律：**任何「将来有人会想推翻」的裁定，必须在做出的当下就提升为 ADR，不能只留在账本里等事后抢救**。判断标准见 ADR 0013 原文（影响多 crate/跨阶段、有被否决的替代方案且理由不会过期、定下将来可能被推翻的规矩、由实测数据支撑）。**这条纪律依赖执行期的自觉，账本本身不会主动提醒**——P5 的控制者/子代理在做出裁定的当下就要对照这套标准自问，而不是假设「反正账本还在，以后需要再翻」。

## 七、F. 已知边界（照实写，不要粉饰）

- **白名单的 18 个「安全」模块（`SAFE_MODULES`，`crates/ll-script/src/whitelist.rs`）是按名称与用途审查的，不是逐函数体审计的**——ADR 0012「已知边界」一节明确写着：「本次审阅了名字与模块用途，没有逐个函数体验证实现细节」。这是比原来的黑名单更小、但不是零的残余面。
- **`steel/time` 模块投毒失效的根因仍未查清**（ADR 0012「待查项」）——「覆盖模块注册表」这条缓解手段对 `steel/random` 确认有效，对 `steel/time` 确认无效，且排查过「进程级缓存」「跨引擎共享 Arc」等假设均被对照实验排除，仍未找到自洽解释。白名单已经从另一个角度（校验完整展开后的 AST）独立堵死了 `steel/time`，因此这条待查项**目前不影响产品代码的正确性**，但意味着「模块覆盖」这个模式在未来遇到新模块时不能被假设「会重演或不会重演」。
- **两处被拒绝的能力标注为「因未验证而拒绝，非已证明危险」**——`crates/ll-script/src/host.rs:114-117`：`module->exports`（探测模块导出了什么，与「能力不存在」的精神有摩擦，保守拒绝）、`inspect`（具体行为未验证清楚是否会暴露内部结构，同样保守拒绝）。**是将来可放开的候选**——若后续任务证明某个 mod 场景确实需要，应该针对具体名字单独复核并写清楚新的判断依据，而不是恢复整批。
- **`TerrainTable` 的稀疏度设计只被地形一种内容类型验证过**（`task-8-report.md` 第八节）——`TerrainTable` 内部按全局 `ContentIndex` 下标定长、配 `defined` 位图区分「这个下标是不是地形」，这个设计已经为未来的技能/物品等内容类型留了余地，但实际混合多种内容类型后号段是否会让 `Vec` 稀疏到不划算，需要等 P5 真正的技能/职业注册落地才能验证——**不要假设这个设计已经被证明适用于所有内容类型**。
- **P4 demo 的 F2 基准图只覆盖世界层**（`crates/ll-ui/tests/visual/baseline/p4_acceptance.png`），文字面板在窗口 surface 上无法读回——窗口 surface 纹理只声明了 `RENDER_ATTACHMENT` 用途、不含 `COPY_SRC`，这是 `ll-text` 「两条渲染通道」架构决定的结果（文字走原生分辨率、直接提交到窗口 surface，不经过世界层的离屏 `RenderTarget`），不是本次疏漏。P5 若要对加载管理界面之外的其他 UI（技能树面板、任务日志）做视觉回归，需要先解决这条读回缺口，否则新增的 UI 内容永远只能靠肉眼截图核对。
- **SendKeys 无法可靠合成方向键**（extended-key 限制）——demo 改用 WASD（`d` 键同样映射到 `GameKey::Right`）。这是这台机器上 Windows `System.Windows.Forms.SendKeys` 的已知历史限制，不是产品缺陷，但意味着**任何未来依赖自动化按键注入的测试/演示流程，都不能假设方向键可靠**，需要用 WASD 或改用更底层的按键合成 API。
