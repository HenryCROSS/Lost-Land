# P3 → P4 交接清单

**冻结于** 2026-08-17，P3 回合与战斗层（`ll-sim`）结束时，对应提交 `071882a92e55a1107ed20429edcb001b6797e298`，345 个测试全绿。
**读者**：P4（脚本层与 Mod 框架：Steel 宿主、内存守卫、注册表、命名空间 ID、加载管理界面）的规划者与实现者。

这份清单不是 P3 成果汇报——交接清单的价值在于把坑说清楚，不在于业绩。以下内容分三类：P3 期间真实发生过、已经修复但暴露了测试层空白的缺陷；一个目前只靠数值约定挡着、P4 引入 mod 后约定会失效的结构性缺陷；以及 P4 直接依赖的一批设计决定与规格调整。

## 一、三个真实缺陷带来的教训

这三处现在都已经修复，**但修复本身不是重点**——重点是它们为什么能在 321～345 个测试、六道 CI 门禁、多轮文档审计之下全部躲过，直到有人**真的把 demo 跑起来**才现形。

### 1. `resolve` 从不读敏捷

`crates/ll-sim/src/resolve.rs` 在修复前，`resolve_wait`/`resolve_move`/`resolve_attack`/`resolve_open_door` 四个分支全部直接向 `action_cost` 传入常量 `BASELINE_EFFECTIVE_SPEED`（现在的 `resolve.rs:51`），不读 `agent.stats.dexterity`。P3 核心验收点「敏捷不同 → 出手频率不同」（时间轴调度器「敏捷高者能在同一窗口内多行动几次」这条手感，`crates/ll-sim/src/timeline.rs` 模块文档开篇）因此**在结算层根本不可能成立**——`Timeline` 的排序逻辑是对的，喂给它的排期时刻却从未因敏捷不同而不同。

现状（已修）：`resolve.rs:78` 的 `effective_speed_from_dexterity` 把敏捷接上了线性比例，`resolve_wait`/`resolve_move`/`resolve_attack`/`resolve_open_door` 四个分支（调用点分别在 `resolve.rs:112`/`135`/`198`/`221`）全部改读 `agent.stats.dexterity`；回归测试 `敏捷更高的角色等待耗时更短`（`resolve.rs:422`）钉死了这条行为。修复提交：`73a2ee5`。

**为什么 321 个测试没抓到**：按 `docs/superpowers/plans/2026-08-17-p3-turn-combat.md` 的任务划分，Task 3（`crates/ll-sim/src/timeline.rs:150` 的 `action_cost`，259 行起）单独测了这个公式本身的正确性（`timeline.rs:163` 的 `行动代价公式在基准敏捷下等于基础代价`）；Task 6（342 行起）单独测了 `resolve` 各分支的纯函数性质（目的地是门则开门、目的地不可通行则作废等）。**两组测试各自都通过，因为各自测的都是「这一段代码在给定输入下行为对不对」，没有人写一个测试去问「敏捷字段真的从 `Agent` 流到了排期时刻吗」**——直到 Task 9（P3 验收 demo）里给两个敌人分配不同敏捷、肉眼观察谁出手更频繁，才第一次触发这条连线。

### 2. 玩家死亡后主循环空转

`crates/ll-sim/examples/p3_acceptance/turn.rs` 的 `TurnEngine::advance_ai`（现 `turn.rs:167`）在修复前，唯一的提前返回条件是「弹出的时间轴条目属于玩家」（`entry.actor == player`）。`Effect::Kill` 把玩家从 `world.actors` 与 `Timeline` 移除后，这条条件永远不会再成立——若玩家在循环进行到一半时被杀死（`advance_ai` 本身每一步都可能结算一次存活敌人对玩家的攻击，玩家因此完全可能死在循环内部，不是只可能死在入口），循环会继续对其余存活敌人反复空转，直到耗尽 `MAX_STEPS_PER_ADVANCE`（`turn.rs:39`，10000）才放弃，实测单帧卡顿达数秒（`turn.rs:163` 注释：「肉眼表现为长达数秒的卡顿」）。

现状（已修）：循环体内部每一步都重新核查 `world.actors.get(player).is_none()`（`turn.rs:175`），玩家一死立即返回；回归测试 `玩家在advance_ai内被杀死后立即返回不耗尽单帧步数上限`（`turn.rs:576`）用敌人攻击力 9999 的极端设定逼出这条路径，断言结算次数远小于步数上限。

这个缺陷本身也印证了 `MAX_STEPS_PER_ADVANCE` 这道防线的价值——它把「未预见的死循环」从「冻结整个事件循环」降级成「本帧卡顿后自动放弃」，但**防线生效不等于缺陷不存在**，玩家死亡那一帧仍然会卡顿到防线兜底为止，只是不会永久卡死。

### 3. 两者都只有把 demo 真正跑起来才会暴露

345 个测试、六道 CI 门禁（`.github/workflows/ci.yml`：格式、clippy、测试、许可证扫描、禁止手写欧氏距离、覆盖率门禁、i18n 硬编码字符串扫描、文档断链检查——比 `knowledge/handoff/p2-to-p3.md` 记录的五道已经多了几道，但增加的是静态检查，不是新的测试层）、多轮文档审计，全部没抓到这两处。

**对照 `docs/qa/04-覆盖率与缺失测试层.md` 的 L1–L8 空白盘点**：两处缺陷都精确落在该文档标注为**「完全没有」**的 **L6 端到端测试**这一层——L1 单元测试（有，235 个）、L2 属性测试（有）、L3 集成/黑箱测试（有，48 个）各自独立看都是绿的，正是因为它们测的是「单个函数/单个模块在给定输入下对不对」，而这两处缺陷的共同特征是**跨模块的连线断了**（敏捷字段没有从 `Agent` 流到 `Timeline` 排期；`Kill` 效果没有让 `advance_ai` 的循环条件跟着更新）。`04` 文档在 L6 一行明确写道：「游戏循环的核心骨架（时间轴调度 + Intent/Effect/Apply）已经在 `ll-sim` 落地……这是端到端测试第一次有了『完整循环』可测的对象——建议下一阶段（P4 前后）就该起步，而不是继续拖到后期」。这份 QA 审计本身早于这两处缺陷被发现（其冻结提交 `4bdd87d` 早于修复提交 `73a2ee5` 与 P3 验收 demo 提交 `ae6d713`），**换句话说，它在缺陷暴露之前就已经预判了这个空白会出问题**。

**结论**：本项目当前最缺的测试层不是覆盖率数字（覆盖率门禁已经补上，见 `scripts/ci/check_coverage.sh`），而是**端到端**——一段脚本化输入序列，驱动完整的 Intent → resolve → Effect → apply → 下一轮 Timeline 弹出这条链路跑够多步，断言若干步之后的 `WorldState` 关键字段或哈希。P4 要在这条链路上再叠一层 Steel 脚本调用（技能效果、AI 决策都可能经脚本产出 `Intent`/读世界黑板），**没有端到端测试的裸结算层，加上脚本层只会让「测了每一段、没测连线」这个模式更严重**——脚本调用本身就是一条新的跨模块连线，而 L6 现在仍然是空的。P4 计划落地时应当把「起步 L6 端到端测试」列为前置任务，而不是又往后拖一个阶段。

## 二、一个结构性缺陷，目前靠数值约定挡着

`crates/ll-sim/src/timeline.rs:150` 的 `action_cost` 公式：

```rust
pub fn action_cost(base_cost: u32, effective_speed: u32) -> u32 {
    let speed = u64::from(effective_speed.max(1));
    let cost = u64::from(base_cost) * 1000 / speed;
    cost as u32
}
```

`resolve.rs:78` 的 `effective_speed_from_dexterity` 把敏捷线性映射为有效速度：`speed = 1000 * dexterity / 10`（基准敏捷 10 对应有效速度 1000）。把两者接起来看：`BASE_ACTION_COST = 100`（`resolve.rs:41`）时，`cost = 100 * 1000 / speed`；当 `speed > 100000`（即敏捷 > 1000）时，整数除法把 `cost` 截断为 0。**行动代价为零意味着该实体在同一个 tick 被无限重排**——`ScheduleNext` 排到与当前完全相同的时刻，`Timeline` 会立刻把它弹出、再立刻排回同一时刻，`advance_ai` 的 `MAX_STEPS_PER_ADVANCE` 防线会在一帧内被这一个实体单独耗尽。

**现在不触发，只因为两条数值约定**：P3 验收 demo 里全部单位敏捷 ≤ 30（`crates/ll-sim/examples/p3_acceptance/main.rs` 的 `spawn` 调用），远低于 1000 这个截断阈值；[种族系统](../design/race-system.md)「四、时间轴：不改公式，改数值预算」一节把种族固有敏捷修正限制在 **±2～4**，且明确说明大幅速度成长（疾风靴、加速术一类）留给装备与技能系统去提供——但那份设计文档同时承认，装备与技能系统本身**没有**对最终敏捷值设任何上限。

**用数值约定守护结构性缺陷，早晚会破**——P4 正是引入 mod 的阶段，mod 作者可以给任意实体注册任意 `BaseStats`，没有任何机制阻止一个 mod 定义的装备或状态效果把敏捷叠加到 1000 以上。这不是「不太可能发生」的边缘情况：一旦发生，表现是该实体（可能是敌人，也可能是被增益到极端值的玩家自己）单帧冻结游戏画面，且现象上很像本节第一条「未保证进展」的死循环，排查者会先怀疑 `advance_ai` 逻辑本身，而不是怀疑 `action_cost` 的整除截断——错误现场与根因隔着一层。

**建议**：在库层给 `action_cost` 加下限钳位（例如 `cost.max(1)`），而不是继续依赖「没人会把敏捷加到这么高」这条会随 mod 生态失效的约定。这处改动成本很低，且不影响现有任何测试（所有现存用例的敏捷都远低于阈值）。

## 三、P4 直接相关的设计决定（本轮新定，尚无代码）

以下四份设计文档是 P3 收尾期间新写的，均为**纯设计，`crates/` 里尚无对应实现**。P4 建注册表、内容 ID、mod 命名空间时会直接撞上其中的形状决定。

### 1. 身份与 ID 空间（`knowledge/design/identity-and-ids.md`）

**类型/实例分离**是这份文档的核心定案，**直接决定 P4 注册表的形状**：

- **类型（`ContentIndex`）**：mod 作者定义的东西——文化、职业、种族，几十到几百条，数量固定，集合封闭。`crates/ll-core/src/ident.rs:84` 的 `ContentIndex` 模块文档已经明确写着「不可持久化——索引依赖 mod 加载顺序」。
- **实例（`WorldId`）**：世界生成器造出来的东西——势力、家族、聚落、宗教团体、历史事件，数量随世界规模增长，且**没有对应的 mod 注册条目可以在存档反序列化时重新校验**。

当前代码现状（文档已核实）：`Affiliation.org: ContentIndex`（`crates/ll-world/src/entity/affiliation.rs`）把这两种根本不同的东西混用同一个类型表示，是这份文档要修正的对象；`WorldId`、`OrgInstance` 均未落地。

另有两条规则 P4 建注册表时需要一并遵守：**`WorldId` 永不复用**（`u32` 单调递增，不回收——40 亿容量对一个 500 年世界只用掉两万多个 ID，不需要考虑回收）；**不需要代际号**（与 `EntityId`《crates/ll-world/src/entity/id.rs:36`》的代际号机制目标相反——`EntityId` 要「引用应该失效」，`WorldId` 要「引用永远不失效，即便指向的对象已经不存在」，两者不能共用同一套机制）。

脚本 API 的形状也由此决定：查类型（`ContentIndex`）可以按名字引用（「所有信奉山地文化的 NPC」），查实例（`WorldId`）**只能按关系/角色/谓词查询**（「玩家所属家族参与过的所有战争」），不能按名字硬编引用——名字是随机生成的，换个种子就对不上。P4 设计脚本 API 时如果把这两类查询混在一起处理，会为「按名字查实例」这个看起来自然、实际上换种子就报废的用法留一个入口。

### 2. 命名与本地化（`knowledge/design/naming-and-localization.md`）

**音素表索引对齐**是 P4 命名空间 ID 之外唯一需要马上关心的约束：`NamingRules` 的各语言版本必须**表长一致、同一下标对应同一个音**（`onsets[7]` 英文版是 `"thr"`、中文版是`"斯"`，指向同一个「音位」）。若两张表各自独立生成，玩家切换语言时全世界 NPC 会同时改名，直接破坏种子分享——这不是命名系统自己的问题，是**一条 mod 数据校验规则**：mod 作者给自己熟悉的语言配表时很容易随手加几个音、不管其他语言版本的表长是否跟着变,这类疏漏单语言测试完全看不出来。文档原文建议**做成 CI 门禁**（mod 装载或构建阶段直接拒绝表长不一致的命名规则集合）。P4 的「加载分阶段隔离」（规格 §10.2 第四道防线）与内容注册表校验管线，是这条规则的自然落点——不应该等到 P7/P9 命名系统真正接入文化时才补这道检查（[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P6/P8 顺移为 P7/P9），那时候已经有 mod 在错误的假设上写了内容。

命名本体（`crates/ll-world/src/naming.rs`）已落地且与本文档一致，P4 不需要碰它；只是「查文化选 `NamingRules`」这一步目前是调用方职责，命名钩子（mod 可以让「所有海盗势力」用特别的命名规则）与 `WorldId` 的标签体系要一起设计（该文档「六、mod 可给生成器挂命名钩子」一节），但文档本身也说明「此事不急」——P4 只需要在 `OrgInstance` 形状里预留 `tag` 字段的位置，不需要现在就把钩子匹配逻辑写完。

### 3. 种族系统（`knowledge/design/race-system.md`）

`RaceDef` 走注册表（`id: NamespacedId`、`stat_modifiers`、`darkvision_floor`、`footprint`、`lifespan_years`），是「本体即 Mod」在种族上的应用，与 `CultureDef` 同一个模式——P4 的内容注册表 API 需要能装下这个形状。

**已知实现债务，P4 建注册表时会碰到**：设计结论是种族完全派生、薄层零列（`race(entity) = weighted_pick(settlement_race_weights[birth_settlement], hash(...))`），但当前 `ThinPopulation::race: Vec<ContentIndex>`（`crates/ll-world/src/entity/thin.rs:42`）是一个显式存储列，`spawn()` 把种族当调用方参数直接写入，`promote()`（`thin.rs:185`）把这一列原样复制进 `Agent.race`——**这是 P3「先把字段布局搭起来」批次留下的过渡状态，不是最终设计**。P4 若要往 `ContentIndex ↔ 字符串 ID` 映射表（见下一节存档相关内容）里登记 `RaceDef`，需要知道这处债务的存在，否则容易顺着现有的「显式列」代码风格继续往前搭,让 P9 真正落地 `RaceDef` 时返工面积更大（[2026-08-18 规格修订] 原 P8 顺移为 P9）。

### 4. 世界历史生成（`knowledge/design/world-history.md`）

体量上是 P7 阶段（[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P6 顺移为 P7），但文档明确列了**三件事必须提前做**，其中两件与 P4 直接相关：

1. **生成物 ID 空间选型**（即上面第一节的 `WorldId`/`ContentIndex` 分离）——定得晚，P7 落地时被迫返工（[2026-08-18 规格修订] 原 P6 顺移为 P7）。
2. **事件日志 ID 空间预留**——事件日志条目需要被查询式脚本 API 引用，ID 空间形状需要与势力/家族的 `WorldId` 方案一起定，不能事后另起一套。

这两条本质上是同一个决定（类型/实例分离）在不同消费方身上的复用,P4 落地内容注册表与 `WorldId` 时应当一次性把这两处的接口占位一起考虑,不要只满足 P4 自己的需求就收尾。

## 四、存档必须分开记录两组 mod 集合

`knowledge/design/identity-and-ids.md`「六、存档与 mod 集合」一节的结论，**P4 建注册表时就要把这个区分做出来**，不能等 P5 存档格式冻结后再补：

```
生成期 mod 集合   ← 这个世界是用这一批 mod 生成的，写入后永久不变
当前 mod 集合     ← 玩家现在实际开着的这一批
```

规格 §10.4 只要求存档头记录「启用 mod 列表」，没有区分这两者。**只有「生成期 mod 集合」能用来复现世界**——世界由种子完全决定这条性质（`knowledge/design/world-history.md`「诚实警告」一节）**只在内容集合相同的前提下成立**：种族分布场、聚落选址、势力形成全部读取 mod 注册的 `CultureDef`/`RaceDef` 等定义，同一个种子换一批 mod 会生成完全不同的世界。玩家中途装卸 mod 是常态,而世界一旦生成就不会重新生成——若存档只存一份「当前」mod 集合,种子分享、缺陷复现、回归测试三者全部失效。

这个决定为什么现在就要定：**存档格式一旦在 P5 冻结**,事后想把「一份」拆成「生成期/当前」两份就是一次存档迁移,而这次迁移追不回那些只存了一份、已经无法分辨「原始生成批次」的旧档。P4 阶段虽然还没有真正的世界生成器（P7 才落地，[2026-08-18 规格修订] 原 P6 顺移为 P7）,但**命名空间 ID 与 mod 内容哈希的记录机制正是在 P4 落地**——P4 决定「存档头怎么记 mod 信息」这件事的接口形状时,应当直接按两组集合设计,而不是先按「一组」实现、留给 P5/P7 再改。

该节另外还有两条建议一并抄录,供 P4 实现存档头/mod 管理器时参考：**光有版本号不够,还需要每个 mod 注册内容的哈希**（版本号没变但内容变了,读档时至少能明确警告,而不是静默炸在某个引用对不上的地方）；**mod 内容不兼容与 schema 版本不兼容必须分开报错**（前者等迁移函数链跑完,后者要玩家自己去找 mod 作者或换版本,混在一起报错会让玩家往错误方向排查）。这两条与 P4 的「加载管理界面」（见下一节）直接相关——错误控制台要能分清这两类失败,用词不能混。

## 五、规格自身的排期矛盾：文本地基已提前到 P4（规格已修订）

`knowledge/pipelines/text-and-font-rendering.md`「6.0 规格自身的排期矛盾」一节发现：规格 §15 把「加载管理界面」列进 P4 交付物,且 §10.6 写明它是「mod 管理器与脚本错误控制台的合体」——结果分组显示、可展开查看含文件名与行号的详细错误,这是信息密度很高的变长文本界面。但规格同时把完整的文本渲染能力（`ll-text`：`cosmic-text` + `glyphon` + `Fluent` i18n）排在三个阶段之后的 **P7** 才交付（写作本节时是「两个阶段之后的 P6」，[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后中间多隔一个阶段，原 P6 顺移为 P7）。**P4 阶段如果没有文本渲染管线,「加载管理界面」这个交付物做不出来**,或者只能沿用 P3 demo 级别的 4×6 手绘点阵字体应付——而那套点阵字体连拉丁字母的可读性下限都撑不住（`M`/`N`、`U`/`L`、`G`/`C` 这类字形在 4×6 分辨率下无法区分,`crates/ll-sim/examples/p3_acceptance/font.rs` 的已知局限）,更不必说要显示任意 mod 文件名与 Steel 错误堆栈。

**本次收尾已按这个结论修订规格**（提交 `d399c04`）：§15 阶段表 P4 行追加「文本渲染地基（`cosmic-text` 排版 + `glyphon` 栅格化,不含完整像素 UI 控件库）提前到本阶段就位」；P6 行（[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后，本条所述行顺移为新 P7 行）相应改为「像素 UI 控件库、游戏内菜单、设置界面」,并注明文本渲染地基已经在 P4 交付,该行不再包含它。

**P4 计划作者需要知道的边界**：提前到 P4 的是「文字能不能画出来」这一层地基（`cosmic-text` 处理整形/断行/字形回退,`glyphon` 渲染到 wgpu,字体是思源黑体 Source Han Sans,不再是像素点阵字体——字体选型的完整调研见同一份文档,规格 §3/决策 14/§5/§11.3 四处已同步修订,不在本次任务改动范围内的还有 `deny.toml` 白名单——该文档已确认思源黑体的 OFL-1.1 与文本栈四个 crate 的许可证均已落在现有白名单内,不需要改）。**没有提前的是**：九宫格切片边框、焦点导航、菜单/设置这些真正意义上的「UI 层」控件库,那些仍在 P7（[2026-08-18 规格修订] 原 P6 顺移为 P7）。P4 只需要能把变长文本清晰地画出来,不需要做出成套的像素风控件。

**未验证项,P4 实现时会第一个撞上**：`cosmic-text`/`glyphon` 与本项目现有 `wgpu` 管线（`ll-render` 的 `GpuContext`/`RenderTarget`）具体怎么接、要不要独立一个原生分辨率的渲染目标——这条完全没有代码验证过,`knowledge/pipelines/text-and-font-rendering.md` 第 8 节「已知风险」明确标注。

## 六、一条工程流程教训：并行代理共享 git 工作树不够安全

本次 P3 收尾评审与另一个并行代理（分别负责 `knowledge/pipelines/` 与 `knowledge/licenses/`）共享同一个 git 工作树,期间发生了三次提交撞车——**精确指定 `git add <path>` 并不足够**,因为两个进程的 `git add`/`commit` 命令会在共享的索引文件（`.git/index`）上交错执行：一次把无关文档改动并进了代码提交,一次把代码改动并进了文档提交,两次提交信息都与实际内容对不上（好在内容本身没有丢失,只是被错误地记进了错误的提交里）。

**结论**：这是工具问题,不是纪律问题。`git add` 精确到路径能保证「这次 commit 收录的文件是我想要的那些」,但**保证不了**「在我 `add` 和 `commit` 之间没有别的进程也在改同一份索引」——`git` 的索引本身就是共享可变状态,两个并发进程对它做读改写,天然存在竞态窗口。并行代理必须给各自独立的 **git worktree**（`git worktree add`),或者退而求其次严格串行提交（一个代理提交完成前另一个不得碰 `git add`/`commit`）,没有第三条路能在共享单一工作树的前提下保证提交内容的正确性。

**这条经验 P4 直接相关**：P4 规划如果打算并行拆分（例如 Steel 宿主与注册表分给不同代理/开发者同时推进,规格「并行切分」一节已经预留了 crate 边界作为任务边界）,**必须先把 worktree 隔离作为并行开发的前提条件写进计划**,而不是假设「大家小心点、精确 add」就够了——本次三次撞车已经证明这个假设不成立。

## 八、方法论：反向核对规格的执行结果

按 `knowledge/handoff/p2-to-p3.md` 第六节立下的纪律——**每个阶段收尾必须反向核对一次规格,不是查实现有没有满足规格,而是查规格有没有被实现淘汰**——本次执行的发现记在这里,不单独开一节重复交接清单其他地方已经写过的内容：

1. **字体方案（§3/决策14/§5/§11.3）已被实现方向淘汰**：规格四处仍写 Fusion Pixel Font,但 `knowledge/pipelines/text-and-font-rendering.md` 记录的字体调研已经把方向改成思源黑体 Source Han Sans,规格原文没有跟着更新——这正是「规格被实现淘汰」的典型案例,如果不做反向核对,P4/P7 的实现者（写作本节时为 P4/P6，[2026-08-18 规格修订] 原 P6 顺移为 P7）会拿着一份指向已废弃字体方案的规格开工。本次已修订全部四处（提交 `d399c04`）,细节见本文档第五节。
2. **§15 阶段表的 P4/P7 排期存在内部矛盾**（写作本节时为 P4/P6，[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P6 顺移为 P7）：P4 交付物（加载管理界面）依赖的能力被排在 P7——这不是规格被实现淘汰,而是规格自身两处互相打架,同样只有认真读一遍两处交付物的具体内容（而不是只看阶段表的一行摘要）才会发现。已修订,见本文档第五节。
3. **两项规格条目仍无认领**（光照透过率、气候条带,见第七节）,一项已在本阶段闭环（季节)。这不是新发现,是对上一轮发现的复核确认——反向核对规格不是一次性动作,每阶段都要重新问一遍「规格里那些没人认的条目,这一阶段有没有谁悄悄把它们实现了、或者悄悄决定不做了却没有落笔」。
4. **没有发现新的「规格声称存在但实际不存在」的机制**（`p2-to-p3.md` 第五节那类问题）——CI 门禁数量在本阶段从 5 道增加到 8 道（`.github/workflows/ci.yml`）,与规格 §14.7 的差距缩小,但本次没有逐条重新核对 §14.7 全部 9 项与当前 CI 的对应关系,这项核对工作建议留给下一轮交接清单或专门的 QA 审计去做,本文档不代为断言「已经对齐」。
