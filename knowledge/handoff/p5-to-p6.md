## 一、P5 收尾评审：反向核对规格

按 `p2-to-p3.md` 第六节立下、历轮交接延续执行的纪律——**每个阶段收尾必须反向核对一次规格，不是查实现是否满足规格，而是查规格有没有被实现淘汰**——本次执行的发现：

### 1. 一项规格已被实现推翻，本次收尾已修订

规格 §15 P5 行原文写着「`WorldState::population`（`ThinPopulation`）与 `WorldState::actors`（`Arena<Agent>`）**当前均标** `#[serde(skip)]`，不参与序列化」——这句话在 P5-A 批次 B（提交 `2e87d33`/`2a02666`）之后已经**不再成立**：两个字段现在直接参与序列化（`crates/ll-world/src/state.rs`，`WorldStateRepr` 交叉校验链已纳入两者），`ContentIndex` 走「存档整体一份字符串映射表（`content_index_map`）+ 主体存裸索引」而不是逐字段转字符串。规格原文继续把这个已经解决的问题写成「当前」状态，是典型的「规格被实现淘汰」——已在本次收尾修订该行，补一段 `[2026-08-19 P5 收尾修订]` 标注三处更正（见下条一并说明），提交见本文档「相关文档」一节。

**顺带核实的第二处**：规格同一行提到 `terrain_table` 「读档后默认为空且目前没有一个显式的『是否已重新灌入』校验点」——这条**也已解决，但解法不是原文暗示的方向**：`WorldState::assert_terrain_table_loaded`（`crates/ll-world/src/state.rs:296` 附近）已经落地，**但没有摘除 `#[serde(skip)]`**——字段本身仍需读档后由调用方显式重新灌入，只是现在有了一个显式的校验点会在忘记灌入时拒绝启动，而不是带着空表安静运行。规格原文若不修订，会让下一个读者误以为这处仍是空白。

### 2. 一项规格指名交给 P5、P5 却始终未认领也未声明推迟的债务（本次新发现）

规格 §15 P5 行还写着：「P2 阶段 `OverviewCell::explored` 恒为 `true`（`WorldState` 尚无探索记忆），**本阶段**接入真实探索记忆时须为 `minimap`/`continent_map` 增加『视角归属』参数」——核实后发现：

- `crates/ll-world/src/overview.rs:11-13` 的模块文档「为什么 `explored` 现阶段恒为真」仍原样存在，`explored: true` 仍是两处硬编码常量（第 82、190 行），没有任何变化。
- **P5 的两份实施计划全程未提及这项债务**——`grep -n "探索记忆\|explored" docs/superpowers/plans/2026-08-19-p5-*.md` 零命中。
- 两份计划各自的「有意留给后续阶段的缺口」一节也**没有把它列为显式推迟**——不是「P5 判断这不该做、明确记录留给以后」，是这项债务在两轮计划撰写过程中被完全遗漏，安静地没人碰。

这与 §7.3「光照透过率」、§7.1「气候条带」那两项**性质不同**：那两项从一开始就没有阶段认领，每轮交接清单都在重复提醒；探索记忆这项**被规格明确点名指派给了 P5**，P5 却没有认领也没有拒绝，只是沉默地跳过了。现状与 P2 阶段完全相同（仍是零实现），**P6 不是这项债务的天然归属**（探索记忆是视野/存档层的问题，不是物品装备），但既然 P5 没有处理，P6 计划作者开工前应当明确一次：这项债务归哪个阶段（P7 UI 层要用它画战争迷雾，是最自然的候选，但规格原文特意把它记在 P5 而非 P7，理由是「玩家探索记忆天然按角色持久化，与双模式存档同属一层」——这条理由在 P6/P7 都要重新审视一次），不能继续放着不认领。

## 二、A. 三处 P5 遗留的真实缺口

### 1. `Interior.origin: Option<GeneratorParams>` 未落地

裁定 P5-7（现 ADR 0024「存档按可重算部分 + 偏差表达空间，分界是有无生成器，不是地表/室内」）要求存档格式必须预留这个字段——**但存档格式已经冻结（P5-A 任务 9），该字段不在里面**。`crates/ll-world/src/interior.rs:94-107` 的 `Interior` 结构体仍只有 `id`/`anchor`/`profile`/`floors` 四个字段，模块文档第 55-74 行描述的「无条件常驻」现状原样未变。

**为什么 P6 会撞上它**：ADR 0024 自己写明「格式一旦冻结成『整层快照』，将来做了生成器也改不回来」——现在没有真实存档（还没有玩家数据），加字段只需要一次 schema 迁移函数（`ll-content::migration::MigrationChain` 已有骨架）；但 P6 一旦落地物品系统，`Interior` 楼层里会开始出现真实的、值得保留的物品掉落/地面物品数据，一旦真实存档开始积累，同样的迁移会变成「有旧档要追」的破坏性变更。P6 的物品持久化设计需要决定：是趁存档还没有真实玩家数据时先把这个字段补上，还是明确记录「继续欠着，下次迁移一并处理」——两者都可以，但不能像 P5 对待探索记忆那样悄悄不决定。

### 2. 技能造成的击杀不产出 `Effect::Kill`

`crates/ll-sim/src/resolve.rs:518-524` 的 `resolve_use_skill` 在 `SkillEffect::DealDamage` 分支只 `push` 一个 `Effect::Damage`，**不检查这一下是否会让目标生命归零**——对照同文件 `resolve_attack`（第 309-326 行）普通攻击的等价分支：`if defender.health - damage <= 0 { effects.push(Effect::Kill { target }); }`，两条路径在同一份代码里，一条做了死亡判定，一条没做。

**为什么 P6 会撞上它**：`crates/ll-sim/src/quest.rs:182-193` 的 `append_quest_kill_progress` 明确写着必须依赖 `Effect::Kill` 才能推进击杀类任务进度——技能杀敌目前完全不会推进任何 `QuestCondition::KillCount` 任务，这条链路只对普通攻击通了一半。P6 加武器/装备后，玩家的攻击手段会从「普通攻击 + 技能」扩展到「不同武器类型触发不同效果」，这个缺口不会自己消失，只会因为攻击方式变多而更容易被撞见（例如某件装备的被动效果或武器技能造成的击杀，同样会静默地不计入任务/掉落判定）。

### 3. 缺敌人类型注册表——`KillCount.target_kind` 借用 `Agent::race` 表达

`crates/ll-sim/src/quest.rs:76-78`（`QuestKillRule::target_kind` 文档）与第 202 行（`append_quest_kill_progress` 实际读 `agent.race`）都明确记录：**当前用 `Agent::race` 冒充「敌人类型」**，模块文档第 31-43 行整段「为什么用 `Agent::race` 作为 `target_kind`，如实记录简化」承认这是「一处已知的语义借用，不是精确解」——`race` 原本设计的用途是种族而不是敌我分类，本体夹具的任务内容（"击杀 3 只哥布林"）目前不会撞见这个混淆，纯粹是因为哥布林这个占位内容恰好把种族和"敌人类型"这两件事叠在了一起。

**为什么 P6 会撞上它**：物品掉落表几乎必然需要按"这是什么类型的敌人/生物"来配置掉落规则（哥布林掉布料、骷髅掉骨头），P6 大概率需要设计一张真正的敌人/生物类型注册表——一旦这张表存在，`QuestKillRule.target_kind` 与物品掉落表的目标类型字段应该指向**同一张表**，而不是各自发明一套。若 P6 先做了自己的敌人类型表却不知道 `target_kind` 早就在借用 `race`，会造出两套并存的"敌人分类"概念，其中一套（`race`）名不副实还继续被任务系统依赖。

## 三、B. 跨表引用校验缺一个统一阶段——已有三个实例

```
SkillDef.owning_class → ClassDef 是否存在        （P5-B 批次 A 发现，task-1-3-report）
KillCount.target_kind → 敌人类型是否存在         （P5-B 批次 C 发现，quest.rs 模块文档「跨表引用」一节）
任务前置 → 技能/职业是否存在                     （同上，P5-B progress.md「批次 A 的两处发现」）
```

三个实例都是同一个根因：`ll-mod` 下的多张内容注册表（`ClassTable`/`SkillTable`/`QuestTable`/`SubclassTable`）各自独立注册、互相看不见对方，任何"这个索引是否指向另一张表里真实存在的内容"这类校验，目前**完全没有地方做**——P5-B progress.md 原话："这与 P4 注册表那次记录的『跨内容约束校验顺序有讲究』是同一个问题，现在有了第二个实例，说明它是结构性的，需要一个统一的交叉引用校验阶段，而不是每张表各自想办法。"三个实例说明这不是巧合，是结构性缺口。

**为什么 P6 会撞上它**：物品系统天然会引入更多跨表引用——材质表、品质表、槽位定义表、掉落表都需要互相指涉（`ItemDef.equip_slot` 指向槽位定义、掉落表的 `target_kind` 指向敌人类型、`ItemDef.crafting_material` 可能指向另一个 `ItemDef`），引用数量会比"技能指向职业"这种单一指向复杂得多。**建议 P6 计划把「加载管线的统一交叉引用校验阶段」列为显式任务**，而不是继续让每张新表各自决定"要不要校验、怎么校验"——这正是当前三个实例反复出现的模式。

## 四、C. 一处判据不可靠的占位值

`WorldState::surface_profile`（`crates/ll-world/src/state.rs:210`）的占位默认值是 `ContentIndex::default()`（即 `ContentIndex(0)`），**与合法索引存在真实歧义**——索引 0 完全可能是某次注册期真正分配给某个内容的索引，不是天然的"未设置"哨兵。P5-A 批次 C 曾经评审是否要给它加一个类似 `assert_terrain_table_loaded` 的「基于相等比较」的检查（`state.rs:195-199` 记录了这次评审的具体理由），**明确拒绝**：「一个基于相等比较的 `assert_surface_profile_loaded` 在这类场景下要么误报（合法的索引 0 被当成"没灌入"拒绝），要么漏报，两者都不可接受」——这是"拒绝制造虚假保证"这条项目纪律的又一次体现，与同批次拒绝「伪造占位种族 `ContentIndex`」（`p5-to-p6.md` 之前的 P5-A ledger「批次 C 完成」一节）同一条判断标准。

真正的修法是把类型改成 `Option<ContentIndex>`（`state.rs:205-208` 已经写明这条），但会牵连 `WorldState::new` 的构造语义与 `resolve_exit_space` 的读取路径，超出 P5-A 单个任务范围，已如实记录为开放项。

**为什么 P6 会撞上它**：这不是物品系统本身的直接依赖，但 P6 落地新内容类型（`ItemDef`/装备槽位定义）时，若沿用"用 `ContentIndex::default()` 当占位默认值、靠读档后显式赋值来保证安全"这个模式，会重新面对同一个选择——**P6 若给某个新字段引入类似占位值，应当直接采用 `Option<ContentIndex>`，不要重蹈"先用魔法值 0、以后再改"这条已经被明确否决过的路径**。这条经验值得作为 P6 设计新的占位字段时的默认起点，而不是各自重新纠结一遍。

## 五、D. 端到端仍是最有效的缺陷发现手段——现在有八个实例

对照 `docs/qa/04-覆盖率与缺失测试层.md` 的 L4-L8 空白盘点，本项目连续五个阶段撞见同一个模式：单元测试全绿，真跑起来（demo/fuzz/程序化走查）才发现连线断了。

| P4-2 | 错误面板换行错位 | L7 视觉回归——`04` 文档明确写 L7「有基准生成机制，没有自动比对」，只能肉眼截图发现 | `p4-to-p5.md` 五 |

**八个实例，不是"七个"**——本轮统计与 D 类别原始描述的分项加总核对后确认是八项（P3 两、P4 两、坐标系两、P5-A 一、P5-B 一），本文档如实按加总结果记录，不沿用可能少算一项的旧说法。

**给 P6 的具体建议，按性价比排序**：

1. **L6 端到端测试仍然没有真正建起来**——这是第五轮交接清单重复同一条建议（`p2-to-p3.md`→`p3-to-p4.md`→`p4-to-p5.md`→本轮），P5-A 任务 12 确实起步了一个脚手架（`crates/ll-content/tests/e2e_save_cycle.rs`），但范围只覆盖"存档→改 mod 列表→读档→降级"这一条链路，**没有覆盖玩法结算**（技能/任务/战斗这条链完全靠验收 demo 手动跑，不是自动化 L6 测试）。P6 引入物品拾取/装备/掉落后，链路会更长（`Intent::PickUp`/`Drop`/`Use` → 背包状态 → 装备槽位 → `DerivedStats` 重算），**建议 P6 把"扩展 `e2e_save_cycle.rs` 这套脚手架，覆盖至少一条完整的物品拾取→装备→战斗结算链路"列为具体任务**，不是继续停留在"建议起步"这句话本身。
2. **fuzz target 只覆盖了存档反序列化，物品数据也是玩家可篡改输入的一部分**——P6 若引入物品序列化（背包/装备栏位存进存档），这些新字段同样会被 `save_load.rs` 现有 fuzz target 覆盖到（因为它 fuzz 的是整个存档主体），但**若物品系统另开了独立的数据文件格式**（例如资产元数据、掉落表配置文件），需要按 `04` 文档 L5 的既有判断标准（"目前存在的、代码里可以直接对上号的入口"）评估是否需要单独的 fuzz target。
3. **视觉回归（L7）仍然只有"生成基准图，肉眼比对"，没有自动化**——`p4-to-p5.md` 已经指出 `ll-ui` 落地后这一层成本很低，P5 没有动它。P6 若给背包/装备栏做出任何 UI 层数据结构（类比 P5-B 的 `SkillTreeView`/`QuestLogView`，见本文档七、G），同样不涉及渲染，这条建议对 P6 大概率仍不适用——真正等到 P7 完整控件库落地时才用得上，继续记录，不重复展开。

## 六、E. 「没接线」是本项目最顽固的失败模式——六次

P1 三次「模块都建好但没有路径通到窗口」；P3 一次 `resolve` 从不读敏捷（躲过全部 321 个测试）；P5-A 一次（`ll_script::host::rebuild_all_engines_after_load`，`crates/ll-script/src/host.rs:543`，脚本状态存储批次 D 就写好了这个函数，但**没有任何调用点**，直到批次 E 的 `save_file.rs::load_full_from_bytes` 才补上唯一的调用点——`ll_script::host::rebuild_all_engines_after_load(current_script_sources)`，见 P5-A task-9-11-report）；P5-B 一次（`ll_sim::skill::SkillCatalog`/`crates/ll-sim/src/quest.rs` 的 `QuestCondition` 判定，两者在批次 A/C 完成时都还只是"定义了接口，没有真实内容目录接进 `resolve`"——直到批次 D 的技能与任务接进真实结算（提交 `4a728ba`，`resolve_with_skills_and_quests` 接线）才真正接上，`resolve()` 本身对 `UseSkill` 意图在此之前的生产行为是"恒不产出效果"，是诚实的默认值，不是缺陷，但如果不知道这一点会误以为技能系统已经能用）。

**共同点**：两端各自都有测试通过——`SkillCatalog`/`rebuild_all_engines_after_load` 各自的单元测试全绿，`resolve()` 对普通意图的测试也全绿——**中间那根"谁调用谁"的线，没有任何一条测试去检查它是否存在**。这正是本文档五、D 节里 L6 端到端反复缺失的直接后果：如果有一条端到端测试从"读档"一路走到"脚本引擎确实被重建"，`rebuild_all_engines_after_load` 无调用点这件事会在写下这条测试的当下就被测试作者自己发现，不需要等到下一个批次的实现者去接线时才顺手补上。

**给 P6 一条可操作的建议，不是"注意接线"**：**每当某个任务的交付物是"新增一个 trait/接口 + 该接口的独立单元测试"，同一批任务必须同时新增一条"这个接口至少有一个真实调用点"的编译期或测试期断言**——具体做法两选一：(a) 若接口只应该有唯一一处生产调用点（如 `rebuild_all_engines_after_load` 这类"读档后必须触发一次"的钩子），补一条集成测试，构造真实的调用路径（读档流程）断言副作用确实发生（P5-A 已经示范了这个做法："读档成功会触发脚本引擎强制重建计数增加"，用 `AtomicU64` 计数器做可观测断言，不是"看起来正常"这种弱验证）；(b) 若接口是"依赖反转，真正持有数据的一方将来才会实现它"（如 `SkillCatalog`），任务报告必须显式写明"当前没有生产调用点，`resolve()` 对相关 `Intent` 的默认行为是 X"，并把这句话放进模块文档最显眼的位置（`ll-sim/src/skill.rs` 模块文档已经这么做），**不能让"接口存在"被误读成"功能可用"**。P6 若延续"先定义接口、后续任务再接线"的模式（大概率会，因为物品系统同样涉及多个 crate），每次拆分接口与接线为两个任务时，都要显式做一次上述判断，而不是假设"下一个任务自然会记得接线"。

## 七、F. 一处工具失效，影响了两个阶段

`.superpowers/sdd/2026-08-19-p5-save-format-and-identity/` 与 `.superpowers/sdd/2026-08-19-p5-gameplay-systems/` 下**全部任务简报文件均为 0 字节**（`task-N-brief.md`，两份计划合计 23 个文件，逐一 `ls -la` 核实确认）——抽取脚本对计划文档里 `### 任务 N：` 这种中文标题格式不生效（P5-B progress.md「批次 A 完成」一节：「P3 那批用的格式可以，验证过有内容」，说明这不是脚本从未测试过，是格式变了脚本没跟上）。

**P5-A 六个批次与 P5-B 全程都在用空简报，没出问题是因为派发指令写得详细，代理靠指令 + 自读计划在干活**——P5-B progress.md 原话：「那是运气，不是设计」。发现者本人也如实记录了这一点，并主动提醒核实了其余几份，避免了这个问题继续悄悄存在。

**处置**：不修脚本。剩余批次改为派发时直接给出计划文档的确切小节标题与行号（P5-B progress.md 已经示范：「任务4 第145行 / 任务5 第160行 / …」）——比修一个只用一次的抽取脚本划算，也少一层会失效的中间件。

**请把这条写进交接，供 P6 沿用**：P6 若继续使用 `.superpowers/sdd/` 这套账本+简报机制，**开工第一批任务前应当先验证简报抽取是否对 P6 计划文档的实际标题格式生效**（哪怕只是 `wc -c task-1-brief.md` 确认非零），不要假设"之前能用"就还能用——P5 的教训恰恰是"之前能用"（P3 那批）与"现在能用"（P4/P5 两批）之间已经出现过一次静默失效，而这次失效连续跨越了两个完整阶段才被发现。

## 八、G. 已知边界（照实写，不要粉饰）

- **P5-B 的验收 demo 未做窗口验收**——环境无桌面自动化工具可用，不是有能力而不用。提交 `b343a60` 原话：「不涉及任何窗口/键盘（ADR 0025）：本次实现环境没有桌面窗口自动化能力，不是『图形环境可用但不用』，如实记录，全程程序化验证。」demo 全程走 `Intent -> resolve_with_skills_and_quests -> Effect -> apply` 程序化路径,与真实按键完全相同的调用层,但没有任何一帧真实渲染画面被人眼确认过。
- **坐标系重写留下的跨区块无缝肉眼验收至今未完成**——ADR 0025 记录的 SendKeys 泄漏事件（合成按键实际出现在了协调者与项目所有者的对话里）之后，验收方式全面转向程序化驱动，换来的代价是「按键触发的跨区块跨越瞬间无一帧接缝」「只渲染当前层（地表/`Interior` 二选一显示）」这两项视觉性质，程序化驱动完全测不到，ADR 0025 后果一节已如实记录为未完成项，P5 期间没有任何批次补上。
- **`quest_progress_key` 在键里嵌了完整命名空间 id，而存储命名空间已携带同一信息**——`crates/ll-sim/src/quest.rs:145` 的 `quest_progress_key` 把完整 `NamespacedId`（含命名空间）拼进键字符串本身，键所在的存储（`Agent::script_state`，`(mod_namespace, key)` 二元组）已经单独携带同一个命名空间。这一层重复是有意的（P5-B task-6-7-report：「让读者从键本身就能确认任务身份，不需要回头看外层命名空间」），已记录为可商榷的设计，不是缺陷。
- **`SkillTreeView` 落在 `ll-sim`（`crates/ll-sim/src/skill_overview.rs`）、`QuestLogView` 落在 `ll-mod`（`crates/ll-mod/src/quest_overview.rs`）**——两者承担同类职责（给未来 UI 层的只读展示数据），选址却不对称。提交 `020a61d` 原话：「`SkillTreeCatalog` 落在 `ll-sim`（与 `SkillCatalog` 同一个家，只需要 `ContentIndex` 级别的信息）；`QuestLogView` 的构建落在 `ll-mod`（必须直接调用 `unlocked_by`，依赖方向不允许 `ll-sim` 反过来依赖它）——两者选址不对称，模块文档如实记录了为什么。」P6 若要给物品/装备栏也做一份类似的"只读展示数据"结构，开工前应该先读这两处模块文档，判断物品系统的依赖方向落在哪一侧，而不是想当然地认为"两个系统都应该放在同一个 crate"。
