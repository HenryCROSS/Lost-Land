# 0022 — 覆盖不全的确定性哈希，等于没有确定性哈希（三个独立实例）

**日期**：2026-08-18（CS-6，坐标系重写批次 D）/ 2026-08-19（P5-2/P5-9，存档格式与身份批次）
**状态**：已生效的项目纪律
**关键提交**：`9fae72e`（fix：确定性黄金基准测试改在有真实地形变化的世界上跑，裁定 CS-6）、`ac27217`（脚本状态存储落地，裁定 P5-8/P5-9，`player_entity` 与脚本状态混入 `hash()`）
**影响范围**：`crates/ll-world/src/state.rs:615`（`WorldState::hash`）、`crates/ll-world/tests/determinism.rs`、`crates/ll-sim/tests/replay.rs`、任何未来新增到 `WorldState` 且影响玩法的字段

## 背景

本项目依赖两条黄金基准回归测试（`ll-world/tests/determinism.rs`、`ll-sim/tests/replay.rs`）守护「同一份世界产出同一个哈希」这条确定性保证——参见 [0002](0002-integer-only-world-state.md) 建立的整数世界状态前提。这条守护链上出现过三次独立的覆盖缺口，性质相同：**判据本身漏掉了它应该覆盖的东西，测试因此在空跑，看起来在守护，实际什么都没测到。**

**先例（P3，原始记录未说明具体提交）**：`WorldState::hash()` 最初完全不含实体状态。战斗结算逻辑跑偏时，确定性回归测试测不出来——因为它的输入根本不包含会跑偏的那部分状态。这次先例只作为 P5 账本反复引用的历史教训收录于此，本 ADR 未能在 git 历史中独立核实到对应的具体提交，如实标注为未核实。

**实例一：`player_entity` 未进 `hash()`（裁定 P5-9）**。存档格式批次按裁定 P5-3 给 `WorldState` 补了「玩家是谁」的显式字段，但补字段的那次提交没有同步把它混入哈希——玩家是谁显然影响玩法（读档要恢复视角、双模式存档要判断玩家死了没），漏掉它意味着「玩家身份被换掉」这类错误不会被确定性测试抓到。已在批次 D（`ac27217`）与裁定 P5-8 一并修正。

**实例二：脚本状态整体未进 `hash()`（裁定 P5-2）**。P4 引入的脚本层允许 mod 往 `WorldState` 写入自定义状态（技能进度、任务标记等，见 [0023](0023-script-state-writes-go-through-apply.md)）。这类状态若不计入哈希，脚本逻辑的 bug——包括跨平台不一致——同样不会被两条黄金基准抓到，而脚本恰恰是「行为最不可预测、最需要被守护」的一层。

**实例三：确定性测试跑在一个不携带区分度的世界上（裁定 CS-6，与前两例形状不同但同一根因）**。坐标系重写批次 D 验证黄金基准时意外发现：`determinism.rs`/`replay.rs` 使用的测试世界（64×64，边长为 2 的幂）在任意种子下都退化成几乎全深水地形。根因是 `TileableNoise::octaves`（`crates/ll-world/src/noise.rs`）大陆尺度层的格点周期 = `period / coarse_scale`，而正方形且边长为 2 的幂的世界会让 `coarse_scale` 恰好等于 `period` 本身——大陆尺度层退化成 1×1，整层在全图范围内是常数。`height_to_terrain`（`crates/ll-world/src/generate.rs`）八条分支只有一两条被走到，`hash()` 的地形部分几乎不携带区分度。**这一次不是哈希函数本身漏字段，是哈希函数覆盖的数据本身不够多样——测试世界的构造方式让判据的输入退化了，效果和「字段没进 hash()」完全一样：很多真实的算法错误不会让测试变红。**

## 决定

**`WorldState::hash()` 必须覆盖 `WorldState` 里全部影响玩法的字段（裁定 P5-2），且守护它的测试数据本身必须有足够的多样性让判据真正被跑到（CS-6 补充的教训）。这不是一次性修复，是一条持续适用的检验：新增任何影响玩法的字段或系统时，必须同时问「它进 `hash()` 了吗」与「测试数据能不能让新逻辑被真正跑到」。**

CS-6 的具体修复：测试世界边长由 64 改为 48（噪声格点周期的整数倍、且刻意不是 2 的幂，避免大陆尺度层退化为常数），种子改为产出全部八种地形（含水域与阻挡视线的山地）的取值。修复经过「故意改坏」验证：把 `sea_level` 从 400 改到 500，确认哈希值确实变化（新旧不同）；改回 400 确认变绿——证明黄金基准值不是照抄实际输出的空判断，而是真的对输入敏感。

## 为什么这三个实例算同一类问题，值得合并成一份 ADR

字面上，P5-9/P5-2 是「哈希函数少算了字段」，CS-6 是「测试世界本身没有区分度」——修复的代码位置不同（`state.rs` vs `determinism.rs`/`noise.rs` 相关的测试参数）。但从「这条守护链条到底在守护什么」的角度看，两者是同一个失效模式：

```
守护 = 判据(输入)
```

判据字段不全 → 输入里该有的东西没被采样 → 守护形同虚设
输入本身退化 → 判据字段虽然都在，但采样到的值区分度不足 → 守护同样形同虚设

**两条路径殊途同归：无论是判据漏了字段，还是输入退化到判据测不出区别，结果都是「测试通过」这件事不再等价于「系统真的正确」。** 这正是本 ADR 标题「覆盖不全的守护等于没有守护」想强调的：写一条测试、让它通过，只完成了表面工作；真正的工作是持续核实这条测试的输入与判据是否仍然覆盖了它声称在守护的东西。

## 被否决的选项

**只修 CS-6 这一次具体的测试世界退化，不追溯 P5-2/P5-9 的字段覆盖问题（把它们当作各自独立的小修复，不合并讨论）**——否决：分开记录会让「确定性哈希需要持续被核实覆盖完整」这条更大的教训消失在三个孤立的提交说明里，未来第四次出现同类缺口时（例如新增任务系统/物品系统时又漏了一个字段）不会有人想起前三次是同一类问题。合并成一份 ADR 是为了让这条判据本身被记住，而不是让每次遗漏都各自成为一次孤立的救火。

## 后果

- **两条黄金基准值已重新冻结**：`determinism.rs` 的 `EXPECTED_WORLD_DIGEST` 因测试世界换了边长与种子而改变（`2_466_608_231_210_883_991` → `2_350_814_586_022_858_977`）；`ac27217` 同样重冻了因新增字段而改变的哈希基准。两次重冻均已人工核验改动只来自对应的那一处输入变化，不掺杂意外的行为漂移。
- **`replay.rs` 顺带核实出一个未在本次范围内修的独立缺口**：其 64×64 测试世界同样地形退化（种子 20260817 下全图 4096 格都是深水），但该测试对移动路径上的关键地形（草地/浅水/门）全部显式 `set_terrain` 覆盖，因此分支覆盖本身不受背景地形退化影响——唯一例外是开门后最后一步「往东走」的目的地在全部四个测试种子下都是深水（不可通行），这一步的 `Move` 意图因此从未真正产生过 `MoveTo` 效果，与模块文档描述的行为不符。这是一个独立、尚未修复的覆盖缺口，已用 `spawn_task` 记录，不在本 ADR 处置范围内，如实标注为已知遗留。
- **未来新增任何进入 `WorldState` 且影响玩法的字段，必须同步检查它是否已计入 `hash()`**——这条检验现在没有自动化强制手段（不是编译期检查），完全依赖开发者在新增字段时的自觉,与 [0013](0013-ledger-vs-adr-discipline.md) 记录的账本纪律面临同一类「依赖执行期自觉」的局限,见 [0026](0026-recurring-ledger-to-adr-discipline-lapse.md) 对这类局限的进一步讨论。
- **测试世界的构造参数（边长、种子）本身现在是一项需要被审查的正确性资产**，不再是「随便选一个能跑的值」——任何未来修改噪声算法、地形阈值、或测试世界尺寸的人，都需要重新确认测试世界仍然产出有区分度的地形分布，而不能想当然地认为「测试之前能跑就还能跑」。

### 本 ADR 承载的到底是哪一条纪律，说清楚

本 ADR 的标题写的是**确定性哈希**，但正文「为什么这三个实例算同一类问题」一节
已经把它抽象成了与哈希无关的形式：

```
守护 = 判据(输入)
```

判据字段不全 → 守护形同虚设；输入本身退化 → 守护同样形同虚设。因此以下几种
说法**都归本 ADR**：「覆盖不全的保护等于没有保护」「改坏了也不红的断言等于没有
断言」「拿不到适配器就跳过的假测试是一条永远绿的假守护」「判据只覆盖了一半，
另一半静默失效」。

**但有一条不归本 ADR，也不归 0018**：「新能力必须有经真实 `mods/` 内容、走生产
路径的端到端证据」。它讲的是证据的**来源与路径**，不是判据的覆盖面。
[0028](0028-steel-engine-construction-memory-corruption.md)「候选 D」一段已经
如实记过「没有任何 ADR 为它背书」，批次 25 复核确认仍然成立，是否新开 ADR 待
项目所有者裁定。
