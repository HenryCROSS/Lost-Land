# 0010 — 白昼判定与光照曲线收敛为同一份真相源

**日期**：2026-08-17
**状态**：已生效
**关键提交**：517f193
**影响范围**：`ll-core::time`、`ll-core::light`（新增）、`ll-world::light`

## 背景

`Tick::is_daylight()`（固定 6..18 点边界）与 `ll-world::light` 的昼夜渐变曲线（日出 5-7 点、日落 17-19 点）此前是**两套互相矛盾的定义**：

- 06:00 时 `is_daylight() == true`，但光照曲线值只有约 550（曲线中点，日出窗口正中）。
- 18:00 时 `is_daylight() == false`，但光照曲线值仍约 550。

每天早晚各约四小时，两套定义结论相反。更值得记录的是：`is_daylight()` 自己的文档早就写着「后续若要让日照长度随季节变化，应在此处调整边界，而非另设时钟」——而 `ll-world::light` 恰恰另设了一套边界，正是这条警告想拦住却没拦住的事。**写了警告不等于警告会被遵守**，这是本条决定要吸取的方法论教训，不只是技术修复。

## 决定

把昼夜基准曲线（日出日落时刻、午夜/正午基准光照、`day_curve` 本身）整体下沉到 `ll-core::light`。`ll_core::time::Tick::is_daylight()`（`time.rs:88`）与 `ll_world::light::ambient_light`（`light.rs:49`）都从这一份定义读数：

```rust
// time.rs:88
pub fn is_daylight(&self) -> bool {
    crate::light::day_curve(*self) >= crate::light::DAYLIGHT_THRESHOLD
}
```

`is_daylight()` 从「独立选定的固定边界」改为「光照曲线是否达到阈值（曲线中点 550）」——不再是另一套判据，而是同一条曲线的一次阈值查询。`ll-world::light` 现在只在这条基准曲线之上叠加季节缩放。

## 为什么下沉到 `ll-core` 而不是反过来

依赖方向是单向的：`ll-core` 不能依赖 `ll-world`（规格 §5 的 crate 分层顺序）。曲线要被两边共用，只能落在两者的公共基础层。季节缩放依赖 `Season`——这是 `ll-core` 已有的类型，不构成新的依赖问题——但「随季节调暗调亮」终归是世界层的玩法参数，**不下沉**：`ll-core::light` 只提供不含季节因素的基准曲线，季节缩放留在 `ll-world`。

## 为什么阈值恰好取曲线中点

阈值取中点使日出窗口正中（6 点）与日落窗口正中（18 点）恰好落在阈值上——**这是「阈值取曲线中点 + 窗口对称」的结构性必然，不是巧合**。新增测试同时锁住了这两个精确对齐点，以及 `is_daylight()` 与曲线阈值在全天各小时采样点上的一致性——这正是本该在两套定义分裂时就存在、却没有存在的回归测试。

## 被否决的选项

**反过来让 `ll-core` 依赖 `ll-world`**——直接违反规格 §5 定死的单向依赖顺序，Cargo workspace 的依赖方向也不允许（会与其余所有依赖 `ll-core` 的 crate 产生循环）。这不是权衡后否决，是架构约束下唯一可行方向的必然结果。

## 后果

- **行为变化**：`is_daylight()` 在 18:00 由 `false` 变为 `true`（曲线在这一点恰好等于阈值），其余 23 个整点小时的判定不变。这是算法行为的**有意变更**，不是平台相关行为泄漏，已在常量旁写明原因。
- **黄金基准需要重冻**：`ll-core/tests/determinism.rs` 的 `EXPECTED_TIME_DIGEST` 按 `day % 24` 采样了全部 24 个小时，因此这次行为变更必须重新冻结基准——这是允许更新黄金基准的正当理由（有意的算法变更），而不是「测试挂了就改期望值」那种不允许的操作，两者的界限由这次改动明确写进了提交记录。
- **P2→P3 交接清单专门重复了这条纪律**：「白昼只有一个真相源」「不要在别处另立昼夜边界」——把一次修复上升为持续性纪律，因为同类问题（一个真相源被悄悄复制出第二份定义）在项目其他地方同样可能发生。
