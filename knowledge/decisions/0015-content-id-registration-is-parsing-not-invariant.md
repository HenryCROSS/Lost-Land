# 0015 — 内容 ID 的注册校验是解析，不是 serde 不变式

**日期**：2026-08-18（P4 开工前裁定，代号 P4-2）
**状态**：已定稿的设计决定，等待实现（`ll-mod` 与内容注册表尚未建立）
**关键提交**：无独立提交——本裁定目前只存在于 P4 阶段账本（`.superpowers/sdd/2026-08-18-p4-script-and-mod/progress.md`，BASE = 7157b4e）；支撑本裁定的 `ContentIndex`/`Interner` 基础设施已由 0dd618b、734dc39、24c1225 落地
**影响范围**：`ll-core::ident`（`crates/ll-core/src/ident.rs`）、未来的 `ll-mod` 内容注册表、`TerrainKind` 等将迁入注册表的类型（P4 Task 8）

## 背景

[0011](0011-serde-try-from-bypasses-validating-constructors.md) 定下一条规矩：任何「私有字段 + 返回 `Option`/`Result` 的构造函数」的类型，加 `serde` 派生时都会被 serde 从背后绕过构造校验，必须用 `#[serde(try_from = "...Repr")]` 中转到校验构造函数。`TorusSize`、`TerrainKind`、`WorldState` 三个类型都用这个模式堵住了「非法值从存档直接怼进私有字段」的口子。

P4 要建内容注册表：mod 与本体的地形、技能、物品等内容统一用命名空间字符串 ID（`lostland:mountain`、`yourmod:fireball`）注册，运行期用紧凑整数 `ContentIndex` 引用（`crates/ll-core/src/ident.rs:84`，模块文档已写明理由：字符串防冲突，整数防热路径变慢）。这带来一个容易顺手套错的问题：**「这个 ID 字符串是否已经被注册」，看起来和 0011 里「宽高是否非零」是同一类校验，套用 0011 的 `try_from` 模式似乎顺理成章——但两者其实是完全不同的两件事。**

## 决定

**serde 只负责结构 ↔ 字符串的转换，不做「是否已注册」的校验。「已注册」的判定是一次解析（parse），不是类型的不变式（invariant）。**

分工：
- `serde::Deserialize` 把存档 / mod 数据文件里的字符串 ID 还原成 `NamespacedId` 结构（`ident.rs:38` 的 `NamespacedId::parse` 已经校验命名空间与路径的字符合法性——这部分**是**不变式，字符集合法与否不依赖任何运行期上下文，0011 的模式在这里适用）。
- 「这个字符串对应的内容是否真的存在」是另一个独立步骤：拿着反序列化出的字符串 ID，去查当前已加载 mod 集合建立的注册表（`Interner::intern`/`resolve`，`ident.rs:112`/`127`），查不到就是「缺失 mod」，直接对接规格 §10.4「缺失 mod 不得崩溃」的错误路径。

本体内部原本硬编码的 13 处 `TerrainKind::MOUNTAIN` 一类字面量，改为取 `lostland:mountain` 等命名空间 ID，在启动时一次性解析进缓存结构（例如 `terrain_ids.mountain`），运行期代码从字面量 match 改成访问这个缓存字段——**仍是常量级开销的字段访问，不会把注册表查询搬进热路径**。

## 为什么这是两件事，不能用同一个机制解决

**不变式（0011 管的）是无上下文的**：`TorusSize` 的宽高是否非零，只需要看这两个数字本身，任何时候、任何环境下答案都一样。这类校验适合绑定在类型的构造路径上，`try_from` 中转把它钉死在反序列化的必经之路，谁都绕不过去。

**「是否已注册」是有上下文的**：同一个字符串 `yourmod:fireball`，在加载了 `yourmod` 的会话里是合法内容，在没加载它的会话里就是缺失引用——**答案取决于当前加载了哪些 mod，不取决于字符串本身**。`try_from` 发生在反序列化那一刻，而反序列化那一刻的类型定义本身并不知道、也不应该知道「当前跑的是哪一局游戏、加载了哪些 mod」——把注册表查询硬塞进 `try_from`，等于让一个理应无状态的类型转换函数偷偷依赖一个全局可变的运行期状态，这本身就违反了 `try_from` 该有的性质（纯粹、无副作用、结果只取决于输入）。

`ContentIndex` 本身不可持久化这一点（`ident.rs:82` 模块文档：「索引依赖加载顺序，存档必须写字符串」）反过来印证了这个划分：**存档天生只能写字符串，字符串到索引的解析天生只能发生在运行期、有注册表可查的地方**，不可能提前到 serde 反序列化那一步完成——那一步压根拿不到注册表。

## 被否决的选项

**把注册校验也塞进 `try_from`（机械套用 0011 的模式）**——否决：`try_from` 的签名是 `fn(Repr) -> Result<Self, Error>`，不接收「当前注册表」这个额外输入。要让它工作，要么把注册表做成全局可变状态供 `try_from` 内部访问（引入隐式全局依赖，且违反本项目「世界状态完全数据化、不含隐藏状态」的一贯纪律，参见 [0006](0006-intent-resolve-effect-apply.md) 对 `WorldState` 的要求），要么在每次反序列化时把注册表作为参数传入（`serde` 的 `try_from` 机制不支持外部上下文传入，需要改用 `DeserializeSeed` 一类更复杂的机制，为一个本质是「查表」的操作背上远超其价值的复杂度）。

**反序列化阶段直接拒绝任何未注册 ID**——否决：这会让 mod 加载顺序产生依赖——如果内容注册表要等所有 mod 的定义文件都读完才能建立完整索引，而某个 mod 引用了另一个尚未读到的 mod 的内容，反序列化阶段的校验会误判为「缺失」。已注册检查必须留到内容注册表**建立完成之后**统一做一遍解析，而不是绑死在每个字段各自反序列化的那一刻。

## 后果

- **P4 Task 8（`TerrainKind` 迁入注册表）是这条分工的第一次真实检验**——截至本 ADR 写下时，`crates/ll-world/src/terrain.rs:73-127` 仍是硬编码的 `pub const` 常量，尚未接入注册表；`ContentIndex`/`Interner` 已经就绪（`ident.rs`），但 `ll-mod` crate 本身尚未创建。这条分工能否成立，要等 Task 8 真正把 13 处字面量替换成解析结果后才算验证完毕。
- **解析失败的错误路径与「缺失 mod」检测复用同一条通道**——不需要为「注册校验失败」单独设计一套错误类型，直接对接规格 §10.4 已经要求的「缺失 mod 不得崩溃」路径，减少一类新错误变体。
- **这条分工依赖「注册表在解析时已经完整建立」这个前提**——如果未来出现允许运行期动态加载/卸载 mod 的功能（当前设计未规划），字符串到索引的解析就不再是一次性的加载期步骤，届时需要重新评估「解析」与「不变式」的边界是否还成立。
- **与 [0011](0011-serde-try-from-bypasses-validating-constructors.md) 的边界需要被后续新增类型持续遵守**：任何新引入的、需要序列化的「内容引用」类字段，在设计校验方式时都要先问一句——这个校验依赖运行期上下文（该用解析），还是只依赖值本身（该用 0011 的 `try_from`）？混淆两者，要么会把无状态的类型转换污染成隐式依赖全局状态，要么会让本该在注册表建立后统一检查的引用错误提前到反序列化阶段误报。
