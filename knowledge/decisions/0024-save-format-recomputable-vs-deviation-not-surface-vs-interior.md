# 0024 — 存档按「可重算部分 + 偏差」表达空间，分界是有无生成器，不是地表/室内

**日期**：2026-08-18（CS-3，坐标系重写批次；批次 E「Interior 不参与淘汰」裁定）/ 2026-08-19（裁定 P5-7，存档格式与身份批次，修正批次 E 裁定的一半）
**状态**：已定稿的设计决定，接口尚未落地（`Interior` 当前仍是「插入后无条件常驻」，未加 `origin`/生成参数字段——本 ADR 记录的是格式必须预留的方向，不是已完成的实现）
**关键提交**：`9162373`（`WorldState.terrain` 换型为 `SurfaceStore`，接入 Interior 共享预算，落地 CS-3）、`0b3244e`（docs：明确记录 Interior 楼层不参与淘汰是本批次的裁定而非遗漏）
**影响范围**：`crates/ll-world/src/interior.rs`（`Interior` 结构体，第 94 行；模块文档第 55–74 行「无条件常驻」的现状说明）、`crates/ll-world/src/surface_store.rs`（`SurfaceStore` 的可重算淘汰模型，与本裁定的对照组）、存档格式（`ll-content`）未来扩展、P7 世界生成器（`Interior` 生成器）落地时的接口约束

## 背景

坐标系重写引入两种空间存储：`SurfaceStore`（地表，按区块流式加载/淘汰，可以随时用噪声函数从种子+坐标重新算出）与 `Interior`（室内空间——地下城、建筑，`crates/ll-world/src/interior.rs`，用 `BoundedGrid` 存楼层）。批次 E 需要给两者的常驻内存定一条规则：

**裁定 CS-3：Surface 与 Interior 共享 256 常驻上限，当前空间的层与其锚点区块钉住不淘汰。** 分开设两份预算会在「刚出地下城就发现地表被淘汰了」这类边界上抖动；共享 + 钉住更简单，且能同时挡住两个方向的问题：巨型地下城不会把玩家将要走出去的地表挤掉，地表漫游也不会把玩家正在探索的地下城挤掉。一个 20 层地下城才 640KB（20 × 32KB），共享池完全装得下。

批次 E 落地这条共享预算时，进一步要回答「`Interior` 楼层本身要不要参与淘汰」，给出的裁定是：**楼层插入后无条件常驻，永不淘汰**（`interior.rs:55-74` 已记录），理由是没有生成器就无法在需要时重新造出同一层，淘汰等于永久丢失玩法数据（地板上的物品、玩家改动过的布局）。这条裁定当时被记录为「评审过，裁定维持现状，不是遗漏」（`0b3244e`）。

**这条裁定后来被发现只对了一半。** P5 存档格式批次追问「存档无界增长会怎样」时，重新审视这条规则，发现它把「地表 vs 室内」当成了分界线，但真正决定「能不能安全淘汰」的从来不是这个维度。

## 决定

**真正的分界不是「地表 vs 室内」，是「有没有生成器」：**

```
存储 = 可重算的部分（生成参数）+ 不可重算的偏差
       ↑ 这部分存不存在，决定它能不能被淘汰
```

| | 可重算部分 | 能淘汰 | 存什么 |
|---|---|---|---|
| 地表地形 | 噪声(种子, 坐标) | 能 | 只存改动 |
| 生成的地下城/洞窟 | 生成器(SpaceId, 种子) | 能 | 只存改动 |
| **玩家盖的建筑** | **没有** | **不能** | **全部（按格计，不按层快照）** |
| NPC 建的城镇 | 聚落生成器 | 能 | 生成参数 + 后来的改动 |

**批次 E「Interior 楼层不参与淘汰」的裁定对了一半，错在把它推广到了所有 `Interior`。** 对玩家所建的建筑（没有生成器，淘汰即永久丢数据）完全正确；但对未来会有生成器的地下城/洞窟是错的——生成的空间明明可以按「生成参数 + 偏差」重算，不需要无条件常驻。**能重算的才淘汰，不能重算的常驻**，这才是通用规则，「地表/室内」只是这条规则在当前系统里凑巧对齐的一个特例（因为目前唯一存在的地表生成器恰好覆盖了全部地表，而 P5 阶段唯一存在的 `Interior` 恰好都没有生成器）。

**为什么这是 P5 的事，而不是等 P7 生成器落地时再改**：`Interior` 生成器本身属于世界生成阶段（现排 P7，见规格 2026-08-18 修订后插入「物品与装备」新 P6，原 P6 顺移）。P5 不实现生成器，但**存档格式必须现在就留对接口**：

```
Interior { origin: Option<GeneratorParams>,  // None = 玩家所建，全靠偏差
           deviations: ... }
```

**格式一旦冻结成「整层快照」，将来做了生成器也改不回来**——存档格式向后兼容的约束比代码内部实现严格得多，是必须现在留对的接口，不是要立即实现的功能。

## 无界增长的实测账（回答「玩久了会怎样」）

P5 裁定时给出的具体账目，附带记录以说明这条规则不是凭空的谨慎：

- 地表地形：0（重算）
- 改动格：约 8 字节
- 探索位图：每去过的区块 2KB
- 被记住的 NPC：几十字节（[0009](0009-derive-by-default-store-only-deviation.md) 默认派生只存偏差原则的又一个应用）
- 历史事件：设计上限约一万条
- 关系记忆槽：每人 8 格 LRU
- 脚本状态：每 mod 256KB 配额（见 [0023](0023-script-state-writes-go-through-apply.md)）
- 玩家建筑：有界，界在玩家时间上——20×20 房子约 3KB，100 栋约 320KB（前提是按格计，不按层整体快照）

**唯一无界者是当时豁免淘汰的 `Interior` 楼层**：200 个地下城 × 10 层 × 32KB = 64MB，而常驻上限是 256 个「区块-层」——地表遵守这个上限，`Interior` 直接豁免。本裁定（区分有无生成器）即为堵住这个洞：一旦生成器落地，多数 `Interior`（有生成器的那部分）将回到「能重算即能淘汰」的常规路径，只有玩家建筑继续无条件常驻，无界增长的范围收窄到「玩家实际盖过的建筑总量」——这本身有界（受玩家游玩时长与建造行为的自然限制）。

## 被否决的选项

**继续按批次 E 的原始裁定，全部 `Interior` 一律不参与淘汰**——否决：这正是本 ADR 要修正的判断。它在 P5 阶段暂时不构成问题（当时唯一的 `Interior` 都没有生成器），但把这条特例当成通用规则写进存档格式，会在生成器落地后制造两难：要么继续让生成的地下城也无条件常驻（浪费，且与 `SurfaceStore` 的既有淘汰模型不一致），要么被迫做一次存档格式的破坏性迁移。

**按「地表 vs 室内」这个表面维度分界**（批次 E 原始裁定实际采用的维度）——否决：见上文「决定」一节，这个维度只是在当前系统状态下凑巧与「有无生成器」对齐，本身不是稳定的判据，换一个未来场景（例如地表某一部分是玩家开垦出的、不可重算的永久改造区）就会立刻失效。

## 后果

- **本 ADR 记录的是接口方向，不是已完成的实现**——`Interior` 结构体（`interior.rs:94`）目前仍只有 `id`/`anchor`/`profile`/`floors` 四个字段，没有 `origin`/生成参数字段，模块文档第 55–74 行描述的「无条件常驻」现状尚未改变。真正的接口调整、淘汰逻辑接入，都留给 P7 生成器落地时的实现批次，本 ADR 不代为完成。
- **`SurfaceStore` 与 `Interior` 现在共享同一套「可重算/不可重算」的概念框架**，即使代码层面尚未统一——这为未来把两者的淘汰逻辑收敛到同一套机制（而不是各写一份）提供了理论依据，但本 ADR 不裁定是否要做这次代码层面的统一,那需要等生成器接口的具体形状定下来之后再判断。
- **CS-3 的共享 256 常驻上限裁定本身未被推翻**——本 ADR 只修正「`Interior` 楼层是否参与这份共享预算的淘汰」这一点，共享预算的存在与「当前空间钉住不淘汰」两条规则原样有效。
- 若未来新增任何一种空间存储类型（例如 P7 之后可能出现的「可进入的载具内部」之类），判断它该不该参与淘汰时，应直接套用本 ADR 的分界（有没有生成器），不需要重新讨论「地表/室内/其他」这类表面分类。
