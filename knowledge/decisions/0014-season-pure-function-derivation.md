# 0014 — 季节维持纯函数派生，不做时间轴事件

**日期**：2026-08-17（P3 收尾裁定，代号 P3-5 / W-03）
**状态**：已生效
**关键提交**：8f88f7c（规格 §7.2 改写，标注裁定 P3-5）、3f8b5f8（P3 收尾，在 `Effect` 与 `season_light_scale` 文档旁落实依据）；同构参照 [0010 — 白昼真相源收敛](0010-single-source-of-truth-for-daylight.md)（517f193）
**影响范围**：`ll-world::light::season_light_scale`（`crates/ll-world/src/light.rs:88`）、`ll-sim::effect::Effect`（`crates/ll-sim/src/effect.rs:33`）、规格 §7.2

## 背景

规格 §7.2 原文把季节更替写成「时间轴上的一个定时事件，其 `Effect` 修改各城镇生产速率、地形通行性与野怪分布表」，但 P2 阶段的实际实现是另一套：季节由 `ll_core::time::Tick::season()` 从时钟直接派生，`ll-world::light::season_light_scale`（`light.rs:88`）是个纯函数，不存储「当前季节」这个状态。

P2→P3 交接清单在一次「反向核对规格」审计（同一次审计还带出了 [0005](0005-torus-topology-and-integer-noise.md) 的「4 份偏移副本」文档过时问题）中把这处分歧升级为独立发现 H-3、工单 `knowledge/audit/worklist.md` 的 W-03：P3 建完时间轴调度器（[0006](0006-intent-resolve-effect-apply.md) 的 `Timeline`）之后，必须在「纯函数派生」与「时间轴事件」之间二选一，两者不能都留着。

## 决定

**维持纯函数派生，不给 `Effect` 加 Season 变体。**

```rust
// crates/ll-world/src/light.rs:88
pub fn season_light_scale(season: Season) -> i32 {
    match season {
        Season::Summer => 1000,
        // ...
    }
}
```

「季节影响生产速率」不需要事件也能实现：速率写成 `f(season(tick), …)`，用时现算。mod 需要的「季节切换」钩子，由推进过程比较 `season(A) != season(B)` **派生出通知**——通知不是状态，不会与时钟脱节。

## 为什么：与白昼判定同一类教训，加一条新约束

**理由一，与 [0010](0010-single-source-of-truth-for-daylight.md) 完全同构**：事件驱动的季节状态是又一个可能与时钟脱节的真相源。本项目已经在白昼判定上真实付过一次这个代价——`is_daylight()` 与光照曲线两套边界定义，每天有 4 小时结论相反，直到 0010 才收敛。若季节也走事件驱动，同一类分裂随时可能重演：时间轴事件的调度可能延迟、可能在批处理中被跳过，季节状态与时钟本身出现分歧的窗口天然存在；纯函数派生没有这个窗口——`season(tick)` 对任意 `tick` 恒定，不存在「事件还没触发所以季节没跟上」这种中间态。

**理由二，是 0010 论证时还不需要考虑的新约束**：项目约束 C4 要求后台世界能够推进到任意确定的 tick（离屏推进必须有界且可达任意目标时刻，不能只是「能跑多少跑多少」）。若季节由时间轴事件驱动，跳跃式推进（例如一次性快进 100 年）就必须补发这段时间里全部季节切换事件——漏发一次，季节状态就永久错位，且这类错位极难在测试里复现（取决于具体跳跃了多长、恰好跨了几次切换点）。纯函数派生对这个问题天然免疫：任意 tick 直接算出季节，不需要重放任何历史事件。

## 被否决的选项

**按规格原文实现——时间轴定时事件 + `Effect` 变体修改生产速率/地形通行性/野怪分布表**：

否决理由有两层。第一层是上面两条同构论证（多一个可脱节的真相源；与 C4 的离屏跳跃推进冲突）。第二层是 3f8b5f8 补充的**时机论证**：规格原文要季节驱动的三个数据结构——城镇生产速率、地形通行性、野怪分布表——在 P3 收尾时**全部尚未实现**（生产/城镇经济属 P9，[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P8 顺移为 P9，野怪分布尚无归属阶段）。为三个还不存在的数据结构预留一个当下没有任何内容可改的 `Effect` 变体，只是多一层没有实质内容的抽象，且会为「这个变体该在哪个阶段真正接线」埋下一个此刻没人能回答的悬而未决问题。

裁定因此不是「规格原文的方案不可行」，而是「规格原文的方案此刻没有东西可供它改」：真正引入生产速率/地形通行性/野怪分布表这些系统的阶段，应由那个阶段的实现者决定各自是否需要接入 `Effect`（这也保留了灵活性——不排除某个未来系统确实需要事件驱动，只是不预先替它们决定）。

## 后果

- **代码侧的依据留在两处消费点**：`crates/ll-sim/src/effect.rs:19-28`（`Effect` 枚举文档，说明「为什么没有季节相关变体」）与 `crates/ll-world/src/light.rs`（`season_light_scale` 文档，完整复述三层理由）。3f8b5f8 的提交信息特别指出，决策本身跨越 `ll-world` 与 `ll-sim` 两个消费点，两边都要看得到，不能只写一处。
- **规格 §7.2 与 `knowledge/handoff/p2-to-p3.md` 需要相应更正**——3f8b5f8 提交时特意注明这两处不在 `crates/**` 范围内，留给负责 `docs/**`/`knowledge/**` 的一方处理；本 ADR 写下时应一并核对这两处是否已经跟上代码侧的裁定。
- **这条规则只覆盖「季节状态本身怎么来」，不覆盖季节将来是否需要通知机制**——mod 若需要在季节切换时触发脚本回调，实现方式是推进过程比较 `season(A) != season(B)` 派生通知事件，通知事件本身不持有状态、不参与重放判定，与本裁定「不做时间轴事件」并不矛盾。
- **真正引入生产速率/地形通行性/野怪分布表时，需要重新面对这个问题**——那个阶段的实现者要决定季节对这些新系统的影响是继续走纯函数查询（`f(season(tick), 其他参数)`），还是这些新系统本身的状态变化需要事件驱动（例如「生产速率」本身可能因为其他原因变成需要存储的量，届时季节只是它的一个输入，而非驱动它变化的机制）。本裁定不预判那个决定，只确保「季节本身」这一层不引入脱节风险。
