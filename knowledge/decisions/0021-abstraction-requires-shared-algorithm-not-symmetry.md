# 0021 — 抽象的理由是「有算法要共用」，不是「看起来该对称」（`Camera`/`BoundedCamera` 与 `compute_fov` 泛化不对称）

**日期**：2026-08-18（裁定 CS-4，坐标系重写批次 B）
**状态**：已生效
**关键提交**：`7d8fbb6`（`compute_fov` 泛化为 `SightGrid`，兼容环面与有界两种网格）、`462ee0e`（新增 `BoundedCamera`，与 `Camera` 各自独立）
**影响范围**：`crates/ll-world/src/fov.rs`（`SightGrid` trait，第 109 行；`compute_fov`，第 250 行）、`crates/ll-render/src/camera.rs`（`Camera` 第 11 行、`BoundedCamera` 第 83 行）、未来任何「一个概念要同时支持环面世界与有界室内空间」的泛化判断

## 背景

坐标系重写批次 B 要把此前只认「环面世界」（`TorusPos`/`ChunkGrid`）的两套代码，扩展到同时支持新引入的「有界室内空间」（`BoundedGrid`，室内地下城/建筑，不环绕、有边界）。批次内有两处结构表面相似、都要做这件事：

- **视野算法**（`compute_fov`）：一套阴影投射算法，此前只喂 `ChunkGrid`。
- **相机**（`Camera`）：记录视口中心与可见范围，此前只服务环面世界的渲染。

两处最终走了不同的泛化写法：`compute_fov` 抽出 `SightGrid` trait，让同一份算法函数通过泛型对两种网格静态分发；`Camera` 没有抽 trait，而是新增一个独立的 `BoundedCamera` 结构体，与原 `Camera` 不共享任何接口。

实施代理把这处不对称列为疑虑，问是否应该统一成同一种手法（要么都抽 trait，要么都各写一份）。

## 决定

**不统一。这处不对称是对的，维持现状。**

判断标准只有一条：**有没有一份算法要被两种网格类型真正共用？**

- `compute_fov`：**有**。阴影投射的扫描逻辑（`scan_row_in_sector`、角度区间收缩、对称性判定）对环面网格和有界网格是同一套步骤，唯一的差异是「怎么从坐标取到格子内容」这一层最基础的访问操作。不抽 trait 的代价是把这一整段算法逻辑复制两份，此后每次修 FOV 的 bug 都要改两处、且容易改漏一处——[0007](0007-symmetric-shadowcasting-fov.md) 记录过这套算法本身有多少反直觉的正确性细节（对称性、边界闭区间），复制品分叉的风险不是理论上的。
- `Camera`/`BoundedCamera`：**没有**。两者方法集不同（环面相机要处理坐标环绕，有界相机要处理边界钳制），且从未被同一份泛型代码统一调用——批次内没有任何一处代码写成「给我一个实现了某个 trait 的相机，我不关心它是哪种」。抽出一个共享 trait，不会消除任何重复逻辑，只会在两个本就不同的类型中间插一层没有实际内容的接口。

**抽象的理由是「有东西要共用」，不是「看起来对称」。** 两个同名字段、同样承担「记录视口」职责的类型，看上去应该走同一套抽象手法，但这种「看上去应该」是审美直觉，不是工程理由——真正的判据是有没有一份逻辑会因为不抽象而被复制。

## 被否决的选项

**把 `Camera`/`BoundedCamera` 也统一抽成 trait，理由是「与 `compute_fov` 保持风格一致」**——否决：这是本 ADR要拦住的那类判断本身。为了风格对称而抽象，会在没有任何重复逻辑消除的情况下，凭空引入一层间接调用（trait 方法分发）与两套需要同步维护的接口签名。若未来两种相机确实开始共享某段逻辑（例如都需要同一种视口裁剪算法），那时候抽 trait 是对的——但那时候的理由是「发现了要共用的算法」，不是「现在」。

**`Space` 做成 enum，内部按环面/有界两个分支 `match`（批次 B 完成记录里提到的另一个被否决方案，适用于 `compute_fov` 那一侧）**——否决：会把阴影投射算法整段复制成两个 `match` 分支，与不抽 trait 是同一个代价，`SightGrid` + 泛型静态分发（单态化后与手写两份代码生成的机器码等价，不引入 `dyn` 或运行时开销）更优。这条否决是 `compute_fov` 选择 trait 泛化的直接理由，附带记录以说明该侧的选择也是权衡过的，不是默认选项。

## 后果

- 这条理由本应写进 `fov.rs`（`SightGrid`/`compute_fov` 附近）与 `camera.rs`（`Camera`/`BoundedCamera` 附近）的文档注释——CS-4 裁定时明确要求了这一点，作为对未来贡献者的直接提醒，而不是只留在这份 ADR 里等人来查。若尚未落地，应作为后续任务的小修复项之一。
- **这条判据不是「trait 总是过度设计」的一般性结论**，也不是「结构体总是更简单」的一般性结论——两个方向的滥用都可能发生。唯一稳定的判据是本 ADR 标题那句话，具体到某个新场景时仍需要重新问一遍「有没有算法要共用」，不能把 CS-4 的具体结论（相机不抽 trait）当成放之四海而皆准的规则直接套用到其他类型对。
- 若未来两种相机确实长出共享逻辑，正确的应对是**那时候**抽出 trait 或共享函数，而不是现在预先抽象等着以后用上——这是 [0009](0009-derive-by-default-store-only-deviation.md)、`coding-style.md` YAGNI 原则在这个具体场景的又一次体现：不为「将来可能需要」的对称性预先付复杂度的代价。
