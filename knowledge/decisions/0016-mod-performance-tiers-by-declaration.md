# 0016 — mod 性能分档按声明方式，不按作者身份

## 背景

本项目奉行「本体即 Mod」——本体内容与 mod 内容走完全相同的注册通道（[0015](0015-content-id-registration-is-parsing-not-invariant.md) 的命名空间 ID 机制正是这条原则的地基）。这条原则唯一的实际作用，是逼着 mod API 必须完备到本体自己都能靠它实现全部内容——若本体走一条 mod 走不到的捷径，这条检验就失效了。

P4 开工前，项目所有者提出一个务实的顾虑：性能敏感的地方，能不能让本体自带一层优化，mod 即便实现了同样的功能也不强求达到这层优化？

## 决定

**同意这个顾虑本身务实，但换一条判断轴：分档看内容是怎么声明的，不看是谁写的。**

| 档 | 开销 | 做法 |
|---|---|---|
| 一 | 零 | 声明静态值 → 注册期物化进 Rust 表，运行期查表 |
| 二 | 低 | 声明受限公式 → 编译成枚举/小字节码，Rust 侧求值 |
| 三 | 有 | 任意脚本回调 → 跨 VM 调用，且游戏明确告知其开销 |

三档对本体与 mod 一视同仁——**只用第一档的 mod 与本体一样快**，因为运行期两者查的是同一张表，没有「本体优化、mod 没有」这回事。本体全部用第一档（因为大多数内容确实做得到，参见 [0017](0017-tiered-declarations-materialize-columnar.md) 的物化方式）；真正需要第三档的是本质动态的东西（例如移动代价随天气实时变化，这类量没有办法预先物化成一张静态表）。

## 为什么不按作者身份分档

若快慢取决于「这是本体代码还是 mod 脚本」，会连锁产生三个后果，都会伤到「本体即 Mod」这条原则本身：

1. **mod 加内容会不可预期地拖垮帧率，作者却无从判断原因**——同样的功能，本体实现是零开销，mod 用脚本实现却带着固定的跨 VM 调用成本（[0012](0012-steel-capability-surface-verification.md) 实测：`call_function_by_name_with_args` 包中断防线后均摊 326ns，`engine.run(源码字符串)` 高达 327~400µs），mod 作者如果不知道有更快的声明式档位可用，会误以为「mod 天生就是慢」，无从优化。
2. **「反正 mod 本来就慢」会变成不修 API 的借口**——一旦分档按身份走，任何 mod 作者抱怨性能，都可以用「你是 mod，本来就该慢」搪塞过去，而不去检查是不是 API 本身有洞、没给 mod 提供声明式的路径。
3. **API 完备性从此不再被本体撞出来**——本体如果享有一条 mod 走不到的性能捷径，本体开发者就没有动力去补全「mod 如何声明式地表达同样的效果」这件事，「本体即 Mod」的检验价值直接归零。

## 守门规则（不可破例）

**若本体需要一个 mod 够不着的性能档位，那是 API 缺陷，不是特性。** 本体必须始终能用公开的声明式档位（一、二档）表达它的内容。这条规则一旦破例——哪怕只破一次，理由是「这个本体功能实在特殊」——API 完备性检验就再也没有约束力：往后任何 mod API 的缺口都可能被同一个借口正当化，而这正是「本体即 Mod」原则设计出来要防的事。

## 被否决的选项

**按作者身份分档（本体自带优化，mod 尽力而为）**——即项目所有者最初提出的方案本身。否决理由见上节三条连锁后果。裁定采纳了「性能敏感处需要更快路径」这个务实判断本身（这点没有被否决），只是换了一条不伤害核心原则的轴来实现它。

**不分档，全部走脚本回调（第三档）**——未被认真考虑，因为这正是「性能敏感处能否有更快路径」这个顾虑想要避免的情况；本体自己的地形、移动代价等内容若也全部走脚本回调，[0012](0012-steel-capability-surface-verification.md) 里 `engine.run` 400µs 级别的开销会直接体现在逐格移动、逐帧渲染这类高频路径上，不可接受。

## 配套：把开销做成可见的

加载管理界面除了显示错误，还要一并显示各 mod 用了哪些档位（例如「某 mod：3 项内容使用脚本回调（运行期开销）」）。**代价可见，人才会去省**——这比任何文档提醒都有效，也是「按声明方式分档」这条设计落到玩家/mod 作者可感知层面的唯一途径：如果开销藏在背后，mod 作者不会有动力去把能声明成一/二档的内容改写成声明式表达。

## 后果

- **本体成为这条规则的第一个测试对象**：P4 Task 8（`TerrainKind` 迁入注册表）就是检验——若迁移后本体的地形查询反而变慢，说明分档与物化方式本身设计有误（详见 [0017](0017-tiered-declarations-materialize-columnar.md)），而不是「数据驱动天生有性能代价，可以接受」。
- **mod API 表面（Task 5）与注册表核心（Task 7）的设计必须为一、二档的声明式表达留出真实的表达力**——若设计到最后发现某类本体内容只能用脚本回调表达（无法降到一、二档），必须回头修 API，而不是把本体那部分内容悄悄开个后门跳过声明式路径。
- **该规则不禁止第三档存在，只要求它的存在必须对 mod 和本体公平**——本质动态的内容（如天气影响的移动代价）本体自己实现时也要走第三档、承受同样的开销；不能因为是本体代码就默许它走一条 mod 走不到的捷径。
- **截至本 ADR 写下时，这条规则尚未被任何真实 Task 5/7/8 的实现验证过**——`ll-mod` crate 尚未创建，`TerrainKind` 仍是硬编码 `match`（`crates/ll-world/src/terrain.rs:73` 起）。本 ADR 记录的是设计决定本身，不代表实现已落地或规则已被证明可行。
