# 0018 — 脚本层边界改按系统类型划分（引擎层 / 玩法层），取代「本体不享有特权通道」的字面读法

- **冻结时间**：2026-08-18
- **基线提交**：`270783e`（写作本 ADR 时的 HEAD，工作区干净，496 测试全绿）
- **状态**：已定稿的设计决定，等待后续任务（若有）落地到代码/文档
- **影响范围**：规格 §10.3（已同步修订）、[0016](0016-mod-performance-tiers-by-declaration.md) 的守门规则（适用范围收窄，见本 ADR「与 0016 的关系」一节，**不改 0016 正文本身**）、未来任何新增系统的归类判断

## 背景

规格 §10.3「本体即 Mod」原文：

> 本体的全部内容——职业、技能、物品、怪物、地图生成器、任务图、行为树、本地化——均通过与 mod 完全相同的注册表 API 注册，本体不享有任何特权通道。

这句话字面上没有限定适用范围。「本体的全部内容」若按字面理解，会把渲染、物理、寻路、FOV 这些显然不该脚本化的系统也卷进「必须能被 mod API 表达」的要求里。这条原则因此陷入两难：

- **字面执行**：渲染管线、寻路算法也要能被 mod 脚本重新定义——荒谬，且与规格 §10.1/§10.2 反复强调的沙箱能力边界（Steel 脚本只应触达明确注册的游戏 API）直接冲突。
- **含糊执行**：大家心照不宣地知道渲染/物理不算，但「那条线到底在哪」从未写下来。P4 实际开发中已经出现真实的边界模糊案例（见下节）。

项目所有者裁定：**换一条判断轴**——不再按「本体身份 vs mod 身份」划界（这条轴从一开始就问错了问题：本体和 mod 都是内容的作者，两者之间当然不该有特权差异），改按**系统类型**划界：这个系统本身是否有「设计者可能想要不同规则」这个自由度。

## 决定

```
引擎层   渲染、物理、寻路、网络同步、时间轴调度（队列机制本身）、FOV、光照计算
         → 永远是原生 Rust，不进脚本层，本体与 mod 都碰不到

玩法层   AI 行为、物品效果、事件响应、任务逻辑、技能效果
         → 用脚本写，本体内容与 mod 用同一套 API
```

「本体即 Mod」的检验价值不变，只是限定了范围：**在玩法层内**，若 mod API 缺了什么，本体自己也做不出来——这仍然成立，而且现在「玩法层」这个范围本身有了可操作的判据（见下节），不再是一句「大家心里有数」的默契。

规格 §10.3 已同步修订，保留原文语气，正文只在「本体的全部内容」前加了「玩法层」限定语，并把归类判据与验证过程指回本 ADR，不重复贴一份。

## 归类判据

新增系统时，按以下三步依次判断，任何一步能给出结论就停止：

### 第一步：有没有「设计者可以选另一种规则」这个自由度

问题不是「这个系统复杂不复杂」「这个系统慢不慢」，而是：**存不存在两种同样『工程正确』、但代表不同游戏设计意图的实现？**

- FOV 的对称阴影投射：不存在这个自由度。你可以选不同的算法（递归阴影投射、光线投射……），但「视野是否对称」不是设计选择，是正确性要求（规格明确写了「必须使用环面坐标」「对称」）——算法本身没有留给内容作者的调节余地。→ **引擎层**。
- 「撞入这格地形会不会变成另一种地形」：存在这个自由度——不同的地形（门、活板门、普通墙）应该有不同行为，这正是「设计者的选择」。→ **玩法层**。

这一步天然排除了「渲染怎么画」「网络包怎么序列化」这类纯粹工程正确性问题——它们只有对错，没有「设计选择」。

### 第二步：这个自由度落在哪个粒度上——算法本身，还是算法读的数据

第一步筛出「有自由度」的系统后，还要分清楚自由度落在**算法**还是**算法消费的数据**上：

- 移动代价（`move_cost`）不是寻路算法本身，是寻路算法读取的输入数据。「不同地形代价不同」是设计选择（玩法层），「最短路径怎么算」不是（引擎层）。两者可以同时成立而不矛盾：**寻路算法是引擎层，它读的地形代价表是玩法层内容**。
- 这一步防止「某个系统里有一丁点可配置的数字」就被整体拖进玩法层——真正决定归类的是「设计自由度落在哪一层」，不是「这个系统沾不沾数据」。

### 第三步：高频调用是实现问题，不是分层问题

一个系统即使被每帧/每格调用（例如 `move_cost` 查表），只要它本身通过第一、二步判定属于玩法层（声明式数据），就应该留在玩法层——用 [0016](0016-mod-performance-tiers-by-declaration.md) 的一/二档解决性能问题，**不是靠把它挪去引擎层解决**。「高频」决定这个玩法层内容该用哪一档物化，不决定它该不该在玩法层里。

反过来，真正把一个系统推向引擎层的，从来不是它的调用频率，而是第一步——它没有「用声明式数据表达」的自由度。FOV 的阴影投射算法不能被「声明」成一张表，它是必须以确定方式执行的算法步骤本身；地形的移动代价可以。

## 用现有系统验证判据

逐项套用三步判据，覆盖规格 §5 Crate 分层与既有代码里能列出的全部系统：

| 系统 | 第一步：有设计自由度？ | 归类 | 依据 |
|---|---|---|---|
| 精灵批渲染（`ll-render`） | 否，纯工程正确性 | 引擎层 | 无设计选择余地 |
| 物理/碰撞判定 | 否 | 引擎层 | 「能不能同图站两个实体」是规则正确性，不是设计选择 |
| 寻路算法本身（A\*/Dijkstra 求解过程） | 否，算法只有对错 | 引擎层 | 第二步：自由度在它读的地形代价表上，不在算法本身 |
| 网络同步（未来） | 否 | 引擎层 | 帧同步/状态同步正确性，无设计选择余地 |
| 时间轴调度器（优先队列机制、`BinaryHeap`+`EntityId`平局规则） | 否，队列机制本身只有对错 | 引擎层 | 第二步：自由度在「什么事件会被插入队列」，不在队列本身怎么弹出 |
| FOV 对称阴影投射 | 否 | 引擎层 | 规格明确要求「对称」，是正确性约束不是设计选择 |
| 环境光照计算（`ambient_light(clock)`） | 曲线数值可以有设计自由度，但当前实现是引擎侧公式 | 引擎层（当前实现），曲线参数化留作未来玩法层扩展点 | `query.rs` 里 `world-ambient-light` 是脚本只读查询结果，不是脚本自己算——即使未来光照曲线开放给 mod 调参，也是「引擎层公式 + 玩法层参数」的第二步分离，公式本身仍是引擎层 |
| **`TerrainKind` 声明**（`move_cost`/`blocks_sight`/`blocks_move`） | 是，不同地形的这些属性代表设计选择 | 玩法层 | 已迁入 `ll-mod::registry`（P4 Task 8），走 ADR 0016/0017 第一档物化 |
| **`opens_into`（撞入即开）** | 是，「哪些地形有这个行为、开成什么」是设计选择 | 玩法层 | 见下节「`opens_into` 仍是真洞」 |
| 行为树 tick 求值器（Rust 侧遍历 selector/sequence 节点） | 否，遍历算法本身无设计自由度 | 引擎层 | 第二步：自由度在节点判断/动作函数（Steel 函数）里，不在求值器怎么遍历 |
| 行为树节点判断/动作（`hp-below?`、`attack-anyone-near`……） | 是 | 玩法层 | 规格 §10.5 已经是 Steel `.scm` |
| 物品效果（`use_effect`） | 是 | 玩法层 | `item-system.md` 已定 |
| 事件响应（季节切换钩子等） | 是 | 玩法层 | §7.2 裁定 P3-5：季节本身是引擎层纯函数，但「季节变化时做什么」是玩法层钩子——同一处系统里第二步分离的又一个实例 |
| 任务系统（`Goal`/`Task` 链） | 是 | 玩法层 | `agent-goals-and-economy.md` 已定 |
| 技能结算公式（`resolve` 内部调用 Steel） | 是 | 玩法层 | 规格 §4：`resolve` 可调用 Steel |
| 经济定价公式（本地价 × 归属系数） | 是 | 玩法层 | `agent-goals-and-economy.md` 已定 |
| 存档序列化/迁移（`postcard`/`lz4_flex`/schema 版本链） | 否 | 引擎层 | 字节格式正确性，无设计选择余地 |
| mod 加载管线（发现/清单解析/依赖拓扑排序） | 否 | 引擎层 | 加载流程本身的正确性，不代表设计意图 |
| 确定性 RNG（`DetRng::for_entity`） | 否，算法必须精确可重现 | 引擎层 | 约束 C3：脚本只消费预先构造好的流，不实现算法本身 |
| 世界时钟（tick 进制换算） | 否 | 引擎层 | 唯一真相源，无设计自由度 |

十九项系统，三步判据全部给出了唯一结论，且与既有代码里已经隐含成立的划分（例如 `rng.rs`/`query.rs` 一直只暴露"读结果"而不是"算法本身"）完全吻合——判据不是凭空发明的新规则，是把代码里已经在做的事说清楚。

## `opens_into` 仍是真洞——且新划法让它更明确

P4 Task 8 已经把 `opens_into: Option<NamespacedId>` 加进 `TerrainAttrs`（`crates/ll-world/src/terrain.rs`），把「哪个地形撞入后变成哪个地形」做成了任意地形都能声明的属性，`ll_sim::resolve::resolve_move`/`resolve_open_door`（`crates/ll-sim/src/resolve.rs:141`/`:223`）相应地把恒等比较换成了查表。**这一半已经不是洞了**——迁移前后的测试（`撞入即开不是只对关着的门生效的特判`）已经验收过。

但还有另一半没解决：`resolve_move` 里"撞入一格『撞入即开』的地形时，产生一个改写地形的 `Effect`，而不是移动效果"这条**通用交互规则本身**，仍然是 `ll-sim::resolve.rs` 里的原生 Rust 代码——`opens_into` 只是这条规则能读的**一个**数据字段。若某个 mod 想发明一种全新的交互（例如"踩上这格地形扣血""撞入这格地形触发爆炸"），现有 API 完全没有对应的声明式字段，唯一的实现路径是去改 `ll-sim` 的 Rust 源码——这正是 ADR 0016 守门规则要抓的那类缺口：**本体（`opens_into` 这一种交互）能表达的，mod（任意新交互）表达不了**。

按旧的「本体身份 vs mod 身份」划法，这个洞的归属是模糊的：`resolve` 本身在规格 §4 里跨在"纯函数""可调用 Steel"这条线上，不容易一眼看出该不该被脚本化盖住。按新划法，第一步判据直接给出结论——"交互规则该做什么"代表设计意图（不同地形/不同触发物应该有不同交互后果，这本身就是设计自由度所在），不是工程正确性问题，**明确落在玩法层**。新划法没有替 P4 把这个洞补上（那是另一项独立的实现任务），但把「这个洞归谁管」这个问题的答案从「说不清楚」变成了「玩法层，等 API 补上一种更通用的『交互规则』声明式表达」——这就是本节标题「仍是真洞，且新划法让它更明确」的含义。

## 与 [0016](0016-mod-performance-tiers-by-declaration.md) 的关系（收窄，不改动 0016 正文）

0016 的守门规则原文：

> 若本体需要一个 mod 够不着的性能档位，那是 API 缺陷，不是特性。

这句话写在「本体即 Mod」尚未按系统类型划界的时期，字面上的「本体」没有排除引擎层——若严格按字面读，会隐含"引擎层比 mod 脚本快，也算 API 缺陷"这种荒谬结论（例如"渲染管线比 Steel 脚本快"显然不该被读成 mod API 有洞）。实际执行中 0016 从未真的被这样误用过（0016 讨论的三档分级本身只针对走注册表的内容），但字面表述留了这个歧义。

本 ADR 把「本体的全部内容」限定为「玩法层内容」之后，0016 守门规则的适用范围也随之收窄为：**若本体在玩法层需要一个 mod 够不着的性能档位，那是 API 缺陷**。引擎层系统（FOV、渲染、寻路……）从一开始就不通过 mod 注册表 API 暴露，谈不上"mod 够不着"，也就不在 0016 守门规则的管辖范围内——这不是对 0016 结论的推翻，是把它一直隐含成立的范围显式写出来。

**不直接修改 0016 正文**：已发布的 ADR 应当被取代而非篡改，这是 ADR 的惯例——0016 记录的是它写下时刻的决定与理由，本 ADR 记录的是后续对适用范围的澄清，两者叠加读才是完整决定，不应该把后来的认识回填进前一份文档、抹去决策演变的痕迹。

## 被否决的选项

**继续按「本体身份 vs mod 身份」划界，只是补一句「引擎系统除外」的免责声明**——否决理由：这只是把「那条线在哪」的问题往后拖延了一步，「哪些算引擎系统」依然没有可操作的判据，回到了「大家心里有数」的含糊执行状态，没有真正解决问题。

**列一份穷尽的系统白名单/黑名单（写死"这十几个系统是引擎层，其余都是玩法层"）**——否决理由：面对未来新增系统（P5 之后可能出现的天气系统、群体寻路优化、粒子特效脚本化等）没有可复用的判断方法，每次都要回来加白名单条目，本质上和"大家心里有数"是同一类问题，只是换了张纸写。三步判据的价值正是可以套在任何未来新系统上，不依赖穷尽列举。

## 后果

- 规格 §10.3 已同步修订（本次提交），保留原文语气，只加了范围限定与指回本 ADR 的引用。
- `opens_into` 剩余的那半个洞（通用交互规则本身仍是原生 Rust）记录在案，留给后续任务判断是否值得为它设计一种更通用的声明式"地形交互"表达（可能是 ADR 0017 第二档"受限公式"的又一个应用场景），本 ADR 不代为决定优先级。
- 未来任何新增系统，按本 ADR 「归类判据」一节的三步法判断即可，不需要每次都回来重新讨论"这个算不算本体特权"。
- 判据本身没有被真实的新系统开发验证过（现有十九项系统是回顾性套用，不是判据设计出来之后真正指导过一次新系统的从零决策）——若未来某个新系统套用判据后依然有争议，说明判据本身可能需要修订，应该记录下来而不是强行套用出一个勉强的答案。

## 【2026-08-23 订正】机制那一半已被取代：玩法层内容改用 JSON5 数据文件 + 引擎内 Rust

**本节是追加的订正，正文一字未改**（ADR 惯例，见本 ADR「与 0016 的关系」一节论证的同一条理由）。

### 什么被取代了，什么仍然成立

本 ADR 有两半：

1. **判断轴**（引擎层 / 玩法层，三步归类判据）——**仍然成立，未被取代**。「这个系统有没有『设计者可能想要不同规则』这个自由度」这条判据与用什么技术实现玩法层无关。
2. **机制**（「玩法层：用脚本写，本体内容与 mod 用同一套 API」，以及由此派生的验收要求「每种玩法层内容类型都能从 mod 脚本注册，且要有真实 mod 脚本为证」）——**前提彻底失效，被取代**。

取代它的是：**内容用 JSON5 数据文件（`mods/<id>/*.json5`），行为逻辑在引擎里用 Rust 写**。

### 为什么

Steel 脚本系统整体拆除。直接起因是
[ADR 0028](0028-steel-engine-construction-memory-corruption.md) 记录的
`steel-core` 0.8.2 上游内存破坏：完整测试套件有 17–33% 的概率不是测试
失败、而是进程被野指针打断，六条假说全部被数据否决，没有任何本项目侧
的规避手段。项目所有者据此裁定去掉整个脚本系统。

**第三方 Rust 扩展能力（注册表 / C ABI）明确推迟，不做。** 也就是说，
玩法层内容现在是**声明式数据**，玩法层**逻辑**（AI 行为树、技能结算、
物品使用效果）住在引擎里的 Rust——mod 作者能声明内容，不能提供新逻辑。

### 本 ADR 的验收要求怎么读

原文要求的「每种玩法层内容类型都能从 mod 脚本注册，且要有真实 mod
脚本为证」，等价改写为：

> 每种玩法层内容类型都能从 mod 的 JSON5 内容数据文件声明，且要有真实
> mod 内容为证。

这条要求本身**没有被削弱**，只是换了通道：`ll_mod::pipeline::GameplayTables`
的字段个数仍然是「mod 能声明几类玩法层内容」的唯一权威清单，
`ll_mod::content_data::CONTENT_FILES` 是它的文件名映射，
`mods/example_mod/*.json5` 是那份真实证据（十八类内容，`crates/ll-mod/tests/example_mod_*.rs`
逐类验收）。

### 换通道带来的一处真实收窄，如实记录

脚本通道曾经允许 mod 提供**逻辑**（行为树、技能效果回调）。数据文件
通道不允许。ADR 0016 那条守门规则（「若本体需要一个 mod 够不着的东西，
那是 API 缺陷」）在这一点上现在**必然不满足**：本体的 AI 行为树是
`ll_mod::native_behavior` 里的 Rust，mod 写不出等价物。这不是被忽略的
缺口，是项目所有者裁定接受的代价——「第三方 Rust 扩展能力明确推迟」
就是这句话的另一种说法。什么时候要补，由项目所有者另行裁定。

## 【2026-08-31 订正】本 ADR 长期被误引为「反例验证」纪律的依据，真正的依据是 0022

**本节是追加的订正，正文与上面那节 2026-08-23 订正一字未改**（ADR 惯例，见本
ADR「与 0016 的关系」一节论证的同一条理由）。本节不改变本 ADR 的任何结论——
它记录的是**别人怎么引用本 ADR**出了错，不是本 ADR 自己错了。

### 什么被误引了

全仓库长期存在这样的句子：

> 「**ADR 0018** 的反例验证是硬要求：每条断言都要用**故意改坏**的方式验证它
> 真的会红。」

**本 ADR 全文与反例验证无关。** 判据：

```bash
grep -c 反例 knowledge/decisions/0018-engine-layer-vs-gameplay-layer-scripting-boundary.md
# → 0（本订正节写下之前）
```

本 ADR 讲的是两件事，都不是反例验证：

1. **判断轴**：引擎层 / 玩法层，三步归类判据（「归类判据」一节）；
2. **验收要求**：「每种玩法层内容类型都能从 mod 的 JSON5 内容数据文件声明，且
   要有真实 mod 内容为证」（2026-08-23 订正节）——注意这条的适用范围是**玩法层
   内容类型**，不是「任何新能力」。

### 真正的依据是哪一份

[**ADR 0022 — 覆盖不全的确定性哈希，等于没有确定性哈希**](0022-guard-coverage-gap-defeats-the-guard.md)。
它「决定」一节记着 CS-6 的原始「故意改坏」验证（`sea_level` 400 → 500，确认哈希
确实变化；改回 400 确认变绿——「证明黄金基准值不是照抄实际输出的空判断，而是真
的对输入敏感」），并把自己的主张概括成**「覆盖不全的守护等于没有守护」**。
仓库把它推广成了通用形式：*一条改坏了也不会红的断言，等于没有断言。*

### 一处仍然没有 ADR 承载的纪律，如实记录

普扫过程中分出第三类引用：**「新能力必须有经真实 `mods/` 内容、走生产路径的
端到端证据」**（例如「不造任何简化夹具」「与本体二进制走同一串调用」）。这一
条既不是本 ADR 的验收要求（本 ADR 只管**玩法层内容类型**能不能由 mod 声明；
存档、世界生成参数、图集打包在本 ADR 的逐项验证表里都是**引擎层**），也不是
0022 的判据覆盖。

**这不是本次才发现的**：[0028](0028-steel-engine-construction-memory-corruption.md)
「候选 D」一段已有一句原地订正——「调查过程中有人把这条做法归给 ADR 0018，实际
不是……这条做法只体现在 `crates/ll-mod/tests/*.rs` 的写法里，**没有任何 ADR 为它
背书**」。批次 25 复核确认该结论至今成立。**是否为它新开一份 ADR，需要项目所有者
裁定；批次 25 不代为决定**，那一类引用因此一处未动，逐条列在批次 25 的报告里。
