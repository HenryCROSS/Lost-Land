# 0025 — demo 交互验收禁止合成键盘事件（SendKeys）盲注，改用程序化驱动同一调用路径

**日期**：2026-08-19（裁定 CS-7，坐标系重写批次 E，验收 demo）
**状态**：已生效的项目纪律
**关键提交**：`260d7ca`（feat：两级坐标系重写验收 demo，`p5_coordinate_acceptance`，同一提交内记录事故与改用 `walkthrough_test.rs` 的处置）
**影响范围**：`crates/ll-sim/examples/p5_coordinate_acceptance/walkthrough_test.rs`（新建的程序化验证范式）、未来任何需要交互式按键验收的 demo（P6/P7 等后续阶段）

## 背景

坐标系重写批次 E 的验收 demo（`p5_coordinate_acceptance`）需要验证「按键 → 渲染」这条完整链路在真实窗口里确实工作——启动一个真实 wgpu 窗口，用截图核实 minimap/FOV/走廊铺设符合预期，然后需要模拟一串方向键（WASD/Enter）走查跨区块移动、进出 `Interior` 等交互场景。

**这类按键走查此前在 P3、P4 的验收 demo 里都用过合成键盘事件（SendKeys 一类的系统级按键注入），当时没有出问题。**

## 事故经过

本批次实测发现：**合成键盘事件的前台窗口锁定在宿主 Claude 桌面应用本身，不是刚启动的 demo 窗口**。继续尝试会把按键泄漏进宿主聊天窗口——**这件事真实发生了**：一串合成按键（`dddd...`）实际出现在了协调者与项目所有者的对话里。实施代理诊断确认问题根源后**立即停止**并如实报告给用户，未造成其他影响。

## 决定

**今后 demo 的交互验收必须先确认前台窗口归属；确认不了就改用程序化驱动，不得用合成键盘事件盲注。**

本批次的具体处置：改用 `walkthrough_test.rs`——不模拟按键，直接驱动 `Intent → resolve → Effect → apply` 这条与真实按键完全相同的调用路径（真实按键最终也是先映射成 `Intent`，见 [0006](0006-intent-resolve-effect-apply.md)），程序化走一遍验收要求的场景。这不是「退而求其次」的妥协方案，而是更可靠的验证手段——它绕开了操作系统级按键路由的不确定性，直接命中被测的业务逻辑层。

## 这条自动化路径本身抓出的真实缺陷

程序化驱动不只是规避了事故，还**真的抓出两个单元测试测不出的连线缺陷**：

1. 出生点到 `Interior` 入口之间的路径未全程强制可通行——只铺了入口那一格，中间路径仍是深水（撞见与 P4 验收 demo「熔岩地板」同一类问题：出生点周边路径规划与地形生成脱节）。
2. 流式加载验证测试的终点算错了区块环面覆盖范围（最初把测试终点设在会被出生点预热邻域环绕覆盖到的区块，实际没有触发真正的流式加载）。

两处均已修复并补了对应的回归断言。**这是本项目第五次验收 demo 抓出单元测试测不出的连线缺陷**，与 P2/P3/P4 此前几次验收 demo 的经验一致——纪律「验收 demo 必须真正跑起来，不能只靠单元测试」持续有效，本次事故没有削弱这条纪律，反而是它的又一次证明（只是验证手段从「真实按键」换成了「程序化走相同路径」）。

## 被否决的选项

**继续用 SendKeys，只是加一步「先手动确认窗口聚焦」的人工检查**——否决：前台窗口的聚焦状态在自动化环境里本身就不稳定（这正是本次事故的根源——诊断确认聚焦锁定在宿主应用，而不是新启动的 demo 窗口），人工检查一次不代表按键注入期间聚焦不会再次跑掉,且这类检查依赖执行环境的具体细节（是否为远程会话、桌面合成器行为等），不是可靠的工程手段。

**放弃交互式验收，只用截图核对静态画面**——否决：会失去对「按键触发的状态转换」这条链路的验证能力（跨区块移动、进出 `Interior` 这类场景本身就是「一系列按键序列 + 期间的状态变化」，静态截图测不出这个）。`walkthrough_test.rs` 证明程序化驱动完全能覆盖这类场景，不需要放弃验收深度换取安全。

## 后果

- **P3、P4 的 demo 都用过 SendKeys 且未出问题——这条纪律是新增的，不是对那两次的追溯性违规认定。** 明确记录这一点，是为了避免以后有人误读本 ADR，去回头「修复」P3/P4 已经完成且未出过问题的 demo。
- **本次验收 demo 遗留了两处已知缺口（如实记录，非粉饰）**：未能肉眼确认「跨区块跨越瞬间无一帧接缝」——这是流式加载最容易做砸处的最强证据，程序化驱动不产生视觉帧，测不到这一层；「只渲染当前层」（地表/Interior 二选一显示）目前是代码结构保证（两个独立绘制函数），未截图对照进入前后两帧的实际画面。这两处需要真正的视觉验证，程序化驱动无法替代，留给后续需要视觉核实时处理。
- **今后任何需要按键走查的验收 demo，第一步应该是判断前台窗口归属是否可控**——在已知会话环境（本地开发机、独占窗口焦点）下，SendKeys 类手段仍然可用；在不确定前台窗口归属的执行环境下（例如当前这种由协调 Agent 驱动的会话），默认改用程序化驱动，不再默认信任按键注入是安全的。
- `walkthrough_test.rs` 建立的范式（程序化驱动 `Intent → resolve → Effect → apply`）本身值得作为未来验收 demo 的默认手段推广，不只是这次事故的善后——它比按键注入更快、更稳定、且能覆盖按键注入覆盖不到的场景（例如需要精确控制时序的连续意图序列）。
