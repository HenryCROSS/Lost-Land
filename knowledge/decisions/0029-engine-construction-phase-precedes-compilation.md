# 0029 — 构造阶段先于编译阶段（约束 C6），作用域单位从脚本文件升格为 mod

**日期**：2026-08-22
**状态**：已生效
**前置**：[ADR 0028](0028-steel-engine-construction-memory-corruption.md)（根因定位与五条假说的逐条否决）
**规格**：新增硬性约束 **C6**（`docs/superpowers/specs/2026-08-16-lostland-design.md` §4）
**影响范围**：`crates/ll-script/src/host.rs`、`crates/ll-script/src/whitelist.rs`、`crates/ll-mod/src/pipeline.rs`、`crates/ll-mod/src/script_behavior_source.rs`、`crates/ll-content/src/save_file.rs`

## 背景

ADR 0028 定位到：`steel-core` 0.8.2 的偶发内存破坏**只在「先编译、后构造」这个相邻关系上出现**。

| 做法 | 样本 | 崩溃 |
|---|---|---|
| 只反复构造引擎 | 16000 | 0 |
| 构造一次、反复编译 | 4800 | 0 |
| 构造、编译、构造、编译…… | — | 崩 |

ADR 0028 把三条候选缓解交给项目所有者裁定，本次是那次裁定的落地。裁定的目标不是「降低概率」，而是**让那个相邻关系一次都不出现**。

## 决定

### 一、约束 C6：同一根线程上，全部构造先于全部编译

一旦某根线程上调用过一次 `ScriptEngine::load_source`，这根线程上就**不得再构造 `ScriptEngine`**。

**机器强制**，不是约定：`ScriptEngine::new()` 里一句 `assert!`（不是 `debug_assert!`），违反当场 panic 并点名。理由是这类规则的失效方式极其隐蔽——将来谁加一处引擎构造点，代码照常编译、测试照常绿，偶发崩溃悄悄回来，而且崩在与新增点毫无关系的地方（ADR 0028：「哪一行炸取决于坏数据先被谁碰到」）。

### 二、为什么是「每线程」而不是「每进程」

**「进程级构造阶段」在类型系统层面就不成立。** 本仓库**不开** `steel-core` 的 `sync` 特性（ADR 0028 已核实），`Engine` 内部是 `Rc`，`ScriptEngine` 因此不是 `Send`——不可能在 A 线程构造、拿到 B 线程使用。要求「进程内所有构造先于所有编译」，等价于要求所有脚本工作都发生在同一根线程上，那不是本仓库的形态（测试框架每条用例各占一根线程）。

「每线程」也与实测机制对齐：steel-core 在不开 `sync` 时全部引擎级状态是 `thread_local!` 的，而 ADR 0028 实测「提高并行度反而压低故障率」，与「跨线程相邻也危险」的方向相反。

新线程天生处在自己的构造阶段（`thread_local!` 初值为 `false`）。**这也是「真的需要在编译之后再造引擎」时唯一被认可的做法**：换一根线程，而不是想办法把标记清掉。`ll-content` 的存档读取路径就是这么处理的（见下）。

### 三、作用域单位从「脚本文件」升格为「mod」

原先每个 `.scm` 入口点各构造一个引擎。改成**每个 mod 一个引擎，该 mod 的全部 `entry_points` 共用它**。

这不只是为了少造几个引擎，**它同时修掉一个真实的设计缺陷**：同一个 mod 的多份脚本此前是互相看不见的孤岛——`races.scm` 里 `define` 的辅助函数，同一个 mod 的 `classes.scm` 调用不到。而这些文件本来就是同一个作者写的同一份内容，拆文件只是为了「本体的种族都写在哪」有个不用搜索就能回答的答案（`mods/lostland/mod.json5` 文件头），不该顺带把它们变成孤岛。

**跨 mod 的隔离原样保住**：换一个 mod 就换一个全新引擎。两条性质各有一条测试钉着（`crates/ll-mod/src/pipeline.rs` 的 `同一个mod的后一个脚本能调用前一个脚本定义的辅助函数` 与 `跨mod的define互相不可见`）。

**白名单必须跟着改，否则这条语义只兑现一半。** `check_whitelist` 每次从空的局部作用域开始，后一份脚本引用前一份的 `define` 会被判成「引用了白名单外的自由标识符」——实测确认过，不是推测。因此 `ScriptEngine` 新增一个 `script_defined` 集合，记录本引擎上已经装载成功的脚本在**顶层** `define` 出来的名字，作为下一次白名单校验的预置局部名。

**这不放宽能力边界**：集合里的每个名字都来自脚本自己写的 `define`，其定义体在装载那一刻已经过过同一道白名单；跨 mod 的隔离靠「换引擎」，不靠这个集合为空。只收「被定义的那个名字」，**不收形参**——形参在完整展开后已被卫生宏重写成 `##a2` 这类内部记号，收进去等于白白放宽白名单。

### 四、逐文件编译这条边界必须保留

同一个 mod 的多个脚本仍然**各自一次 `load_source`**，绝不拼接成一个大编译单元。

拼接在崩溃层面没有任何好处——危险的相邻关系是「编译 → 构造」，多编译几次完全安全。而逐文件边界是后续批次的立足点：脚本顶部的显式依赖声明（`requires-file`/`requires-mod`）及其反向校验（「引用了别的命名空间的 id 就必须声明」）靠注册期记账实现，那需要「当前正在编译哪个文件」这个信息。拼接会把它做没。

### 五、行为树引擎：拆开「构造」与「填充」

`ScriptBehaviorSource::new` 原本一口气做两件事：造引擎 + 注册 API 并编译 `behavior.scm`。后者需要装载完毕才有的数据（`registry`、技能索引），所以天然排在 mod 装载（一连串编译）之后——正好凑成被禁的相邻关系。

拆开之后：`PreparedBehaviorEngine::new()` 只造空引擎，不需要任何装载期数据，调用方把它提到装载之前；`ScriptBehaviorSource::from_prepared` 负责注册 + 编译，留在原位。

**不合并两种引擎**：装载期引擎与行为树引擎的白名单能力表刻意不兼容（见 `mods/example_mod/mod.json5` 里 `entry_points` 上方的注释），那道隔离墙保留。改的是**什么时候造**，不是**造几个**。

### 六、存档读取路径：换一根线程

`ll_content::save_file` 在读档时调用 `ll_script::host::rebuild_all_engines_after_load`（约束 C1 要求的「VM 强制从零重建」）。读档必然发生在 mod 装载之后，调用线程早就编译过脚本——这是 C6 在生产路径上唯一一处真实冲突。

解法是把这次重建整个搬到一根新线程上（`std::thread::scope`）：新线程处在自己的构造阶段，而且 steel-core 的内核镜像本来就是线程局部的，换线程等于拿到一份没有被任何编译动作污染过的全新内核。返回的引擎在那根线程上就地丢弃——`ScriptEngine` 不是 `Send`，本来也搬不回来，而该调用点原本就没有使用它们（`let _ =`）；`REBUILD_COUNT` 是进程级原子量，跨线程照样可见，「重建确实发生」这条断言不受影响。

`rebuild_all_engines_after_load` 自身也从「造一个编一个」改成「先造齐 N 个再逐个编译」。

## 强制手段抓到了什么

断言不是装饰——**接上的当天就抓到 8 处真实的「先编译、后构造」**，全部是此前无人知道的：

| 位置 | 形态 |
|---|---|
| `ll_script::host::rebuild_all_engines_after_load` | 函数**自身**就是 N 次「造一个编一个」交替；两条测试同时变红 |
| `ll_content::save_file`（生产路径） | 读档时在已经编译过的线程上重建全部引擎 |
| `ll_script::api::state` 四条单元测试 | 一条用例里造两个引擎，中间夹着编译 |
| `ll_script::api::rng` 一条单元测试 | 同上 |
| `ll_script::tests::steel_syntax_reference` 一条 | 同上 |
| `ll_mod::tests::example_mod_guard_inspection` 一条 | 同一条用例构造两个 `ScriptBehaviorSource` |
| `ll_mod::tests::example_mod_stealth` 两条 | 装载真实 mods（编译）之后再构造行为树引擎 |

其中 `save_file` 那一处是**生产路径**，`ll-game` 每次读档都会走。它此前从未被识别为问题。

## 引擎构造的真实成本（供「每 mod 还是每脚本」这个粒度取舍用）

约束 C6 要求全部构造先于全部编译，于是装载期的 N 个引擎会**同时活着**——「粒度按 mod（4 个）还是按脚本文件（11 个）」因此从「有没有崩溃风险」变成了纯粹的「启动耗时 + 装载期内存峰值 对 文件级隔离」。这两个数此前没人量过，`crates/ll-script/examples/probe_engine_cost.rs` 是量它们的工具。

release 构建实测（本仓库开发机，Windows）：

| 项目 | 实测 |
|---|---|
| 一次 `ScriptEngine::new()`（内核已 bootstrap，只剩 `deep_clone`） | **约 65 ms**（10 次取平均，59–73 ms） |
| 主线程首次构造（含该线程的内核 bootstrap） | 84 ms —— 即 **bootstrap 约 19 ms** |
| 另一根线程的首次构造 | 103 ms（冷缓存，量级同上） |
| 一个引擎活着占多少堆 | **约 12.8 MiB** |

**编译完之后引擎可以立刻丢弃，内存真的回得来**：11 个引擎逐个编译再逐个析构后，存活堆从 140.6 MiB 回落到 7.7 MiB（回收 132.9 MiB）。残留的 7.7 MiB 是 ADR 0028 记过的两处已知泄漏（`compute_allowed_identifiers` 的 `Box::leak`、steel-core `InterruptHandler::drop` 不 `join` 的看门狗线程），不随引擎析构回收。**内存峰值只存在于装载期间**，装载完就回落。析构不受 C6 限制（C6 禁的是编译之后再**构造**），`load_all` 因此在每个 mod 编译完就地丢弃它的引擎。

据此推算 **4 个引擎 vs 11 个引擎**：

- 启动耗时差：7 × 65 ms ≈ **0.45 s**
- 装载期内存峰值差：7 × 12.8 MiB ≈ **90 MiB**（4 个约 51 MiB，11 个约 141 MiB）

debug 构建的绝对值会明显更大（steel-core 自身也是 debug），但比例不变。

## 实测：故障率降了 2.5 倍，但**没有归零**——原假说被证伪

门禁口径（`cargo test -p ll-mod --tests` 的全部 26 个测试二进制，判据是进程退出码），**交错** A/B 16 轮（一轮基线、紧接一轮改动后，用交错抵消 ADR 0028 记过的机器状态漂移）：

| 条件 | 轮数 | 崩溃轮数 |
|---|---|---|
| 基线 `3f02896` | 16 | **10（62.5%）** |
| 本 ADR 的改动 | 16 | **4（25%）** |

**这是一次真实的下降，但目标是零，没有做到。** 而且下降的原因大概率**不是**约束 C6 本身：C6 是机器强制的，违反就 panic，所以改动后**「同一根线程上的编译 → 构造」相邻关系一次都不存在**——如果那真是唯一触发条件，故障率应当归零。它没有。

剩下的 25% 里，崩溃签名与基线一模一样（`steel-core/src/compiler/passes/mod.rs:356` 的 `misaligned pointer dereference: address must be a multiple of 0x8 but is 0x4`，发生在 `Engine::new_sandboxed()` 内部编译 steel 自己的 prelude 时）。

更直接的证伪来自探针（`probe_engine_churn.rs` 新增的 `mixed` 模式与 `pure` 的多线程对照）：

| 模式 | 每进程做什么 | 样本 | 崩溃进程 |
|---|---|---|---|
| `pure`，**8 线程** | 每根线程只反复 `Engine::new_sandboxed()`，**一次都不编译** | 40 进程 × 8 线程 × 60 周期 | **1**（段错误） |
| `mixed`，8 线程 | 0 号线程只编译（构造一次、反复 `load_source`），其余 7 根只构造 | 40 进程 × 8 线程 × 60 周期 | **1** |

**`pure` 多线程崩了。** ADR 0028 记的 `pure` 0/16000 是**单线程**的；这条结论不能外推到多线程。也就是说：**一个完全不编译任何脚本的工作负载，只要并发构造引擎，照样会崩。**

因此 ADR 0028「触发条件是同一根线程上反复交替构造与编译」这条结论**至少是不完整的**：真正的变量里还有「多根线程并发构造引擎」这一项，而 ADR 0028 当时用「提高并行度反而压低故障率」把并发假说整个否决了——那次观测（`load` 模式 12 线程 0/14400）与本次 `pure` 8 线程 1/40 并不矛盾（样本量都小），但它显然不足以支撑「并发无关」这个否决。

**下一步该查什么**（本 ADR 不做，留给后续批次）：

1. 把 `pure` 多线程与 `pure` 单线程各跑 ≥500 个进程，把 1/40 这个单次观测变成有统计意义的对照。**这是现在最薄的一环**，也是最便宜的一步。
2. 若确认并发构造是变量，最直接的缓解是**给引擎构造加一把进程级互斥锁**（`ScriptEngine::new` 全程持锁），代价只是装载慢一点——注意这与 C6 正交，两条可以同时成立。
3. ADR 0028 列的「进程内只装载一次」（把 1200 次装载期构造压到 26 次）仍然有效，且在「构造次数本身就是风险源」这个新认识下，价值比原先估计的更高。

**C6 本身仍然应当保留**：它花的代价接近于零（一次 TLS 读），它抓到了 8 处真实的时序违反（含一处生产路径），而且「先编译后构造」这个相邻关系在 ADR 0028 的单线程最小复现里确实是唯一能复现的组合。**但不要把它当成这个 bug 的修法**——它不是。

## 后果

- **新增内容时必须对照 C6**：任何新的 `ScriptEngine::new()` 调用点，都要先回答「这根线程上编译过脚本没有」。答案是「编译过」时，正确做法是把构造提前，或者换一根线程——不是加豁免。
- `ll_mod::pipeline::load_all` 的引擎数量从「入口点数」降到「有脚本的 mod 数」（真实 `mods/` 目录：10 → 4）。装载耗时随之下降，但那是副产品，不是目的。
- **mod 作者可见的语义变化**：同一个 mod 的脚本现在共享定义。这是能力增加，不是限制，且与「顺序有意义」这条既有事实（`mods/lostland/mod.json5` 里 `crafting.scm` 必须排在 `subclasses.scm` 前）方向一致。
- **`--test-threads=1` 不受影响**（已实测）：libtest 即使把并发度设成 1，仍然为每条用例单独起一根线程，因此每条用例各自处在自己的构造阶段，断言不会误伤单线程调试跑法。
- **不做 mod 热重载**这条既有裁定让 C6 长期成立：不需要为「运行中途重新装载一批 mod」留后路。若将来推翻那条裁定，C6 的落地方式要重新设计（大概率是「热重载整个跑在一根专用线程上」）。
