# 0017 — 声明式分档物化为列式数据，注册期完整校验

**日期**：2026-08-18（P4 开工前裁定，代号 P4-5）
**状态**：已定稿的设计决定，等待实现（`ll-mod` 尚未建立；影响 Task 5/7/8/11）
**关键提交**：无独立提交——本裁定目前只存在于 P4 阶段账本（`.superpowers/sdd/2026-08-18-p4-script-and-mod/progress.md`，BASE = 7157b4e）
**影响范围**：未来的 `ll-mod` 内容注册表、`TerrainKind` 迁入注册表（P4 Task 8）、未来的 `tools/ll-datacheck`

## 背景

[0016](0016-mod-performance-tiers-by-declaration.md) 定下「一、二档走声明式表达，运行期查表/求值，不进脚本 VM」这条分界线，但没有回答一个更具体的问题：一、二档的声明具体**物化成什么形状**？以及，物化之后拿什么保证声明本身没写错？

项目所有者在同一次讨论里提出：某些地方可以用数据驱动进一步加快速度。

## 决定

**这已经是本项目的主心骨，此条只是给它命名并把它推广到 mod 内容层。**

本项目在多处独立地做过同一件事——薄层列式实体存储（[0004](0004-two-layer-entity-storage.md)）、钱包/姓名/关系/性格默认派生（[0009](0009-derive-by-default-store-only-deviation.md)）——核心思想都是「按属性分列存，不按个体/内容分结构」。这条决定把它正式推广到 mod 内容注册表：

### 物化形状：按属性分列，不按内容分结构

第一档声明物化成**按 `ContentIndex` 索引的平铺列**，而不是「每个内容一个结构体」：

```
move_cost:    Vec<u32>     按 ContentIndex 索引
blocks_sight: BitVec
blocks_move:  BitVec
```

批量处理时遍历连续内存，与薄层人口（[0004](0004-two-layer-entity-storage.md)）同一套道理——一次查询一个属性，读的是这个属性自己的那一整条连续数组，不会像「每个内容一个结构体」那样把同一条记录里用不到的其他字段一起拖进缓存行。

第二档的受限公式**不留成 AST 递归求值**，编译成平铺指令数组，Rust 侧一个小循环跑完，无分配、无 VM——这条要求直接呼应 [0012](0012-steel-capability-surface-verification.md) 的性能实测结论：`engine.run` 级别的开销（327~400µs）绝不能出现在逐格查询这类高频路径上，AST 递归求值虽然不进 Steel VM，但仍然是比平铺数组慢得多的间接层。

### 追加要求：注册期完整校验

**第一、二档的声明必须在注册期就能被完整校验。** 填错的数在加载时报到加载管理界面，而不是等玩到某个场景才表现成怪行为。

这个要求之所以在此处追加，是因为数据驱动本身让它变得**可能**：正因为内容是声明式数据而不是任意代码，才能不运行游戏、只靠静态分析就检查出「这个数越界了」「这个公式引用了不存在的字段」——这正是规格里已经规划的 `tools/ll-datacheck`（数据表与脚本静态校验，CI 使用）存在的理由。数据驱动同时让这个工具**必要**（表述能力更大，出错的地方也更多）和**可能**（内容是数据，才能被静态检查覆盖）。

## Task 8 的额外验收标准：迁入注册表后不得变慢

`TerrainKind` 当前是硬编码 `match`（`crates/ll-world/src/terrain.rs:73` 起，分支预测 + 代码膨胀）；迁入注册表后是 `move_cost[idx]` 一次数组访问。逐格地形查询是热路径，**消掉分支是净赚，不是打平**。

这条要求把「数据驱动」从「为了可 mod 化而接受的性能代价」，反转成「数据驱动本身就更快」的论断——若 Task 8 迁移完成后地形查询反而变慢，说明物化形状本身选错了，这个反例本身就应该被当作验收失败，而不是被当作「为了灵活性可以接受的代价」含糊放过。

## 为什么按属性分列，不按内容分结构

「每个内容一个结构体」（例如 `struct TerrainDef { move_cost: u32, blocks_sight: bool, blocks_move: bool, ... }`，存一个 `Vec<TerrainDef>`）是更符合直觉的写法——大多数数据建模教程都这么教。但批量遍历只关心其中一个属性时（比如「把全部地形的 `move_cost` 求一遍某种聚合」），行式排布会把同一条记录里用不到的其它字段一起拉进缓存行，这正是 [0004](0004-two-layer-entity-storage.md) 在薄层人口存储上实测判断过的问题（约十倍内存带宽浪费）。列式排布让每次查询只触碰真正需要的那一条连续数组。

## 被否决的选项

**每个内容一个结构体（行式存储）**——否决理由见上节，与 [0004](0004-two-layer-entity-storage.md) 否决单层 `Vec<Agent>` 行式存储的理由完全同构：内容注册表和薄层人口都是「数量可观、批量按属性查询」的访问模式，适用同一个判断。

**第二档公式留成 AST，运行期递归求值**——否决：虽然不需要进 Steel VM，但递归求值本身仍然是带分支预测失败与间接跳转的树遍历，比平铺指令数组的线性扫描慢得多；而编译成平铺指令数组的转换本身只需要在注册期做一次，不增加 mod 作者书写声明的负担。

**放弃注册期完整校验，靠运行期报错兜底**——未被认真考虑：与规格已有的 §14.3「任何输入都不得 panic，只允许返回 Err」的精神相悖（虽然这里说的是内容声明而非存档输入，但道理相通——错误应该在能发现的最早时机被发现）；且运行期报错意味着填错的数只有在真正触发对应场景时才会暴露，调试成本远高于注册期直接报到加载管理界面。

## 后果

- **数据驱动的真实代价是调试变难**——行为藏在表里，填错一个数就是行为不对，且没有栈回溯指向它。这是本决定主动接受的代价，靠「注册期完整校验」缓解（把尽可能多的错误挪到加载时刻暴露，而不是消除调试难度本身）。
- **`tools/ll-datacheck` 从「加分项」变成「地基的一部分」**——数据驱动的声明式内容越多，这个工具没做到位的代价越大。P4 若最终没能交付这个工具，本条 ADR 描述的物化方案在生产环境的可用性会打折扣（错误会漂移到运行期才暴露，退化为「放弃注册期完整校验」那个被否决的选项）。
- **截至本 ADR 写下时，物化方案尚未被任何真实 Task 5/7/8 实现验证过**——`ll-mod` crate 尚未创建，`TerrainKind` 仍是硬编码 `match`。Task 8 的「迁入后不得变慢」是本条 ADR 能否成立的第一个真实检验点，需要用真实的基准测试数据核实，而不是靠直觉判断「数组访问理应比 match 快」。
- **与 [0016](0016-mod-performance-tiers-by-declaration.md) 是同一套设计的两个互补部分**——0016 定义了「按什么标准分档」，本 ADR 定义了「档位物化成什么形状、怎么保证声明没写错」。两者共同构成 P4 mod 性能架构的完整回答，任何后续想调整其中一条时，都应该同时检查另一条是否还自洽。
