# ADR 0001 — Steel 沙箱能力实测

- 日期：2026-08-16
- 状态：已采纳
- 版本：`steel-core` 0.8.2，许可 MIT OR Apache-2.0

## 背景

选定 Steel 作为脚本语言后，出现一个足以推翻架构的未知数：

**mod 作者写的脚本能否搞死游戏进程？**

若 Steel 无法在宿主侧掐断失控脚本，架构必须退化为「每次脚本调用都跑在独立线程 + 超时丢弃」，代价是每次调用都要付线程通信开销——而技能结算与行为树 tick 是每帧高频调用的，这个开销无法接受。

因此在规格定稿前做了一次实测探针。

## 实测方法

临时工程接入 `steel-core`，跑两轮探针，覆盖：死循环中断、运行时错误、深递归、引擎复用、看门狗开销、参数个数语义、无限内存分配。

## 结论

### 可依赖的能力

| 项目 | 结论 |
|---|---|
| 死循环中断 | 305ms 掐断，返回 `Err`，**不 panic** |
| 中断粒度 | 精确到单条字节码 |
| 中断后复用 | 同一 `Engine` 可继续使用，无需重建 |
| 看门狗开销 | 2000 轮实测 **0.96x，零开销** |
| Rust 注册函数的 arity 检查 | 缺参 / 多参均报 `ArityMismatch` |

`InterruptHandler` 位于 `steel::steel_vm::interrupt`，**无 feature 门控**，默认构建即可用。

机制：看门狗线程置原子标志，VM 在指令分发循环每一轮开头调用 `safepoint_or_interrupt()` 检查；命中则走 `stop!(Generic => ...)` 返回 `Err`。快路径仅一次 relaxed 原子读，故开销可忽略。

### 缺口

| 项目 | 结论 |
|---|---|
| 内存守卫 | **原生缺失** |
| 深递归 | 调用栈在**堆**上，不击穿原生栈，但深度只受内存限制 |

实测：非尾递归 100 万层 59ms、1000 万层 644ms，**均正常返回**。无限 `cons` 靠 500ms 超时救下——**这依赖分配速度，不是硬保证**。分配足够快的脚本可能在超时触发前耗尽内存。

**对策**（P4 交付）：自研 `#[global_allocator]` 包装器，以原子计数器统计脚本执行期间的分配量，超阈值时调用同一个 `ThreadStateController::interrupt()`。复用现成中断通道，开销为每次 alloc/dealloc 一次原子加减。

### 参数个数的真实语义

第一轮曾误判此项为「失败」，第二轮定性后纠正：

| 场景 | 行为 |
|---|---|
| Rust 侧注册函数（缺参 / 多参） | `ArityMismatch` 报错 |
| `lambda` 缺参 | `ArityMismatch` 报错 |
| **具名函数缺参** | 缺失参数成为未绑定标识符，**仅在实际引用时**报 `FreeIdentifier`；不引用则静默通过 |
| **具名函数多参** | **静默忽略**多余参数 |

**影响评估：可接受。** 所有游戏 API 均为 Rust 侧注册函数，具备严格 arity 检查，因此 **mod 与引擎的接口边界是安全的**。宽松仅存在于 mod 内部自有函数之间，属 mod 作者自身代码质量问题，由 `tools/ll-datacheck` 静态检查兜底。

## 后果

1. **架构不需要退化**：脚本可直接在主线程调用，不必强制隔离到独立线程。
2. **P4 必须交付内存守卫分配器**，这是唯一的原生缺口。
3. `Engine::run` 要求 `'static` 输入——脚本从文件读入天然满足，无影响。
4. 「一键重载 mod」成本低，因为中断后引擎仍可复用。

## 踩坑记录

- `Engine::run` 接受的是 `'static` 生命周期的源码，传 `&str` 局部变量会编译失败（`E0521` / `E0597`）。传 `String` 即可。
- 测试「参数个数」时若函数体未引用缺失的参数，不会报错。设计此类测试必须让函数体实际使用每一个参数，否则会得到假阴性结论。
