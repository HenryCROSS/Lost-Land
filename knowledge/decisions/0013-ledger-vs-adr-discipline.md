# 0013 — 阶段账本记过程，ADR 记决策

**日期**：2026-08-18
**状态**：已生效的项目纪律
**关键提交**：无单一提交——本 ADR 本身是这条纪律第一次被真正执行的证据（连同 0014–0017）
**影响范围**：`.superpowers/sdd/*/progress.md`（全部阶段账本）、`knowledge/decisions/`（ADR 目录）、任何后续阶段的控制者/子代理

## 背景

本项目从 P0 到 P4，所有阶段执行期的裁定（编号形如 P1-2、P2-6、P3-5、P4-4）都写在 `.superpowers/sdd/<日期-阶段名>/progress.md` 这份账本里。账本记录的是控制者在执行简报、批次评审、修复轮次期间做出的实时判断——包括冲突预扫结论、任务拆分方式、评审发现、以及真正的架构裁定，全都混在一起，按时间顺序流水记账。

问题在于 `.superpowers/sdd/.gitignore` 把整个目录标记为忽略（`git check-ignore` 已确认命中）。这意味着**这份账本从诞生起就没有进过版本库**。新克隆一份仓库，四份账本连同其中记录的全部裁定——尤其是「当初否决了什么、为什么」——一并消失。commit 信息与设计文档里能找到部分结论的痕迹，但被否决的选项与权衡过程本身，只存在于这份从未被跟踪的文件里。

**这个缺口是怎么被发现的**：P4 期间，一个子代理需要引用裁定「P4-4」时，在版本库能看到的范围内找不到任何对应记录——它没有编造一个听起来合理的解释去填补空白，而是如实报告了这处引用缺失。这次如实报告，而非静默补全或凭空编造，是本次「账本抢救」任务存在的直接原因。

## 决定

**账本继续保持被忽略，不解除 `.gitignore`；但建立一条纪律：任何「将来有人会想推翻」的裁定，必须在做出的当下就提升为 ADR，不能只留在账本里等事后抢救。**

判断「该提升」的标准（本次抢救任务据此筛选，后续阶段裁定时应在当场就用这套标准自问）：

**应当提升**：
- 影响多个 crate 或跨阶段的架构选择
- 有被否决的替代方案，且否决理由半年后依然成立（不是「当时没空做」这种会过期的理由）
- 定下一条将来有人会想推翻的规矩——推翻它的人需要知道当初排除了什么
- 由实测数据支撑的判断（跨平台哈希比对、随机地图交叉验证、延迟基准之类）

**不应当提升**：
- 一次性的任务编排决定（批次怎么划分、两个任务拆不拆开）
- 纯粹的缺陷修复记录，git 历史本身就是完整记录
- 已被后续裁定推翻或取代的判断（除非推翻本身有教育意义——那就写进取代它的那份 ADR 的背景里，而不是单独立一份「已作废」的 ADR）
- 已被现有 ADR 覆盖的内容

## 为什么不索性把账本纳入版本控制

这是本决定唯一认真权衡过的替代方案，评估后否决：

**账本本身的密度对读者不友好。** 翻开任意一份账本（例如 P1 的 215 行），除了 7 条裁定，还混着「执行前冲突预扫」表格、「批次划分」列表、五轮修复的逐条勾稽、「minor: deferred」这类当场记下、下阶段自然过期的技术债提醒、以及控制者自我修正的过程记录（比如 P2 账本里「控制者撤回自己的意见」那一段，本身有价值，但价值在于展示决策过程，不在于成为可检索的架构参考）。这些内容对**执行期的控制者自己**是必需的工作记事本，但对**事后来查「这个架构决定是怎么定的」的读者**是噪音——把账本整体入库，会让四份账本里真正值得记住的十几条裁定，淹没在几百行任务编排与验收勾稽里。

ADR 与账本因此不是同一份文档的两种存储方式，是两种不同的产物：**账本记过程（谁在什么时候做了什么、发现了什么问题、怎么修的），ADR 记决策（选了什么、为什么、放弃了什么、代价是什么）**。账本的读者是当时的执行者与评审者，天然应该是易失的；ADR 的读者是未来任何想理解「为什么是这样」的人，天然应该被版本控制永久保留。

其他被否决的选项：

- **每条裁定自动生成一份 ADR，不做人工筛选**——否决：账本一个阶段动辄十来条裁定，多数是任务编排细节，机械转换会让 ADR 数量迅速膨胀，稀释掉真正重要的十几条，索引失去导航价值。ADR 的价值一部分来自「进了这个目录就值得读」这条隐含承诺，自动化会破坏这条承诺。
- **只在阶段收尾做一次性审计，比照本项目已有的「每阶段收尾反向核对规格」纪律（见 P2 账本、[0005](0005-torus-topology-and-integer-noise.md) 后果一节）**——否决：反向核对规格能抓「文档与代码不一致」，因为规格文档本身受版本控制、可比对。但账本从设计上就不受版本控制，审计比对不到一份不存在于版本库里的东西——这类审计能抓「写错的文档」，抓不到「压根没写进任何持久位置的决策理由」。

## 后果

- **本次任务提升了四条裁定为正式 ADR**（0014–0017）：P3-5/W-03（季节纯函数派生）、P4-2（内容 ID 注册校验是解析不是不变式）、P4-4（mod 性能分档按声明方式）、P4-5（分档物化为列式数据）。其余账本条目经过逐条核对，或属于任务编排噪音，或已被现有 ADR 0001–0012 覆盖，未重复立卷。
- **P0 阶段没有账本目录**——`.superpowers/sdd/` 下只有 P1 至 P4 四个日期目录，没有 P0。ADR 0001–0003 覆盖的正是 P0 阶段的裁定（Steel 沙箱验证、整数世界状态、winit 依赖策略），它们从一开始就是直接写成 ADR，不经过账本这一层。这是否意味着账本机制在 P0 结束后才建立，或 P0 账本存在过但从未保留，原始记录未说明。
- **以后任何人（包括子代理）在版本库范围内找不到某个裁定编号（如「P4-4」）对应的 ADR 时，正确反应是如实报告缺失，而不是猜测编号打错、编造合理内容，或悄悄跳过引用。** 这正是本 ADR 存在的起因，值得作为持续适用的行为准则明确写下来。
- **这条纪律本身依赖执行期的自觉**——账本继续不受版本控制，意味着「这条裁定是否需要提升」的判断只能在裁定做出的当下，由当时的控制者对照上面这套标准自问；账本本身不会主动提醒任何人。若某个阶段的控制者疏忽，下一次抢救仍然要等到有人（人或子代理）撞上一处缺失的引用才会被发现——这是本决定接受的代价，因为唯一能杜绝这个代价的办法（账本整体入库）代价更大，见上节。
