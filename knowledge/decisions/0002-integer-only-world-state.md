# 0002 — 世界状态一律用整数，禁止浮点

**日期**：2026-08-16
**状态**：已生效，P0 起强制
**影响范围**：全部 crate

## 背景

游戏支持自由读档（模式 3）与确定性重放。两者都要求：同一个种子加同一串
操作，在任何机器上都必须产出**逐位相同**的世界状态。

浮点运算不满足这个要求。同一段 `f64` 表达式在不同平台、不同优化等级、
不同指令集扩展（x87 与 SSE 的中间精度差异、FMA 融合与否）下可能产出不同
的最低位。差一位，世界就分叉。

## 决定

**世界状态中不出现任何浮点数。**

| 世界量 | 表示 |
|---|---|
| 位置 | 瓦片坐标 `i32`（`TorusPos`） |
| 时间 | 刻度 `i64`（`Tick`，一刻度 = 一游戏秒） |
| 货币、价格、比例、速率 | 千分之一定标整数 `Milli(i64)` |
| 属性 | `i32` |
| 概率 | 分数 `(numerator, denominator)`，不是小数 |

**浮点只允许出现在渲染层与音频层，且结果绝不得回流入世界状态。**

配套措施：
- 距离只提供**平方值**（`squared_euclidean`），不开方——开方必然引入浮点
- 比例运算用分数而非小数（`Milli::mul_ratio(num, den)`），中间乘积用 `i128` 承接
- `tests/determinism.rs` 用 FNV-1a 摘要冻结黄金基准，在 Windows 与 Linux 双平台比对

## 被否决的选项

**定点数库（如 `fixed` crate）**：能表达小数且跨平台确定，但引入一个运行时依赖，
而 `ll-core` 必须保持零依赖（它被所有 crate 依赖，任何依赖都会传染全项目）。
且本项目绝大多数世界量本来就是整数，只有价格与比例需要小数精度，
一个千分之一定标的 `i64` 就够，不值得为此背一个库。

## 后果

**好的**：跨平台确定性已实测成立——三个黄金基准在 Windows 与 Arch Linux x86_64
上逐位相同。并行结算天然安全（纯整数运算无平台差异）。

**要付的代价**：需要小数时得多想一步。`Milli::from_whole` 无溢出保护
（debug panic / release 回绕），不可信来源须用 `checked_from_whole`。

**最危险的破防点**：P1 做子格移动插值时，渲染层的浮点结果**绝不能回流世界状态**。
这种污染是渐进的、无声的——等黄金基准跨平台对不上时，已经无从追溯是哪次改动。
P1 计划必须把这条写成显式检查项。
