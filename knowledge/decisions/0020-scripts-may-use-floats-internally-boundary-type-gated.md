# 0020 — 脚本内部允许浮点，安全边界收拢到 `register_fn` 类型签名，部分取代 0002

- **冻结时间**：2026-08-18
- **状态**：已定稿的设计决定，等待实现（`ll-script` 尚未落地任何强制这条边界的代码，本 ADR 记录决定本身）
- **影响范围**：`crates/ll-script`（`register_fn` 签名的类型选择约定）、[知识/design/script-state-storage.md](../design/script-state-storage.md)（`ScriptValue` 值类型系统的论证基础）、[0002](0002-integer-only-world-state.md)（部分取代，见下）、[0019](0019-denied-capability-needs-substitute-or-justification.md)（「浮点」一行的对照表条目）

## 背景

[0002](0002-integer-only-world-state.md) 写于 P0，`ll-script` 尚不存在。它的原文只裁定「世界状态中不出现任何浮点数」，并且已经明确留了一个口子——「浮点只允许出现在渲染层与音频层，且结果绝不得回流入世界状态」。

P4 引入脚本层之后，项目在事实上把这条禁令**默认推广**成了「脚本层任何计算都不得引入浮点」——这个推广没有被单独裁定过，是顺着 0002 的字面精神做的最保守解读。已核实的一个具体例子：[脚本层数据句柄与批量查询](../design/script-entity-handles-and-batch-queries.md) 5.2 节 `filter-within-distance` 的设计明确写着「距离用……换算成平方欧氏距离做比较（避免 `sqrt`——`ll_world::noise` 模块文档已经论证过 IEEE 754 超越函数跨平台不确定性的问题，同样的顾虑适用于这里）」——这是把 0002 的精神原样套用到脚本设计上的真实先例。

**未核实项**：项目所有者提到这个论证此前"错过一次"，指向 0002 的修订史与相关提交。已核实：`git log --oneline --all -- knowledge/decisions/0002-integer-only-world-state.md` 只有一条提交（`435b4ec`，ADR 首次写入），没有找到任何后续修订记录或专门讨论这个问题的提交。本 ADR 如实标注**没有核实到项目所有者所指的具体历史事件**，不代为编造一个具体的"上次错误"叙事——本 ADR 的论证完全建立在下面独立的技术分析上，不依赖那段未核实的历史。

## 决定

**脚本内部允许使用浮点数。安全边界不再是"语言层面禁止浮点"，而是"`register_fn` 的类型签名只接受整数与 `Milli`"。**

```
脚本内部（Steel VM 求值过程）    允许浮点——语言本身的能力，此前也从未被
                                白名单拦截过（[0019] 表格已核实：浮点运算
                                不触达六类被禁能力中的任何一类）

register_fn 边界（跨过 Rust/     只接受整数与 Milli——这是可强制的：每一个
脚本边界的每一个函数）           跨界函数的参数/返回值类型都由 Rust 侧的
                                register_fn 调用写死,脚本没有办法让一个
                                声明为 i64 的参数/返回值携带浮点数据

WorldState 的 Rust 类型          继续不含 f32/f64——这是前一条能够成立的
                                基础,也是 0002 唯一没有被本 ADR 触碰的部分
```

## 为什么类型把关能彻底解决三件事

因为每一个跨边界函数的签名都由本项目自己的代码写死（`register_fn::<Args, Ret, F>` 是 Steel `RegisterFn` trait 的静态调用，参数/返回值类型在 Rust 编译期就固定），这不是靠脚本作者自觉遵守的约定，是编译期就无法违反的保证：

- **存档**：`WorldState` 里永远不会出现 `NaN`/`-0.0`/精度丢失——因为能写进 `WorldState` 的唯一路径是经过某个 `register_fn` 注册的写入函数，而这些函数的参数类型本身就不是浮点。
- **哈希与相等**：`WorldState::hash()`（`state.rs` 已有的确定性摘要函数）不会被浮点相等性坑到——`NaN != NaN`、`0.0 == -0.0` 这类浮点比较语义上的陷阱，从一开始就没有机会混进摘要计算,因为参与摘要的字段类型本身没有浮点。
- **累积漂移**：任何"存进去"的动作，落地的永远是整数——脚本内部可以用浮点反复迭代计算一个中间结果，但只要最终交给某个 `register_fn` 写入函数的那一刻转换成整数,此前浮点计算过程中累积的任何跨平台漂移都在这次转换里被"截断"成同一个整数（除非恰好卡在量化边界，见下节残余风险）。

## 残余风险：量化边界，如实写明，不夸大也不隐瞒

类型把关保证的是「只有整数能进世界状态」，**不保证「每个平台把同一段脚本浮点计算量化成同一个整数」**。风险的具体形状：

```scheme
(quantize (atan2 dy dx))   ; atan2 是超越函数,不同平台 libm 实现可能在
                            ; 最低有效位上不同;若量化步长恰好卡在这条
                            ; 计算结果的边界上,两个平台可能把同一次
                            ; "几何上应该相等"的角度量化成相邻的两个
                            ; 不同整数
```

**这个风险确实存在，但范围很窄，具体到只有一种组合会触发**：

1. **加减乘除与 `sqrt` 不在风险范围内**——IEEE 754 标准要求这五种运算（`+`/`-`/`*`/`/`/`sqrt`）**必须正确舍入**（correctly rounded），即结果必须是无限精度真值按当前舍入模式舍入后的唯一正确浮点值。这是标准强制的，不是"通常如此"——任何声称遵循 IEEE 754 的浮点实现，这五种运算在相同输入、相同舍入模式下必须产出逐位相同的结果，与平台/编译器无关（前提是没有被编译器用 FMA 等重排序优化悄悄改变运算顺序——这是一个真实但独立的风险点，`ll_world::noise` 模块文档大概率已经处理过，本 ADR 不重新展开）。
2. **只有超越函数（`sin`/`cos`/`atan2`/`exp`/`log` 等）没有这条保证**——IEEE 754 不要求超越函数正确舍入（长期以来被公认为"表格制造者困境"，各平台 libm 实现允许在最后一两位上不同）,这正是 `ll_world::noise` 模块文档此前已经论证过的跨平台不确定性来源。
3. **只有「超越函数 + 粗量化」这个组合会真正触发风险**——若脚本只用超越函数算出一个浮点结果直接使用（不量化成整数、不流入世界状态)，压根不触及本 ADR 的边界；若脚本只用加减乘除/`sqrt`做量化，量化结果保证跨平台一致。只有"用超越函数算出浮点结果，再把这个结果量化成整数、这个整数流入世界状态"这一条链路上,才存在"两个平台在量化边界附近取整成不同整数"的可能。
4. **触发概率量级很小**——单次计算恰好落在量化边界（浮点结果与量化步长边界的距离小于两平台间超越函数实现的最大误差)的概率，按典型量化步长与 libm 实现误差量级（通常在个位 ULP,即最后一两个二进制位)估算约在 `1e-16` 量级——这是一个数量级估算，**不是本 ADR 实测验证过的精确数字**，如实标注为未核实的推论，但方向上是可靠的：ULP 级别误差相对于典型量化步长（如"把角度量化成 360 个整数格"）的比例本来就极小。

## 与「确定性重放」的关系：诚实降级，不含糊过去

**确定性重放的保证从「逐位一致」降为「绝大多数情况下一致」。**

这是这次调整的**真实代价**，必须明确写出，不能因为残余风险小就含糊过去：

- 此前（纯整数世界状态 + 脚本层同样禁浮点)：只要两次运行输入相同，`WorldState::hash()` 理论上应当逐位相同,这是黄金基准回归测试（`tests/determinism.rs`）赖以成立的前提。
- 现在（脚本内部允许浮点，边界量化)：绝大多数情况下依然逐位相同，但**存在一个概率量级约 `1e-16` 的、由"超越函数+粗量化"触发的例外路径**，理论上可能让两次"逻辑上应该等价"的运行在某个量化整数上分叉。

**这意味着黄金基准回归测试不能再被当作唯一判据**——它仍然是有效的调试与排查工具（大多数情况下依然能揪出真实的逻辑回归），但"黄金基准比对通过"不再等价于"逐位确定性在数学上被证明成立"，只能说"在实践中绝大多数场景下成立"。**这条降级本身需要被写进 `tests/determinism.rs` 或相关测试文档，明确告诉未来遇到黄金基准跨平台对不上的人：先检查是不是撞上了这条已知的窄风险,而不是假设代码本身一定有 bug**（这条落地属于实现批次，本 ADR 只记录决定与理由，不代为完成）。

## 判据只有一句：结果的去向，不是模块或层

上一版裁定按「渲染层/音频层/脚本层」这类**模块**划线，边界画得太粗——真正决定安不安全的不是浮点运算发生在哪个模块，是**这次计算的结果最终会不会变成世界状态的一部分**。同一个模块内部完全可能同时存在两种计算：脚本里既可以算"这一帧要不要播放某个视觉特效的透明度渐变"（结果只影响画面），也可以算"这次攻击造成多少伤害"（结果要写回 `Agent.health`）——前者与后者都"发生在脚本层"，但安全性天差地别。因此本 ADR 改用单一判据重新划区：

> **这个浮点计算的结果，最终有没有变成世界状态的一部分（写进 `WorldState`，或者改变任何将来会被写进 `WorldState` 的东西）？**

### 甲区：结果只变成像素与声音，完全安全，用浮点更方便

| 场景 | 备注 |
|---|---|
| 渲染、相机、动画插值、粒子 | 传统意义上的"表现层"，已核实 `ll_render`/`ll_world::light` 等模块文档一贯把这类计算划在世界状态之外 |
| **UI 布局与文本排版** | 已核实：`crates/ll-text/src/lib.rs` 模块文档明确写着「排版结果（断行位置、字形前进宽度）是浮点且依赖字体/库版本，这些值只用于当前帧的屏幕绘制，绝不可回流入 `ll-world`/`ll-sim` 的世界状态」——`cosmic-text` 本身的排版算法就是浮点几何，这是本项目现有代码里甲区判据的一个真实先例，不是本 ADR 新发明的分类 |
| 音频音量、声像 | 同一类"只影响输出设备，不影响游戏逻辑"的计算 |
| 血条宽度、小地图缩放等纯展示计算 | 从整数血量/坐标派生出的**屏幕像素**值，派生方向是"世界状态 → 像素"，不是反过来，因此结果不会回流 |
| 调试统计与性能数字 | [脚本层数据句柄与批量查询](../design/script-entity-handles-and-batch-queries.md) 5.4 节设计的跨界调用计数器一类——展示给开发者看，不参与任何游戏逻辑判断 |

**在甲区应当推荐使用浮点**，不要因为"项目禁浮点"这个旧印象在这里也套用整数/定点——`cosmic-text` 的排版度量本来就是浮点，在这类场景强行改用定点整数只会让代码更绕、更容易出错，而且完全没有对应的确定性收益（甲区的结果本来就不需要跨平台逐位一致）。

### 乙区：结果会进世界状态，必须在边界量化

| 场景 | 备注 |
|---|---|
| 伤害计算、属性派生 | [属性系统](../design/attribute-system.md) `derive_stats` 这类结算最终要写回 `Agent` 字段 |
| **AI 打分与决策** | 打分**过程**可以用浮点（多因素加权评分,浮点算起来更直观），但最终"选中哪个动作"这一步产出的是一个离散标识（`ScriptEntityHandle`/方向符号/动作符号），量化点在"选出获胜者"这一步,不是把浮点分数本身存下来——见下文「量化辅助」一节 |
| 经济定价 | [Agent 目标与经济](../design/agent-goals-and-economy.md) 的定价公式，结果要影响钱包（世界状态） |
| 生成算法 | 世界生成产出的地形/势力/聚落等最终都要落进世界状态或存档 |

**量化之后即安全**——一旦浮点结果被转换成整数/`Milli`/离散符号，本 ADR「残余风险」一节已经论证过：残余风险只剩"超越函数 + 粗量化"这一个组合，且概率量级很窄。

### 三组工具，不是两组

**这不改变「`register_fn` 边界只收整数与 `Milli`」——那条边界正是甲乙两区的物理分界线：类型把关不是额外加的限制，它就是这张分区表的机器执行版本**（脚本无论在甲区还是乙区怎么算，唯独"跨过 `register_fn` 边界进入乙区所在的世界状态"这一步，类型系统会拦住浮点）。工具库应当按用途分成三组，而不是简单的"整数工具 vs 浮点工具"两组——中间还需要一组专门负责"从浮点安全落到整数"的转换原语，否则乙区的一致性没有保障：

1. **浮点工具**（供甲区使用）——不设限制，怎么方便怎么来，`cosmic-text`/`ll_render` 已经在用的浮点几何/插值函数都属于这一组，本 ADR 不需要为这一组新增任何东西。
2. **整数/定点工具**（乙区的默认好路）——整数平方根、定点三角函数表（以 `Milli` 表示）、范围/视锥判定、整数插值。这是 [0019](0019-denied-capability-needs-substitute-or-justification.md) 对照表"整数几何工具"一行要补的缺口，见下节。
3. **量化辅助**（甲乙两区之间的边界工具，**最容易被忽略却最重要**）——若不提供标准的量化函数，每个 mod 作者会各自发明一套"浮点转整数"的取整规则（有的四舍五入、有的向零截断、有的向下取整），乙区看似都在用"整数"，实际取整规则五花八门，`WorldState` 的一致性名存实亡。至少应该提供：

   - `(quantize-round x)` / `(quantize-floor x)` / `(quantize-ceil x)`——把脚本内部算出的浮点值按固定规则转换成 Steel 整数类型，这是最基础的边界原语，其余量化函数都可以在其上组合出来。**必须是这三个规则里选定的一种，不能让脚本自己调用 Steel 内置的四舍五入函数然后假装结果已经是整数**——Steel 内置的浮点取整函数返回的可能仍然是浮点类型的"整数值"（例如 `3.0` 而不是整数 `3`），不经过这几个专门的量化原语，值不会真正跨过 3.1 节 `ScriptValue` 要求的类型边界。
   - `(quantize-to-milli x)`——浮点值按 `Milli` 的千分之一刻度量化（内部即 `quantize-round(x * 1000)`），供经济定价、属性加成一类需要小数精度的乙区场景使用，与既有 `ll_core::scaled::Milli` 的既定刻度（`SCALE = 1_000`）保持同一套换算，不需要脚本作者自己记住"1000"这个魔法数字（沿用 [脚本层数据句柄与批量查询](../design/script-entity-handles-and-batch-queries.md) 5.2 节 `average` 已经确立的 `(milli-scale)` 换算模式）。
   - `(quantize-damage x)`——伤害类结果的专用量化：取整规则固定为"向下取整,下界钳制到 0"（`max(0, floor(x))`）——避免"浮点误差导致伤害算出一个极小负数"这类边界情况被直接写进 `Agent.health`,伤害计算的量化规则单独拎出来而不是要求作者自己拼 `quantize-floor` + `max`，是因为这个组合足够常见、且"钳制到 0"这条规则本身不是显然的（不熟悉的作者可能直接用 `quantize-round` 导致极小负伤害被四舍五入成 `-0` 或 `0`，看似无害但语义不清）。
   - **AI 打分场景不需要单独的"分数量化"原语**——如上文乙区表格所述，打分的量化点是"选出获胜动作"这一步，产出的天然就是一个离散标识（`ScriptEntityHandle`/符号），不是一个需要转换的连续值。若脚本要实现"多因素加权打分，取分数最高的动作"，量化辅助不需要为"分数"本身提供转换函数，脚本内部完成 `argmax`（用浮点比较找出最大值对应的动作)之后,真正跨边界的值已经是那个动作的整数/符号标识,天然落在类型把关范围内，不需要额外量化步骤。

具体几何工具（第 2 组）的完整接口形状不在本 ADR 范围内,是一项独立的设计任务，见下节。第 3 组量化辅助的完整清单同样留给该设计任务，本节只给出几个最有代表性、最容易被遗漏的样例，不是穷尽列表。

### 给 mod 作者的判断法

面向作者的文档（未来的 mod API 参考）应当收录这段判断法，取代"哪些模块能用浮点"这种需要不断维护清单的表述方式：

> **问自己一句：这个数算完之后，会不会被存进存档、或者改变任何会被存进存档的东西？**
> 会 → 你在乙区，用第 2 组的整数/定点工具，或者在最后一步用第 3 组的量化原语把结果落成整数。
> 不会 → 你在甲区，随便用浮点，不需要多想。

这条判断法比列举"哪些模块算甲区/哪些算乙区"更耐用——未来任何新系统（P5 的技能树、任务图，P6 的世界历史生成）出现时，作者不需要等文档更新一份新清单，靠这一句自己就能判断,这也是它比"按模块分类"更贴合[0019](0019-denied-capability-needs-substitute-or-justification.md)"通则应当可执行、可套用到未来未知场景"这条要求的地方。

## 整数几何工具的定位：不再是「浮点被禁后的替代品」，而是「默认更优的路径」

这条调整改变了 [0019](0019-denied-capability-needs-substitute-or-justification.md) 对照表里"整数几何工具"一行的框架，必须同步理解：

```
旧框架（浮点被禁）：  没有整数工具 → mod 作者做不成距离/角度计算 → API 缺陷
新框架（浮点开放）：  没有整数工具 → 人人都得用 atan2/sqrt 等浮点函数 →
                     残余风险（本 ADR 上一节量化的那条窄风险）人人在踩
                     提供整数工具 → 只有极少数有特殊需求的场景才会绕出去
                     用浮点 → 风险收敛到可控范围，且用的人自己清楚在
                     承担什么
```

**这比"禁止"更符合本项目"给正路，而不是堵歪路"的一贯思路**（[0019](0019-denied-capability-needs-substitute-or-justification.md) 通则的核心)：与其宣布"浮点不安全,禁止使用"（这句话现在已经不准确——本 ADR 刚论证过浮点在类型把关下是安全的),不如提供一条默认好走、天然不触碰残余风险的路径，让"多数人默认安全，少数人明确知情地承担窄风险"，而不是"多数人被禁止，少数需求做不成事"。

具体的整数几何工具设计（距离/角度/三角函数表/范围判定/插值的完整接口形状）不在本 ADR 范围内，是一项独立的设计任务，留给 [0019](0019-denied-capability-needs-substitute-or-justification.md) 对照表条目与后续设计文档展开。

## 取代 0002 的哪一部分，哪一部分仍然有效

按 [0013](0013-ledger-vs-adr-discipline.md) 的纪律——已发布的 ADR 应当被取代而非篡改——本 ADR **不修改** `0002-integer-only-world-state.md` 原文，只记录本次范围收窄：

**仍然完全有效、未被本 ADR 触碰的部分**：
- 「世界状态中不出现任何浮点数」——`WorldState` 的 Rust 类型继续不含 `f32`/`f64`，本 ADR 全部论证的前提就是这一条继续成立。
- 0002 表格里「位置用 `i32`」「时间用 `i64`」「货币/价格/比例用 `Milli`」「属性用 `i32`」「概率用分数」——这些具体的世界量表示方式完全不变。
- 0002「被否决的选项」（定点数库依赖）与「后果」（跨平台确定性已实测成立、`Milli::from_whole` 无溢出保护）两节，与脚本层无关，原样有效。

**被本 ADR 收窄的部分**：
- 0002 原文「浮点只允许出现在渲染层与音频层」这句话里隐含的"除了渲染/音频，别处都不能有浮点"——这条边界现在扩大成三层：渲染层、音频层、**脚本内部计算**。三者共享同一个约束（"结果绝不得回流入世界状态"），脚本层只是新增的第三个允许浮点存在、但结果必须被类型边界拦住的层。
- 项目在 P4 期间对 0002 的**推广解读**（脚本层任何计算都不得引入浮点，`filter-within-distance` 等设计据此排除浮点）——这条推广本身从未被正式裁定过，本 ADR 现在正式裁定它不完全成立，收窄为「脚本内部允许浮点，但跨越 `register_fn` 边界、真正写进 `WorldState` 的值不许是浮点」。**已有的、按旧推广解读做出的具体设计（例如 `filter-within-distance` 用平方距离而非 `sqrt`）不需要因此撤销或改写**——那仍然是"默认更优路径"的一个正确应用，本 ADR 只是改变了"为什么这么设计"的理由（从"浮点被禁,别无选择"改成"浮点可用,但这条路径更省心，默认这么做"），不改变设计本身的结论。

## 被否决的选项

**继续全面禁止脚本内部使用浮点**——否决理由见上文「整数几何工具的定位」一节：这条禁令的实际后果是逼着 mod 作者要么做不成需要浮点数学的功能（弹道、AOE 范围、复杂几何判定），要么被迫用整数近似算法自己手搓（结果往往比直接用浮点+边界量化更难写对、更难维护），而现在已经证明"边界类型把关"能把风险收窄到一个已知、量化过的窄范围内，继续全面禁止是用更大的开发成本换取一个已经不再必要的安全边际。

**放开浮点但不设类型边界，靠脚本作者自觉不把浮点存进世界状态**——否决理由：这退化成"约定而非机制"，与 [0019](0019-denied-capability-needs-substitute-or-justification.md) 通则的核心精神（替代品必须由引擎层提供、确定性由 Rust 侧保证，不能指望脚本自律）直接冲突，也是本项目从黑名单换成白名单（`crates/ll-script/src/whitelist.rs` 模块文档「为什么从黑名单换成白名单」一节）时已经吸取过的同一条教训——靠自觉的边界迟早会被绕过或遗忘。

## 后果

- **`register_fn` 签名的类型选择因此获得一条正式纪律**：任何跨脚本/Rust 边界的函数，参数与返回值类型只能是整数（`i64`/`u64`/`bool`）、`Milli`（或其裸 `i64` 表示）、字符串，以及本文档「值类型」范围内的其余整数复合类型（列表/映射），**绝不能是 `f32`/`f64`**——这条纪律此前散落在各个具体设计文档的个别论证里（如 `filter-within-distance` 的"避免 sqrt")，本 ADR 第一次把它提升为跨越全部 `register_fn` 调用的统一强制要求。
- **`tests/determinism.rs` 的黄金基准测试需要补一条说明**（实现批次工作，本 ADR 只记录要求）：当跨平台比对失败时，排查流程第一步应该检查是不是撞上了本 ADR 「残余风险」一节描述的"超越函数+粗量化"路径，而不是默认假设是逻辑回归。
- **本 ADR 生效前，脚本层实际上还没有任何真正暴露浮点的 API**（已核实：`crates/ll-script/src/api/` 现有的 `query.rs`/`rng.rs` 全部函数签名都是整数/布尔)——本 ADR 记录的是一条面向未来 API 设计的纪律，不是对现有代码的修正,当前代码没有违反本 ADR 的地方。
