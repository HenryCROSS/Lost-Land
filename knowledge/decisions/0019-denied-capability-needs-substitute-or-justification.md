# 0019 — 每禁一项脚本能力，必须提供确定性替代品，或写明这个需求不正当

- **冻结时间**：2026-08-18
- **状态**：已定稿的设计决定，通则本身立即生效；对照表里标注为「待办」的条目留给后续任务落地
- **影响范围**：`crates/ll-script`（`whitelist.rs`/`host.rs` 的拒绝清单与 mod API 表面设计）、未来全部新增能力拒绝决定、mod 作者文档

## 背景

`crates/ll-script/src/host.rs` 的 `META_DENY_LIST` 系列（49 个具名标识符）加 `FULLY_POISONED_MODULES`（4 个整体清空的模块）加 `Engine::new_sandboxed()` 本身排除的文件系统/网络，构成了脚本能力面上"明确被挡住"的部分；`whitelist.rs` 的白名单机制则默认拒绝一切没有被显式放行的标识符。这两层机制此前的裁定逻辑都是"这项能力危险，挡住"——却没有一条纪律要求"挡住之后，这项能力背后的正当需求怎么办"。

项目在事实上已经用过这条思路两次，只是没有命名：

```
禁掉 OS 随机源     → 提供 DetRng::for_entity（ll_core::rng）       确定性随机
禁掉 VM 全局可变状态 → 提供受认可的状态存储（knowledge/design/script-state-storage.md） 进存档
```

`crates/ll-script/src/host.rs` 里也已经有两条被明确标注为「因未验证而拒绝，非已证明危险」的条目（`module->exports`、`inspect`）——这两条正是本 ADR 要处理的典型情况：一项能力被拒绝，但拒绝的理由是"没空验证"而不是"证明了危险"，这类条目不应该无限期挂着不了了之。

## 决定

**每禁一项脚本能力，必须回答两个问题：**

> ① 这项能力背后是否存在正当的玩法/mod 作者需求？
> ② 若有，游戏能否提供一个**确定性的、由引擎层（Rust 侧）保证**的替代品？

**若某项能力被禁且给不出替代品，必须在文档里写明"为什么这个需求本身不正当"——不能什么都不写就让它一直挂在拒绝清单上。**

### 为什么替代品必须来自引擎层，不能是"脚本自己更小心地用"

这条要求直接呼应 [0018](0018-engine-layer-vs-gameplay-layer-scripting-boundary.md) 的引擎层/玩法层划分：确定性是这个项目能自由读档、能确定性重放的地基，而**确定性只能由 Rust 侧的实现保证，不能指望脚本作者自律**。「小心地用某个被禁能力」不是替代品，是换了个说法的"部分放行"——`crates/ll-script/src/whitelist.rs` 模块文档已经在别的场景吸取过这个教训（「为什么从黑名单换成白名单」：黑名单只能挡住写进清单里的写法，白名单才是"能力不存在"而不是"已知能力被拦下"）。替代品必须是"脚本想要那种效果，游戏在 Rust 侧模拟出一条同样能达到效果、但确定性由类型/实现强制的路径"，而不是"提醒脚本作者小心"。

### 为什么替代品应尽量落在 [0016](0016-mod-performance-tiers-by-declaration.md) 一/二档，而不是又变成第三档回调

若每个被禁能力的"替代品"都是"开一个新的脚本回调钩子"，等于把一种跨界开销换成另一种，没有真正解决问题——[0016](0016-mod-performance-tiers-by-declaration.md) 的分档思路（声明式数据优于受限公式优于任意回调）同样适用于这里：越靠近一档（零开销的声明式表达），替代品的质量越高。本 ADR 表格里的"已有"替代品（`DetRng`、`world-tick`）都是这个模式——脚本传入几个整数参数，Rust 侧用纯函数算出确定结果，不需要任何回调。

## 对照表怎么读

- **状态**列：`已有` = 替代品已经注册进脚本引擎且可用；`部分` = 骨架/原则已经存在但通用机制未完成；`待办` = 需求成立但完全没有替代品，真正的缺口；`不正当` = 判断这个需求本身不该被满足，理由写在备注里；`不适用` = 这项能力不是"被脚本禁止"，是别的性质（例如已经在放行清单里）。
- 每一行的核实方式都在备注里写明；没有直接读到代码依据的一律标"未核实"，不假装验证过。

## 一、现有拒绝清单逐项过一遍

### A. 动态代码执行 / 宏反射（`eval!`、`eval`、`eval-string`、`load`、`load-expanded`、`emit-expanded`、`expand!`、`#%expand`、`#%expand-syntax-case`、`#%match-syntax-case`、`#%macro-case-bindings`、`read!`）

| 正当需求 | 替代品 | 状态 |
|---|---|---|
| 动态生成/执行内容（程序化生成技能效果、按数据拼代码） | 声明式内容定义——[0016](0016-mod-performance-tiers-by-declaration.md)/[0017](0017-tiered-declarations-materialize-columnar.md) 一/二档，用数据表达而非生成代码；确实表达不了的逃生舱走 [脚本层数据句柄与批量查询](../design/script-entity-handles-and-batch-queries.md) 5.4 节已设计的模式（把集合物化成列表，脚本侧用白名单内的 `map`/`filter` 处理，而不是动态生成新代码） | 已有（原则与逃生舱模式均已设计） |
| 把 mod 代码组织到多个文件（`load` 字面意义上的"加载另一个脚本文件"） | mod 清单（`ModManifest.entry_points`，`crates/ll-mod/src/manifest.rs` 已核实存在）本身就是"按顺序加载多个入口文件"的机制，脚本不需要在运行期自己 `load` 别的文件 | 已有 |

### B. 独立/不受限 Engine 构造（`Engine::new`、`Engine::clone`、`Engine::add-module`、`Engine::modules->list`、`Engine::raise_error`、`run!`）

| 正当需求 | 替代品 | 状态 |
|---|---|---|
| 脚本抛出自定义业务错误（如"参数不合法"） | 顶层 `raise-error`/`error-with-span`/`call-with-exception-handler` 已经放行（`host.rs` META_DENY_LIST 文档「放行的例子」一节已核实列出）——`Engine::raise_error` 这个方法变体被拒绝，不影响这条正当需求，因为语言层面已经有另一条满足它的路径 | 已有 |
| 构造/操纵独立 VM 本身 | 无——VM 的生命周期归宿主管（[脚本状态存储](../design/script-state-storage.md) 第九节「VM 状态是一次性的」正是这条原则的具体化），脚本不需要、也不应该有能力构造另一个不受限的引擎实例 | 不正当 |

### C. 读写宿主进程环境（`env-var`、`maybe-get-env-var`、`set-env-var!`）

| 正当需求 | 替代品 | 状态 |
|---|---|---|
| 无——游戏配置不应该通过进程环境变量传给脚本 | 若 mod 确实需要可配置项，应该走 mod 清单声明的配置字段（声明式，注册期可校验），不是运行期读环境变量（环境变量本身在不同机器上取值不同，直接违反确定性要求） | 不正当 |

### D. 泄漏宿主机信息（`current-os!`、`platform-dll-extension!`、`platform-dll-prefix!`、`steel-home-location`、`path-separator`、`command-line`、`target-arch!`、`feature-dylib-build?`）

| 正当需求 | 替代品 | 状态 |
|---|---|---|
| 内容本不该随操作系统变化——若有平台差异展示需求（如"按 Ctrl+点击"在 macOS 上应显示"按 Cmd+点击"），这是**渲染/输入提示层**该处理的事，不该由玩法脚本判断 | 若未来真有这类需求，应由引擎层（`ll-ui`/`ll-render`）按运行平台选择要显示的文本，脚本不需要知道自己跑在什么系统上 | 不正当（脚本层面） |

### E. 原生代码加载（`#%build-dylib`、`#%get-dylib`）

| 正当需求 | 替代品 | 状态 |
|---|---|---|
| 无——加载原生动态库直接绕过整个沙箱能力边界 | 无需替代品 | 不正当 |

### F. 暴露运行期内部状态（`memory-address`、`dump-profiler`、`#%snapshot-stacks`、`%#interner-memory-usage`、`active-object-count`、`callstack-hydrate-names`、`make-callstack-profiler`、`current-function-span`）

| 正当需求 | 替代品 | 状态 |
|---|---|---|
| `memory-address`：无——真实指针值，两次运行不保证一致，直接破坏确定性 | 无需替代品 | 不正当 |
| **`dump-profiler`/`#%snapshot-stacks`/`active-object-count`/`callstack-hydrate-names`/`make-callstack-profiler`/`current-function-span`：mod 作者想给自己的脚本做性能分析** | **游戏提供的确定性计数器——[脚本层数据句柄与批量查询](../design/script-entity-handles-and-batch-queries.md) 5.4 节已经设计的"运行期跨界调用计数器"（`ScriptEngine` 实例上的原子调用计数，按 mod/tick 汇总，喂给加载管理界面）。这是本通则最贴切的一个例子：我们禁了脚本自己用墙钟/内存地址计时，同时正在造一个更适合这个系统的东西给它——步数/调用次数是确定的、可复现的，比宿主 profiler 暴露的墙钟时间/内存地址更适合一个要求确定性重放的游戏** | 部分（设计已存在，`5.4 节` 明确标注"具体接线方式……留给后续任务"，尚未实现） |

### G. 调试/测试基础设施（`set-test-mode!`、`get-test-mode`、`breakpoint!`）

| 正当需求 | 替代品 | 状态 |
|---|---|---|
| 无——这些是宿主开发/测试工具，脚本不该有能力开关宿主的测试模式或设置断点 | 无需替代品；mod 作者若要调试自己的脚本，应使用下文 B-7「结构化日志」这条替代品 | 不正当 |

### H. 异步/future 执行模型（`poll!`、`block-on`、`local-executor/block-on`、`futures-join-all`、`join!`）

| 正当需求 | 替代品 | 状态 |
|---|---|---|
| 长时间操作、延迟执行（"5 回合后触发某效果"） | 时间轴调度——见下文 B-4，需要设计"具名处理器 + 可序列化载荷"的调度接口，当前 `ll_sim::timeline::Timeline` 只支持"某实体在某 tick 行动"，不支持通用的"任意回调 + 数据"调度 | 部分（骨架存在，通用机制待设计，见 B-4） |

### I. 模块内省（`module->exports`、`inspect`）

这两条正是 `host.rs` 已经标注「因未验证而拒绝，非已证明危险」的条目，按本 ADR 通则必须"验证后放开 / 给替代品 / 写明不正当"三选一，不能无限期挂着：

| 条目 | 判断 |
|---|---|
| `module->exports` | 正当需求：mod 作者想知道自己能调用哪些 API。**但这个需求不该由运行时脚本自省满足**——脚本不该有办法在运行期探测自己够不着什么（`host.rs` 原文本身也是这个判断）。这个需求应该在**加载期/文档层**满足：`tools/ll-datacheck`（规格已规划，仓库尚不存在，见 [脚本状态存储](../design/script-state-storage.md) 1.2 节已核实）与静态 API 文档才是正确的满足层，不是运行期自省。**结论：不正当（就"运行时自省"这个具体形式而言），但背后的需求应由文档/静态工具满足——写明理由：不是"这个需求不该被满足"，是"不该在这一层被满足"** |
| `inspect` | 具体行为**未核实**——尝试定位 `steel-core` 源码中 `inspect` 的实现以判断它是纯值内省（打印结构内容，无害）还是暴露内部实现细节（与 `memory-address` 同类），过程中命令执行超时，未能在预算内完成核实。**按 [0019](#) 本条通则，不确定时应保守维持拒绝**，本 ADR 如实标注"仍未验证"，不代为裁定，留给后续任务专门核实 `steel-core-0.8.2` 源码中 `inspect` 的具体实现 |

### J. 文件系统、网络（`Engine::new_sandboxed()` 层面排除，不在 `META_DENY_LIST` 里逐项列举）

| 正当需求 | 替代品 | 状态 |
|---|---|---|
| 文件系统：读取自己 mod 目录下的资源（贴图、音效、数据文件） | 资产 VFS——已核实**规格 §5 crate 分层原文写着** `ll-mod` 负责「mod 发现、清单解析、依赖拓扑排序、**资产 VFS**、内容注册表」，即项目已经规划了这条替代路径，限定在本 mod 目录内、不暴露真实文件系统路径。**2026-08-20 资产 VFS 批次已落地**：`crates/ll-mod/src/asset_vfs.rs`（图片资产，路径穿越校验、`assets/overrides/` 同路径覆盖、冲突产出 `LoadStatus::Warning`）+ `crates/ll-render/src/atlas_pack.rs`（运行期图集打包）。**范围限定**：只覆盖精灵图片，不含音频（仓库无音频 crate，独立缺口）与任意数据文件（YAGNI，脚本注册已够用） | 已落地（图片资产），音频/任意数据文件仍缺 |
| 网络：无——本项目未见任何联网/多人机制的规划痕迹 | 无需替代品 | 不正当（**推断，非直接证据**：通读规格与全部 ADR/设计文档未见任何联网/多人字样，且模式 3"自由读档"、确定性重放这套架构本身是单机存档模型的典型特征，但没有找到一句"本项目是单机游戏"的原文明确声明，故标注为强推断而非已核实事实） |

### K. VM 全局可变状态（`set!` 等语言特性本身从未被拒绝，见下）

**这一条与前面几组性质不同：它不是"被拒绝的能力"，是"能力存在但缺失去处"**——`set!`/闭包捕获从未被白名单拒绝过（[脚本状态存储](../design/script-state-storage.md) 1.1 节已核实：不触达六类被禁能力中任何一类）。替代品就是[脚本状态存储](../design/script-state-storage.md)本身——本 ADR 通则的第二个具名范例。状态：**已有设计，未实现**（该文档明确标注「纯设计，不要求本次实现」）。

### L. 浮点

**这一行在 P4 阶段的推广解读下曾经被当作"脚本层禁止浮点"处理，本 ADR 与 [0020](0020-scripts-may-use-floats-internally-boundary-type-gated.md) 已经把这条重新定性——它不是"被禁能力 + 替代品"模式，是"开放能力 + 默认更优路径"模式，两者的差别本身值得写明，见 [0020](0020-scripts-may-use-floats-internally-boundary-type-gated.md) 全文。** 简述结论：脚本内部允许浮点（从未被语言层面禁止），安全边界收拢到 `register_fn` 只接受整数/`Milli`；`WorldState` 继续零浮点。整数几何工具（距离、定点三角函数表、范围判定）作为"默认更优路径"提供，但不是"唯一合法路径"，见 [0020](0020-scripts-may-use-floats-internally-boundary-type-gated.md)「甲区/乙区」判据与三组工具划分。**状态：设计已定（本 ADR + 0020），第 2/3 组具体工具接口未设计，是本 ADR 表格里唯一被单独标注"待办且已知严重"的条目**，见下文 B-1。

## 二、从 mod 作者需求出发核实到的八条

第一节是"从拒绝清单出发"倒着推正当需求；这一节反过来，从"mod 作者写真实内容时会撞到什么"出发，核实到八条，均已逐条核实代码现状（不是猜测）：

### B-1. 整数几何工具集——已核实的真实缺口，优先级最高

**核实结果**：`crates/ll-core/src/torus.rs` 确实已经实现 `TorusSize::{delta, chebyshev, squared_euclidean}`（距离相关方法），但**已核实这些方法从未被注册给脚本**——`crates/ll-script/src/api/query.rs` 现有的四个注册函数（`world-move-cost-at`/`world-blocks-sight-at`/`world-tick`/`world-ambient-light`）里没有任何一个暴露距离/几何计算。`crates/ll-core/src/*.rs` 里搜索三角函数（`sin`/`cos`/`atan`/`sqrt`）**没有命中任何实现**（唯一的字面匹配是 `ident.rs` 里无关的字符串，已核实排除）。

**严重程度判断**：这是一个**真实、当下就存在的空白**，不是假设性的未来需求——[脚本层数据句柄与批量查询](../design/script-entity-handles-and-batch-queries.md) 5.2 节 `filter-within-distance` 自己内部用到了 `squared_euclidean`，但那只是**批量查询原语内部**使用，不是暴露给脚本自由调用的通用几何工具；脚本若想在批量查询框架之外（比如自定义技能范围判定、弹道计算）自己算一次距离，**现在完全没有工具可用**，会被逼着要么做不成，要么找非正规路径（例如笨拙地用整数减法手搓一个近似,或者干脆放弃这个功能）。**这已经在阻塞现有 mod API 的可用性**——不是"将来可能需要"，是"脚本层数据句柄与批量查询设计文档已经写完的批量查询框架，此刻就缺一层通用几何原语可供脚本在框架之外使用"。

**替代品（按 [0020](0020-scripts-may-use-floats-internally-boundary-type-gated.md) 的"三组工具"框架，属于第 2 组"乙区默认好路"）**：

- 距离：把 `TorusSize::{delta, chebyshev, squared_euclidean}` 注册给脚本——已经是现成的 Rust 实现，只差 `register_fn` 这一步。
- 整数平方根——`squared_euclidean` 给出的是平方值，若脚本确实需要"实际距离"而非平方值做比较，需要一个整数平方根原语（牛顿迭代法的整数版本，跨平台确定，比 `f64::sqrt` 更适合落进乙区）。
- 定点三角函数表（`Milli` 表示）——供角度/朝向计算，避免脚本被迫直接调用浮点 `sin`/`cos`（那属于 [0020](0020-scripts-may-use-floats-internally-boundary-type-gated.md) 甲区/乙区判据下"乙区里可以用但要走量化"的场景，而查表法从一开始就不需要经过量化，是更省心的路径）。
- 范围/视锥判定——技能范围、AOE 判定的常见需求，可以用已有的 `chebyshev`/`squared_euclidean` 组合表达，值得包成一个更直接的注册函数而不是让每个 mod 作者自己拼算式。
- 整数插值——商队价格插值（[Agent 目标与经济](../design/agent-goals-and-economy.md)）已经是先例，可以复用同一套整数插值逻辑,不需要为脚本层重新发明。

**结论：这条不补，"浮点默认更优路径已经存在"这句话就是空话**——[0020](0020-scripts-may-use-floats-internally-boundary-type-gated.md) 的整个论证依赖"乙区有一条不需要碰浮点的默认路径可走"，若这条路径实际上是空的，唯一可用的路径就变成了"人人都用 `atan2`/`sqrt`"，[0020](0020-scripts-may-use-floats-internally-boundary-type-gated.md) 论证过的窄残余风险就从"极少数特殊需求才会踩"变成"人人都在踩"。**具体的完整接口形状是一项独立的设计任务，本 ADR 只确认缺口真实存在、优先级最高，不代为完成这项设计。**

### B-2. 本地化——裸字符串 + 带具名参数的格式化工具（不是不透明句柄）

**核实结果**：`crates/ll-script/` 目前没有任何本地化/字符串格式化相关的注册函数。`crates/ll-text/src/lib.rs` 模块文档提到"文本的语义内容（来自 Fluent 翻译键+变量插值）才需要确定性"——已核实项目确实规划用 Fluent 做翻译后端，但这是**渲染侧对"排版结果不确定、翻译内容需要确定"这条区分的论证**，不是一个已经暴露给脚本的 API。

**结论调整（覆盖本 ADR 早前草稿的"不可拼接句柄"提案）**：不做不可拼接的句柄。不可拼接句柄更安全，但也更烦人，而**烦人的 API 会被绕过**——若 `(localize key args...)` 返回一个只能整体传递、不能做任何字符串操作的不透明值，作者遇到句柄不够用的场景（哪怕只是想拼一个调试用的字符串)，大概率会找旁路（比如干脆不用这个 API，自己手写英文硬编码字符串），那样反而更糟。

**替代品**：裸字符串 + 一套好用的、带**具名参数**的格式化工具：

```scheme
(format-text "you-defeated" 'name name 'count n)
```

**为什么必须是具名参数，不能退化成手工字符串拼接**：`"你击败了" + name + "！"` 这种拼接方式假设了目标语言的语序与源语言相同——中文"你击败了{name}！"与英文"You defeated {name}!"字面语序恰好一致，容易让人误以为拼接没问题，但换一种语序完全不同的语言（例如日语"{name}を倒した！"，被击败者在最前面、动词在最后)，拼接出来的句子结构完全错位,无法通过简单换词修好。Fluent 这类 i18n 系统的参数化消息（`{ $name } を倒した！`）本来就是为了解决这个问题——翻译者拿到的是"这条消息有 `name`/`count` 两个具名占位符"，可以按目标语言的语序自由重排,而不是"这条消息是三段字符串拼接,第二段是变量"。`format-text` 只要比手工拼接更好用（不需要脚本作者自己算字符串索引、不需要处理多语言的语序差异），大多数作者会自然选择用它——这与本 ADR 通则"若某项能力被限制，必须给出比原来更好走的路"是同一个精神,不是靠强制,是靠"更好用"这个事实本身。

**兜底**：剩下没有走 `format-text` 、直接手写硬编码用户可见字符串的情况，靠既有的「无硬编码用户可见字符串」CI 门禁兜底（已核实**目前是警告模式**,不是强制拦截——这条门禁本身的强度不在本 ADR 范围内讨论）。

**状态：待办**——`format-text` 与底层 `localize` 查找机制均未实现，Fluent 翻译键+变量插值的具体接线方式也未设计到脚本 API 层面。

### B-3. 每个 mod 需要独立的随机流——已核实的真实确定性陷阱，当前完全未处理

**核实结果**：`ll_core::rng::DetRng::for_entity(world_seed, entity_id, event_counter)` 三个参数里**没有任何一个携带 mod 命名空间**——已核实全部现有调用方（`naming.rs` 用固定常量 `GIVEN_NAME_EVENT`/`SURNAME_EVENT`，`thin.rs` 用 `days`，`noise.rs` 用 `0`）都是**引擎自己代码**手工挑选 `event_counter`，各自约定互不冲突。**已核实：`set_active_rng`/`set_active_world` 目前只在 `ll-script` 自己的测试代码里被调用**（`grep` 未在任何非测试代码路径找到调用方）——也就是说，"脚本触发的 AI 决策该用什么 `event_counter`"这件事**当前完全没有真实wiring，是一个尚未出现在代码里的问题**,不是"已经存在但设计不当"的问题。

**风险的具体形状**（协调者原话核实无误）：若脚本触发的每一次 RNG 消耗都共用同一个"该实体本回合的事件计数"（例如所有 mod 都读同一个"这是本实体第 N 次请求随机数"的递增计数器），那么装一个新 mod（哪怕它与其他 mod 的游戏逻辑完全无关）只要它也调用了 `rng-next-u64`，就会让排在它之后调用的其他 mod 的 `event_counter` 往后移一位，从而拿到完全不同的随机流——同一个种子，加一个不相干的 mod，世界就变了。这类问题极难排查：现象是"某个跟这个 mod 毫无关系的系统的随机结果变了"，没有人会第一时间怀疑到"事件计数空间被共享"。

**替代品**：`event_counter` 的分配必须按 mod 命名空间隔离，形如 `DetRng::for_entity(seed, id, hash(mod_namespace, 本地事件计数))`——具体是"整体哈希混合"还是"给每个 mod 划一段独立的计数器区间"，属于需要专门设计的接口细节，本 ADR 不代为决定，只确认方向。

**状态：待办**——已核实这是一个真实存在但目前完全没有代码涉及的空白，不是"已经用了不安全的共享方案"，而是"这个问题此刻还没有被任何真实代码撞到过"，风险目前是潜在的，但一旦 P5 真正开始接线 AI 决策调用 `set_active_rng`，若不预先设计好隔离方案，第一版接线大概率会踩进这个陷阱（因为最直观的做法就是"每个实体维护一个全局递增的事件计数器"，恰好是最容易共享出问题的形状）。

### B-4. 定时/延迟执行必须引用具名处理器，不能是闭包

**核实结果**：`ll_sim::timeline::Timeline` 已核实只有 `schedule(actor: EntityId, at: Tick)`——只能安排"某个实体在某个 tick 行动"，不携带"要执行什么处理逻辑"与"任意数据载荷"，与"5 回合后触发某个自定义效果"这类通用延迟执行需求不是同一个东西。

**为什么必须是"具名处理器 + 可序列化 payload"，不能是闭包**：闭包无法序列化——时间轴队列本身要参与存档（`EntityId` 已经因为"时间轴队列/Intent 都需要完整序列化"这个理由补上了 `Serialize`/`Deserialize` 派生，见 `crates/ll-world/src/entity/id.rs` 模块文档「新增的原因」一节，已核实）。若调度接口允许脚本传入一个闭包，这个闭包本身携带的捕获状态就是无法序列化的 VM 内部数据——存档时要么整个调度队列跳过这一条（悄悄丢失一个已经排定的延迟效果），要么直接崩溃，两者都不可接受。

**接口形状**：

```scheme
(schedule-after ticks 'handler-name payload)
```

`handler-name` 必须是**注册过的具名处理器**（类似 mod 声明的一个函数名符号，宿主到期时按名字查找并调用，而不是直接持有一个函数值），`payload` 必须是 3.1 节值类型系统覆盖的**朴素可序列化数据**（整数/布尔/字符串/`NamespacedId`/列表/映射，与[脚本状态存储](../design/script-state-storage.md) 3.1 节的 `ScriptValue` 是同一套类型，值得复用而不是另起一套）。**这个限制必须在文档里写清楚，否则实现者会顺手接受闭包参数（Steel 语言本身完全支持把函数当值传递，没有类型系统会自动拦住这个用法），直到真正测试存档往返时才会发现存不下**——这正是本条目本身要求"写清楚"的原因，是一个容易被忽略的隐藏陷阱，不是危言耸听。

**状态：待办**——`schedule-after` 及配套的具名处理器注册机制均未设计到实现级别，本 ADR 只给出接口形状与理由,完整设计留给后续任务（很可能与 [脚本状态存储](../design/script-state-storage.md) 同批，因为 `payload` 本身需要落进 `WorldState` 才能让延迟调度跨存档存活，两者共享同一套值类型系统与序列化纪律）。

### B-5. 每实体扩展数据——已在 [脚本状态存储](../design/script-state-storage.md) 正面设计，不重复展开

见该文档第二节「两种存储形状，不是一种」与 3.3 节。结论摘要：每实体扩展数据挂在厚层 `Agent` 上（随实体生死自动回收），不对薄层 `ThinPopulation` 开放（避免重蹈 [0009](0009-derive-by-default-store-only-deviation.md) 棘轮问题的覆辙）。**状态：已有设计，未实现**。

### B-6. 步数预算应当可查询，而不是只能被超时杀掉

**核实结果**：`crates/ll-script/src/host.rs` 的中断机制是**墙钟超时**（`INTERRUPT_TIMEOUT = Duration::from_millis(300)`，`InterruptHandler::run_with_timeout`），`crates/ll-script/src/alloc_guard.rs` 另有一个独立的**内存预算**（`set_memory_budget`）。**已核实：两者都只在"超限时中断/拒绝"，没有任何注册函数让脚本在执行过程中查询"我还剩多少预算"**。

**为什么这是一个值得补的缺口**：被硬杀（超时中断，`ScriptError::Interrupted`）和脚本主动降级是两回事——一个写复杂 AI 决策树的 mod 作者，若能在脚本内部查到"预算快不够了"，可以让脚本自己提前收尾、退回一个更简单的策略（例如放弃精细的多因素评分，直接选"最近的敌人"），而不是被硬中断后整个决策直接丢失（`ScriptError::Interrupted` 发生后，`call_raw` 返回 `Err`，宿主按既有降级策略处理，但脚本自己完全没有机会体面收场）。

**替代品**：暴露一个"剩余预算"查询函数。**确定性上这比暴露墙钟时间更好**——墙钟本身在不同硬件上运行速度不同，若脚本内部逻辑依据"还剩多少毫秒"做分支判断，这个分支本身在不同机器上可能走向不同结果,直接违反确定性；换成"步数"（Steel VM 求值步数,或者更粗粒度的"已进行了多少次跨界调用"）是可复现的整数指标,同一段脚本在任何机器上跑，步数应当完全相同。

**状态：待办**——`InterruptHandler` 目前是纯墙钟机制，没有暴露任何"剩余预算"查询接口；把中断机制本身从墙钟迁移到步数计数（若要让"剩余预算"这个查询有意义，中断判据本身最好也是步数而不是墙钟，否则"查到的预算"与"真正触发中断的条件"是两套不同的计量单位，查询结果会失真）是一项更大的改动，本 ADR 只标注方向，不代为决定是否需要连中断机制本身一起换掉。

### B-7. 结构化日志，归属到具体 mod

**核实结果**：`crates/ll-script/src/api/log.rs` 确实存在，但**已核实它是纯 Rust 侧类型**（`ScriptDiagnostic::from_error`，从一次 `ScriptError` 构造诊断)——没有任何 `register_fn` 调用把它注册成脚本可调用的函数。`crates/ll-script/src/api.rs` 的 `pub mod` 列表虽然包含 `log`，但该模块没有 `pub fn register(engine: &mut ScriptEngine)`。**结论：脚本此刻完全没有办法主动打印一条日志**——`log.rs` 现有的机制只在脚本**调用失败**（语法错误/超时/参数不匹配）时由宿主自动构造诊断，不是脚本正常执行过程中可以调用的"打印一句话"能力。

**为什么这是正当需求**：mod 作者调试自己的脚本时，需要一种"打个断点/打印一个中间值"的手段。裸 `display`（Steel 内置，若放行会打到进程 stdout）不满足需求——玩家看不到 stdout，也不知道是哪个 mod 打的，且 stdout 本身在打包发行的游戏里可能根本没有可见的终端窗口。

**替代品**：一个脚本可调用的结构化日志函数，注册时同样绑定 mod 命名空间（与 4.1 节写入函数的命名空间绑定方式同构，脚本不需要、也不能指定"我要以哪个 mod 的名义打日志"），带级别（沿用 `log.rs` 已有的 `Severity::Error`/`Severity::Warning`,可能需要新增 `Info`/`Debug` 供正常调试用），**直接显示在加载管理界面的控制台里**（复用 `ScriptDiagnostic` 已有的展示通道），并做**限流**——防止一个失控的每 tick 打印日志的脚本把渲染这块面板的成本拖垮帧率（限流策略：例如每 mod 每秒最多 N 条,超出的静默丢弃并计数,面板显示"另有 N 条被限流",而不是無限增长的日志列表)。

**状态：待办**——`log.rs` 需要新增一个脚本可调用的注册函数（类似 `(log-info "message")`/`(log-warn "message")`），并补上限流机制,当前完全没有这层。

### B-8. 事件历史查询——双重受阻：数据层与 API 层都不存在

**核实结果**：`knowledge/design/world-history.md`「六、事件日志」一节已经设计了"只记可被引用的事件"（约一万条量级）这套机制，且该文档「落地状态」一节已核实标注**「纯设计，代码中无任何对应类型」**——不存在历史生成器、`Settlement` 结构、势力形成逻辑或事件日志的任何实现。

**这与前面几条待办的性质不同**：B-1 到 B-7 缺的是"API 层没有暴露一个已经存在的 Rust 能力"，B-8 缺的是**两层都不存在**——数据本身（事件日志）没有生成，查询 API 自然也无从谈起。`world-history.md`「三、」一节已经预留了"事件日志 ID 空间需要能被查询式脚本 API 引用"（已核实原文），说明设计阶段已经意识到这个未来需求，但**具体的查询接口形状完全没有设计**。

**与既有原则的配套**：这条需求与 `identity-and-ids.md`「脚本 API 必须是查询式，不是引用式」（已核实的既有设计原则）正好呼应——"玩家是否杀过龙""这个家族参与过哪场战争"这类问题，天然只能通过查询表达（不能硬编码"卡拉克之战"这个具体事件的名字，因为换个种子这场战争可能根本不存在，`identity-and-ids.md` 已有论证)，事件历史查询 API 一旦设计，应当直接遵循这条既有原则，不需要另立新规则。

**状态：待办，且依赖 P7 世界历史生成器落地（数据层前置依赖，本 ADR 无法绕过；[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P6 顺移为 P7）**——在事件日志真正被生成之前，讨论"查询 API 长什么样"意义有限，只能停留在"这是一个已知的未来缺口"这个层面。

一节 A-L 共 12 类（含"能力/模块分组"与"VM 状态""浮点"两条特殊行）覆盖了 `META_DENY_LIST` 系列 49 个具名标识符、`FULLY_POISONED_MODULES` 4 个整体模块、`Engine::new_sandboxed()` 层面排除的文件系统/网络、以及"从未被禁止过"的 `set!` 与浮点两条特殊情况。二节 B-1 到 B-8 覆盖协调者从 mod 作者需求角度提出的八条,全部已核实（代码现状,不是猜测）。

**未能验证、如实标注的**：I 组 `inspect` 的具体行为——尝试读取 `steel-core-0.8.2` 源码核实时命令执行超时，未能在预算内完成，留给后续任务。

- **[0020](0020-scripts-may-use-floats-internally-boundary-type-gated.md)**：浮点这一行的重新定性直接由本 ADR 的通则推导而来（"给正路才能理直气壮地封死歪路"同一条精神），但由于涉及独立的技术论证（IEEE 754 舍入保证、残余风险量化），拆成独立 ADR，本 ADR 只做摘要与索引。

## 五、被否决的选项

**不设通则，逐条被质疑时再个案讨论**——否决理由：这正是 `host.rs` 现状本身（两条"因未验证而拒绝"的条目已经挂了一整个 P4 阶段没人处理）,没有通则,"该不该给替代品"永远排不上优先级,直到某个 mod 作者真的撞上才会被动响应。

**把全部拒绝清单里没有替代品的条目立即实现替代品**——否决：不现实,B-1 到 B-8 里多条待办本身就是需要独立设计任务的工作量（尤其 B-1/B-4/B-8),本 ADR 的职责是**确立通则并盘点现状**,不是在一次性提交里交付全部实现。

## 六、后果

- 本 ADR 生效后，未来任何新增的能力拒绝决定，必须在裁定的同时回答通则的两个问题，不能只写"这个不安全,禁掉"就结束。
- 二节列出的八条待办，其中 **B-1（整数几何工具）与 B-3（每 mod 独立随机流）标注为优先级最高**——前者已核实正在阻塞现有 mod API 可用性,后者已核实是一个真实但尚未被任何代码触发的确定性陷阱,越早设计好隔离方案,越不容易在 P5 真正接线 AI 决策时被动踩坑。
- `inspect` 的核实工作未完成，本 ADR 明确记录为遗留任务，不假装已经处理。
- 本 ADR 与 [脚本状态存储](../design/script-state-storage.md)、[0020](0020-scripts-may-use-floats-internally-boundary-type-gated.md) 三份文档同批产出，互相引用，建议同批阅读。
