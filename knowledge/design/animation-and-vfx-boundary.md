# 动画与视觉特效的边界

**冻结于** 2026-08-19。**落地状态**：纯设计，但不是从零开始——`crates/ll-render/src/anim.rs` 已经实现「原地循环动画」所需的全部核心机制（`Clip`/`Playback`，整数帧号驱动，见二、2.1），本文档只补它没有覆盖的两类（一次性特效、投射物，见二、2.2/2.3）与三条配套规则（相位派生、非格子位置的类型归属、连续输入的手感策略）。`crates/ll-sim/src/effect.rs` 当前有 11 个 `Effect` 变体，均已核实不含任何表现层字段——本文档确认这是对的，不是缺口。**冻结时对应 git 提交**：`7cbdfe4`（本文档写作时的仓库 HEAD）。

## 一、核心边界：结算是瞬时的，动画只是回放

回合制里 `Intent → resolve → Effect → apply`（规格 §4）在同一帧内完成：`resolve` 读世界、算出一串 `Effect`，`apply` 把它们逐条写回 `WorldState`（`crates/ll-sim/src/apply.rs` 模块文档「三条纪律」：唯一写入口、不含逻辑、极短）。这一步结束时，世界的下一个状态已经**完全确定**——火球命中了没有、伤害扣了多少、目标死没死，全部是既成事实。

```
世界状态层   火球命中、伤害已结算    整数、确定性、进 WorldState::hash()
                                    （apply 写完的这一刻就已经成立）

表现层       火球飞行的那 0.3 秒     浮点、不进世界状态、从 Effect 流派生
                                    （事后的回放，纯粹是给玩家看）
```

### 两条铁律

1. **动画绝不能影响结算结果**——`resolve`/`apply` 不得读取任何动画播放状态（是否播完、播到第几帧），播放进度是纯粹单向的下游产物。
2. **回合绝不能等动画播完**——`apply` 写完 `WorldState` 的那一刻，下一个 `Intent` 就可以立刻被 `resolve`。约束 C4（后台推进必须到达确定 tick）与这条边界是同一个精神的两个应用：世界的推进速度永远由结算本身决定，不受任何表现层耗时影响。

### 甲区/乙区：这是 ADR 0020 分区表用在动画上

[ADR 0020](../decisions/0020-scripts-may-use-floats-internally-boundary-type-gated.md) 的判据是「这个浮点计算的结果，最终会不会变成世界状态的一部分」，甲区表格第一行原文就是「渲染、相机、动画插值、粒子」——本文档要落的东西完整落在这一格里，不是新发明一条规则，是把已经裁定的分区应用到一个此前只有循环动画覆盖过的具体领域。`crates/ll-render/src/lib.rs` 模块文档「浮点边界」一节同样写着「本层内部使用 `f32`……这些值绝不可回流入世界状态或被存档序列化」，与 ADR 0020 甲区表述完全一致——本文档不需要新增任何浮点使用上的例外或限制，动画与特效系统在这条既有边界内随便用浮点。

反过来，`anim.rs` 模块文档「整数帧号而非墙钟秒数」一节解释的是另一件事：`Playback` 恰好落在**乙区**——它虽然只影响画面，但因为要在存档读回后从正确的帧号接续播放（不是随机跳帧），需要参与序列化，所以它的时间基准选的是整数帧号（`FrameId`）而不是浮点墙钟秒数。这不是说动画系统本身要遵守乙区那套「结果进 `WorldState`」的纪律——`Playback` 从未进入过 `WorldState`（它属于渲染层自己的状态，不属于 `ll-world`/`ll-sim`），选整数只是因为「可以安全序列化」这个性质本身对整数更友好，是工程选择，不是甲乙分区意义上的「乙区」。本文档新增的两类动画（一次性特效、投射物）不需要跨存档接续播放（见二、2.2/2.3 生命周期论证），因此不必比照 `Playback` 的整数纪律,用浮点当场计时即可,仍然稳稳落在甲区。

### `Effect` 流是表现层唯一的输入，方向单一、无反馈

`Effect` 已经是「发生了什么」的完整记录（`effect.rs` 模块文档：`resolve` 的产出「纯数据,不含任何执行逻辑」）。表现层不需要额外的信号来源——订阅同一批 `Effect` 就足够派生出「该播什么」：`Damage` 对应受击闪光与飘字、`MoveTo` 对应位移动画、`Kill` 对应死亡特效。这条依赖天然单向：表现层读 `Effect`，`Effect` 从不读表现层，不存在任何反馈通路能让动画状态影响下一次 `resolve`。

**这里有一处需要写清楚的接线细节，不是对 `effect.rs` 的修改，是对调用方的要求**：`effect.rs` 模块文档明确说 `Effect` 「算完立刻被 `apply` 消费掉，不需要跨进程/跨存档留存」——`Effect` 不是 `Copy`（见该文档「为什么不再 `Copy`」一节），`apply` 的签名是逐条消费 `&Effect`（`fn apply(world: &mut WorldState, effect: &Effect)`）。表现层要「订阅」这批 `Effect`，唯一可行的时机就是**在调用方把 `resolve` 产出的 `Vec<Effect>` 逐条喂给 `apply`的同一个循环里，把同一份 `&[Effect]` 也交给表现层**——不能等 `apply` 消费完之后再去别处找,因为消费完之后这批 `Effect` 就不存在了,`WorldState` 里也没有任何字段记录「刚刚发生过什么」。这是当前调用方（尚未在 `ll-app` 落地，`crates/ll-app` 本身还未建立）接线时必须遵守的顺序，不需要改动 `ll-sim::effect`/`ll-sim::apply` 任何一行代码——只是同一份 `Vec<Effect>` 多喂给一个消费者：

```
resolve(&world, intent) -> Vec<Effect>
        │
        ├──→ for effect in &effects { apply(&mut world, effect) }   ← 既有代码，唯一写入口
        │
        └──→ presentation::spawn_animations(&effects, now: FrameId)  ← 本文档新增的消费者
              （读同一份 &[Effect]，只产出表现层实例，不持有
               &mut WorldState，不回写任何东西）
```

两个消费者读的是同一份数据、互不知道对方存在——`apply` 不知道表现层订阅了它正在消费的这批 `Effect`，表现层也不需要等 `apply` 跑完才能开始派生动画（`Effect` 本身已经是终局数据，`apply` 只是把它誊抄进 `WorldState` 的字段，不会再改写 `Effect` 的内容）。这个顺序无关紧要，只要两条路径读的是同一份 `&[Effect]` 切片即可。

## 二、三类动画，性质完全不同

### 2.1 原地循环——`anim.rs` 已经够用

营火、烟雾、水波这类效果吸附在固定格子上，永久循环播放，不随游戏事件触发或结束。`Clip { frames, frames_per_step, looping: true }` + `Playback::new(clip, started_at)` 已经完整覆盖这个需求：`current_frame` 对循环剪辑用 `step_index % frame_count` 算出当前帧，恒定成立,不需要任何生命周期管理——这类动画从世界生成时就在播，直到对应的地形/装饰物本身被移除。

### 2.2 一次性特效——`anim.rs` 有一半基础，缺生命周期管理

施法闪光、命中溅射、飘字，播完即弃，可能吸附格子（命中溅射）也可能不吸附（飘字通常要向上飘一小段再消失，这段位移本身也是甲区浮点插值,与投射物同理但轨迹更简单）。

`anim.rs` 已经支持非循环剪辑（`Clip { looping: false }`），`current_frame` 对这类剪辑播完后「停在末帧」——模块文档明确写着这是有意为之：「施法、受击这类一次性动画播完应停住，跳回起手姿势会看起来像抽搐」。**但停在末帧不等于消失**：`current_frame` 对非循环剪辑永远返回 `Some(最后一帧)`，没有任何信号告诉调用方「这个播放已经结束，可以从活跃列表里移除了」。这正是一次性特效缺的那一半——需要在 `anim.rs` 现有能力之上新增一个独立的「是否播放完毕」判定（`elapsed >= frames_per_step * frame_count`，用现有 `Playback` 的两个私有字段加 `Clip` 的两个公开字段就能算出来，不需要改动 `Playback` 的内部表示),以及一个持有「当前活跃的一次性特效实例」的表现层集合——每帧过滤掉已播完的实例。这个集合本身不进 `WorldState`，纯粹是渲染层的运行时状态：

```
struct OneShotInstance {
    playback: Playback,       // 直接复用 anim.rs 现有类型，不需要新的播放机制
    position: TorusPos,       // 吸附格子的情形（命中溅射）；不吸附的情形
                               // （飘字）见下方「位移」字段
    offset: Option<(f32, f32, FrameId)>, // 起始屏幕偏移、目标偏移、起飘帧号，
                               // 仅飘字这类带位移的一次性特效需要，与投射物
                               // 的插值是同一套数学，只是轨迹通常是直线上飘
                               // 而非两点连线
}
```

**为什么不直接复用 `Playback` 本身表达"播完即弃"，而要在它外面再包一层**：`Playback` 是「一段剪辑该播放到第几帧」这个纯粹的时间计算,不持有「这个实例还活不活着」这类生命周期信息,也不应该持有——把生命周期塞进 `Playback` 会让循环动画（永远不消亡）与一次性动画（终将消亡）共用同一个类型却有着不同的解释,增加调用方每次读 `Playback` 时都要多想一层"这个具体实例是不是该判断消亡了"的心智负担。`OneShotInstance` 这层薄包装把"要不要移除"这个判断留在外面，`Playback` 本身继续保持"纯粹的帧号计算器"这一个单一职责，两类动画的差异只体现在外层容器的生命周期管理上，不体现在 `anim.rs` 内部。

### 2.3 投射物——`anim.rs` 完全没有覆盖，需要新概念

火球、箭矢从 A 飞到 B，中途的位置**不吸附任何格子**——这与前两类的根本区别不在「播不播完就消失」（一次性特效也播完即弃），而在**位置本身是插值出来的连续值，不是某一格的坐标**。`anim.rs` 的 `Playback` 只回答「现在该显示图集里的哪一帧」，从不回答「现在该画在屏幕的哪个像素」——后者对吸附格子的动画是免费的（格子坐标经 `Camera::world_to_screen` 直接换算），但投射物没有格子坐标可用。

需要的新形状（表现层私有，不进 `WorldState`，细节见四）：

```
struct ProjectileInstance {
    start: TorusPos,        // 起点格（Effect 触发时刻的施法者位置）
    end: TorusPos,          // 终点格（Effect 触发时刻的目标位置）
    started_at: FrameId,    // 起飞帧号
    duration_frames: u32,   // 飞行时长，甲区数值，随便定
    clip: usize,            // 复用 anim.rs 的 Clip 索引，画投射物本身的翻滚/拖尾帧
}
```

每帧渲染时计算 `progress = (now - started_at) / duration_frames`（浮点,钳制到 `[0, 1]`），插值出当前屏幕位置。**插值必须在位移向量上做，不能直接对 `TorusPos` 的整数分量做线性插值**：环面世界里两点之间可能存在「绕远路」与「走近路」两种位移，`TorusSize::delta`（`ll_core::torus`，`Camera::world_to_screen` 内部已经在用）算出的才是最短带符号位移；若改成直接对 `(x, y)` 数值插值，起点终点恰好跨越接缝时（例如 `x=0` 飞向 `x=世界宽度-1`）插值路径会绕经世界另一侧，火球会「穿过整个大陆」才飞到隔壁格——这与 `sprite.rs` `DrawOrder` 模块文档强调的「必须用屏幕坐标而非世界坐标」是同一类陷阱的又一个实例，正确做法是先用 `world_to_screen` 把起点终点都换算成屏幕坐标（或直接用 `TorusSize::delta` 拿到最短位移向量），再在屏幕空间/位移向量上插值。

投射物播放结束的判定与一次性特效相同：`progress >= 1.0` 即从活跃集合移除，不需要额外机制。

### 三类动画的差异一览，为什么不能用同一套机制

| | 原地循环 | 一次性特效 | 投射物 |
|---|---|---|---|
| 位置 | 吸附格子，恒定 | 吸附格子，或带小幅位移 | 不吸附，两点间连续插值 |
| 生命周期 | 永久，随宿主存在 | 播完即弃 | 播完即弃 |
| 现有覆盖 | `anim.rs` 完整覆盖 | `Playback` 覆盖播放本身，缺生命周期判定 | 完全没有覆盖 |
| 时间基准 | `FrameId`（可安全序列化，虽然实际不需要） | `FrameId` + 一个外层「是否播完」判定 | `FrameId` + 插值进度 `progress` |
| 相位来源 | 三节：坐标派生，零存储 | 触发时刻的 `Effect`，一次性，不需要派生 | 同左 |

三者的共同底座（帧号推进、图集条目查找）完全一样,都直接复用 `anim.rs`；差异只在“位置从哪来”与“什么时候该消失”这两个维度上，这正是不能用同一个类型囊括三者的原因——把这两个维度都塞进一个大而全的 `Playback` 会让循环动画（两个维度都不需要）平白多背负两块从不使用的字段。

## 三、环境动画的相位必须派生，不能存

世界可能有几十万到一百万个格子挂着循环动画（大片沼泽的水泡、密林的风吹草动），若每个格子存一份 `Playback`，仅 `started_at: FrameId`（8 字节）一项就是几百万到几千万字节，且这类环境动画天生不需要在存档里保持连续——重新读档后从任意相位重新开始播放，玩家根本感觉不到差别。

应当 `相位 = f(格子坐标, tick)`——不存储任何东西，每次渲染现算，公式满足两个要求：

1. **零存储**：不占用 `WorldState` 或任何持久结构的一个字节。
2. **相邻格子不同步**：若所有营火共享同一个 `started_at`（比如都用世界创建时刻），画面上所有火焰会同一帧跳变到同一帧，这是最常见也最廉价的视觉穿帮来源之一。正确做法是把格子坐标本身混入相位计算，让 `(x, y)` 不同的格子天然落在剪辑循环的不同位置。

具体实现可以照抄 `ll_core::rng` 里 `DetRng`/`splitmix64` 已经验证过的思路——用坐标做种子的整数位混合（`crates/ll-core/src/rng.rs` 的 `splitmix64` 目前是模块私有 `const fn`，不能被 `ll-render` 直接调用；`ll-render` 可以在自己的 `anim.rs` 或新模块里写一份独立的、同样是纯整数位运算的哈希函数，不需要依赖 `ll-core` 新增一个公开导出——两处各自实现一份简单的整数混合函数不算真正的重复,因为动机不同：`DetRng` 服务约束 C3「按实体 ID 派生的确定性随机流」，是结算层的正确性要求；这里只是想要「看起来不规则」，不需要与结算层共享同一套算法或保证跨越 mod 边界的比特级一致）。`偏移 = hash(x, y) % (frames_per_step * frame_count)`，把这个偏移量当成 `Playback::started_at` 的等效值代入现有 `current_frame` 公式即可，不需要改动 `anim.rs` 一行代码——只是调用方每次现算一个「虚拟起始帧」而不是从某个持久化的 `Playback` 里读。

**顺带获得的好处，虽然不是本节的诉求**：这套相位公式全程整数运算（位移、异或、乘法），不涉及任何超越函数——ADR 0020「残余风险」一节论证过的「超越函数 + 粗量化」跨平台分叉风险，在这里根本不存在触发条件（它压根不属于乙区，不需要这条论证）。这意味着同一个格子在 Windows 与 Linux 上算出的相位逐位相同，同一个存档在两台机器上打开时环境动画的观感也完全一致——这不是本节要解决的正确性问题（甲区的画面差异从不影响正确性），但对第 14.1 节 L7 视觉回归测试（离屏渲染 → 基准 PNG 容差比对）是有意义的副产品：若相位公式引入了任何跨平台不一致的浮点/超越函数，L7 测试会在两个平台上产出不同的基准图，容差比对形同虚设。

**这是「默认派生，只存偏差」（[ADR 0009](../decisions/0009-derive-by-default-store-only-deviation.md)）的又一次复用**——`knowledge/design/README.md` 「三、贯穿全局的设计原则」一节按出现顺序列了十项已识别实例，最后一项（第 10 项）是增益/减益的 `expires_at` 惰性到期，本文档的环境动画相位派生是同一个模式在表现层的第 11 个应用（已同步补进该索引列表）：默认值（这一格现在该播哪一帧）由坐标 + tick 现算，零存储；这里甚至没有「偏差」这一半——环境动画不存在「被剧情或玩家改变过的相位」这种概念，与命名系统（ADR 0009 表格「姓名」一行）是同一种「极端情形」：连偏移都不允许存在。

## 四、非格子对齐的位置属于表现层，绝不进 `WorldState`

投射物飞行途中的位置、一次性特效若带位移（飘字上浮）的中间坐标，这些值：

- **类型上是 `f32`/`(f32, f32)`（屏幕像素）或至少是浮点插值的产物**，落在 ADR 0020 甲区，可以随便用浮点，不需要走 `Milli` 或任何整数近似——这类位置从不参与任何判定（不检测碰撞、不影响命中，命中判定在 `resolve` 阶段已经用整数格子坐标算完,投射物的飞行只是把"已经确定命中"这件事演给玩家看)。
- **归属上属于渲染层的运行时状态**（如二、2.3 的 `ProjectileInstance`），活在 `ll-render`（或未来的表现层 crate）自己的一个集合里，不进 `ll-world::WorldState`，不参与 `WorldState::hash()`，不被存档序列化。若这类瞬时状态真的进了存档格式，[ADR 0022](../decisions/0022-guard-coverage-gap-defeats-the-guard.md) 的教训会立刻适用——每一发飞行中的火球都要占存档一条记录、都要考虑要不要混入哈希，这既没有必要（读档后火球直接消失或瞬移到终点，玩家不会察觉),也会把黄金基准测试的输入搞得毫无意义地膨胀。

**DrawOrder 的排序键怎么给投射物用**：`sprite.rs` 的 `DrawOrder::new(layer, foot_y, entity)` 第三个参数要求一个 `u64`（不是 `EntityId`——签名就是裸 `u64`,`entity` 字段的语义是「用于打破平局的稳定标识」,不要求它是一个真正的世界实体）。投射物、一次性特效都不是 `WorldState::actors` 里的实体，没有 `EntityId`，但仍然需要参与同层内的绘制排序（避免与其他特效同层同 `foot_y` 时抖动，见 `sprite.rs` 「同层同纵坐标时按实体号打破平局」的测试)。做法是表现层自己维护一个独立的单调计数器，给每个新建的 `ProjectileInstance`/一次性特效实例分配一个 `u64`，与 `EntityId` 的号段完全不相关（两者从不比较、从不混用，只是恰好共用同一个 `u64` 参数位置）——这不需要改 `DrawOrder` 的定义，现有签名已经足够宽松。

## 五、连续行动时动画怎么办：可跳过，不排队

回合制连续结算（玩家按住方向键连续移动）时，`resolve`/`apply` 推进世界状态的速度天然快于动画能播放的速度——每一步移动的 `Effect` 都会瞬间产生并写入 `WorldState`，而对应的位移动画哪怕只有零点几秒也来不及播完下一步就已经开始。三种做法效果差异很大，必须明确选一种，不能含糊：

### 可跳过（推荐，作为单体位移/受击动画的默认策略）

新回合的 `Effect` 到达时，若该实体上一步的动画还没播完，直接丢弃，从世界状态**当前**已经生效的位置/状态重新起播下一步动画。

- **好处**：画面永远反映世界的最新真相，不会出现「玩家看着角色停在 A 格，其实角色早就在 D 格」这种画面与状态脱节的情况——这正是回合制游戏最容易让人产生"操作和画面对不上"挫败感的错误。连续按键时,画面会自然表现为「加速跑动」的观感（因为每一步动画都被下一步打断,只播出一小段位移就切到下一段),这在大多数像素 roguelike 里是被接受、甚至是期待的手感。
- **代价**：中间步骤的完整位移过程可能一帧都没画完就被打断，单看某一步动画不「完整」。

### 排队（不推荐作为默认策略）

每一步动画依次播放，不被打断，画面因此落后于世界状态。

- **致命问题**：连续输入没有天然的收敛点——只要玩家持续按键，世界状态推进的速度不受动画拖累（铁律二），队列只会越积越长,画面与真实状态的差距没有上限。更危险的是,若 UI（血条、小地图）也跟着"画面进度"走而不是跟着世界状态实时更新,玩家会根据一个滞后几步的画面做出下一步决策——这比"动画不完整"严重得多,是真正会让人对不上操作预期的错误。若 UI 始终跟世界状态实时更新（不排队),又会出现"血条已经掉了但受击特效还没播到"这种观感撕裂。
- 唯一说得通的用法是给队列设一个很短的硬上限（例如最多缓冲 1～2 步，超过直接丢弃最旧的),但那样做本质上退化成"有限缓冲的可跳过"，不如直接用可跳过更干净、没有额外状态需要维护。

### 叠加（推荐，但仅用于彼此独立的并发特效，不适用于同一实体的连续位移）

多个动画同时播放，互不打断。

- **适用场景**：一次 AOE 命中多个目标,每个目标各自的受击闪光/飘字彼此独立,天然应该同时播放——这类特效不共享同一个视觉焦点,叠加不会产生矛盾。
- **不适用场景**：同一个实体连续多步移动时，"叠加"没有意义——角色精灵只有一个，不能同时画在两个位置上；如果字面地叠加播放会变成好几帧动画的位置互相覆盖闪烁，比排队更糟。

**结论**：单体位移/受击这类"同一视觉焦点的连续动画"用可跳过；彼此独立的并发特效（多目标同时受击、多个环境特效同时触发）用叠加；排队不作为任何场景的默认策略，只在极少数需要保证呈现顺序的场合（例如连续暴击的伤害数字必须按发生顺序从上往下排列）作为特例使用，且必须配一个硬上限。

### 一个具体走查：按住方向键连续移动五格

假设位移动画设计时长是 12 帧（约 0.2 秒，60fps），玩家按住"东"键，输入系统在一次主循环里（或连续几帧内）连续产出五个 `Move` 意图，每个都立刻 `resolve`/`apply` 完毕：

```
tick    T0    T1    T2    T3    T4          （世界状态：五次 apply 瞬间完成）
                                              实体已经稳稳站在 (x+5, y)

画面    ├─12帧─┤                              可跳过：第 0～11 帧播 T0→T1 的位移，
              ├─新起点，从当前实际位置开始播12帧┤
                                              第 12 帧起：无论 T0→T1 的动画播到第几帧，
                                              立刻改为从"世界状态现在的实际位置"
                                              （可能已经是 T3 甚至 T4 对应的位置）
                                              播向下一个目标格
```

若改用排队，五段 12 帧的动画会依次首尾相连，总计 60 帧（1 秒）才播完，而世界状态在几毫秒内就已经站定在终点——这 1 秒里玩家若继续按键，队列还会更长；若此时玩家已经松开按键并按了别的操作（比如攻击），攻击的 `Effect` 也会被排到队列末尾等前面的移动播完，输入到反馈之间出现肉眼可察觉的延迟。可跳过策略下，画面最多只播出"当前这一步"到"世界状态最新位置"的一段位移（长度可能远小于 12 帧，因为新的 `Effect` 随时可能打断当前播放并重新起播），玩家松开按键后画面在一帧内就能追上真实状态，不存在任何滞留的队列。

## 六、mod 能不能定义特效：按 ADR 0018 三步判据，播放机制是引擎层，播什么是玩法层

[ADR 0018](../decisions/0018-engine-layer-vs-gameplay-layer-scripting-boundary.md) 的判据不问"这个系统是谁写的"，问"是否存在设计自由度，以及这个自由度落在算法本身还是算法读的数据上"。逐条套用：

**第一步：有没有"设计者可以选另一种规则"的自由度？** 有——同一个 `Damage` 类 `Effect`，火焰系技能应该有火焰粒子与灼烧后残留的焦黑贴花，冰系技能应该是冰晶飞溅，这是设计意图的一部分，不是工程正确性问题（与 `TerrainKind` 的 `move_cost`/`opens_into` 是同一类：这些数值背后没有唯一"正确答案"，是内容作者的选择）。`sprite.rs` `Layer::EFFECT` 的文档注释「特效（技能光效、粒子）」也印证了特效内容本身天然是与具体技能/物品绑定的可变内容,不是引擎的固定行为。

**第二步：这个自由度落在算法本身，还是算法读的数据上？** 落在数据上，不在算法上。`Playback::current_frame` 怎么从帧号推算当前帧、`DrawOrder` 怎么排序、投射物插值怎么算屏幕位置——这些算法步骤本身没有设计自由度，任何 mod 定义的特效都要走同一套播放引擎，不存在"这个 mod 想要另一种插帧算法"这种自由度（如同寻路算法本身是引擎层，但寻路读的 `move_cost` 是玩法层数据）。真正有自由度的是"这次 `Damage` 效果该播哪个 `Clip`、时长多少、吸不吸附格子、颜色染色参数"这些**参数**。

**第三步：高频调用不改变分类。** 特效可能每回合触发几十次（多目标 AOE），但按第一、二步已经归类为"玩法层内容（声明式数据）"，高频只决定它该走哪一档物化（[ADR 0016](../decisions/0016-mod-performance-tiers-by-declaration.md)/[0017](../decisions/0017-tiered-declarations-materialize-columnar.md) 的分级/列式存储），不改变归类结论。

### 结论：动画播放引擎（`anim.rs`/`DrawOrder`/投射物插值）是引擎层，"该播哪个特效"是玩法层内容，走注册表

与 `TerrainDef`（`crates/ll-mod/src/base_terrain.rs` 等）、`SkillDef`（`crates/ll-mod/src/skill.rs`）同一套既有模式——本体与 mod 用同一份注册 API：

- 新增一个 `EffectDef` 类内容注册表（可以是独立的 `ll-mod::vfx` 模块，也可以是给 `SkillDef`/未来的 `ItemDef` 加一个可选字段,两种做法都不违反本文档的边界结论，具体选哪种是实现批次的决定，本文档不代为选定）。字段大致形状：`clip: 图集条目名序列（复用 anim.rs 的 Clip）`、`duration_frames`、`anchored: bool`（吸附格子还是投射物式插值）、`layer`（默认 `Layer::EFFECT`，也可能是 `Layer::UI` 如飘字）。
- 索引方式沿用 `ContentIndex` + 列式存储（`SkillTable`/`TerrainTable` 已验证的模式：`define(index, attrs) -> Result<(), Error>`、`get(index) -> Option<View>`，按 `ContentIndex::get` 数值升序遍历以满足约束 C5）。
- **`ll-sim::Effect` 本身不应该新增任何"该播哪个特效"的字段**——这与 `Effect::ApplyStatModifier` 等既有变体只携带纯数值（属性/增量/到期时刻）是同一条纪律：结算层不知道、也不需要知道表现层的存在。真正的关联关系是"触发这次 `Damage` 的技能/物品 `ContentIndex`"（已经在触发 `resolve_use_skill` 时可得）→ 表现层自己查一张"技能 `ContentIndex` → `EffectDef` `ContentIndex`"的映射表决定播什么。这张映射表的归属同样是玩法层内容（技能作者决定"我这个技能对应哪个特效"），可以直接挂在 `SkillDef` 新增的可选字段上，不需要发明第三套映射结构。

`EffectTable` 照抄 `SkillTable`（`crates/ll-mod/src/skill.rs`）已验证的列式存储形状即可，不需要新发明一套注册表模式：

```rust
pub struct EffectAttrs {
    pub clip: Vec<String>,       // 复用 anim.rs::Clip 的帧序列表示
    pub frames_per_step: u32,
    pub duration_frames: u32,    // 一次性特效/投射物的总时长；循环特效忽略此字段
    pub anchored: bool,          // 吸附格子 vs 投射物式插值
    pub layer: u8,               // 对应 sprite.rs::Layer，多数是 EFFECT，飘字可能是 UI
}

pub struct EffectTable {
    clip: Vec<Vec<String>>,
    frames_per_step: Vec<u32>,
    duration_frames: Vec<u32>,
    anchored: Vec<bool>,
    layer: Vec<u8>,
    defined_ids: Vec<ContentIndex>,   // 与 SkillTable 同一理由：按数值升序遍历满足 C5
}
```

`define(index, attrs) -> Result<(), EffectError>`、`get(index) -> Option<EffectView<'_>>`、`defined_indices()` 按 `ContentIndex::get` 升序返回——三个方法签名照抄 `SkillTable` 对应方法即可。mod 若想给自己定义的技能配一套完全自定义的粒子效果，只需要在自己的 `mod.toml`/注册代码里 `define` 一条 `EffectAttrs`,再把这条 `ContentIndex` 填进自己 `SkillDef` 的可选字段——不需要碰任何引擎层代码，这正是「本体即 Mod」在特效系统上的落点：本体自带的技能与 mod 自定义的技能用同一张 `EffectTable`、同一套播放引擎，唯一的区别只是 `id` 里的命名空间字符串不同。

这个结论与 ADR 0018 逐项验证表里"精灵批渲染（`ll-render`）——否，纯工程正确性——引擎层"完全一致：批渲染算法本身不会因为本文档而改变归类，改变归类的只是"每个技能对应哪个 `Clip`"这一条声明式数据。

## 七、阶段归属：属于 P1，边界规则立即生效

规格 §15 阶段表把「渲染与动画」整体列为 **P1**：「wgpu 精灵批处理、图集、混合尺寸精灵、Y 排序、相机、跨接缝绘制」。`anim.rs` 已经落地，属于这一行已交付的部分；但 P1 这一行的字面描述从未明确点名过"一次性特效"与"投射物"这两类,规格里也没有任何后续阶段（P6 物品装备、P7 UI、P8 随从）明确认领过它们。

**如实标注,不代为认领优先级**：这与 `knowledge/design/README.md`「落地状态速览」一节记录的其他几处"未被明确认领"的缺口是同一种模式（例如规格 §15 P5 行记录的 `OverviewCell::explored` 债务：「本行明确写着『本阶段接入』，但……全程未被提及、未被实现、也未被显式记录为推迟」）。本文档同样只如实指出：一次性特效与投射物的动画能力，按内容归类属于 P1「渲染与动画」范围内，但目前既不在已交付清单里，也没有任何阶段显式认领它的实现时间点——留给后续计划作者显式排期,本文档不代为决定它该排进哪一次实施计划。

`EffectDef` 注册表本身依赖的基础设施（`ContentIndex`、注册表 `define`/`get`/列式物化模式）已经在 P4「脚本层与 Mod 框架」完整交付，随时可以补，不受任何未来阶段门槛限制。

**但有一条不受"哪个阶段实现"影响、必须立即生效的规则**：一、二两节确立的「动画绝不能影响结算结果」「回合绝不能等动画播完」这两条铁律，不是本文档新创造的规则——它们是规格 §4 单向数据流架构与 [ADR 0006](../decisions/0006-intent-resolve-effect-apply.md)（`Intent → resolve → Effect → apply`）已经隐含成立的推论，只是此前从未针对"动画"这个具体领域写清楚过。**从本文档冻结的这一刻起，任何未来触碰 `resolve`/`apply`/`Effect` 的改动，都不得引入对渲染层/动画状态的读取或等待**，无论一次性特效与投射物具体在哪个阶段落地实现——这条边界不需要等实现批次到来才生效，因为它约束的是结算层代码不能做什么,而不是表现层代码要做什么,前者现在就可以、也应该被遵守。
