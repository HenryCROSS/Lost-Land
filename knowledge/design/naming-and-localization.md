# 命名、改名与本地化

**冻结于** 2026-08-17。**实现阶段** 命名生成本体已落地（P2/P3 批次）；改名（作为 `Effect`）与 i18n 音素表对齐属于[世界历史生成](world-history.md)同一时期（约 P7，[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P6 顺移为 P7），需要 `WorldId`（见[身份与 ID 空间](identity-and-ids.md)）先落地。

**落地状态**：部分落地。`NamingRules { onsets, nuclei, codas, syllables, surname_first }` 与 `given_name`/`surname`/`full_name` 三个纯函数（`crates/ll-world/src/naming.rs`）已完整落地并有测试覆盖，`hash → 索引 → 取音素表 → 拼接` 的核心机制与本文档描述一致。**以下均未落地**：与「出生地文化」挂钩的裁定（当前 `given_name`/`surname` 只接受调用方直接传入的一份 `NamingRules`，不涉及任何「查文化」的中间步骤，出生地/文化关联需要在调用方拼起来）、i18n 多语言音素表对齐机制、改名 `Effect` 与 `HistoricalEvent`、覆盖名存储、mod 命名钩子与 `tag` 体系。

---

## 一、现状：命名已经是纯函数，先读代码再读本文档

`crates/ll-world/src/naming.rs` 的核心结构：

```rust
pub struct NamingRules {
    pub onsets: Vec<String>,      // 声母表
    pub nuclei: Vec<String>,      // 韵腹表
    pub codas: Vec<String>,       // 韵尾表
    pub syllables: (u8, u8),      // 音节数区间，闭区间
    pub surname_first: bool,      // 姓在前还是名在前
}
```

`given_name`/`surname`/`full_name` 都是纯函数：`hash(种子, 实体/家族 ID) → 音节数 → 逐音节按 rng 取声母/韵腹/韵尾 → 拼接`。零存储，任何时候调用都得到相同结果，同族同姓是姓氏由家族号（而非实体号）派生的直接结果。**这是[0009](../decisions/0009-derive-by-default-store-only-deviation.md)登记的实例之一，且是其中最极端的一例——它甚至不允许偏移，因为「同一个 NPC 永远同名」是设计要求本身，不是性能优化。**

本文档在这个已落地的基础上，往上叠三层此前没有覆盖到的设计：命名依据什么选 `NamingRules`（跟文化，不跟种族）、多语言下同一个人怎样保持「同一个名字」、以及改名怎么发生。**写这三层之前必须先读真实实现，不要凭这份文档的转述去猜代码长什么样**——转述与实现之间总会有落差（一个已知的落差：本文档默认命名会「查文化」，但当前 `given_name` 的签名要求调用方直接给一份 `NamingRules`，查文化这一步不在 `naming.rs` 里，是调用方的责任）。

---

## 二、裁定：命名跟「出生地的文化」走，不跟种族

### 理由

**名字是被取的，不是被继承的**——给一个婴儿取名的是他的父母，父母生活在某个文化里，用那个文化的命名习惯给孩子取名。种族只决定这个孩子长什么样、体质如何，不决定他叫什么。一个被人类家庭收养、在人类聚落长大的矮人孤儿，理应有一个人类名字——这不是特例处理，是命名机制本身的直接推论：他的名字是由抚养他的文化决定的，而不是由他的种族决定的。

这个裁定比「清一色种族命名」更有意思，也更符合真实的命名机制：现实里没有一种语言是「某个种族专属」的，语言随族群的社会归属流转，不随血统流转。

### 零额外成本

[种族系统](race-system.md)「存储」一节已经决定要给薄层新增一列 `birth_settlement: u16`（出生地，用于种族权重现算，防止迁徙后种族随聚落突变）。命名同样需要「出生地属于哪个文化」这个信息——**同一列 `birth_settlement` 同时供两处查询**，种族现算查 `settlement_race_weights[birth_settlement]`，命名现算查 `settlement_culture[birth_settlement].naming`。一列付两笔账，不需要为命名单独再加一个字段。

### 于是两种反直觉的组合都能自然出现

有矮人名字的人类（在矮人聚落长大的人类孤儿）与有人类名字的矮人（前面那个例子）都能在这套规则下自然产生，各自都能讲出一个理由。这不是刻意埋的彩蛋，是「命名依据出生地文化」这条规则运行的直接结果——不需要为这类组合单独编写内容或规则例外。

## 三、i18n 的坑与解法：音素表必须索引对齐

### 坑

中文版与英文版必然是两张不同的音素表（英文用拉丁字母拼音节，中文用汉字或拼音音节）。若两张表各自独立生成，同一个矮人英文名叫 `Thrain`，切到中文版却生成出**完全不相干的另一个名字**——因为两张表各自按自己的长度、自己的顺序被随机索引到，`hash → 索引` 这一步得到的索引即便相同，两张表里同一下标存的音节完全没有对应关系。

后果不止「翻译得不像」这么简单：**玩家切换语言，全世界所有 NPC 都会改名**——这直接破坏种子分享这个设计目标（[世界历史生成](world-history.md)「诚实警告」一节明确要求「种子可分享、结果可复现」）。把种子发给一位用另一种语言客户端的朋友，双方看到的地图、人名、家族姓氏全部对不上，没法互相指认「你说的那个城市」「你遇到的那个 NPC」——种子分享这个功能名存实亡。

### 解法：各语言版本的表长必须相同，同一下标必须是同一个音

同一套 `NamingRules` 有多个语言版本，但**约束表长一致、同一下标对应同一个音**：

```
onsets[7] = "thr"   （英文版）
onsets[7] = "斯"    （中文版）
```

`hash → 7` 这一步与语言完全无关——`DetRng::for_entity` 算出的索引只依赖种子与实体 ID，不依赖当前显示语言。各语言版本只负责把索引 `7` 渲染成自己那套字形，但指向的是同一个「音位」、同一个人。`Thrain` 与 `斯莱因` 因此成为同一个名字的两种转写，这与现实世界翻译人名的方式一致（`Thrain` 音译成中文，而不是重新给这个人起一个毫无关联的中文名）。

### 代价几乎为零，但需要一条校验规则

现有 API（`given_name`/`surname`/`full_name`）**一字不改**——它们本来就只接受一份 `NamingRules` 并纯函数式地产出结果，多语言只是「调用方按当前显示语言选一份对齐好的 `NamingRules`」，不涉及 `naming.rs` 内部逻辑的任何调整。

真正的代价是新增一条**校验规则**：同一套命名规则的各语言版本，`onsets`/`nuclei`/`codas` 三张表的长度必须两两相等。这条校验必须写进 mod 文档，因为若不加约束，mod 作者很可能只顾着给自己熟悉的语言配一张音素表，随手往表里加几个音而不管其他语言版本的表长是否跟着变——这类疏漏在单语言测试下完全不可见，只有切换语言时才会暴露成「这个矮人换了名字」。**建议把表长一致性做成一项 CI 门禁**，在 mod 装载或 CI 构建阶段直接拒绝表长不一致的命名规则集合，而不是留给玩家在游玩时自己发现。

## 四、改名是需要权限的历史事件，不是字段编辑

### 不是字段编辑，是世界中的一个行为

改名走 `Effect` → `apply`（符合[0006 — Intent → resolve → Effect → apply 单向数据流](../decisions/0006-intent-resolve-effect-apply.md)），并产生一条 `HistoricalEvent`（[世界历史生成](world-history.md)「事件日志」一节定义的那类「可被引用」的事件）——这与[装备栏位与占位掩码](equipment-slots.md)「装备是一个 Effect 序列，不是一次原地修改」是同一条纪律在命名系统上的应用：任何看起来像「改一个字段」的操作，只要它在游戏世界里有意义，就应该走意图/效果管线，而不是绕过去直接写值。

### 白送：旧名字被保留

改名事件天然携带「改名前」与「改名后」两个值——「卡拉克，旧称铁砧堡，于第三王朝时更名」这类曾用名描述，不需要额外设计一套「历史名称」存储，它就是 `HistoricalEvent` 记录里本来就有的两个字段。城市可以有曾用名，家族可以有旧姓，都是同一个机制的直接产物。

### 权限从既有归属派生，不需要新的权限系统

| 改什么 | 需要 | 查哪里 |
|---|---|---|
| 自己的名字 | 无条件 | — |
| 家族姓氏 | 家主 | `Kinship` |
| 势力名号 | 统治者 | `Affiliation.standing` + 统治家族 |
| 聚落名 | 控制它 | 征服或统治关系 |

「权限」在这个世界里本来就是「你在组织里的地位」——[社会系统](society-and-affiliation.md)`Affiliation.standing` 正是这个定义本身。改名权限判定因此不需要一套独立的权限系统，只需要在改名 `Effect` 的 `resolve` 阶段读取既有的归属与血缘结构，判断发起者是否满足对应档位的条件。

**NPC 也应该能改名**——征服者攻占一座城池后把它改名，是[世界历史生成](world-history.md)历史推进阶段白送的风味内容：历史生成本来就要模拟战争与征服（见该文档「生成流程七步」第六步），征服事件顺带触发一次改名 `Effect`，不需要为「NPC 改名」单独设计触发时机。

## 五、两类名字，规则不同

| | 存储 | i18n |
|---|---|---|
| **派生名** | 零存储（音素索引现算） | 按语言渲染 |
| **覆盖名** | 一条字面字符串 | **原样显示，不翻译** |

派生名走本文档第一、二节描述的机制——出生地文化 + 确定性哈希，零存储。**覆盖名**是被改名 `Effect` 动过的那一小撮：专名是谁起的就保持谁起的样子，切换显示语言时**原样透传**，不做任何翻译或音译——玩家给自己的城堡起名「铁血堡」，切到英文客户端不应该被机器翻译成 `Iron Blood Castle`，那不是这个名字的原意，是翻译引入的走样。

### 这是「默认派生，只存偏差」的又一次复用

50 万人口的世界里，真正被改过名的大概率只有十几个城市和几个家族——存储成本约等于零，但玩家能感知到的却是「我可以给任何东西改名」这样一个完整功能。这与[0009](../decisions/0009-derive-by-default-store-only-deviation.md)登记的钱包、关系、性格三个实例是同一个思想：默认值零存储现算，真正偏离默认值的极少数才占用一条记录。

## 六、mod 可给生成器挂命名钩子

已批准：mod 可以让「所有海盗势力」使用一套特别的命名规则——不是「海盗文化」这种需要预先注册一整个 `CultureDef` 的重量级机制，而是一个更轻量的、按条件匹配的命名覆盖钩子。这要求生成物（见[身份与 ID 空间](identity-and-ids.md)`OrgInstance`）携带一个**mod 可匹配的标签** `tag`，命名生成器在选择 `NamingRules` 时按标签匹配规则做覆盖。

### 前瞻判断：命名只是第一个例子，钩子体系要与 `WorldId` 一起定

命名钩子不会是 mod 作者唯一想要的介入点——很快就会有人想让「所有海盗势力」偏好特定的初始选址、特定的初始目标（劫掠而非贸易）、甚至想注册自定义的历史事件类型。**与其每加一个特性就临时开一个专属回调点**（一个专门给命名用的钩子、一个专门给选址用的钩子、一个专门给初始目标用的钩子……），**不如把「生成器钩子」这件事一次性设计好**：钩子按什么匹配（标签、类型、区域）、什么时机触发（生成前/生成后/历史推进中）、能读写哪些数据。否则若干版本之后会积累出十几个互不相干、命名各异、行为模式还不一致的回调点，维护成本远高于一次性设计的成本。

**此事不急**——生成器本身还没写，钩子体系的设计可以等到真正实现命名钩子这个具体需求时再展开。但有一件事**现在就要定**：标签体系要与 `WorldId` 一起定（见[身份与 ID 空间](identity-and-ids.md)），因为标签是 `OrgInstance`（实例）的字段之一，`OrgInstance` 的形状一旦定案又要经历一次存档迁移，不宜等钩子体系细节都谈妥了才把标签字段补上去——标签字段本身现在就该在 `OrgInstance` 的设计里占好位置，即便钩子的匹配逻辑还没写。
