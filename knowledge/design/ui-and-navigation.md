## 零、诊断：不像回事的根源不是「不好看」，是三套模态系统互不知情

盘点之前先给结论，否则后面五节的清单会读成一堆互不相干的小毛病。

这个界面是**十几个批次各自加出来的**，每一批都在自己的范围里做了正确的选择。
问题出在**批次之间**：今天屏幕上能盖住东西的模态 UI 有三套，**三套各有各的
开关、各有各的取消键处理、互相不知道对方存在**：

| 模态系统 | 状态住在哪 | 进入 | 退出 | 进入时输入上下文 |
|---|---|---|---|---|
| 模态屏 | `Demo::screen: Option<ScreenState>`（`app.rs:453` 结构体，`menu_screen.rs:60-119` 枚举） | `open_menu`（`app.rs:1088`）等 | `close_screen`（`app.rs:1125`） | 切到 `Menu`/`TextEntry` |
| 玩家菜单 | `Demo::menu: PlayerMenu`（`player_action.rs:160`） | `player_command` 第 ① 步（`player_action.rs:571-604`） | `player_command` 第 ④ 步（`player_action.rs:612-615`） | **不变，仍是 `Gameplay`** |
| 世界地图 | `Demo::world_map_open: bool`（`app.rs:537`） | `GameKey::Map`（`app.rs:785-791`） | **只有 `GameKey::Map`**（`app.rs:791`） | **不变，仍是 `Gameplay`** |

三套系统的存在本身不是错——`player_action.rs:119-127` 对「玩家菜单为什么不进
`InputContext::Menu`」有一段完整论证，它是成立的。**错的是没有任何一处代码同时
认识这三套**，于是：

- Esc 的含义被实现了**两遍**（`app.rs:2703-2708` 与 `player_action.rs:612-615`），
  而世界地图**一遍都没有**——按 Esc 关不掉地图（详见 2.2 节 D3）。
- 「现在有没有东西盖着屏幕」这个问题**没有唯一答案**：`ui_modes` 只知道第一套，
  `input_context()`（`app.rs:2848`）因此在背包开着、地图开着的时候都返回
  `Gameplay`。
- 每加一套新的模态 UI，就要在 `on_frame` 里手工补一条 `&& !xxx.is_open()`
  （`app.rs:2673` 已经有一条，`app.rs:2703-2706` 有两条）。这是一条**每批都会
  多一项、且漏了不报错**的账。

**「更像回事」的第一优先级不是换皮，是把这三套收敛成一套。** 后面的规格（七节）
围绕这一条展开。

> **【2026-08-30 已落地，批次 15】** 上面那张表描述的是**收敛之前**的
> 现状，保留以便追溯。三套现在封在 `crates/ll-game/src/modal.rs` 的
> `Modal` 里（四个私有字段 + 一条配对断言），`Demo` 上只剩一个
> `modal` 字段；`UiMode` 加了 `PlayerMenu` 与 `Overlay` 两个变体，两者
> 仍映射到 `InputContext::Gameplay`。本节列的三条后果（Esc 实现两遍、
> 地图那套一遍没有、每加一套要手工补 `&& !xxx.is_open()`）随之消失：
> 顶层取消判据现在是一条 `modal.is_empty()`。

### 2.2 死路总表

**共九处**，按严重度排序。前五处是真正的死路或陷阱，后四处是「进得去、出来的
地方不对」。

#### D1（**最严重**）转生流程能走到一个会抹掉玩家世界的按钮

`chargen.rs:274-279` 有一段明确的论证：死亡转生时**必须跳过世界配置屏**，因为
「再进一次世界配置屏等于让玩家重新生成一个世界——这局玩过的一切当场被抹掉」。
这段论证是对的，跳过也确实做到了（`chargen.rs:279` 直接去 `SpawnPick`）。

但 `SpawnPick` 的取消目标是**写死的**：

```rust
// crates/ll-game/src/spawn_pick.rs:318-323
if input.was_just_pressed(GameKey::Cancel) {
    return SpawnPickDecision {
        update: SpawnPickUpdate::going(ScreenState::WorldSetup { cursor: 0 }),
```

于是：**死亡 → 角色创建 → 下一步 → 选点屏 → 按一下 Esc → 世界配置屏**——正是那
段注释说「必须跳过」的那块屏。在那里按确认走「生成世界」，`generate_draft_world`
在 `app.rs:1378` 用一个**全新的世界**覆盖 `draft.world`，而 `draft.existing_target`
（老槽位）从头到尾没被清空（`chargen.rs:466-491` 设进去，无人清），于是
`finish_entering_world` 在 `app.rs:1609-1610` 仍然选中老槽位，此后每一次自动
存档、退出存档都把**新世界写在玩家那份老存档上**。

**两次按键，无确认，无提示，进度永久消失。** 这是全表唯一一条会造成数据丢失的。

#### D2 选点屏三个入口共用一个写死的出口

`SpawnPick` 有三个进入点——`app.rs:1380`（从世界配置）、`chargen.rs:279`（转生）、
`save_name.rs:190`（从命名屏退回）——而取消目标只有一个（`spawn_pick.rs:320`）。
**这个问题在同一个代码库里已经被解决过一次**：`Settings` 用
`SettingsOrigin`（`menu_screen.rs:144-176`）记住自己是从哪来的，取消时回
`origin.screen()`（`:678`、`:713`）。选点屏没有照做，而 `SpawnPickUpdate` 结构体
本身就有一个 `next: Option<ScreenState>` 字段（`spawn_pick.rs:220`）能承载它。

#### D3 世界地图开着时按 Esc，开出来的是暂停菜单，而且两块 UI 同时吃方向键

世界地图是 `Demo` 上一个裸 `bool`（`app.rs:537`），**只由 `GameKey::Map` 翻转**
（`app.rs:791`，全仓库仅此一处写入）。它既不是 `ScreenState` 也不是 `PlayerMenu`，
所以 `on_frame` 那条顶层取消判据：

```rust
// crates/ll-game/src/app.rs:2703-2708
if self.screen.is_none()
    && !self.menu.is_open()
    && input.was_just_pressed(ll_platform::input::GameKey::Cancel)
{
    self.open_menu(input);
}
```

在地图开着时**成立**——按 Esc 不关地图，而是在地图上面盖一层暂停菜单。

更糟的是接下来这一帧：`advance`（`app.rs:779`）里，地图的早退判据排在模态屏的
早退判据**前面**——

```rust
// app.rs:820
if self.world_map_open { self.pan_and_zoom_world_map(input); return; }
// app.rs:832（下一道闸门，永远轮不到）
if self.screen.is_some() { return; }
```

于是方向键**同时**被 `update_screen`（菜单光标）与 `pan_and_zoom_world_map`
（地图平移）消费。玩家按一下「下」，菜单光标动一格，地图也跟着滚一格。

#### D4 交互列表按 Esc 一次退两级，与既有裁定「Esc 逐层往回退」直接冲突

方向列表 → 交互列表是**两级**（`player_action.rs:660-666` 从前者进后者）。但取消
键的处理在 `match *menu` **之前**：

```rust
// crates/ll-game/src/player_action.rs:612-615
if input.was_just_pressed(GameKey::Cancel) {
    *menu = PlayerMenu::Closed;
    return PlayerCommand::Idle;
}
```

任何形态一律 `Closed`。玩家在交互列表里发现选错了格子，按 Esc 想退回方向列表
重选——整个菜单没了，得从按空格重来。项目所有者已经裁定的「Esc 逐层往回退」
（`app.rs:2687-2708` 的那段论证）在这里**没有被兑现**。

#### D5 存档列表的光标是装饰品，确认永远读最新那份

```rust
// crates/ll-game/src/app.rs:1757-1762
fn selected_slot(&self) -> Option<crate::save_slot::SaveSlot> {
    // 列表已经按「最近存过的排在最前」排好；本提交只有首页那一条
    // 触发路径，取最近的那一份。存档列表屏（玩家自己挑哪一份）在
    // 下一个提交里接上，届时这里改成读它的光标。
    self.save_slots.first().cloned()
```

那个「下一个提交」没有来。光标该动的都动了——`save_list.rs:74-78` 移动它、
`app.rs:1194` 存住它、`app.rs:2281-2284` 画出它——只有读它的人没接上。玩家把光标
移到第三份、按确认，进的是第一份；而 `app.rs:1648` 之后每一次存档都写进那个错的
槽位。

#### D6 从角色创建按 Esc 回首页不清草稿，转生时会把一整个世界丢在那儿

`chargen.rs:264-266`（Esc）与 `:281`（「返回」行）都直接去 `Title`，**不动
`new_game_draft`**。对比 `back_to_title` 是显式清的（`app.rs:1736`）。后果两条：
玩家选好的种族/性别/职业在下次按「开始游戏」时被 `app.rs:1293-1297` 无条件覆盖；
转生场景下那份草稿**持有一整个 `GameWorld`**（`chargen.rs:390`），回到首页之后再
没有任何路径能回到它，只能从磁盘重新读档。

#### D7 提示语跨屏粘连

`screen_notice` 只在四处被清（`app.rs:1092`/`:1128`/`:1298`/`:1742`），而屏切换那个
漏斗（`app.rs:1238-1252`）**不清**。于是首页那句「没有存档」
（`title_screen.rs:142`）会跟着玩家出现在设置界面上；「你死了」（`app.rs:968`）
会跟到世界配置屏和选点屏。

#### D8 Tab 能开菜单，却关不掉菜单

`GameKey::Menu` 只绑在 `Gameplay` 上下文（`keybind.rs:424`），菜单一开上下文就变
`Menu`，Tab 解析不出任何动作。开关键不对称。

#### D9 任何模态屏开着时截不了图

`GameKey::Screenshot`（F2）同样只绑 `Gameplay`（`keybind.rs:427`）。消费点虽然排在
每帧最前（`app.rs:2661-2663`），但绑定压根解析不出来。而
`crates/ll-platform/src/input.rs:53-56` 明说这个键是「冻结视觉回归基准的入口，不是
调试功能」——**结果所有 UI 屏都进不了视觉回归基准**。

## 三、盘点：布局现状

### 3.1 四种互不相干的定位方式，同住在一个函数里

`build_hud_frame`（`hud/render.rs:277-506`）一个函数里同时用了四套：

| 方式 | 例子 | 随窗口缩放吗 |
|---|---|---|
| 绝对像素、贴边 | 状态栏 `(SCREEN_MARGIN, SCREEN_MARGIN)`（`render.rs:303`） | 否 |
| 相对前一块堆叠 | `stack_below`/`stack_right`（`render.rs:315-320,338,360-365,372,393-395,404`） | 否 |
| 屏幕居中算术 | 弹窗 `(screen_width - ACTION_MENU_WIDTH) * 0.5`（`render.rs:191`）；反馈行（`:491`）；模态屏（`screen/mod.rs:130-131`） | 部分 |
| 屏幕比例 | 世界地图 10% 边距（`render.rs:224-233`） | 是 |

**只有第四种真的跟着窗口走。** 而「居中」这件事被**独立实现了四遍**
（`render.rs:198`、`render.rs:491`、`screen/mod.rs:130-131`、`world_map.rs:243-256`），
「贴右边」被实现了两遍（`render.rs:144`、`render.rs:303`）——
`crates/ll-ui/src/widget/geometry.rs` 里**没有任何**居中或锚定辅助函数，
`geometry.rs:1-12` 明说这是刻意的（「只做 Rect + 堆叠，不做约束求解器」）。

### 3.2 常量分两套，互不知情

`widget/` 里**一个屏幕布局常量都没有**。全部住在两个地方，且两套没有任何共享的
间距刻度：

- HUD 那一套：`render.rs:84` `SCREEN_MARGIN=16`、`:86` `PANEL_GAP=10`、
  `:88` `STATUS_WIDTH=620`、`:90` `CHARACTER_WIDTH=260`、`:92` `INVENTORY_WIDTH=220`、
  `:94` `EQUIPMENT_WIDTH=220`、`:100` `RESOURCE_BAR_WIDTH=300`、
  `:106` `DAY_NIGHT_BAR_WIDTH=610`、`:109` `ACTION_MENU_WIDTH=360`、
  `:112` `FEEDBACK_WIDTH=420`、`:114` `FEEDBACK_BOTTOM_MARGIN=48`。
- 模态屏那一套：`screen/mod.rs:54` `SCREEN_LINE_HEIGHT=18`、`:56` `SCREEN_PADDING=10`、
  `:58` `SCREEN_FONT_SIZE=14`、`:62` `SCREEN_WIDTH=520`。

**三处已经因此对不齐**：

1. 状态栏 620 宽，正下方的昼夜条 610 宽（`render.rs:106` 的算式
   `RESOURCE_BAR_WIDTH * 2.0 + PANEL_GAP` 恰好差 10），而 `:104-105` 的注释声称
   它们「读起来是对齐的一列」。**没有任何测试盯着这条**。
2. 经验条与角色面板之间的间距是一个裸字面量 `4.0`（`render.rs:395`），全 HUD 唯一
   一处不走 `PANEL_GAP` 的间距。
3. `hud/mod.rs:42` 的模块文档说面板坐标住在「各面板模块的 `DEFAULT_*` 常量」里。
   **那些常量不存在**——四个面板模块一个像素常量都没定义，全在 `hud/render.rs`。
   文档过期。

### 3.3 一个会在重构时咬人的参数错位

```rust
// crates/ll-ui/src/hud/render.rs:404
let inventory_origin = bar_rect.stack_below(PANEL_GAP, INVENTORY_WIDTH).origin();
```

`stack_below(gap, height)` 的第二个参数是**高度**（`geometry.rs:60-62`），这里传的
是一个**宽度**常量。今天无害，因为紧跟的 `.origin()` 把高度扔了。哪天有人保留这个
`Rect`，就会拿到一条 220 像素高的条。

### 3.4 面板高度按「标签数」算，不是按「渲染出几行」算

`widget/list.rs:44-51` 的 `RowCursor::push` 每压一个 `Label` 就把 `cursor_y` 加一个
固定 `row_height`；`hud/mod.rs:121` 与 `screen/mod.rs:196` 都用这个游标反推面板
高度。**只要有一个标签发生换行，第二行就正好画在下一行的位置上，而面板背景矮了
一行。** 这不是推测——`load_report_view.rs:199-201` 已经记录过这个缺陷真实发生过，
并打了一个按字符数截断的补丁（`:210` `PANEL_MESSAGE_MAX_CHARS=44`），**那个补丁是
`load_report_view` 私有的，`hud/` 和 `screen/` 一行都用不上**。

## 四、盘点：输入约定的一致性

八处不一致，全部有 `文件:行号`。

### I1 Esc 有五种含义

| 屏 | Esc 做什么 | 出处 |
|---|---|---|
| 首页 | **什么都不做** | `title_screen.rs:126-134` |
| 游戏内菜单 | 关掉模态、回到世界（不是「回上一级」） | `pause_menu.rs:113-115` |
| 设置 / 世界配置 / 命名 / 存档列表 | 回上一级 | `menu_screen.rs:677`、`world_setup.rs:175`、`save_name.rs:186`、`save_list.rs:63` |
| 角色创建 | **直接跳回根**（首页），丢掉草稿 | `chargen.rs:264-266` |
| 选点屏 | 去一块**可能从没去过**的屏 | `spawn_pick.rs:318-323`（D1/D2） |
| 世界地图 | **开出暂停菜单** | `app.rs:2703-2708`（D3） |
| 玩家菜单 | 一次关到底 | `player_action.rs:612-615`（D4） |

### I2 确认键的物理按键随上下文变，而玩家菜单落在「错误」的那一边

`Gameplay` 里 `Confirm` 只绑 Enter（`keybind.rs:414`），空格是 `Interact`（`:422`）；
`Menu` 里 Enter **和空格**都是 `Confirm`（`:512-523`）；`TextEntry` 里只有 Enter
（`:544-549`），空格是一个字符（`:532-542`）。

问题在于**背包/制作/交互列表跑在 `Gameplay` 上下文**（`player_action.rs:119-127`
的裁定）。于是同样是「一个带光标的列表」，在模态屏里按空格能确认，在背包里按空格
不但不确认、还会去开交互列表（`player_action.rs:588`）。

### I3 左右键有四种含义

焦点移动（首页/菜单，`focus.rs:97-102`）；改数值（设置 `menu_screen.rs:743-755`、
角色创建 `chargen.rs:245-259`、世界配置 `world_setup.rs:150-157`）；移动地图光标
（选点屏 `spawn_pick.rs:295-302`）；什么都不做（存档列表、命名屏）。

### I4 上下键在一半的屏里循环，另一半到头就停

循环：首页/菜单（`focus.rs:73-77`）、设置（`menu_screen.rs:733-738`）、存档列表
（`save_list.rs:74-78`）。到头即停：角色创建（`chargen.rs:208-220`）、世界配置、
选点屏（`spawn_pick.rs:192-201`）。**两边都在注释里写着这是刻意的**，而它们互相
矛盾。

### I5 长按在一半的屏里连发，另一半不连发

`was_activated`（连发）：首页/菜单/设置（`menu_screen.rs:726-728`）。
`was_just_pressed`（不连发）：角色创建、世界配置、存档列表、选点屏。后果：24 行的
设置列表能长按滚，9 行的世界配置列表不能。

### I6 两套选中模型并存，其中一套「一开始什么都没选中」

**【2026-08-30 已修，批次 15】** 下面这一段描述的是修改前的现状，保留
以便追溯。首页与游戏内菜单现在一进屏就预选第 0 行（规格 N10，所有者
2026-08-29 裁定），`app.rs` 里那段「刻意不预置」的论证**重写保留**在
`Demo::open_menu` 的文档里（连同它作废的理由），不是删掉——过期的论证
删掉就没人知道它为什么曾经成立、又为什么不再成立。

首页与游戏内菜单用 `WidgetStateTable` 焦点，**刻意不预置焦点**
（`menu_screen.rs:409-413` 返回 `usize::MAX`，`app.rs:1094` 注释写明理由）：玩家不
先按一下方向键，按确认什么都不会发生（`title_screen.rs:153`、
`pause_menu.rs:121-125`）。其余七块屏用普通 `usize` 光标从 0 开始，第 0 行天然
选中，按确认立刻触发。

**这条对新玩家的伤害最直接**：进游戏第一眼是首页，第一反应是按 Enter，
**什么都不发生**。

### I7 在「数值行」上按确认，三块屏三种行为

设置屏把它当「把这个值往前推一档」（`menu_screen.rs:719-722`）；角色创建
（`chargen.rs:284`）与世界配置（`world_setup.rs:184`）刻意做成空操作，且
`chargen.rs:282-283` 有注释说明这是有意的。

### I8 一条挡不住任何东西的断言

```rust
// crates/ll-ui/src/hud/action_menu.rs:252-255
fn 两种前缀等宽以免整列文字随光标抖动() {
    assert_eq!(CURSOR_PREFIX.chars().count(), IDLE_PREFIX.chars().count());
}
```

`screen/mod.rs:69-71` 的文档说这两个前缀「**等宽**，否则整列文字会随光标抖动」。
断言比的却是**字符数**。在思源黑体这样的比例字体里 `"> "` = 10.91px、`"  "` =
6.27px，**光标每移动一行，其余每一行的文字都横移 4.64 像素**——正是那句注释说要
防住的抖动，而这条断言按 ADR 0018 的标准是改坏了也不会红的。

## 五、盘点：层级

`UiLayer` 是刚落地的（`layer.rs:68-78`）。**四层内部的归属全部正确**，逐条核实：

| 元素 | 实际层 | 应该在的层 | 结论 |
|---|---|---|---|
| 状态栏/血条/法力条/昼夜条/角色/经验/背包/装备面板 | `Hud`（`render.rs:301`） | `Hud` | 对 |
| 世界地图 | `Overlay`（`render.rs:450`） | `Overlay` | 对 |
| 交互/背包/制作弹窗 | `Popup`（`render.rs:479`） | `Popup` | 对 |
| 反馈行 | `Notice`（`render.rs:498`） | `Notice` | 对 |

**问题不在选错层，在于两块最该被层管住的东西根本不在层里：**

1. **模态屏（第 24 块）完全不走 `LayeredFrame`。** `screen/render.rs:36-38` 说明了
   理由——「套一层层级只会多出三个永远为空的层」——这个理由在**只看模态屏自己**时
   成立。代价是它与 HUD 的前后关系**只由调用顺序保证**（`app.rs` 先 `draw_hud` 再
   `draw_screen`），没有任何结构性约束。D3 那个「暂停菜单盖在世界地图上、两者同时
   吃输入」的缺陷，正是「地图在 `Overlay` 层、菜单在层之外」这条裂缝的可见后果。
2. **装载报告视图（第 25 块）早于层级系统，同样在层外。**

另有一条层内的既有限制值得记进规格：`layer.rs:104-112` 说明**同一层内纯色永远被
贴图盖住**（两个 pass 无法交错），所以同层里两个会重叠的元素必须放进同一个容器才
轮得到压入顺序说话。

## 六、规格 B1：布局系统

### 6.1 先纠正一条前提：这一层用 `f32` 是对的，ADR 0002 管不到这里

本批次的任务书写着「整数坐标（这个仓库全项目整数纪律，见 ADR 0002）」。
**核实结果：这条前提不成立，不能照着做。**

ADR 0002 的标题是「**世界状态**一律用整数」，正文原话：「浮点只允许出现在渲染层与
音频层，且结果绝不得回流入世界状态。」而 `widget/geometry.rs:18-28` 的 `Rect` 四个
字段全是 `f32`，`quad.rs`/`label.rs`/`ll-text` 整条链路也都是 `f32`——这不是违规，
这正是 ADR 0002 允许的那一半。`animation-and-vfx-boundary.md` 对同一条边界有更细的
论证（「甲区」纯表现层可以用浮点）。

**把 UI 布局改成整数坐标是一次没有收益的大改**：它要改 `Rect`、`QuadInstance`、
`TextRun` 三条链路，而 `ll-text` 的字形推进本身就是分数（思源黑体 1000 upm，ASCII
`i` 在 14px 下推进 3.85px），到边界上还是要转回浮点。

**规格采纳的是像素风真正需要的那一条**：

> **规则 L0（P1）**：布局计算用 `f32`，**但每一个进入 `QuadInstance` 的矩形边界与
> 每一个 `Label` 原点，在提交前做一次 `round()` 取整**。像素画糊掉的原因是半像素
> 边界，不是浮点本身。
>
> **落点**：`crates/ll-ui/src/widget/geometry.rs` 新增
> `Rect::snap(&self) -> Rect`；在 `panel_quads`（`panel.rs:110`）/
> `textured_panel_quads`（`:130`）与 `RowCursor::push`（`list.rs:42`）里各调一次。
>
> **判据**：新增测试——对任意非整数 `Rect`，`panel_quads` 产出的九块矩形的
> `x`/`y`/`right()`/`bottom()` 全部满足 `v.fract() == 0.0`；且相邻两块之间**没有
> 缝隙也没有重叠**（`round` 之后角块的右边界必须恰等于边块的左边界）。

### 6.2 屏幕分区：三个区，边界写死

> **规则 L1（P1）**：屏幕划成三个区，任何新面板必须声明自己属于哪一个。

| 区 | 归谁 | 定位方式 | 层 |
|---|---|---|---|
| **常驻区** | 状态栏、资源条、昼夜条、角色/背包/装备面板 | 贴边锚定 + 纵向堆叠 | `Hud` |
| **浮层区** | 世界地图、交互/背包/制作弹窗、反馈行 | 相对**常驻区之外的空白**居中或贴边 | `Overlay`/`Popup`/`Notice` |
| **模态区** | 九块 `ScreenState` 屏 | 整屏压暗 + 居中面板 | 新增 `UiLayer::Modal`（见 7.5 N9） |

**留白规则**：常驻区左列（角色/背包面板，x 起点 `SCREEN_MARGIN`）与右列（装备
面板，右对齐）之间的中段**永远不放常驻元素**——那是玩家看世界的地方，也是浮层区
居中时唯一不会挡住角色的落点。今天这条是巧合成立的，规格把它变成约束。

> **判据**：新增测试，在 1280×720 与 1920×1080 两个尺寸下调用 `build_hud_frame`，
> 断言所有 `Hud` 层矩形要么 `right() <= 屏宽/2` 要么 `x >= 屏宽/2`，中段无常驻元素。

### 6.3 锚点与边距：一套刻度，一个辅助函数

> **规则 L2（P1）**：把四遍居中、两遍贴边收敛成一个函数。
>
> **落点**：`crates/ll-ui/src/widget/geometry.rs` 新增
> ```rust
> pub enum Anchor { TopLeft, TopRight, TopCenter, Center, BottomCenter }
> impl Rect {
>     pub fn anchored(screen: (f32, f32), anchor: Anchor,
>                     size: (f32, f32), margin: f32) -> Rect;
> }
> ```
> 改写 `render.rs:144`（装备贴右）、`:191-199`（弹窗居中）、`:491`（反馈行）、
> `screen/mod.rs:130-131`（模态屏居中）四处。
>
> **这不违反 ADR 0021**：这里有一个**真正可共享的算法**——「已知屏幕尺寸、锚点、
> 自身尺寸、边距，求原点」——今天被抄了四遍且四遍在边界钳制上各不相同
> （`render.rs:491` 对 y 做了 `.max(0.0)`，`render.rs:144` 和 `:198` 刻意不钳，
> 三处没有任何一处说明为什么不同）。ADR 0021 拦的是「形状对称就抽象」，不是这个。
>
> **判据**：`anchored` 的属性测试（任意屏幕尺寸/尺寸/边距下，`TopRight` 的
> `right() == 屏宽 - margin`，`Center` 的中心与屏幕中心差 < 1px）；四处改写点各留
> 一条「改写前后逐像素相同」的回归断言。

> **规则 L3（P2）**：间距刻度统一成 `SCREEN_MARGIN=16` / `PANEL_GAP=10` 两档，
> 消灭 `render.rs:395` 那个裸 `4.0` 与 `render.rs:192` 那个未命名的
> `SCREEN_MARGIN + PANEL_GAP`。模态屏那套（`SCREEN_PADDING=10`）与 HUD 那套
> （`DEFAULT_PADDING=6`）合并成一个 `PANEL_PADDING`。
>
> **判据**：布局表达式里不再出现未命名的像素字面量（颜色分量与比例除外）。

### 6.4 面板尺寸怎么定

### 7.9 鼠标与按钮：四条新约定

**所有者裁定**（2026-08-29，交接文档第〇之二节第 1 条原话）：

> 「我觉得应该要预选一项，同时我希望能有按钮选项，鼠标点击也有反应。」

前半是 N10。后半是**增量**——`widget/hit_test.rs`、光标输入、
`widget/button.rs` 在 P7 就已落地，只是新加的那批屏一块都没接上。交接
文档同节「记在案的债」点名：接鼠标会引出「焦点由键盘还是指针驱动」
「hover 要不要改变焦点」这类新约定，**落地批次要一并定**。

以下四条已于批次 15 落地，代码文档在 `crates/ll-game/src/pointer.rs`。

> **M1 指针悬停不改变键盘焦点。** 划过一行只画一块淡一档的高亮，焦点
> 不动。
>
> **理由**：hover 即聚焦会让「键盘走到第 3 项、手碰了下鼠标、焦点跳回
> 第 1 项」——玩家没做任何操作，选中项却变了。它的代价（「高亮在 A、
> 点击生效在 B」）由 M3 堵住：**按下**那一刻焦点就跳到指针所在行，玩家
> 在触发之前一定先看见高亮跟了过去。
> `widget/state.rs` 的 `WidgetState` 本来就是 `hovered` 与 `focused`
> 两个独立字段，这条不是新发明的分工。

> **M2 点击落在没有条目的空白上：什么都不做。** 不改焦点、不触发、
> **不关屏**。
>
> **理由**：「点空白关掉模态」会在 N2（取消键只退一层）之外多出第二条
> 退层路径，而在角色创建 / 世界配置这类多步流程上误关一层的代价是玩家
> 白填一遍。这条也是最容易反转的一条。

> **M3 点中的正好是已经聚焦的那一项：照样确认。** 与点别的项完全一样。
>
> **理由**：「按下 = 聚焦，松开 = 确认」是同一个手势的两半。若已聚焦的
> 那项要点两下才生效，玩家的行为就取决于一条他看不见的历史状态。

> **M4 按下与松开必须落在同一行才算一次点击。** 按下在 A、松开在 B 或
> 空白 → 不触发，焦点留在 A。
>
> **理由**：直接沿用 `widget/button.rs` 模块文档「按下与触发」一节已经
> 写死的桌面手感，不发明第二套。

**「按钮选项」怎么落**：模态屏的**每一行本身就是按钮**——可命中、可点击，

### 8.5 规格

> **【2026-08-31 已落地，批次 19】** `ll-text` 新增 `measure` 模块
> （`MeasureText`/`TextMeasurer`/`TextMetrics`），`layout_text` 从此在无 GPU
> 环境里也调得动——这正是「测量 API 已经存在却零调用点」的真实原因：唯一的
> 持有者 `TextRenderer` 要 `wgpu::Device`。`Label` 新增 `max_width` 字段，
> 唯一写入点是 `RowCursor`，其值由 `hud::content_width(面板宽)` /
> `screen::build_screen_panel` 从面板宽度派生。`400.0` 已删除。
>
> **一处与本条规格不同的落地取舍**：规格写「面板构造函数改成先测量再定尺寸」。
> **模态屏照做了**（宽度按内容伸缩，见下方 W3），**六块常驻 HUD 面板没有**——
> 它们的内容（物品名、修正条数）每帧都在变，按内容现算会让面板宽度随玩家捡起
> 一件东西而跳变，而跳变的面板比换行的行更刺眼。HUD 那一侧改的是「断行宽度
> 等于内容宽」+「高度按渲染行数」，长行在面板内换行，不再画到面板外面。
> 这条取舍规格没裁定，取的是最保守、最容易反转的那个。
>
> **W1（P0）面板宽度按内容测量决定，不再猜。**
> `ll-text` 的测量 API **已经存在**（`layout.rs:64`、`render.rs:111`），
> `ll-ui`/`ll-game` **零调用点**。这不是要造新东西，是要把已经造好的接上。
>
> **落点**：`hud/mod.rs` 与 `screen/mod.rs` 的面板构造函数改成先测量再定尺寸；
> `hud/render.rs:709` 那个 `400.0` 删掉，改成传入本面板的**内容宽**。
> **判据**：新增测试，对每块面板取该面板会显示的**全部** i18n 键在 **en 与 zh-CN
> 两种语言下**的最长渲染宽，断言 ≤ 内容宽。O-1、O-6、O-7 会红。

> **【2026-08-31 已落地，批次 19】** `RowCursor::push` 先量再推进；`hud::mod`
> 的 `cursor_y()` 与 `screen::mod` 的面板高度都跟着对。**规格没写、但同一个
> 根因还咬着另一处**：模态屏的**行矩形**此前按 `(i+1) × 行高` 的公式算，
> 那条公式的前提正是「每行恰占一行」——W2 落地后它会与实际位置静悄悄地错开，
> 点击落到隔壁那一行上。行矩形因此改成与行文字同一次游标推进的产物。
>
> **W2（P0）行高按渲染出的行数走，不按标签数走。**
>
> **落点**：`widget/list.rs:44-51` 的 `RowCursor::push` 接收测量结果，
> `cursor_y += 实际行数 × row_height`；`hud/mod.rs:121` 与 `screen/mod.rs:196` 的
> 面板高度随之正确。
> **判据**：构造一个必然换行的标签，断言面板 `rect.height` 覆盖全部渲染行，且下一个
> 标签的 y 不与它重叠。**这条修好，O-1/O-2/O-3 的「压住下一行」就同时消失**——它们
> 是同一个根因。

> **【2026-08-31 部分落地，批次 19】** **模态屏伸缩那一半已经做了**——它是
> F5（P0）的判据，不做 F5 就没有落点。`screen::SCREEN_WIDTH` 从「写死宽度」

> - **截断（否决）**：`load_report_view.rs:212` 已经试过按字符数截，O-9 那条算术

> - **面板伸缩（采纳，用于模态屏）**：模态屏面板宽度今天写死 520，理由是「现算会让

> 解析 TTF（那就是在真相源之外造一份度量副本，本仓库反复付过代价的形状），
> 要么引第三方字体库。Rust 集成测试走的是渲染器自己那条 `layout_text`，零副本，
> 且由 `run_tests.sh` 在 windows 与 ubuntu 两个 target 上各跑一次（只在 ubuntu
> 跑的脚本 job 反而覆盖面更小）。
>
> **判据与规格设想的不同**：规格写「超宽即 fail」。但 W1/W2 落地之后断行宽度
> 恒等于面板内容宽，「渲染宽 ≤ 内容宽」成了 `cosmic-text` 自己保证的恒真命题
> ——**一道永远绿的门禁没有牙**。改成**行数预算**：一行的按钮标签超过一行、
> 一句散文超过两行就红。规格指定的反例（`screen-worldsetup-hint` 的 en 文案
> 加三个词）实跑变红。
>
> **「这张表怎么来」那一条部分不成立**：规格设想 W1 落地后每块面板都会声明
> 自己显示哪些键、门禁复用同一份声明。实际落地里面板**不持有键的清单**——
> `item-*` / `equip_slot-*` / `race-*` 全是经数据表的 `display_name_key` 字段在
> **运行期**解析出来的，没有任何静态调用图给得出这层映射。因此门禁按前缀分类，
> 并做成**两个方向都会红**：有键命中不到规则红（缺一条），有规则匹配不到任何键
> 也红（多一条死规则）。面板内容宽则严格现取（`ll_ui` 的公开常量），门禁里没有
> 任何像素字面量。
>
> **W5（P1）门禁补上英文那一侧。**
> `check_i18n_strings.py` 抓不到英文硬编码（`:57-58` 自陈）。**但比补那个更值的是
> 补一条新门禁**：`scripts/ci/` 新增一个脚本，加载两份 `.ftl`，用 `ll-text` 的度量
> 算出每个 UI 键在两种语言下的渲染宽，与一张「键 → 它会被画进哪块面板」的表比对，
> 超宽即 fail。
>
> **这张表怎么来**：W1 落地后每块面板已经声明了自己会显示哪些键（它要拿来做测量），
> 门禁直接复用同一份声明——**不另抄一份**（抄一份就是本仓库反复付过代价的那个形状：
> 真相源之外的副本迟早分叉）。
> **判据**：把 `screen-worldsetup-hint` 的 en 文案加三个词，门禁必须红。

> **W6（P2）状态栏拆成字段，不再拼成一整行。**
> O-1 的根子是 `status_bar.rs:187-206` 把 6 段翻译拼成**一个** `Label`（`:220` 只压
> 一个）。拆成 6 个独立标签横向排列之后，即使某一段变长也只影响它自己那一格。
> **判据**：`status_bar_panel` 产出的 `Label` 数 ≥ 6；en 下整行宽 ≤ 内容宽。

> **W7（P2）光标前缀改成等宽的判据。**
> I8 那条断言比的是字符数。**落点**：`action_menu.rs:252-255` 改成比渲染宽度；若不
> 等宽，把 `IDLE_PREFIX` 从 `"  "`（两个空格 6.27px）改成一个能与 `"> "`（10.91px）
> 等宽的组合，或者干脆把光标从文字前缀改成一块 `Popup` 层的高亮矩形
> （`action_menu.rs:28-31` 说当时不做高亮是因为「这一层拿不到文本测量」——**W1 落地
> 之后这个前提消失了**）。
> **判据**：断言两个前缀的**渲染宽度**相等；今天这条会红。

## 十一、被否决的方案（记下来，免得后来人再想一遍）

| 方案 | 否决理由 |
|---|---|
| 把 UI 布局改成整数坐标 | ADR 0002 的范围是**世界状态**，明文允许渲染层用浮点。改造要动 `Rect`/`QuadInstance`/`TextRun` 三条链路，而字形推进本身就是分数，边界上还得转回去。真正要的是**提交前取整**（规则 L0），不是全链路整数。 |
| 引入第三方 UI 布局库（flexbox / taffy 之类） | 许可证门禁 + 这个项目刻意无引擎。而且 6.2 那张表只需要「锚点 + 堆叠」两种能力，`Rect::stack_below`/`stack_right`（`geometry.rs:60-68`）已经提供了一半。 |
| 造一个通用的「列表控件」 | ADR 0021：今天九块屏的列表在**光标模型、循环与否、连发与否、左右键含义**四个维度上各不相同，把它们塞进一个控件等于把四个开关做成参数，那不是抽象是伪装。规格改的是**行为一致性**（N10~N12），不是造控件。**行为统一之后**再谈控件才有真正可共享的算法。 |
| 让背包/地图切到 `InputContext::Menu` | 会把 `Gameplay` 那张表整个换掉，I/C/空格在背包里全部解析不出来；`player_action.rs:119-127` 已经论证过。N8 的做法是**只进栈、不换表**。 |
| 按字符数截断超长文案 | `load_report_view.rs:210` 的 `44` 已经证伪：比例字体里 44 个汉字 = 616px，超过它自己 600px 的上限（O-9）。字符数兜不住宽度。 |
| 模态屏面板宽度按内容现算（每帧） | `screen/mod.rs:59-61` 否决过，理由（光标移动导致面板抖）成立。W3 的做法是**进屏时算一次、屏内固定**，绕开那条理由而不是无视它。 |
| 用合成键盘事件跑一遍 UI 流程来验收 | **ADR 0025 明令禁止**，且有真实事故（合成按键泄漏进了协调者与所有者的对话）。本文档全部判据都写成「构造 `InputState`、直接驱动 `update_screen`/`player_command`」——那正是 `app.rs:3341` `frame()`、`app.rs:3986` `走一帧` 这两个既有测试辅助函数在做的事，**不新造范式**。 |
| 加一个「确认要放弃吗」的对话框来堵 D1 | 治标。D1 的根子是「转生流程能走到世界生成」，N6 用一道结构性闸门堵在生成函数入口——**写不出来**比**提醒一下**可靠，与 `SaveHeader` 那次「存档时重算生成期 mod 集合现在编译不过」是同一种解法。 |
| 把 `world_map_open`/`PlayerMenu` 两个字段直接删掉、状态全塞进 `UiModeStack` | 栈只回答「有没有、哪一类」，回答不了「地图视野中心在哪、背包光标停在第几行」。N8 的做法是**栈与状态并存、开关时配对**，并用一条「关掉后栈必空」的断言盯住配对。 |

## 十二、怎么验证（ADR 0025 与 ADR 0018）

**全部判据都必须能在 `cargo test` 里跑，不开窗、不合成按键。** 现成的范式有三个，
照抄即可：

1. `crates/ll-game/src/app.rs:3341` `fn frame(demo, at, keys)`——构造 `InputState`、
   按下若干 `GameKey`、跑一帧。
2. `crates/ll-game/src/app.rs:3986` `fn 走一帧(demo, at, keys) -> FrameOutcome`。
3. `crates/ll-game/src/app.rs:4243` `fn 开到菜单行(demo, target)` / `:4261`
   `开到设置屏` / `:4273` `开到捕获模式`——多步导航的组合子。

**渲染侧**走 `build_hud_frame` / `build_screen_frame` 的纯函数返回值断言
（`hud/render.rs:1648-1680` 已有先例），不截图、不开 GPU。视觉回归基准要等 N13
（F2 在模态上下文可用）落地之后才有意义。

**ADR 0018 的反例验证是硬要求**：本文档每一条判据都标注了「今天会红 / 今天会绿」。
标了「今天会红」的，落地时必须先跑一遍确认它真的红；标了「今天会绿」的（例如 L2
的四处改写回归），必须用故意改坏的方式证明它咬得住。**I8 那条断言是反面教材**——
它比的是字符数而不是宽度，改坏了也不会红，落地 W7 时要把它换掉而不是留着。
