# 坐标系与空间模型：区块、连续地表、离散空间

**冻结于** 2026-08-18，对应提交 `4736bb61333e236e2eae23af06db6d01f88f753c`。

**落地状态**：纯设计，尚无代码。已核实：`crates/` 中没有区块（zone）、`Space`、`Interior`、`SpaceProfile` 的任何实现。现有的连续地表（`crates/ll-world/src/{chunk,generate,noise}.rs`）、FOV（`fov.rs`）、光照（`light.rs`）、相机（`crates/ll-render/src/camera.rs`）均按「整张世界是一张连续瓦片图」的旧模型实现，本文档在此基础上提出替换方案，不修改既有代码。

## 一、为什么要改：现状与它装不下什么

### 现状

`WorldState.terrain: ChunkGrid` 是**一整张连续瓦片图**（环面 512×320，见 `knowledge/decisions/0005-torus-topology-and-integer-noise.md`）。玩家在这张图上连续行走，相机（`ll-render::camera::Camera`）跟随滚动。`chunk.rs` 里的 `CHUNK_SIZE = 32` **只是存储/生成粒度**——32×32 一块是为了避免整张图一次性分配、支持按块惰性生成，与玩法完全无关。这一点极容易与本文档要引入的「区块」概念混淆，见第三节的专门澄清。

### 装不下什么

`knowledge/design/world-history.md` 要求历史生成产出「几十王朝 + 几百望族」「500 年 × 500 聚落」这个量级的聚落分布。现有 512×320 单张图，若按一个聚落需要的活动范围粗估为 64×64 格一块，只有 40 块——连零头都不够。世界历史生成的聚落、势力是在**世界尺度**上生成的聚合量，而现有地图连「世界尺度」这个分辨率都没有，只有「逐格地形」一个分辨率。

### 为什么两级坐标系与它天然契合

聚落、势力在世界尺度上生成，瓦片按需生成——这正是「玩家落地后才从聚落属性派生百万 NPC」（`world-history.md`「白送的三件事」）同一条思路在地形层面的对应物：**世界地图先以粗粒度存在，细节按需实现化**。

### Z 轴的性价比

在现有的「一整张连续图」模型上加 Z，意味着把这张图变成一个三维体——完全不同量级的工程（矮人要塞式挖空/塌方/流体）。而在「世界是一张区块网格，每块地形按需生成」这个模型上加 Z，只是给区块网格加一维索引，**存储与生成的机制不用变**，只是多了一个「哪一层」的维度。这是本文档标题把两件事并列的原因：不是两个独立决定，是同一个模型换档之后 Z 轴几乎白送。

## 二、模型总览

最终模型不是单一的 `(i, j, z)` 三元组寻址，而是**两种性质不同的空间**共用一套统一接口：

| | 地表 `Surface`（`z = 0`） | 地下城 / 洞窟 / 建筑内部 `Interior` |
|---|---|---|
| 地形连续性 | **全局连续无缝**，相机平滑滚动跨区块无接缝 | **各自独立**的一张有界局部图，互不连续 |
| 进入方式 | 走过去，边界不可见 | 显式过渡点（楼梯、坡道、洞口、门） |
| 生成器 | 世界尺度连续噪声场的一个采样窗口 | 洞穴算法 / 房间走廊算法 / 建筑定义，各自独立 |
| 世界地图坐标 | 就是玩家的实际位置 | **锚定**在进入点，内部移动不改变世界地图坐标 |
| 与地表尺寸的关系 | 就是地表本身 | **无关**——内部地图大小由内容决定，不受入口占地限制 |

这不是自相矛盾，而是两类空间的物理性质本就不同：地表是同一张大陆的连续表面，玩家应当能在上面无缝行走；地下城、洞窟、建筑内部本来就是彼此独立的空间（一栋房子的二楼不是它旁边空地上方的「天空」），离散建模才是对的，强行用同一个连续坐标系统一，只会制造「站在空地上按上楼键该发生什么」这类没有答案的伪问题。

第四节给出统一这两类空间的接口形状（`Space`），第五、六节分别展开地表与离散空间各自的设计。

## 三、三个「块」与两个 `(i, j)`，必须先分清楚

这是本文档最容易被读错的地方，专门用一节钉死。

### 三个「块」

| 名称 | 大小 | 是什么 | 谁在用 |
|---|---|---|---|
| **存储块**（既有，`CHUNK_SIZE`） | 32×32 格 | 纯粹的内存分配粒度，不携带任何玩法语义 | `crate::chunk::ChunkGrid` 内部 |
| **区块**（新，本文档称 zone） | 默认 128×128 格（见第五节） | **逻辑单位**：世界地图的一格、流式加载的粒度、聚落归属与 LOD 边界、Z 轴的锚点 | 世界地图、聚落系统、经济系统 LOD、Z 轴过渡 |
| **视口** | 43×25 格（`LOGICAL_WIDTH/TILE_SIZE` 等既有渲染常量算出） | 相机一次能画出来的范围，纯渲染概念 | `ll-render::camera::Camera` |

三者互不相同：存储块是「内存怎么分配」，区块是「世界怎么划分逻辑单位」，视口是「屏幕能看见多少」。**第十节会把「区块 = 4×4 存储块」定为写死的结构性约束**，但这只是二者之间的一个数值对齐关系，不改变它们各自的性质——存储块依然只管分配，区块依然只管逻辑。

### 两个 `(i, j)`

本文档到处出现 `(i, j)`，但实际指两种不同分辨率的坐标，必须区分：

1. **区块坐标**：粗粒度，取值范围是「世界区块数」（默认 128×80，见第五节），回答「我在哪个区块」。
2. **世界瓦片坐标**：细粒度，就是既有 `ll_core::torus::TorusPos`，取值范围是「区块数 × 区块边长」（默认 128×128 = 16,384 × 80×128 = 10,240），回答「我站在哪一格」。

**这两套坐标不需要各自独立存储，是同一个环面的两种分辨率**——区块坐标 = 世界瓦片坐标 ÷ 区块边长（整数除法），纯函数派生，不是第二个真相源。实现上甚至不需要为区块坐标发明新类型：`TorusPos` 本身只是「一对被规范化的 `i32`」，不携带「这是瓦片还是区块」的标签；用同一个类型、喂给它不同的 `TorusSize`（瓦片级或区块级），就分别得到瓦片坐标与区块坐标的语义。这与「默认派生，只存偏差」（`knowledge/design/README.md` 三、贯穿全局的设计原则）是同一个模式的又一个实例，也避免了重新发明一遍 `TorusSize::wrap`/`delta` 这套已经验证过的机制。

## 四、`Space`：统一地表与离散空间的接口

### 为什么不能用单一 `(i, j, z)`

一栋建筑的二楼，和它旁边空地正上方的「z = 1」，不是同一种东西：前者是一个与地表占地无关、可以任意大小的独立房间序列；后者（如果地表真的支持垂直分层）应当仍是连续地表的一部分。硬把两者塞进同一个 `(i, j, z)` 索引，会立刻带出两个没有答案的问题——「站在空地上按上楼键会发生什么」（那格根本没有建筑）、「建筑内部的尺寸是不是被它的地表占地形状限死」（见下文「建筑内部不受占地限制」的裁定，答案是不该限死，但 `(i, j, z)` 这个索引形状本身会诱使实现者假设「每层的边界跟地表一样」）。

### 形状

```rust
pub enum Space {
    /// 露天层。地形来自世界尺度连续噪声场的窗口采样（见五）。
    Surface {
        /// 区块坐标（见三）。
        zone: ZoneCoord,
        /// 预留字段，当前设计下恒为 0——见下方「z 字段为什么保留」。
        z: i8,
        /// 指向注册表的层属性，见七。
        profile: ContentIndex,
    },
    /// 建筑内部 / 地下城 / 洞窟。各自独立生成，与地表占地无关。
    Interior {
        /// 这个空间实例的持久标识，复用既有 WorldId 机制（见下文）。
        id: SpaceId,
        /// 楼层号，允许负数（地下室、地下城更深层）。
        floor: i16,
        /// 锚点：这个空间在世界地图上显示为哪一格。
        anchor: TorusPos,
        /// 指向注册表的层属性，见七。
        profile: ContentIndex,
    },
}
```

两处类型选用需要说明：

- **`ZoneCoord` 就是 `TorusPos`，只是喂给它区块级 `TorusSize`**（见三）。不单独定义新类型。
- **`SpaceId` 复用 `identity-and-ids.md` 已经定案的 `WorldId`**，不发明新 ID 空间。理由：建筑、地下城、洞窟实例与聚落、势力、家族是同一类东西——「世界生成器（或建造玩法）造出来的、没有 mod 注册条目可供反序列化校验、数量随世界规模增长」的实例。`identity-and-ids.md`「类型/实例分离」一节的判据（`ContentIndex` 给类型、`WorldId` 给实例）在这里直接适用：`SpaceProfile` 的注册表条目（本体定义了哪些「空间类型」，见七）走 `ContentIndex`；某一栋具体的房子、某一处具体的地下城入口走 `WorldId`。

**`Surface` 为什么还留一个 `z` 字段**：当前没有任何玩法要求地表本身垂直分层（悬崖多级台地、树屋一类需求不在本次任务范围内）。留这个字段只是给「未来若真的需要贴着地表的多层露天结构」预留一个不需要改枚举形状的扩展口——按本文档「结构性约束 vs 数值」的原则（见十二），这不是现在就要设计的功能，触发条件是「出现具体玩法需求」，届时再决定 `z ≠ 0` 时地形怎么来（大概率仍是「同一张连续噪声场，只是查询时多带一个高度参数」，但这需要那时候的具体需求来定，本文档不预先展开）。

### 锚定关系：单一真相源在哪一侧

**锚点信息只存在 `Interior` 自己身上（`anchor` 字段），不在世界格子那一侧另存一份「这里有哪些空间入口」的列表。**

两个方向的查询都需要——「这个空间在世界的哪」与「这个世界格子上有没有入口」——但只应该有一份权威数据：

- **权威数据**：每个 `Interior` 实例的 `anchor: TorusPos`，与 `Agent.pos` 是同一种字段（实体自己知道自己在哪，不是世界格子记着「谁在我这」）。
- **反向查询**：`TorusPos → Vec<SpaceId>`（「这一格有哪些入口」）**不是第二份存储，是从权威数据现算或缓存的派生视图**。若查询频繁到需要缓存，缓存的更新规则必须是单向的——`Interior.anchor` 变了就重建对应的索引条目，索引本身永远不能被直接修改。

这条纪律不是新发明的，是 `knowledge/decisions/0010-single-source-of-truth-for-daylight.md` 的教训在这里的直接应用：白昼判定曾经因为「同一个概念被独立定义了两次」在四小时窗口内给出相反结论。本项目已经为这类缺陷付过一次代价，`Affiliation.org` 的 `ContentIndex`/`WorldId` 混用是第二次（`identity-and-ids.md` 记录），这里是第三处要提前避免的地方：**锚点只有一个真相源，反向索引是派生视图，不是第二个真相源。**

### 已裁定：建筑内部不受地表占地面积限制

**结论**：`Interior` 是完全独立生成的空间，其地图尺寸与该建筑在地表占据的格数无关。地表 3×3 格的房子，内部可以是 40×40 的大厅。

**收益**：

- 生成器彻底解耦——房间走廊算法不必迁就地表占地形状。
- 小屋与大殿可以用同一套地表表现，内部规模由内容决定而非几何决定。
- 与「空间锚定」模型天然一致：`Interior` 只需要 `{ id, floor, anchor }`，不需要任何与地表几何对账的字段——这正是上面那个形状里没有「footprint」「与地表尺寸的映射关系」这类字段的原因。

**代价（如实写出，不是缺陷，是本模型有意接受的取舍）**：

1. **外观不再是内部规模的线索。** 玩家从外面看不出这栋楼里是储物间还是宫殿——这是真实的信息损失。若某些玩法依赖「远远看见一座大宅就知道值得进去」，需要另找表现手段（招牌、规模等级、地图标注），本文档不代为设计。
2. **窗户不能真的透视到外面。** 内部与地表是两个独立空间，且只渲染当前空间（见九），因此看不到窗外的真实场景。若将来想要「从楼上射箭打街上的敌人」这类内外互见的玩法，本模型做不到，需要专门设计。**这是已知限制，不是本次任务要解决的问题。**
3. **内外一致性只在过渡点成立。** 进出门是唯一的对应关系，其余部分内外互不参照。

**重新评估的触发条件**：若未来确实需要内外互见的攻防玩法（代价 2），或「外观即内容线索」成为核心体验诉求（代价 1），需要回到这条裁定重新评估——但那是全新的设计任务，不在本文档范围内。

## 五、地表 `z = 0`：连续无缝 + 流式加载

### 核心机制：全局连续噪声场的窗口采样

**地表不是「每个区块各自生成一张图」，而是整个世界共享同一张连续噪声场，区块只是这张场的一个采样窗口。** 区块 `(i, j)` 的地形 = 对世界瓦片坐标区间 `[i·W, (i+1)·W) × [j·H, (j+1)·H)`（`W`/`H` 为区块边长）逐格采样这张全局场。连续性由采样方式本身保证，不需要任何拼接步骤——相邻区块只是同一张连续场里相邻的两个窗口，天然首尾相接。

**这一点在现有 `crates/ll-world/src/generate.rs` 的实现下已经成立，核实结论如下**：

- `terrain_at_coord(noise, params, x, y)`（`generate.rs:98`）接受的是**未经环绕的原始整数坐标**，对每个坐标独立求值，不依赖「正在生成整张图」这个上下文——这正是为了支撑该文件末尾接缝测试而刻意保留的接口形状（模块文档：「接缝测试需要比较 `x = 0` 与 `x = world.width()` 这两个坐标」）。窗口化调用（只对某个区块的窗口范围调用它，而不是对整张世界的双重循环）不需要改这个函数一行。
- `build_noise`（`generate.rs:77`）只依赖世界总尺寸构造一次 `TileableNoise`，是 O(1) 操作，不遍历——可以在世界创建时构造一次，此后所有区块窗口共用同一个噪声源实例。
- 无缝性是 `TileableNoise` 的**构造性质**（格点索引对周期取模，见 `noise.rs` 模块文档「用模格点而非 4D 投影」一节），不是「先生成整图、事后检查边界对不对」这种可能因切分方式改变的近似性质。`0005` 的实测结论——「接缝比世界内部还平缓」——是这条构造性质的直接推论：切多大的窗口来采样，都不会在窗口边界引入新的不连续，因为不连续从一开始就不存在，切分是外部强加的观察窗口，不是生成过程的一部分。

**差距**：`generate_terrain`（`generate.rs:56`）当前是「一次性构造整张 `ChunkGrid` 并双重循环遍历整个世界写入」的接口，不是「按需对单个区块窗口求值」的接口。真正做到按区块流式生成，需要把这个函数拆开——`build_noise` 与 `terrain_at_coord` 已经是分离的、可独立复用的两步（前者构造一次，后者按坐标现算），这不是巧合，是原实现为了让接缝测试能绕过 `ChunkGrid` 直接调用而已经做的拆分。**这是一次调用方式的重构，不是算法重新设计。**

### 区块大小：128×128，论证

三个约束共同决定这个数：

1. **必须是 `CELL_SIZE`（16）的整数倍。** 这不是「区块大小恰好满足约束」，而是一个更强的结构性理由：只要区块边长本身是 16 的倍数，**世界总瓦片尺寸（区块边长 × 区块数）对任意区块数量都自动是 16 的倍数**——不再需要像旧模型那样在「选定世界总尺寸」这一步单独校验整除性。约束从「作用在一个会变的总量上」收窄成「只作用在一个固定的配置参数上」，这是把约束往前挪到更早、更稳定的位置，减少后续每次调整世界区块数时都要重新校验的负担。
2. **必须是 `CHUNK_SIZE`（32）的整数倍。** 见第十节「甲案」——这是写死的对齐约束，128 = 4 × 32。
3. **需要显著大于视口（43×25），给流式加载留出缓冲。** 128 / 43 ≈ 3 屏宽、128 / 25 ≈ 5 屏高——玩家在一个区块内部能走好几屏才会触及边界，边界生成有充裕的时间窗口完成，不会出现「走两步就要等加载」的体验。

128 同时满足三条，且是 2 的幂，区块坐标与世界瓦片坐标之间的换算（`÷128`、`%128`）可以用移位与掩码而非除法/取模实现。**这是配置数值，不是结构约束**——256×256 同样满足全部三条（见第十节内存论证），只是缓冲更宽、常驻内存略高。当前无法给出「128 一定优于 256」的量化证据，只能说 128 已经充分满足约束，且更保守（同样条件下常驻集合更小）。

### 常驻集合与 LRU

**结论：区块-层（某个区块在某个 z/floor 上的一份具体地形数据）常驻上限 256 个，超出按 LRU 淘汰。**

**内存核实**：`TerrainKind`（`crates/ll-world/src/terrain.rs:31`）是 `pub struct TerrainKind(pub u16)`，2 字节。一个 128×128 区块-层 = 128×128×2 = 32,768 字节 = 32 KiB。256 个常驻上限 = 256×32 KiB = 8,192 KiB = **8 MiB**。即便区块放大到 256×256（128 KiB/份），256 个上限也只是 32 MiB。这两个数字都已核实与项目所有者给出的估算一致。

**地形之外，一个常驻区块-层还需要携带什么**：

- **光照**：不需要。`ll_world::light::ambient_light` 明确「绝不进世界状态」，是纯函数现算，不缓存——不给常驻区块-层增加任何字节。
- **探索记忆（战争迷雾）**：当前 `WorldState` 完全没有这个概念（`overview.rs` 模块文档：`explored` 恒为真），`knowledge/handoff/p2-to-p3.md` 记它是 P5 的债务项。真正落地后，若按每格一比特实现，一个区块-层的探索记忆 = 128×128 bit = 2,048 字节 = 2 KiB，约为地形本身的 6%，量级上不改变上面的结论。这是未来要补的字段，不是本文档的设计范围。
- **实体**：**这才是真正会涨的部分，也是这个 256 上限存在的真正理由**——见下方专门说明。

**这个上限主要是为了限制模拟量，不是为了省地形内存**：地形本身即便按 8 MiB/256 个的量级计算，在现代机器上完全可以忽略。真正昂贵的是「这个区块-层里有多少实体在跑真实决策」——只有落在**常驻**区块-层范围内的实体才可能进入 `agent-goals-and-economy.md` §七之二定义的「前景层」（跑真实 AI 决策），常驻集合之外的实体一律走批量公式。**256 这个数字的作用是给「同时可能处于前景层的实体」画一条空间边界**，与既有的 NPC 棘轮问题解法（「被记住」可以是几百万份、「被模拟」必须有界，见同一文档）是同一条纪律在空间维度上的具体化，不是两套独立机制。**若后人为了「省内存」把这个数字调小，实际上是在收紧模拟预算而不是省内存——这条区分必须写清楚，否则这个数字的用途会被误解。**

**常驻集合的构成**：

1. **玩家周围的邻域**——推荐 **5×5**（25 个区块-层）而非 3×3。3×3（9 个）只够保证「玩家当前所在区块的八个相邻区块已就绪」这个下限，一旦玩家跨过边界、新暴露出的边缘区块必须立刻可见，完全没有缓冲时间；5×5 在跨过一次边界之后仍有整整一圈已就绪的区块作为下一次跨界的缓冲，能从容吸收后台异步生成的延迟，不需要精确调校「提前多少格开始生成」这类脆弱的阈值。7×7（49 个）能进一步加宽这个缓冲，但收益边际递减，除非未来出现明显快于步行的移动手段（坐骑、传送），本文档不预先加宽，需要时它仍在 256 的预算内轻松放大。
2. **当前所在建筑/地下城的全部层**——`Interior` 一旦进入就应整体常驻（内部地图通常不需要像地表那样流式滚动，见第六节）。
3. **最近访问过的**——补足到 256 上限，最久未访问者优先淘汰，与既有 NPC 重定基准机制用的是同一种 LRU 思路。

25（邻域）＋ 少量 Interior 层 ＋ LRU 补足，256 的预算留有充裕余量。

### 对齐关系：区块与存储块

见第十节「已裁定：区块 = 4×4 存储块」——这条决定需要与本节的区块大小一起读，故只在此处提示交叉引用，具体论证与被否决方案放在第十节，避免本节被拉得过长。

## 六、离散空间：`Interior`

### 为什么不做真三维（Caves of Qud 参照）

每层是各自独立的一张 2D 图，靠楼梯/坡道/洞口等显式过渡点连接，不做矮人要塞式的真三维体积。真三维会把一堆没人要求的东西一起拖进来——水要流、物件要掉、挖空要塌方，每一样都是独立的大工程。而「二楼三楼、地窖、地下城、洞窟」这些真实需求，离散层全部能满足，不需要额外的体积模拟。

### 稀疏性：拆成两条

第四节已经说明 `Surface` 的 `z` 字段当前恒为 0——这意味着「层是稀疏的」这条原本笼统的规则，现在要拆成两个真正独立的稀疏维度：

**① `Surface` 的 `z` 维度**：当前设计下这一维平凡地不需要稀疏索引——只有 `z = 0` 一个取值存在，不需要为「不存在的 z」预留或校验任何东西。存储上，区块-层直接按区块坐标 `(i, j)` 索引即可，不需要额外套一层 `z` 的稀疏映射。**若未来真的启用 `Surface` 的多 z（见第四节「z 字段为什么保留」），届时需要为这一维补一层与下面 `Interior` 同构的稀疏索引，本文档现在不预先设计。**

**② `Interior` 的存在性稀疏**：这才是真正需要稀疏存储的地方。绝大多数世界瓦片坐标上没有任何 `Interior` 锚定；有锚定的地方对应一个或多个 `Interior` 实例（一栋楼可能同时有自己的地窖，两者是不同的 `SpaceId`，共享同一个 `anchor`）。存储形状：

```
Interior 实例本身：按 SpaceId（复用 WorldId）索引的稀疏表，
                    数量与聚落/建筑同量级（几百到几千，参考
                    world-history.md「约一万五千名历史人物」的量级）
每个 Interior 内部的楼层：HashMap<floor, FloorGrid>，按需生成/持久化，
                    一栋楼可能只有 {0, 1, 2, -1} 四个 floor，不为
                    未使用的楼层号付任何存储代价
反向索引（世界格子 → 入口）：从上面的权威数据现算或缓存的派生视图，
                    见四「锚定关系」一节，不是独立存储
```

**内存量级对比（说明「为什么必须稀疏，不能稠密」，非精确预测）**：若改用稠密三维数组——即每个区块都为 `-32..=8` 全部 41 个可能的 z 值各分配一份区块-层（对 `Surface` 而言这个假设本身已经不成立，但作为「如果当初做成稠密数组会付出什么代价」的反例仍然成立，这里借用旧模型「向下 32 层向上 8 层」的深度假设来量化）——世界默认 128×80 = 10,240 个区块 × 41 个 z 值 = 419,840 个槽位，每份 32 KiB，合计 **≈ 12.8 GiB**。

按一个粗略假设估算稀疏方案的实际占用：假设约 5%（512 个）区块是「特殊」区块（聚落或地下城入口），平均每个额外挂 5 层（例如小镇 2～3 层建筑 + 1～2 层地窖，或一个中等地下城），则占用槽位 ≈ 512×5 = 2,560 个（`Surface` 本身按需流式加载，不计入这个「结构性存在」的比较，见五「常驻集合」一节对流式加载的单独说明）。2,560 × 32 KiB ≈ **80 MiB**。

12.8 GiB 对 80 MiB，约 **160 倍**的差距——这组数字全部基于上面明确标注的假设（5% 特殊区块、平均 5 层），不是精确预测，但足以说明稠密方案在这个量级下不可接受，稀疏是唯一现实的选择。**这与第五节「常驻集合 256 个上限、8 MiB」是两个不同的问题**：本节比较的是「世界模型要不要为不存在的层预留结构性存储槽位」（存档/索引层面），第五节讨论的是「同一时刻内存里实际驻留多少份」（运行时流式加载层面）——两者都要稀疏/惰性，但不是同一件事，处理机制也不同（前者是数据结构选型，后者是 LRU 淘汰）。

### 环面在 i/j 上闭合，z 不闭合——这条规则现在归属哪

这条规则原本笼统地作用在「区块坐标」上，现在精确到：**区块坐标（`ZoneCoord`）本身构成一个环面**（世界区块数默认 128×80，向东/向南走到头会绕回西/北）——这是第三节已经说明的「区块坐标是世界瓦片坐标除以区块边长」这个派生关系的直接推论，瓦片坐标本身环绕，商自然也环绕。**`Interior` 的 `floor` 字段则明确不环绕**——`floor` 从某个入口层出发向上/向下延伸，有顶有底（由具体建筑/地下城的生成内容决定，不是一个全局统一的上下限），走到最底层不会绕回最高层。这条边界必须写死并解释：否则会有人「顺手」让 `floor` 也环绕，导致从地下城最深处一层电梯坐回天空。

### 生成器与内容注册表的接口

不同空间用不同生成器：`Surface` 来自世界尺度连续噪声（见五）；洞窟走洞穴算法；地下城走房间走廊算法；建筑内部由建筑定义。这正好接上 P4 的内容注册表——生成器本身可以是注册的内容，`Space.profile: ContentIndex` 已经在第四节的形状里体现了这一点（层的属性走注册表），生成器的选择同理：一个 `SpaceProfile`（或与之配套的一张生成器注册表）可以携带「这个空间类型用哪个已注册的生成函数」这条信息，mod 可以注册新的生成器（例如「深渊层」用一个 mod 自带的算法），本体的洞穴/房间走廊生成器与 mod 生成器走同一条注册路径——这与规格「本体即 Mod」的一贯纪律一致。

**这个接口设想目前只能停在「形状」层面，不能给出实现细节**：正在开发中的 `docs/superpowers/plans/2026-08-18-p4-script-and-mod.md`（P4 脚本层与 Mod 框架计划）已经明确了内容注册表的通用模式——第一档静态声明（mod 装载时用类似 `(register-terrain "lostland:mountain" ...)` 的调用产出数据）、物化成按 `ContentIndex` 索引的平铺 Rust 结构（`Registry`）、注册期可完整校验（该计划「任务 8：`TerrainKind` 迁入注册表」是这个模式第一次真正落地的例子）。`SpaceProfile` 与「空间生成器」应当走同一条模式——这与项目所有者提到的「裁定 P4-4 与 P4-5」在内容与做法上完全对得上，**但本文档核实时未能在仓库中找到「P4-4」「P4-5」这两个具体编号的落点**（该计划文档本身没有用这两个编号标注任何决定，也没有找到其他记录这两个编号的文件）——本文档因此只引用能在仓库里核实到的具体依据（上述计划文档的「注册期/运行期分界线」与「任务 8」两节），不代为断言这两个编号具体指向哪一条裁定。若这两个编号确有出处但尚未落进本仓库，后续需要补一条交叉引用；若编号本身尚未正式记录，这里的引用可以在它被记录后回填。

### `compute_fov` 是否真能原样复用：核实结论

**算法本身可以一行不改直接复用**：`compute_fov`（`crates/ll-world/src/fov.rs:119`）的核心——`scan_octant`/`scan_row_in_sector`/`Slope` 比较——是纯粹的几何阴影投射算法，只通过 `grid.terrain_at(pos)` 读地形、通过 `world.wrap`/`world.squared_euclidean` 做坐标运算，完全不感知「这是环面世界地图还是一张有界局部地图」这个上下文，也完全不感知种族/暗视（`race-system.md`「暗视」一节已经确认这一点：暗视的介入点在光照输入，不在 FOV 本身）。**加上本次已裁定「只渲染当前层、FOV 严格按层计算、不跨层」（见九），FOV 的调用范围进一步收窄到「只在当前这一个 `Space` 内部求值」，算法逻辑不需要为跨层场景增加任何分支。**

**但它现在吃的入参类型需要一个新变体**：`compute_fov` 接受 `&ChunkGrid`，而 `ChunkGrid`（`chunk.rs`）内部绑定的是 `TorusSize`——环面语义。这对 `Surface`（本身就是环面的一部分）没有问题；但对 `Interior`（有界、不环绕的局部地图，`ll_core::torus` 模块文档本身也写明「进入具体区域后的分区场景是有界局部地图……不做环绕」）是一处不匹配：若直接把 `Interior` 的楼层地图也塞进一个 `ChunkGrid`（内部用 `TorusSize::wrap` 归一化坐标），当视野半径接近楼层地图尺寸的一半时，`wrap` 会把视线从地图一侧接到另一侧，产出「隔着地下城两端却相互看得见」这种不该出现的结果——这不是猜测，是 `TorusSize::wrap`/`squared_euclidean` 的既有实现在有界场景下的直接推论。

**结论**：算法可以直接复用，但需要一个新的、有界（非环绕，坐标越界视为无效而非取模折返）局部地图类型，提供与 `ChunkGrid` 相同的接口（`terrain_at`、一个能提供 `wrap`/`squared_euclidean` 等价物的「世界」上下文），供 `Interior` 使用。这不是重新设计 FOV，是给它的输入类型补一个非环绕的姊妹类型——这项工作应归入 P7（或更早，视具体实现顺序；[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P6 顺移为 P7）的实现任务，不属于本文档的坐标系设计范围，此处只诚实记录这个缺口，不假装已经解决。

### `ll-render` 是否需要改动

**`z = 0`（`Surface`）：不需要改动。** `Camera`（`crates/ll-render/src/camera.rs`）操作的始终是同一个环面世界的 `TorusPos`/`TorusSize`——区块流式加载是 `ll-world` 内部「`terrain_at(pos)` 从哪个已加载的区块-层里取数据」这一层的实现细节，对 `Camera` 完全透明，`world_to_screen`/`visible_tiles` 不需要感知任何区块或流式加载的存在。

**`Interior`：需要一个新的相机变体。** 与上面 FOV 的结论同源——`Camera.world: TorusSize` 硬绑定环面语义，而 `Interior` 是有界不环绕的局部地图。这不是要重写 `world_to_screen`/`visible_tiles` 的屏幕换算算法本身（那部分逻辑与拓扑无关），而是需要给 `Camera` 提供一个基于有界坐标（非环面）的等价「世界」上下文——与 FOV 需要的新类型是同一处技术缺口，两者可以合并成一次实现工作。**这里如实指出「不是零改动」，而不是笼统地说「不需要改」**：`ll-render` 现有的 `Layer`（`crates/ll-render/src/sprite.rs:61`，`TERRAIN`/`DECOR`/`ENTITY`/`EFFECT`/`UI` 这五档绘制顺序）是同一屏幕内的精灵分层，与本文档的 `Space`/Z 完全是两回事——排查代码时若看到 `Layer` 字样，不要误当成本文档的空间层，这也是本节顺带要澄清的一处命名巧合。

## 七、层/空间属性：`SpaceProfile` 与光照的连锁反应

### 形状

```rust
/// 一种空间类型的静态属性，由注册表提供，mod 可注册新类型
/// （例如「深渊层」，自带光照与温度基准）。
pub struct SpaceProfile {
    pub id: NamespacedId,
    /// 环境光基准，千分比，与 ll_world::light::LightLevel 同一量纲。
    /// 仅在 exposed_to_sky 为假时生效，见下方「与光照系统的组合」。
    pub ambient_light_floor: i32,
    /// 是否露天——受天气、昼夜、四季影响。
    pub exposed_to_sky: bool,
    /// 温度基准。
    pub base_temperature: i32,
    pub diggable: bool,
    pub buildable: bool,
    /// 音效环境（回响等），仅预留字段，不在本文档展开。
    pub reverb_tag: Option<NamespacedId>,
}
```

`Space::Surface`/`Space::Interior` 都携带 `profile: ContentIndex` 指向这张表（见四）。这与 `RaceDef`/`CultureDef` 是同一个「本体即 Mod」模式：本体注册「地表」「洞窟」「地下城」「建筑内部」这几种基础 `SpaceProfile`，mod 可以注册新的空间类型。

### 与既有光照系统的组合，而非替换

`ll_world::light::ambient_light(tick)`（见 `light.rs`）是一个纯函数，只依赖世界时钟，模块文档明确写着「绝不进世界状态」——**这条设计不需要为 `Space` 改一行**。真正需要新增的是**调用方**这一层的判断：

```
effective_ambient_light(profile, tick) =
    若 profile.exposed_to_sky 为真 → ambient_light(tick)   // 既有函数，原样调用
    否则                          → LightLevel(profile.ambient_light_floor)  // 与 tick 无关
```

`sight_radius_at`（`light.rs`）与 `race-system.md`「暗视」一节的 `effective_light = max(light, darkvision_floor)` 同样不需要改——它们的输入本来就是「一个光照值」，不关心这个值是怎么算出来的。**唯一需要写清楚的新增纪律是：任何消费光照的调用方，必须先查 `Space.profile.exposed_to_sky`，不能对地下/室内空间直接调用 `ambient_light(tick)`**——直接调用会让地下城在正午呈现满光照，这是一个纯粹的接线错误，不是设计冲突。

### 回头核对 `race-system.md`「暗视」一节：不需要改

`race-system.md` 五、暗视一节的接口设计——`darkvision_floor` 是喂给 `sight_radius_at` 的一个地板值，`compute_fov` 完全不感知种族——本来就与「光照从哪来」这件事解耦，天然兼容「光照现在可能来自 `Space.profile` 而不是全局 `ambient_light(tick)`」这个变化。**不需要修改该文档正文**；上面这条「消费方必须先查 `exposed_to_sky`」的纪律属于坐标系/空间模型这一侧的接线细节，记在本文档即可，不属于种族系统的设计范围。

**连锁效果值得写明**：有了地下之后，地下层 `exposed_to_sky = false`、`ambient_light_floor` 多半接近零，视野半径完全靠光源与暗视撑起来——矮人暗视从「小加成」变成「能不能下矿」的差别，火把、灯油从装饰变成真实资源压力。这是本次架构变更的一个意外收益：暗视系统在纯地表世界里本来无足轻重（白天大家都看得见），有地下空间之后才真正有了用武之地。**点光源（火把等）如何提供局部光照，本文档不展开**——这需要在 `SpaceProfile` 的地板值之上再叠一层「附近有没有光源」的查询，是独立的一块设计，留给光照/物品系统的后续批次。

## 八、LOD 与「玩家所在」的界定

「非玩家所在层不做完整模拟」现在要拆成两个独立维度回答，两者的判据完全不同。

### 维度一：`Space` 之间——离散判定

`Interior` 之间、以及 `Interior` 与 `Surface` 之间没有连续性（第四节已经论证过为什么不能强行统一），因此「玩家在哪个 `Space`」是一个离散的二元问题：要么是玩家当前所在的这一个 `Space`，要么不是。**当前 `Space` 完整模拟，其余全部 `Space`（不论是别的区块的地表，还是任何一个 `Interior`）一律走批量公式**，不存在「距离近所以稍微精细一点」这种中间状态——因为不同 `Space` 之间根本没有「距离」这个共同的度量。这条规则与已裁定的「只渲染当前 `Space`、不做往下看」（见九）在方向上完全一致：不可见、不模拟、不渲染，三者绑在同一个判据上。

### 维度二：同一个 `Surface` 内部——按区块算，不按距离算

玩家所在的这一个 `Space` 如果是 `Surface`（连续地表），内部仍然存在「哪些区域该精细模拟、哪些走批量公式」的问题——这时候才是「按区块算还是按距离算」这个问题真正适用的场景，两种方案的后果对比：

| | 按连续距离算 | 按区块算（推荐） |
|---|---|---|
| 与聚落归属的关系 | 聚落边界与 LOD 边界不重合，可能出现「一个聚落一半前景一半背景」，需要按格子拆分 cohort，随玩家移动这条切分线连续变化 | 聚落完整归属某个区块（区块职责之一，见三），因此完整落在同一侧，不需要拆分 |
| 与常驻集合的关系 | 需要为 LOD 单独维护一套距离判定，与第五节的 256 个常驻区块-层 LRU 是两套独立机制 | **直接复用同一个常驻区块-层集合**——玩家所在区块及其常驻邻域＝前景，其余＝背景，LOD 判定与流式加载共用同一份数据结构，不需要额外维护 |
| 边界处的观感 | 平滑但实现复杂 | 跨区块边界时模拟精度有一个台阶——但区块边界在地表上不可见（连续地表），且区块边长（128）远大于视野半径，实践中这个台阶不会被玩家直接看见；即便看见，也与既有「背景 NPC 靠近后升格」的渐进升格机制是同一种性质的过渡，不是新问题 |

**推荐按区块算**：不额外引入一套判据，直接复用第五节已经确定要维护的常驻区块-层集合——「玩家所在区块的常驻邻域」既是流式加载的边界，也是模拟 LOD 的边界，一份数据结构服务两个目的。

## 九、已裁定：只渲染当前层，不做「往下看」

### 结论

- 渲染只画玩家所在的 `Space`。
- FOV 严格按 `Space` 计算，不跨层、不跨空间。
- 不做下层压暗叠加。

### 后果

**这让离散层模型彻底干净。** `Space` 之间除了显式过渡点（楼梯、坡道、洞口、门）之外没有任何耦合——渲染不跨、视野不跨、光照不跨、模拟不跨（见八，维度一）。`compute_fov` 因此不需要为跨层场景增加任何逻辑（第六节已核实这一点）。

**未知带来的是玩法收益，不是损失。** 传统 Roguelike 正是如此——不知道洞口下面有什么，跳下去是一次真实的赌博。若能预先看清下层，探索的紧张感会显著削弱。

**已知设计缺口（不在本文档展开）**：玩家从高处掉落或主动跳下时，落点是未知的。这需要机制上的配套（掉落伤害、是否允许先探查、绳索一类工具），属于后续玩法阶段的事，此处只记一句提醒。

## 十、已裁定：区块 = 4×4 存储块（甲案）

### 三案比较

| | 甲案：写死对齐 | 乙案：不对齐，各自可调 | 丙案：取消存储块，区块即存储单位 |
|---|---|---|---|
| 做法 | 区块尺寸必须是 `CHUNK_SIZE` 的整数倍（当前 128 = 4×32） | 两个尺寸各自自由设置 | 删除 `chunk.rs` 的存储块概念，区块（128×128）本身就是唯一的分配/生成粒度 |
| 优点 | 区块加载/卸载即整块存储块的增删，边界干净；不出现「半个存储块属于两个区块」；两者都是 2 的幂，索引换算可用移位与掩码，无除法/取模 | 两个尺寸互不牵制 | 少一整层概念，「三个块」的混淆风险从根上去掉一个（存储块与区块合而为一） |
| 缺点 | 区块尺寸被锁定为 32 的倍数；改 `CHUNK_SIZE` 会连带影响区块尺寸 | **一个存储块可能横跨两个区块**，加载/卸载语义需要引用计数才能处理干净；这类缺陷通常表现为「地图某处偶尔不刷新」，极难定位（错误现场与根因隔着一层，与 `knowledge/handoff/p3-to-p4.md` 记录的 `action_cost` 截断缺陷是同一种「排查者会先怀疑别处」的模式） | `ChunkGrid` 既有的 `terrain_at`/`set_terrain` API 需要重写 |

**乙案已否决**：横跨存储块边界的区块需要引用计数才能正确处理加载/卸载，边界缺陷极难定位（症状是「偶尔不刷新」而不是崩溃，排查者很难第一时间联想到根因）。记在这里，供将来想推翻这条决定的人知道当初排除的是什么。

**丙案的真实改动量**：`CHUNK_SIZE = 32` 的存储块最初是在「世界是一整张连续 512×320 网格」的前提下选定的——它是那个模型里的惰性生成单位，其模块文档给出的理由是「再小则块管理开销占比过高，再大则单块内存浪费明显」。**但在新模型里，区块本身已经是惰性生成与流式加载的单位**（第五节），存储块因此在结构上变得冗余。128×128（32 KiB）作为一个分配单位本身完全合理，不需要在它内部再套一层 32×32 的子分块。若丙案成立，需要重写的是 `ChunkGrid` 的 `terrain_at`/`set_terrain` 两个接口——但 `WorldState.terrain` 本来就要为两级坐标系重写（见十三），丙案的增量成本可能很小。**需要先核实一件事：区块内部是否存在「只生成一部分」的需求**——若区块本身要支持部分生成（例如只生成玩家视野覆盖到的那一角），存储块这层还承担着比「分配粒度」更多的职责（脏标记、序列化粒度），丙案就不能简单合并；若区块始终整块一次性生成（第五节的设计正是如此——一个区块-层要么完整生成，要么完全不存在），丙案的合并就没有额外阻碍。**本文档没有在现有代码里找到区块需要部分生成的证据**，但这项核实需要在真正着手实现丙案之前重新确认一次，而不是仅凭本文档的推断就动手删除存储块层。

### 最终决定：甲案，丙案有条件推迟

**采用甲案：区块 = 4×4 存储块。** 128 与 32 都是 2 的幂，区块坐标到存储块索引的换算可以用移位（`>> 5`）与掩码（`& 31`）实现，不需要除法与取模。

**这是有意的推迟，不是遗忘**，记录如下，避免这条决定的理由随时间流失：

- **推迟的是什么**：丙案（取消存储块层，区块直接成为存储与生成单位）。
- **推迟的理由**：甲案改动面小、边界语义清晰，先让两级坐标系跑起来；丙案是否可行还依赖上面「区块是否需要部分生成」这项尚未核实的前提。
- **代价**：`ChunkGrid` 这层概念继续存在，「三个块」（存储块 32 / 区块 128 / 视口 43×25）的混淆风险保留，需要靠第三节的澄清持续起效，而不是靠合并概念从根上消除。
- **重新评估的触发条件**：若实现中发现存储块层只是对区块的穿透转发（`terrain_at`/`set_terrain` 全部直通区块、不做任何存储块粒度的独立处理），或「三个块」的混淆在评审中真实发生过一次，即应重新评估丙案。**且这个窗口正在关闭**——`WorldState.terrain` 本来就要为两级坐标系重写，此刻合并丙案的增量成本最低；等更多代码依赖 `ChunkGrid` 之后再改会更贵。

### 顺带一条：这条对齐关系是结构性约束，不是数值

「区块尺寸必须是 `CHUNK_SIZE` 的整数倍」本身是**结构性约束**（甲案生效后不可违反）；「区块尺寸具体取 128 还是别的倍数」是**数值**（可配置）。两者不要混为一谈——见十二的完整清单。

**这条对齐关系不适用于 `Interior` 的楼层地图**：`Interior` 的每一层地图整体一次性加载（第五节「常驻集合」已把「当前所在建筑/地下城的全部层」列为无条件常驻，不做区块式的跨边界流式滚动），大小由内容决定（第四节「不受地表占地限制」），没有理由要求它是 32 的倍数——这条约束只作用在 `Surface` 的区块这一级存储粒度上。

## 十一、三个默认数字

项目所有者尚未给定最终数字，以下按已核实的约束给出默认值与论证，仍然是可调的配置数据，不是写死的结构。

| | 默认 | 依据 |
|---|---|---|
| 区块大小 | **128×128 格** | 16 与 32 的公倍数、2 的幂、约 3～5 屏宽高，给流式加载留缓冲（见五） |
| 世界区块数 | **建议下调至 48×32（1,536 个）**，见下方说明 | 见下方说明 |
| 地下深度（`Interior.floor` 的推荐范围） | 向下 32 层、向上 8 层，作为「一栋建筑/一处地下城」内部楼层数的**建议上限**，不是全局结构限制 | 稀疏存储，不受这个数字直接约束内存（见六），只是给内容设计一个参考量级 |

**世界区块数为什么建议下调**：原始设计（区块 ≈ 一屏）下，128×80 = 10,240 个区块对应的世界瓦片总量级约为一千万格出头（10,240 × 一屏 ≈ 1,075 格）。区块放大到 128×128 之后，若仍沿用 128×80 这个区块数，世界瓦片总量暴涨到 128×128 × 80×128 ≈ **1.68 亿格**，比原来的量级大了一个数量级还多——这个膨胀不会带来任何问题（地形是惰性生成的，不会真的分配这么多内存），但意味着世界的物理尺度会变得异常庞大，与「几百个聚落，尚有余量」这个原始目标脱节（聚落分布密度会显得异常稀疏，纯粹是因为世界变大了，不是因为聚落变多了）。**建议把世界区块数下调到与新的区块尺寸相匹配**：48×32 = 1,536 个区块，世界瓦片总量 ≈ 48×128 × 32×128 ≈ 2,520 万格，量级上与原始设计的「千万格出头」接近，同时 1,536 个区块相对「几百个聚落」仍有数倍余量。**这是数值，不是结构**——具体取多少最终应由内容设计（世界历史生成需要多大的地理多样性来支撑几百个聚落的分布）来定，本文档只给出「不要不假思索沿用旧默认值」这个提醒与一个自洽的替代默认。

**世界历史生成不受这次膨胀影响**：`world-history.md` 流程七步里的聚落播种、势力形成、历史推进，全部工作在**区块粒度**（或更粗的聚合层面），不逐格遍历世界瓦片，因此区块数从 10,240 降到 1,536、或世界瓦片总量涨落一个数量级，都不改变历史生成的计算量级——这条工作量分析在 `world-history.md`「一、核心架构判断」一节已经论证过，本文档的坐标系变更不影响那条论证。

## 十二、结构性约束 vs 可配置数值

| 结构性约束（不可配置） | 可配置数值 |
|---|---|

| 项目 | 结论 | 说明 |
|---|---|---|

| 光照 `ambient_light`/`sight_radius_at`（`ll-world/src/light.rs`） | **可复用，不改一行** | 见七：需要新增的是调用方判断（`exposed_to_sky`），不是改光照函数本身。 |
| 昼夜四季（`ll-core::light`/`ll-core::time`） | **可复用** | 纯函数，与位置无关；地下空间是否应用昼夜由 `exposed_to_sky` 在调用方决定，不改这套曲线本身。 |
| `ChunkGrid` 存储（`ll-world/src/chunk.rs`） | **要改，且改动方式待定（甲/丙两案，已选甲）** | **修正原始草稿**：草稿把它归入「大概率可复用」，核实后发现它绑定的 `TorusSize` 环面语义与 `CHUNK_SIZE` 分块粒度都要为两级坐标系重新安排，且丙案（取消这层概念）是有条件的候选方案，不是简单复用。见十的完整讨论。 |
| 相机 `Camera`（`ll-render/src/camera.rs`） | **`Surface` 不改，`Interior` 需要新变体** | 见六：`world_to_screen`/`visible_tiles` 的算法逻辑不变，但需要一个基于有界坐标的「世界」上下文供 `Interior` 使用。**修正原始草稿**：草稿笼统写「可复用」，未区分这两种情形。 |
| `overview::minimap` | **基本可复用，内部改接线** | `minimap` 本来就是「取玩家附近一小块窗口」，与流式加载的常驻区块-层天然重合，只需要把 `terrain_at` 的实现从直读 `ChunkGrid` 改成经过区块索引层查询，不需要改 `minimap` 本身的窗口逻辑。`Interior` 内的 minimap 同理，读当前 `Space` 的局部图即可。 |
| `overview::continent_map` | **要改，需要新的数据源** | **修正原始草稿**：草稿写「改读世界尺度数据」但未说明这份数据从哪来。核实结论：`continent_map` 不能强行为了渲染一张下采样概览图就把全部 1,536（或更多）个区块的完整地形都生成出来——那正是流式生成要避免的事。需要一份**独立的、在世界创建时就整体生成的粗粒度场**（类似「种族分布场」，按区块而非瓦片分辨率），专供 `continent_map` 使用；精细的逐瓦片地形仍然按需生成，两者是两份不同粒度的数据，不是同一份数据的两种读法。`continent_map` 只展示 `Surface`，不展示任何 `Interior`（与「不做往下看」的裁定一致）。 |
| `Layer`（`ll-render/src/sprite.rs`） | **不涉及，与本次改动无关** | 见六末尾：这是同一屏幕内的精灵绘制顺序（地形/装饰/实体/特效/UI），与本文档的 `Space`/Z 是两个不同的概念，只是恰好都叫「层」，容易混淆。 |

## 十四、时间窗与阶段归属

**坐标系形状必须在 P5 冻结存档格式之前定**——本文档正是为此写就。P4（内容注册表）几乎不受影响，只多一类需要注册的内容（`SpaceProfile`，与 `TerrainDef` 走同一条路径）；P5 存档格式与 P7 世界生成（[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P6 顺移为 P7）直接建在这个模型上，`WorldState.terrain` 的重写、`Space`/`SpaceProfile` 的落地都需要在 P5 冻结前完成结构定案（数值可以之后再调）。

### 对既有 P2 成果的影响范围：诚实评估

| P2 成果 | 影响 |
|---|---|
| `ll_core::torus`（`TorusSize`/`TorusPos`/`delta`/`chebyshev`/`manhattan`/`squared_euclidean`） | **不受影响，平移使用** | 这套机制本身与「世界是一整张图还是分区块流式加载」无关，两级坐标系直接复用（见十三）。 |
| `ll_world::noise`（`TileableNoise`） | **不受影响，平移使用** | 见五、十三。 |
| `ll_world::generate`（`generate_terrain`/`build_noise`/`terrain_at_coord`） | **要重写调用方式，核心算法不动** | `terrain_at_coord`/`build_noise` 本身零改动；`generate_terrain` 这个「一次性生成整张图」的入口函数需要拆分/替换成「按区块窗口生成」的调用方式，见五。 |
| `ll_world::chunk`（`ChunkGrid`） | **要重写** | 见十三；甲案下需要重新设计「区块 → 存储块」的索引层，丙案下需要整体替换。 |
| `ll_world::fov`（`compute_fov`） | **算法平移，配套类型需要新增** | 见六、十三。 |
| `ll_world::light` | **不受影响，平移使用，新增调用方判断** | 见七。 |
| `ll_world::state`（`WorldState`） | **要重写** | `WorldState.terrain: ChunkGrid` 这个「整个世界一张图」的字段本身与两级坐标系的前提直接冲突，必须替换成区块索引 + 流式加载的结构；`WorldState` 的序列化（`try_from` 交叉校验模式，见 `state.rs` 文档）这套纪律要延续，但校验的对象要跟着新结构变。 |
| `ll_world::overview`（`minimap`/`continent_map`） | **`minimap` 小改，`continent_map` 要补新数据源** | 见十三。 |
| `ll_render::camera`（`Camera`） | **`Surface` 不变，`Interior` 需要新变体** | 见六、十三。 |
| `ll_render::sprite`（`Layer`/`DrawOrder`） | **不受影响** | 见六末尾、十三——这是同屏绘制顺序，与本次改动无关。 |

**不粉饰的结论**：`ll_world::state`/`chunk`/`generate`（的调用方式）三处需要实打实的重写，`fov`/`camera` 需要新增一个非环绕的姊妹类型但核心算法保留，`torus`/`noise`/`light`/`ll_render::sprite` 四处完全不受影响。这不是一次「加一个字段」量级的改动，是 P2 世界层的存储与生成入口要按这个模型重新搭一遍——但重新搭的是「怎么组织存储与调用」，不是「重新发明地形怎么生成、视野怎么算、光照怎么算」这些已经验证过的核心算法，这也是为什么本文档反复强调「哪些函数的算法本身不用动」：真正要花的实现成本集中在几个入口函数与新的索引/流式加载层，不是推倒重来。
