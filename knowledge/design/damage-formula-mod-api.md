# 伤害公式的 mod API：D&D 骰子表达式，s-表达式载体，第二档

**冻结于** 2026-08-20。**落地状态**：纯设计，`crates/` 中无任何对应类型。核对提交 `2226469`（`main` 分支）。已核实的现状：`damage_after_defense`（`crates/ll-sim/src/combat.rs`）与调用它的唯一真实入口 `resolve_attack`（`crates/ll-sim/src/resolve.rs:462`）——见「一、现状核实」。本文档是同一次设计任务的第三版：第一版判定「受限公式,Rust 侧构造指令」，项目所有者两次追加要求后改为「参考 D&D 骰子记号 + 本项目属性」「表达式载体用 s-表达式,仿照 `mods/example_mod/behavior.scm` 的既有模式」——本文档正文直接给出修正后的结论,不逐版本重复推导过程。

---

## 零、项目所有者的要求（三次，累加）

> 「关于伤害计算公式，我希望也能留个 api 给 mod，让 mod 有能力写出不同的计算公式。」

> 「那能不能参考 dnd 设计一套伤害系统以及对应的表达式呢？再基于我们的属性加入新的表达式。这样脚本也可以通过写伤害表达式确认，这样还能一早加载成静态声明。」

> 「这个表达式应该还很适配 steel 那种 lisp 的函数风格。也就是变成对应的函数。」

三条要求共同定出的形状：**mod 写一份 D&D 风格的骰子表达式（`1d8 + 力量调整值`这一类），载体是 Steel 的 s-表达式（不是自定义字符串文法），装载期一次性编译成扁平指令数组，运行期零脚本调用**。机制在 Rust 里实现好,真正可游玩的内容由 mod 填充——这是 P4 定下的架构划分（[ADR 0016](../decisions/0016-mod-performance-tiers-by-declaration.md)）,本文档回答的是「机制该长什么样」,不产出任何具体武器/技能的数值内容。

## 一、现状核实（写作本文档前已去代码核实）

**`damage_after_defense` 目前只有一个真实调用点，且恒为单体、恒不判空**：

```rust
// crates/ll-sim/src/resolve.rs:462，resolve_attack
let attack_power = attacker.stats.strength;
let damage = damage_after_defense(attack_power, 0, Penetration::NONE);
```

一次 `Intent::Attack` 对应**恰好一次**公式求值——`Intent::Attack` 目前的 `target` 字段类型是 `EntityId`（单体），[三轴战斗结算](combat-three-axis.md) 设计的 `TargetSpec`（可展开成多目标）尚未落地，所以「范围伤害命中十个目标算十次」是**设计中的未来数字**，不是当前代码里能实测到的数字——下一节的定档论证会同时用到这两个数字。

**第二个必须记录的现状缺口**：`resolve_use_skill` 的 `SkillEffect::DealDamage` 分支（`resolve.rs:689`）**完全不调用** `damage_after_defense`——技能伤害目前是 `effects.push(Effect::Damage { target, amount: base })`，防御与穿透对技能伤害完全不生效。本文档不实现这个缺口，只在「九、与既有系统的接口」指出接线点重合。

**第三处核实（本次新增，回应「骰子载体」的要求）**：`mods/example_mod/behavior.scm` 与 `crates/ll-script/src/behavior.rs` 已经是「quote 包起来的 s-表达式，Rust 侧遍历」这套模式在本项目的真实先例——`goblin-ai-tree` 返回 `(quote (selector ...))`，`tick_control`/`eval_call` 按 `selector`/`sequence` 语义遍历这份数据。**但这个先例的求值方式不能直接照抄**：`eval_call` 在每个叶子节点上调用 `engine.call_raw(head, args)`，即**每个叶子跨一次 VM 边界**——这是行为树按 tick 求值、每次决策只需要跑一次的场景下可以接受的开销（一次 tick 一棵树，叶子调用次数是「决策深度」量级，不是「每帧/每次攻击」量级的问题）。伤害表达式如果照抄这套「遍历时回调 Steel」的求值方式，就是本文档二节要否决的第三档——「一早加载成静态声明」的整个意义会当场蒸发。本文档取 `behavior.rs` 的**数据表示**（quote 包起来的 s-表达式，白名单跳过 `quote` 内部）,不取它的**求值方式**（回调 Steel）——伤害表达式的 s-表达式在装载期被**编译**（不是被遍历求值）成一份不含任何 `SteelVal`/`ScriptEngine` 引用的纯 Rust 数据（`Vec<FormulaOp>`），运行期求值这份编译产物，从此与 Steel VM 再无瓜葛。

## 二、定档：仍然是第二档——重新论证，结论不变，但要讲清楚为什么"声明式装载"这个表象不改变分类

### 三步判据（[ADR 0018](../decisions/0018-engine-layer-vs-gameplay-layer-scripting-boundary.md)）逐步核对

**第一步：有没有设计自由度？** 有——同一组攻防输入完全可以套一套结构不同的规则（四节会给出两个真实反例）。**→ 玩法层**。

**第二步：自由度落在算法还是数据上？** 落在算法本身（「怎么把攻防数值组合成一个伤害数」），不是某个数值参数——这是「表达式」而不是「配置项」的分野,四节的两个示例会证明这一点。

**第三步：调用频率是档位问题，不是层问题。**

### 为什么「一份声明式的 s-表达式」不等于「第一档」——重新论证

项目所有者观察到：mod 写一份表达式交给 `register-damage-formula`,这个动作本身与 `register-terrain` 传几个 `bool`/整数在**装载期的调用形态**上没有区别——都是「一次性调用,交出数据,从此不再触碰」。这个观察**完全正确**,但它描述的是**装载期的作者体验**,不是**运行期的求值成本**——而 [ADR 0016](../decisions/0016-mod-performance-tiers-by-declaration.md) 给三档分类用的判据，从第一天起就是运行期成本,不是作者怎么写：

| 档 | 判据原文（[ADR 0016](../decisions/0016-mod-performance-tiers-by-declaration.md)） | 运行期实际发生什么 |
|---|---|---|
| 一档 | 「声明静态值 → 注册期物化进 Rust 表，运行期查表」 | 一次数组下标访问（如 `move_cost[idx]`），**不需要任何运行期才存在的输入** |
| 二档 | 「声明受限公式 → 编译成枚举/小字节码，Rust 侧求值」 | 遍历一个小指令数组，**消费只有运行期才知道的输入**（本文档是攻击力/防御/骰子结果） |
| 三档 | 「任意脚本回调」 | 跨 VM 调用 |

伤害不是一个可以脱离「这一下具体是谁打谁」而提前算好的静态值——攻击力、防御、穿透、骰子结果全部是**运行期才存在**的量,`move_cost[某种地形]` 这类一档内容恰恰相反：查询时不需要任何「这一刻」才知道的输入,同一个 `ContentIndex` 永远查出同一个数。**这才是一档与二档的真正分界,不是"作者写的是不是一份声明"**——`TriggerDef` 的一档变体（`buffs-and-triggers.md` §三：`ApplyBuff`/`DealDamage` 两个一档变体）同样是"mod 写一次声明式调用"交出来的,但它们能落一档,是因为参数本身就是最终答案（"命中时固定造成 20 点伤害"不需要任何运行期计算）,伤害表达式做不到这一点——即使不含骰子,`(- attack-power defense)` 这个最简单的表达式,答案也必须等 `attack-power`/`defense` 在运行期出现才能算,这就是"公式"与"静态值"的本质区别,与装载时是"一次性声明"还是"分散多次调用"无关。

**结论不变，仍然是第二档,但项目所有者指出的"声明式装载"这个特征值得明确肯定**：它不是本次改用 s-表达式才第一次具备的性质——[ADR 0017](../decisions/0017-tiered-declarations-materialize-columnar.md) 对第二档的原始定义就是"声明式受限公式…编译成平铺指令数组",**"整个公式在装载期一次性交出、运行期零脚本调用"从定义之初就是第二档的核心特征,不是第一档的专利**。本文档只是把"声明的载体从 Rust 侧构造函数调用换成 s-表达式"，这一步改变了**作者写公式时用什么语法**,没有改变**这份公式编译完之后在运行期是什么**——仍然是一份要被求值的指令数组,不是一次表查询。

### 真实调用频率（与第一版相同，未变）

现状：每次 `Intent::Attack` 恰好一次。设计后（`TargetSpec` 落地）：命中 N 个目标算 N 次,逐个求值,理由与排序要求见 [三轴战斗结算](combat-three-axis.md) §三/§六。一局百小时游玩累计到几十万次量级（[击杀与死亡记录](kill-and-death-events.md) §三的遭遇战量级估算）。**这个量级承受不起 326ns 的固定跨界开销**——见 [ADR 0012](../decisions/0012-steel-capability-surface-verification.md) 实测数字,与 [增益与通用触发器](buffs-and-triggers.md) §三同一组数字的引用方式相同。

### 被否决的选项（追加一条，其余与第一版相同）

- **判成一档**——否决：见上文,运行期需要消费只有那一刻才存在的输入,不可能预物化成一张表。
- **判成三档（表达式在运行期由 Steel 求值,像 `behavior.rs` 那样逐叶子回调）**——**新增的否决项,直接回应"表达式载体是 s-表达式"这一变化带来的新风险**：s-表达式的载体天然容易让人联想到"干脆复用 `behavior.rs` 现成的遍历求值器",但一、节已经论证过,那条路径每个叶子跨一次 VM,等于把伤害计算重新推回三档,与「一早加载成静态声明」的初衷正面冲突。**载体是 s-表达式,求值器不是 `behavior.rs` 那一个**,两者必须分开看待,这是本节要着重澄清的一点。
- **判成"一档+二档混合"**——否决,理由见上文核心论证：装载形态与运行期成本是两个独立的轴,分类判据只看后者,不存在"部分一档部分二档"这种中间态——这份表达式从第一条指令到最后一条,每一步运行期求值都需要真实输入,没有任何一部分能被物化成纯查表。

## 三、表达式语法：s-表达式，仿照 `behavior.scm` 的 `quote` 模式

### 载体：`quote` 包起来的数据，不是被求值的代码

```scheme
(register-damage-formula "mymod:brutal_strike_formula"
  (quote (max 1 (- attack-power (max 0 (- defense pen-flat))))))
```

`register-damage-formula` 是第七个 `register-*` 内容注册函数（与既有六个同一模式：`Result<bool, String>` 返回值，完整命名空间 ID 做第一个参数）。**第二个参数必须是 `quote` 包起来的列表**——原因与 `goblin-ai-tree` 完全相同：`max`/`attack-power`/`defense`/`pen-flat` 这些符号从未注册给 Steel 求值,若不用 `quote` 包住,白名单会在**这份数据本身还没被当成公式看待之前**就因为「引用了不在白名单内的标识符」拒绝整份脚本（`steel-script-reference.md` 一.6：白名单专门跳过 `quote` 包住的部分）。`quote` 因此不是可选的写法习惯,是让这份数据能够通过装载检查的必要条件。

**编译器不是 `whitelist.rs`,是一套独立的小校验器**——白名单机制检查的是「一般 Steel 程序里出现的自由标识符是否安全」,而 `quote` 包住的部分**从设计上就被白名单跳过**（正是上一段说的那条既有规则）,白名单因此**结构上就管不到** `quote` 内部这份数据长什么样。校验这份数据是否是一个合法的伤害表达式,必须是另一套**独立的、只认识本文档下面这张表的编译器**——两者的相似之处只在于"都是走一遍 s-表达式树、按一张封闭表判断每个节点合不合法",但表的内容完全不同（白名单表里有 `map`/`lambda`/`box` 这类通用能力,伤害表达式的表里没有任何一项是通用能力,只有算术/骰子/属性读取）,不能把"伤害表达式编译器"当成"复用白名单",必须是本文档下面定义的这套新表。

### 编译产物住在哪个 crate

**编译器**（`SteelVal` → `Vec<FormulaOp>`）住在 `ll-mod`（与既有六个 `register_*_api.rs` 同级，作为第七个 `script_damage_formula_api.rs`）——这一层需要读 `steel::rvals::SteelVal`，依赖 `steel-core`。**`FormulaDef`/`FormulaOp`/`FormulaOperand` 类型定义与求值器**住在 `ll-sim`（与 `combat.rs`/`resolve.rs` 同级，新增 `formula.rs`）——这一层是纯 Rust 整数运算，不依赖 `steel-core`，与 `SkillEffect`/`ResourceCost` 已经确立的先例（`crates/ll-mod/src/skill.rs`：「`ll-mod` 现在必须依赖 `ll-sim`……`ll-sim` 那份定义现在是唯一真相源，`ll-mod` 只是复用者」）完全同构——`ll-mod` 的编译器 `use ll_sim::formula::{FormulaOp, FormulaOperand, FormulaDef, ...}`，编译完直接产出 `ll-sim` 认识的类型，不需要 `ll-sim` 反过来知道 `steel-core` 存在。求值发生在 `ll-sim::resolve`（调用方），全程不接触 `ll-script`/`steel-core`。

### 允许的形式（封闭表，编译器只认识这些）

**算子（列表形式 `(op a b)`，严格二元，不做变参）**：

| 算子 | 语义 |
|---|---|
| `(+ a b)` / `(- a b)` / `(* a b)` / `(/ a b)` | 加减乘除，除法截断（见五节） |
| `(mul-permille a b)` | `a * b / 1000`——千分比运算专用原语，理由见五节 |
| `(min a b)` / `(max a b)` | 取小/取大 |
| `(if (cmp a b) then else)` | 唯一的分支形式，`cmp` ∈ `< <= > >= = !=` |
| `(d N S)` | 骰子：掷 `N` 个 `S` 面骰求和，`N`/`S` 必须是**字面整数常量**，不能是子表达式（见六节） |
| `(adv (d N S))` / `(disadv (d N S))` | 优势/劣势骰：把**同一个** `(d N S)` 掷两遍，取较大/较小（见七节）。只能包住一个字面 `(d N S)`，不能包住任意子表达式（见七节「为什么限定成只包骰子」） |
| `(multi-hit N chance per-hit)` | 多轮命中判定：独立掷 `N` 轮，每轮以 `chance`（千分比，整数常量或操作数）概率命中，命中的轮次各贡献一份 `per-hit`（一个已算好的操作数，不逐轮重掷），总和即这条指令的结果。`N` 必须是**字面整数常量**（见五节），`chance`/`per-hit` 可以是操作数（含引用更早指令的结果） |

**操作数（裸符号，不加括号）**：

| 符号 | 含义 |
|---|---|
| `attack-power` | 攻击方按伤害系别选好的攻击力 |
| `defense` | 防御方按伤害系别选好的防御力 |
| `pen-flat` / `pen-permille` | 固定/千分比穿透 |
| `str-mod` / `dex-mod` / `con-mod` / `int-mod` / `wis-mod` / `cha-mod` | 攻击方对应主属性的调整值（`attribute-system.md`「调整值 = (属性 − 10) / 2」，整数除法向零截断，与既有公式同一惯例） |
| `crit` | 本次攻击是否暴击，`0`/`1`，调用方预先判定好（见七节） |
| 整数字面量（如 `100`、`1000`） | 编译期常量 |

### 明确禁止：lambda、高阶函数、任意函数调用

**没有 `lambda`，没有 `define`，没有 `let`/`let*`/`letrec`，没有 `map`/`filter`/`apply`，没有任何不在上表里的符号被当成函数调用**。编译器遇到列表头部是一个不认识的符号（例如 mod 作者笔误写了 `(mac attack-power defense)`，或者更危险地写了 `(lambda (x) x)`）时,**装载期直接拒绝**,产出 `ModError::UnknownFormulaSymbol { formula: NamespacedId, symbol: String }`,这个 mod 整体加载失败——与其余 `register-*` 的编译期错误语义一致,**不静默忽略这个节点、不把它当成 0、不假装它是个常量**。

**为什么这条禁令必须结构性,不能靠"文档提醒作者不要这样写"**：一旦 `lambda` 能出现在这份数据里,编译器要么（a）拒绝对它求值（那 `lambda` 出现在这里毫无意义,不如从语法上直接不认识它）,要么（b）在运行期真的把它当成一个可调用对象求值——而 (b) 意味着运行期重新需要一个 Steel 求值上下文,**本文档二节否决的"表达式在运行期由 Steel 求值"这条路径会经由 `lambda` 这个后门重新打开**,「一早加载成静态声明」的整个设计意图当场作废。所以正确做法不是"允许 lambda 但不调用它"（那样 lambda 存在的意义是什么？）,是**编译器的封闭表里压根没有 `lambda` 这一项**——遇到它就是遇到一个不认识的符号,和遇到任意笔误拼错的符号走同一条"拒绝并报错"的路径,不需要专门为 `lambda` 写一条特判「检测到 lambda,报错」,普适的"未知符号即拒绝"规则本身已经覆盖了这个情况。

**为什么没有循环、没有递归**：语法里没有任何"跳转"或"自我引用"的手段——`Local` 式的中间结果引用完全是编译器内部的实现细节（下一节说明）,**作者写的 s-表达式本身永远是一棵有限深的树**,树的深度直接决定编译后指令数组的条数,天然有界,不需要额外的成环检测。这与「二 — 三、受限公式的形状 — 为什么没有循环」一节（第一版遗留的论证,结论不变）是同一条道理，只是这次由「s-表达式是一棵树」这个事实直接保证,不需要额外的下标单调性规则。

### 编译产物：扁平指令数组，作者不写、只由编译器生成

作者写的是**嵌套**的 s-表达式,编译器做**深度优先、从左到右**的展开,把每个子表达式的结果放进一个隐式的局部槽位,后续指令按需引用——这与三节示例、及第一版文档已经定义的 `Vec<FormulaOp>` 形状完全一致：

```rust
// crates/ll-sim/src/formula.rs（设计，未落地）
pub struct FormulaDef {
    pub id: NamespacedId,
    pub instructions: Vec<FormulaOp>,
    /// 编译期可判定：指令数组里含骰子/多轮判定类指令时为真——见六节。
    pub needs_rng: bool,
}

pub enum FormulaOp {
    Const(i64),
    /// 把一个输入槽的值原样放进当前槽位——author 写一个裸符号作为
    /// 整个表达式（或某个子表达式）的值时，编译器生成这一条。
    Ref(FormulaOperand),
    Add(FormulaOperand, FormulaOperand),
    Sub(FormulaOperand, FormulaOperand),
    Mul(FormulaOperand, FormulaOperand),
    Div(FormulaOperand, FormulaOperand),
    MulPermille(FormulaOperand, FormulaOperand),
    Min(FormulaOperand, FormulaOperand),
    Max(FormulaOperand, FormulaOperand),
    Select { cond: FormulaCond, if_true: FormulaOperand, if_false: FormulaOperand },
    /// 掷 count 个 sides 面骰求和——count/sides 是编译期常量。
    Dice { count: u32, sides: u32 },
    /// 同一个 (count d sides) 掷两遍取较大和。
    AdvantageRoll { count: u32, sides: u32 },
    /// 同上，取较小和。
    DisadvantageRoll { count: u32, sides: u32 },
    /// 多轮命中判定（五节）：独立掷 rounds 轮，每轮以
    /// hit_chance_permille/1000 概率命中，命中的轮次各贡献一份
    /// per_hit_damage（同一个已算好的值，不逐轮重掷），求和即结果。
    /// rounds 是编译期常量，与 Dice::count/sides 同一套注册期范围校验。
    MultiRoundHit {
        rounds: u32,
        hit_chance_permille: FormulaOperand,
        per_hit_damage: FormulaOperand,
    },
}

pub enum FormulaCond {
    Lt(FormulaOperand, FormulaOperand), Le(FormulaOperand, FormulaOperand),
    Gt(FormulaOperand, FormulaOperand), Ge(FormulaOperand, FormulaOperand),
    Eq(FormulaOperand, FormulaOperand), Ne(FormulaOperand, FormulaOperand),
}

pub enum FormulaOperand {
    Const(i64),
    Local(u8),               // 引用第 i 条指令的结果，i 严格小于当前下标
    AttackPower,
    Defense,
    PenetrationFlat,
    PenetrationPermille,
    AttributeModifier(AttributeKind), // str-mod/dex-mod/…
    Crit,                              // 0 或 1
}
```

**作者永远不写 `Local`**——它纯粹是编译产物的内部寻址方式,不出现在作者面对的 s-表达式语法里,这是「装载期书写形态」与「运行期求值形态」两层分离的直接体现（本文档二节强调过的那条区分）：mod 作者只写代数式嵌套,编译器负责把嵌套拍平成寻址数组。

### 注册期完整校验（[ADR 0017](../decisions/0017-tiered-declarations-materialize-columnar.md) 的追加要求，本次追加两条新检查）

1. `instructions.len() <= MAX_FORMULA_INSTRUCTIONS`（`64`，与第一版一致）。
2. 每个 `Local(i)` 引用的 `i` 严格小于所在指令下标（结构性防环，本次由 s-表达式树本身天然保证，编译器实现上仍需要一次断言）。
3. `Crit` 操作数没有额外限制（任何位置都能读，值恒为 0/1）。
4. `Div`/比较里若一侧是编译期常量 `Const(0)` 且恰好是除数位置,直接拒绝注册。
5. 空表达式（长度 0）拒绝。
6. **`(d N S)` 的 `N`/`S` 必须是正整数字面量,且 `N ∈ [1, 20]`、`S ∈ [2, 1000]`**——上限防止一条 `Dice` 指令自己就消耗过多随机抽取（例如 `(d 100000 6)` 会让"指令数组只有 64 条"这条上限失去意义,一条指令内部仍能藏一个昂贵循环）,下限排除 `S=1`（一个"每次都摇出 1"的骰子没有意义,大概率是笔误,不如直接写常量 `N`）与 `N=0`（同理）。
7. **任意不在三节封闭表里的符号（含 `lambda`/`define`/`let`/`map`……以及任何拼写错误）→ `ModError::UnknownFormulaSymbol`，整个 mod 拒绝加载**。
8. **`(multi-hit N chance per-hit)` 的 `N` 必须是正整数字面量，且 `N ∈ [1, 10]`**——与 `(d N S)` 的 `N`/`S` 同一套理由：`rounds` 是一条指令内部的有界重复次数（编译期展开成"抽 `N` 次命中判定",不是运行期循环，见五节），上限防止单条指令内部藏一个过大的重复；`10` 取得比骰子的 `20` 更保守，是因为多轮判定每一轮都要额外做一次概率比较 + 条件求和（比单纯掷骰的 `gen_range` 略重），且五节的分析显示超过 10 轮后"变得更平滑"的边际收益本身已经很小，没有必要放开更大的上限。

## 四、两个示例：证明这是「不同的一套规则」而不是调系数

### 示例一：本体默认公式，s-表达式复现（无骰子，纯确定性），风格一

```scheme
(register-damage-formula "lostland:default_damage_formula"
  (quote
    (max
      (/ (* (- attack-power
               (max 0 (mul-permille (- defense pen-flat) (- 1000 pen-permille))))
            1000)
         (+ 1000 (max 0 (mul-permille (- defense pen-flat) (- 1000 pen-permille)))))
      (mul-permille attack-power 100))))
```

逐项对照 `attribute-system.md` §四：`(mul-permille (- defense pen-flat) (- 1000 pen-permille))` 即「(防御−穿透.flat)×(1000−穿透.permille)/1000」,外层 `max 0` 即有效防御的下界钳制；`(- attack-power 有效防御)` 除以 `(+ 1000 有效防御)` 再乘 1000 即比例项减免；最外层 `max` 与 `(mul-permille attack-power 100)` 即 10% 下限——**与本体现有 Rust 实现逐行对应,不是重新发明**,这也是本体自己「即便走 mod API 也不吃亏」（ADR 0016 守门规则）的直接验证：本体的默认公式与任何 mod 公式用同一条注册路径、同一套指令集表达。

### 示例二：骰子驱动的"重击巨斧"，风格二——与示例一在四个维度上都不同

```scheme
(register-damage-formula "mymod:reckless_greataxe_formula"
  (quote
    (max 1
      (- (if (= crit 1)
             (+ (d 2 12) str-mod)
             (+ (d 1 12) str-mod))
         (max 0 (- defense pen-flat))))))
```

**这为什么算「不同的一套规则」而不是调系数**：

1. **随机性的引入方式不同**——示例一恒定确定（同样的攻防输入永远算出同样的伤害），示例二每次攻击的基础伤害由 `1d12`（暴击时 `2d12`，D&D 5e 的真实暴击规则：骰子数翻倍，调整值不翻倍，`str-mod` 只加一次）决定,这不是「给示例一的结果乘一个随机系数」,是从代数公式换成了概率分布——分布的形状（`1d12` 的均匀离散分布 vs 示例一的确定性映射）本身就是设计选择,不可能靠调整示例一的某个系数得到。
2. **减伤模型的结构不同**——示例一的百分比比例项（`× 1000/(1000+有效防御)`）在示例二里完全不存在,减伤只是线性减法（`攻击力 − 有效防御`）,且**完全无视千分比穿透**（`pen-permille` 从未被引用）——对拿着「破魔穿透」词条的角色而言,这把巨斧的减伤行为与拿着示例一公式的武器截然不同,这是两套武器与穿透系统的**交互方式**不同,不是数值不同。
3. **下限的语义不同**——示例一的下限是「攻击力的 10%」（跟随攻击力浮动）,示例二的下限是绝对值「1」（不跟随任何输入浮动，「这把斧子这一下无论如何至少划出一道口子」）——一个是百分比保底,一个是「不为 0」保底,两种设计承诺不同,回应的玩家体验也不同（示例一保证「高伤害武器永远有存在感」,示例二只保证「never完全打空」)。
4. **暴击的处理点不同**——示例一没有暴击概念,示例二把暴击接进了骰子数量（而不是像常见做法那样简单把最终结果乘二）,这是 D&D 5e 的真实规则细节（暴击翻倍的是「骰子」不是「加成」）,本体默认公式没有对应的表达位置——想在示例一的公式结构里加同样的暴击语义,需要重新设计公式,不是调一个系数能做到的。

### 示例三：多轮判定的"连续突刺"匕首——展示与既有减伤链路正交共存（五节机制的具体示范）

```scheme
(register-damage-formula "mymod:flurry_dagger_formula"
  (quote
    (max
      (/ (* (- (multi-hit 5 700 (d 1 4))
               (max 0 (mul-permille (- defense pen-flat) (- 1000 pen-permille))))
            1000)
         (+ 1000 (max 0 (mul-permille (- defense pen-flat) (- 1000 pen-permille)))))
      (mul-permille (multi-hit 5 700 (d 1 4)) 100))))
```

**这为什么既是「不同的规则」又不是推翻既有系统**：`(multi-hit 5 700 (d 1 4))` 是「5 次独立判定，每次 70% 概率命中，命中打 1d4」——与示例一（恒定攻击力）、示例二（单次大骰子）在**随机性的形状**上是第三种、彼此都不同的样子（二项分布 × 骰子，而不是恒定值或单个骰子的均匀分布）；但公式的**减伤部分**（`mul-permille`/`max 0`/外层比例项/10% 下限）与示例一逐字相同——`multi-hit` 算出的总量只是替换了 `attack-power` 这个输入的来源,减伤链路本身完全未改。这是五节结论（"多轮判定与减伤模型正交,不是三选一"）的直接落地证明,不是纸面论证。

## 五、命中/减伤模型：多轮判定评估，与既有减伤模型正交共存，不是三选一

### 重新出发：项目所有者松绑了"照抄 AC 或维持现状"这个二选一

第一轮否决方案乙（纯 AC）的理由是「二元命中会制造连续几回合全砍空,与 10% 下限当初要防的死局是同一种劝退」。项目所有者的回应不是要求照抄 AC,而是指出一条更贴合本项目的路：**把一次攻击拆成 `N` 次独立的小判定,每次判定命中就贡献一部分伤害,整体伤害是这 `N` 次判定的加权和**。这条路确实解掉了纯 AC 的反对理由——全部落空的概率是 `(1 − 命中率)^N`,随 `N` 指数下降,期望值不受影响,方差被摊平（`N` 次独立贝努利分布之和,`N` 越大越集中在期望值附近）。本节认真评估这条路,并给出最终结论。

### 评估结论：采纳，但不是"替换减伤模型"，是"多轮判定产出的总量，作为减伤公式的攻击力输入"——两者正交，不是三选一

**多轮判定解决的问题（"这一下会不会因为运气差而形同没打"）与减伤公式解决的问题（"面对高防御目标，会不会打不穿"）是两个不同来源的"打不疼",不是同一个机制的两种实现**——因此正确的整合方式不是"选多轮判定就必须放弃减伤公式"（否决），而是让多轮判定成为**攻击力这个输入本身的一种新算法**,产出的总量像本文档一直以来的 `attack-power` 一样,**照常送进现有的、不改一个字的减伤公式**（十一节示例一那套「固定减 + 百分比减 + 10% 下限」）。这既不是「方案甲」（骰子只算 attack-power，不含命中概念）,也不是「方案乙」（二元命中,减伤退场）,是两者的正交组合：

```
attack-power 的来源，现在有三种可以任选（mod 作者在表达式里自由组合）：
  纯数值:        str-mod、常量……
  单次骰子:      (d 1 8)、(adv (d 1 20)) ……
  多轮判定:      (multi-hit 5 700 (d 1 4))  —— 5 轮，每轮 70% 命中，命中打 1d4

算出的 attack-power，无论来自哪一种，都送进同一套未改动的减伤链路：
  有效防御 = max(0, (defense − pen-flat) × (1000 − pen-permille) / 1000)
  减后伤害 = (attack-power − 有效防御) × 1000 / (1000 + 有效防御)
  最终伤害 = max(减后伤害, attack-power × 100 / 1000)
```

**`damage_after_defense` 与它的单元测试完全不受影响，明确声明**：本文档不改动 `crates/ll-sim/src/combat.rs` 的 `damage_after_defense`,也不使 `防御极高时伤害仍不低于攻击力的一成` 这条测试变得冗余或失效——多轮判定只是产出了一个新的、**在减伤链路开始之前就已经算好**的 `attack-power` 数值,减伤链路本身（含 10% 下限）原封不动地继续处理这个数值,与它是「一个固定属性」「一次骰子」还是「五轮判定的加权和」无关。减伤链路不知道、也不需要知道 `attack-power` 是怎么来的。

### `N` 由谁定：mod 作者，作为表达式的一部分

`multi-hit` 的第一个参数 `N`（`rounds`）**是表达式的一部分,由撰写这份公式的 mod 决定**——不是引擎写死的全局常量,也不是从武器的某个别的字段派生。这与 `(d N S)` 的 `N`/`S` 是同一种处理方式：字面整数常量,注册期校验范围（三节新增第 8 条：`N ∈ [1, 10]`）。**这意味着"要不要用多轮判定、用几轮"完全是内容设计层面的选择**——本体默认公式（十一节示例一沿用的既有公式）不使用 `multi-hit`（保持与现有 `resolve_attack` 行为一致，`attack-power` 直接是 `attacker.stats.strength`）；某把强调"打得又快又碎"的武器可以声明 `(multi-hit 5 700 (d 1 4))`；某把强调"一击入魂"的武器可以完全不用多轮判定,只用 `(d 2 12)` 一次性掷出大骰子——两种设计哲学被同一套表达式体系表达,互不干扰。

### 求值次数：数组整体只跑一遍，`N` 表达为一条指令内部的有界重复，不是重跑整个数组

**`multi-hit` 编译成`Vec<FormulaOp>` 里的**一条**指令**（`FormulaOp::MultiRoundHit { rounds, hit_chance_permille, per_hit_damage }`），**不是把整份表达式数组重复 `N` 遍**。求值器遍历指令数组仍然是「每条指令执行一次」（六节已定的既有纪律，不因为多轮判定被打破）,只是遇到这一条指令时,它的内部实现要连续做 `rounds` 次"抽一个随机千分比、与 `hit_chance_permille` 比较、命中则累加 `per_hit_damage`"——这与 `Dice { count, sides }` 内部"连续抽 `count` 次求和"是完全同一个模式（三节已经在用),`multi-hit` 只是把"抽随机数求和"换成"抽随机数做判定、判定通过才累加"，**指令集的"有界执行时间"保证没有被打破**：`rounds` 在编译期就已知（三节新增校验第 8 条),这条指令的执行时间是一个编译期就能算出的确定上限（≤ 10 次比较+条件加法),与 `Dice` 指令"这条指令内部有界重复"是同一类保证,不是引入了新的、运行期才能确定的循环。

**为什么"每轮命中量不逐轮重掷"（`per_hit_damage` 只算一次,不为每一轮各自摇骰子）**：若允许每一轮各自重新求值一个含骰子的子表达式,`multi-hit` 就不再是"一条指令内部的有界重复",而是"重复执行一段任意长度的子指令序列 `N` 次"——这会让指令集从"固定次数的原语内部循环"滑向"真正的、需要专门处理嵌套子程序的循环结构",复杂度显著上升（编译器需要处理"子表达式在一条指令内被重复引用"这类新问题）,却只换来"随机性来源从『命中与否的二值抽取』变成『命中与否 + 伤害量的联合抽取』"这一点点额外的方差来源——收益不足以覆盖复杂度代价（YAGNI）。**这不代表逐轮伤害不能变化**——`per_hit_damage` 完全可以是 `(d 1 4)` 这类表达式的结果,只是这个骰子在**求值这条 `multi-hit` 指令之前**先摇一次、摇出一个值,之后 `N` 轮里凡是命中的都用同一个数;若确实需要"每轮伤害独立浮动",应该在 `rounds` 与 `per_hit_damage` 的取舍上倾向"更多轮、更小的固定值"（例如 `(multi-hit 8 600 1)` 而不是 `(multi-hit 2 600 (d 1 8))`）,用轮数本身的随机性替代逐轮重新掷骰,这与本文档"用有界重复而非真正循环表达变化"的一贯思路一致。

### C3 取数顺序：延伤直接复用六节已定的"单条共享流,程序顺序取数"，多轮只是多消耗几次

`multi-hit` 消耗随机流的方式与骰子指令完全同构，不需要新机制：

1. `MultiRoundHit` 同样计入 `FormulaDef::needs_rng`（六节已定义的编译期布尔，现在的判定条件扩展为「含 `Dice`/`AdvantageRoll`/`DisadvantageRoll`/`MultiRoundHit` 任意一种」)。
2. 求值到这条指令时,从**同一条**（六节已定：整个公式求值共享一条流,不是每条指令各开一条)流里**连续**取 `rounds` 个「命中判定」抽取——第 1 轮用流里的下一个值算「本轮是否命中」,第 2 轮用再下一个值,以此类推,严格按轮次序号 1..rounds 取值,不并行、不乱序。
3. 若 `per_hit_damage` 本身含骰子（例如 `(d 1 4)`），按六节已定的"深度优先、从左到右展开"规则,这个骰子的取值发生在 `MultiRoundHit` 指令本身求值**之前**（它是这条指令的一个操作数,操作数总是先于使用它的指令被求值,与既有 `Add`/`Sub` 等指令的操作数求值顺序完全一致）——取数顺序因此仍然完全由编译产物的指令数组顺序决定,不依赖任何运行期状态,与六节「多骰子的取数顺序为什么确定」是同一条论证的直接复用。

**这一次的确比之前更吃紧**（项目所有者原话）：一次攻击如果同时用了骰子伤害与多轮判定,单次公式求值消耗的随机抽取次数会明显变多（例如 `(multi-hit 8 700 (d 1 4))` 一次求值最多消耗 `1（前置骰子）+ 8（命中判定）= 9` 次抽取)——但**取数次数变多不改变"顺序是否确定"这件事**,顺序确定性来自"同一条流 + 程序计数器式的固定遍历顺序"这个机制本身,与消耗多少次无关,`N` 次和 `1` 次在这条纪律下没有本质区别,只是次数不同。真正需要留意的是性能量级：`rounds ≤ 10` 的校验（三节）正是为了让"多轮判定让单次求值变慢"这件事有一个可预期的上限,不会因为某个 mod 写了一个过大的 `N` 而让本文档二节论证过的"纳秒级、可承受"的开销预算失控。

### 10% 下限是否还有必要：有必要，两者解决的是不同来源的"打不疼"

**结论：有必要，不冗余。** 多轮判定摊平的是**随机性带来的方差**（运气差导致这一下伤害偏低,即便期望值正常）;10% 下限防的是**防御数值本身带来的系统性压制**（对方防御高到让 `attack-power − 有效防御` 趋近于零或更低,不论掷骰结果好坏,减伤链路本身就会把伤害压得很低）。两者是正交的：

- 一把完全不用 `multi-hit`、`attack-power` 恒定的武器（例如本体默认公式,`attack-power = attacker.stats.strength`,没有任何随机性）,面对极高防御的目标时依然需要 10% 下限兜底——多轮判定在这种场景里根本不存在,救不了它。
- 一把用了 `multi-hit` 的武器,即使摊平了"运气差全砍空"的风险,面对极高防御目标时,`multi-hit` 算出的 `attack-power` 总量**依然要送进同一套减伤链路**,若这个防御高到让减伤链路本身把结果压到接近零,10% 下限依然是唯一的兜底——多轮判定只保证"多轮判定这一步产出的 `attack-power` 本身不会因为运气而归零",**不保证减伤链路后续不会把这个已经算好的数字再压到接近零**,这是两个独立的步骤,各自需要各自的安全网。

**所以：多轮判定不取代 10% 下限,是给"随机性来源"多提供一种更平滑的选项;10% 下限继续是减伤链路自己的、与随机性来源无关的兜底。** `damage_after_defense` 的既有测试因此继续有效,继续保护一个真实存在、且多轮判定完全没有触及的问题。

### 被否决的具体形态（多轮判定内部的设计选择）

- **纯 AC 二元命中**——否决：会推翻 `damage_after_defense` 已经过测试守护的既有实现,需要新增一个本项目战斗系统目前完全没有的「AC/命中判定」派生属性与判定点（超出本次任务范围，YAGNI），且「10% 下限」这句承诺在二元命中下没有对应的机制承接——未命中就是 0 伤害,不存在"减伤后夹一个下限"这一步,要解决"完全打不动"的死局只能换一套完全不同的手段（例如给命中率本身设一个硬下限），不是简单迁移。多轮判定不是"温和版的 AC"，是完全不同的机制（AC 是"一次判定决定全部",多轮判定是"许多次判定各自决定一小部分",两者的数学性质——尤其是方差随判定次数的变化方向——是相反的)。
- **每轮伤害各自重新掷骰**——否决,见上文「为什么每轮命中量不逐轮重掷」：需要真正的循环/子程序机制,复杂度代价不成比例,用"更多轮、更小固定值"可以达到类似的平滑效果。
- **每轮各自独立走一遍完整减伤公式（穿透、百分比、下限都按轮计算）**——否决：一次攻击算 `N` 次完整减伤链路,运行期成本乘以 `N`,而多轮判定要解决的问题只是「原始攻击力怎么来」,不需要防御也按轮拆分——防御是针对"这一下攻击"整体的属性,不是针对"这一下攻击的第几轮"，拆开计算没有对应的设计意图,纯粹是不必要的复杂度。
- **`N` 由引擎写死或由武器的某个已有数值字段派生（而不是表达式自己声明）**——否决：`N` 本质上是"这把武器/技能的设计选择的一部分"（"这是一把打五下的武器还是打一下的武器"),与调整值/骰子面数处在同一个层级,理应像它们一样由表达式直接声明,不需要发明一个额外的"武器属性"间接指定它，那样反而多了一层不必要的映射。

## 六、随机数与骰子求值：单条共享流，程序顺序取数，不破坏 C3

### 骰子算子与算术算子是不是同一类节点：是——区别体现在求值时的副作用，不体现在节点类型上

`Dice`/`AdvantageRoll`/`DisadvantageRoll`/`MultiRoundHit` 与 `Add`/`Sub`/`Select` 等**同属 `FormulaOp` 的变体，插在同一个扁平数组里**,求值循环用同一个 `match` 按类型分派,骰子/多轮判定类分支多做一件事——从传入的随机流里取值,算术类分支不做这件事,**仅此而已,不存在"骰子节点"与"算术节点"两套并行的求值机制或两种不同的数组**。这个区别在编译期就完全已知（一条指令是不是消耗随机数的类型,是语法决定的,不依赖任何运行期状态）,因此可以在编译完成的那一刻就算出 `FormulaDef::needs_rng`（指令数组里只要有任意一条 `Dice`/`AdvantageRoll`/`DisadvantageRoll`/`MultiRoundHit`，这个布尔就是真）,供调用方决定要不要在求值前构造随机流——**这是一个编译期可判定的静态属性,不是运行期才知道的事实**。

### 取数机制：调用方构造一条流，求值器按程序顺序（指令下标升序）从这条流里顺序取值

**与既有脚本 API 的 `rng-gen-range` 同一条纪律**（`crates/ll-script/src/api/rng.rs`：「脚本拿不到种子本身……宿主在每次调用前用 `DetRng::for_entity` 构造好一个流,脚本只能『要下一个数』」)：

1. `resolve` 在调用公式求值**之前**,若 `FormulaDef::needs_rng == true`,用 `DetRng::for_entity(world.seed, attacker_id, event_counter)` 构造**恰好一条**流（`event_counter` 是这次攻击专属的一个单调计数,与该实体其余随机消耗——例如未来可能的命中判定——各自占用独立的计数位,不与本文档无关）。
2. 求值器按**指令数组下标升序**遍历,遇到 `Dice { count, sides }` 就从这条流里连续取 `count` 个 `gen_range(sides) + 1`，按取出顺序求和；遇到 `AdvantageRoll`/`DisadvantageRoll` 就**连续两次**对同一个 `(count, sides)` 重复上述取值过程（先取「roll A」的 `count` 个值求和,再取「roll B」的 `count` 个值求和),结果取两次和的较大值/较小值。
3. 算术类指令（`Add`/`Sub`/…）不触碰这条流,直接读取操作数当前已经算好的值。

**多骰子的取数顺序为什么确定**：因为公式一旦编译完成,指令数组的顺序是固定的（三节：作者写嵌套表达式,编译器做深度优先、从左到右的展开）,**同一个 `FormulaDef` 每次求值,访问骰子指令的顺序永远相同**——`(+ (d 1 8) (d 1 4))` 编译后 `(d 1 8)` 在数组里排在 `(d 1 4)` 之前（左操作数先展开是编译器的固定规则),求值器严格按下标升序遍历,`(d 1 8)` 永远先从流里取值,`(d 1 4)` 永远后取——**不存在"这次谁先取谁后取不确定"的问题**,因为"谁先谁后"从编译产物的数组顺序那一刻起就已经固定,不依赖任何运行期状态。**一个 `Dice` 指令内部的 `count` 个骰子同理**：固定按「第 1 个、第 2 个……第 count 个」的顺序连续取值,不是并行、不是乱序。

**为什么是"一条共享流"而不是"每条骰子指令各自开一条流"**：一条流更简单——`resolve` 只需要决定一次「这次攻击的随机流从哪个 `event_counter` 开始」,不需要给公式里每一条骰子指令分别分配一个独立的 `event_counter`（那样反而需要在编译期给每条骰子指令编号,增加不必要的复杂度）。这与脚本层「一次调用里连续要好几个数」（`rng-next-u64` 可以在同一次 Steel 调用里被连续调用多次,共享同一条流）是同一个思路——**流是「这次求值」的资源,不是「这条指令」的资源**。

### `Select`（`if`）分支：两侧都无条件求值——一个明确的取舍，不是疏漏

三节的编译产物是**扁平数组,不含真正的控制流跳转**——`if` 编译出的 `Select` 指令，`if_true`/`if_false` 两个操作数对应的子表达式**都会被无条件求值**（各自的指令仍然在数组里、仍然会被执行到）,`Select` 只是在两个已经算好的值之间挑一个。**这意味着即使某次攻击没有暴击,`(+ (d 2 12) str-mod)` 这个"暴击专用"分支仍然会掷骰、消耗一次随机抽取**——是刻意的取舍,不是遗漏：

- **好处**：求值器永远是"每条指令恰好执行一次",不需要实现"跳过某个分支不执行"的控制流逻辑,复杂度更低,而且给出一个比"有界"更强的保证——**每次求值消耗的指令数与随机抽取次数是一个固定值,不随运行期条件变化**,不需要在"公式最坏情况下要跑多久/摇几次骰子"这个问题上考虑分支组合。
- **代价**：多消耗一点随机流位置（两个分支都摇了骰子,只用一个）——这个代价是纯粹的"随机数生成器往前多走了几步",不产生任何可观测的游戏效果差异（未选中分支的骰子结果被计算出来又被丢弃,不会被任何后续状态读取到),也不影响确定性（同样的输入,同样的分支选择,同样的求值路径,逐位可重放）。
- **需要更省随机数的场景怎么办**：不要在 `if` 的分支里塞骰子——把「要不要暴击」这类判断放到公式**之外**（`resolve` 用一次 `rng-chance`/`gen_range` 判定,结果作为 `crit` 操作数喂给公式,公式内部只用 `crit` 做算术/条件判断,不再需要在分支里重新摇骰子）。示例二的 `crit` 用法正是这个推荐模式的示范——`crit` 本身不消耗公式内部的随机流,是调用方在公式求值前就已经判定好、以「不可再分」的整数形式喂进来的。

## 七、幸运 ↔ 优势/劣势骰：机制相同，但目前只在"判定"上生效，不在"伤害骰"上——如实指出，不强行圆

### 机制层面：确实是同一个原语

`attribute-system.md` §五：「优势掷骰：幸运每满 20 点，判定时多掷一次取较优（DnD 的 advantage 机制）」——这句话描述的正是「掷两次取较大值」，与本文档三节定义的 `AdvantageRoll`（`adv`）是**同一个数学操作**，`attribute-system.md` 原文括号里已经点名「DnD 的 advantage 机制」,只是没有落成一份具体的表达式语法。本文档把这个已有的文字描述,第一次给出可执行的形状（`(adv (d N S))`）。

### 但目前没有自然的挂载点：本项目战斗里没有「判定」这一步

`attribute-system.md` §五/§八说的「判定」，具体所指是 §八「掷骰 = `DetRng::for_entity(...).gen_range(20) + 1`；成功 ⟺ 掷骰 + 调整值 ≥ 难度等级」这类**成功/失败二元检定**（技能检定、能力检定），**不是伤害数值计算**。而 `resolve_attack` 目前（且本文档五节选定的方案甲维持这一点）**完全没有"这次攻击是否命中"这一步判定**——攻击恒命中,只有伤害数值会变。这意味着：

**幸运的「优势掷骰」机制,按 `attribute-system.md` 现有文字,目前在"战斗"这个场景下没有天然的挂载对象**——它服务的是"判定",而战斗当前不做判定。若未来方案乙（或类似的命中检定机制）真的落地,幸运驱动的优势骰应该挂在**那次命中检定的 d20 掷骰**上,用的正是本文档定义的同一个 `AdvantageRoll` 原语（复用,不是重新发明）;但在当前方案甲下,`adv`/`disadv` 这两个原语在伤害表达式里**依然可用**——它们不专属于"幸运驱动的判定",是通用的"掷两次取一边"原语,mod 作者完全可以写一把武器「这一下伤害骰是有利骰」（`(adv (d 1 8))`）,这与角色的幸运属性无关,是武器自己的设计意图,与四节示例二的 `crit` 是同一层次的"公式内部自带的随机特征",不需要外部的幸运数值驱动。

### 幸运真正接进伤害表达式的地方：暴击率，不是优势骰

`attribute-system.md` §五「暴击率：每点幸运 +5‰」**是**一条能在当前架构下直接生效、且服务"伤害"而非"判定"的幸运效果——`resolve` 在调用公式求值之前,用幸运值算出暴击千分比,走一次 `rng-chance`（脚本 API 已有的同名原语 `rng-chance permille` 的 Rust 侧对应实现,或直接调用 `DetRng` 等价逻辑）判定这一下是否暴击,结果作为 `crit` 操作数喂给公式——四节示例二的 `crit` 用法正是这条真实接线的样子。

**结论（如实标注，不强行圆）**：幸运→优势骰,机制相同,但当前只服务"判定"（本项目战斗目前没有这一步）；幸运→暴击率,机制不同（不是"掷两次取一边",是"按概率决定走哪个分支"),但**是**当前架构下真正能接进伤害表达式的幸运效果。本文档把 `adv`/`disadv` 设计成通用原语（不专属于幸运)、把 `crit` 设计成暴击的真实接线点——两者都在,但服务的是伤害表达式系统里两个不同的位置,不是同一件事的两种写法。

## 八、浮点边界与 `Milli`（[ADR 0020](../decisions/0020-scripts-may-use-floats-internally-boundary-type-gated.md)）

与第一版结论相同，s-表达式改动不影响这一节的论证，摘要如下（完整论证见 [ADR 0020](../decisions/0020-scripts-may-use-floats-internally-boundary-type-gated.md) 原文）：

- **编译产物里没有浮点存在的空间**——`FormulaOp`/`FormulaOperand` 全部是 `i64`/`u32`，没有浮点变体，求值全程整数运算，不经过 Steel VM，ADR 0020「残余风险」一节的窄风险（超越函数+粗量化）在这条路径上完全不存在。
- **浮点只可能出现在 `register-damage-formula` 这次一次性调用本身的 Steel 侧计算里**（例如作者用浮点算出一个系数再 `quantize-round` 成整数字面量写进表达式）——这不是本文档新引入的规则,是 ADR 0020「`register_fn` 边界只接受整数与 `Milli`」的既有纪律的直接应用。
- **`Milli` 与千分比共用同一个刻度**（`SCALE = 1000` 与 `PERMILLE_SCALE = 1000` 恰好相同）——`mul-permille` 这条原语同时可以服务两种语义,不需要为 `Milli` 单独发明一条指令。
- **除法舍入方向：截断（向零）**，与既有 `combat.rs` 实现一致，不引入第二套舍入约定。

## 九、伤害类型与抗性：目前都不存在，本节只给未来的容纳形状

### 核实结论

- **伤害系别（`DamageSchool`：物理/魔法/精神）**——存在于**设计**（[三轴战斗结算](combat-three-axis.md)），**代码中不存在**（该文档「落地状态」已标注纯设计）。
- **元素伤害类型（火/冰/雷/毒/暗/光）与状态抗性（流血/中毒/眩晕……）**——只在 `attribute-system.md` §六「次级属性」的一份**名词清单**里出现,**没有任何数值规则**（没有减免百分比、没有免疫/易伤倍率、没有任何字段定义），该文档「落地状态」明确标注次级属性「均未落地」。
- **免疫/半伤/双倍这类抗性乘数机制**——**在本项目任何设计文档或代码里都不存在**，是本文档核实后确认的一处真正的空白，不是遗漏去找。

**结论：伤害类型与抗性系统都不存在，符合项目所有者的预判。本文档不实现它——不止是「实现属于代码任务、本文档只做设计」这条一般理由，是这个系统本身连数值规则都还没有被设计过，本文档若现在就为它设计表达式接口，等于在一个空白上凭空捏造需求形状（YAGNI 的双重违反：既不需要，也没有可以参照的既有设计）。**

### 未来怎么容纳，不需要改动本文档的指令集

若未来伤害类型/抗性系统落地,自然的接线方式是给 `FormulaOperand` 追加一个 `ResistanceMultiplier` 变体（`resolve` 按命中目标对该伤害类型的抗性,算出一个千分比乘数,类似 `PenetrationPermille` 已经存在的接线方式——免疫 = `0`、半伤 = `500`、双倍 = `2000`），公式作者只需要在末尾追加一条 `(mul-permille 结果 resistance-multiplier)`——**不需要修改指令集本身**（`mul-permille` 已经存在），只需要新增一个输入槽,这与 `PenetrationFlat`/`PenetrationPermille` 当初被设计成独立槽位而不是揉进 `Defense` 里是同一个思路的复用。本文档只给出这个形状,不现在实现,也不现在追加这个操作数变体（真正落地时再加,现在加一个没有任何生产者会填值的字段没有意义）。

## 十、协议边界：机制可以照抄，SRD 具体文本不行

**D&D 5e SRD（System Reference Document）以 CC-BY-4.0（5.1 版本）或 Open Game License（更早版本）发布**——这两份协议覆盖的是 SRD 收录的**具体文本**（法术描述、怪物属性块、条件效果的具体措辞……），**不覆盖游戏机制本身**——骰子记号（`XdY+Z`）、优势/劣势（掷两次取高/取低）这类**规则的抽象概念**在通行的著作权理论下属于"思想/系统/方法"（idea-expression dichotomy 下不受著作权保护的一侧），且骰子记号本身在 D&D 之外的桌游/TRPG 传统里早已是通用记法,不是 D&D 独占发明。本文档设计的表达式语法借用的正是这一层——**记号本身、优势/劣势这个数学操作、暴击"骰子翻倍"这类规则性描述,可以自由使用**。

**但绝不能做的事**：把 SRD 里的**具体内容**原样搬进本项目——法术的具体描述文本、怪物条目的属性块与背景文字、条件效果的规则原文措辞,这些是 SRD 受协议保护、需要遵守署名/等同方式共享等条款的**表达**部分,不是"机制"。本文档四节的两个示例、以及未来任何具体武器/技能的数值内容,应该是**本项目自己设计的内容**,借用的只是"用骰子表达伤害"这个记法习惯,不是照搬某本 SRD 手册的具体条目。

**这与本项目一贯的协议谨慎姿态一致**——字体选 OFL-1.1、图标选 MIT,都带着许可文件与来源说明；本文档在这里把同一条纪律写清楚,是为了让未来任何往 mod 内容里添加具体数值/法术/怪物设定的人,有一条明确的边界可以对照,不需要每次都重新判断"这样写算不算抄"。

## 十一、替换还是叠加：按内容各自声明，不是全局单例

（与第一版结论相同，字段名从 `damage_formula` 沿用，摘要如下）

**替换，不是叠加**——一个武器/技能引用**恰好一个** `FormulaDef`（`ContentIndex`），这个公式的输出就是这一下的基础伤害数。**命中之后的追加效果**（吸血、中毒、连锁触发）永远是 [增益与通用触发器](buffs-and-triggers.md) 的地盘，不会被公式机制吞并——公式回答「这一下伤害是多少」，触发器回答「命中之后还发生什么」。

**不是全局一套**：每个武器/技能定义新增 `damage_formula: ContentIndex` 字段（挂在 [三轴战斗结算](combat-three-axis.md) §四已定的接线点上，与 `aim_shape`/`damage_school`/`delivery` 同级），本体默认全部指向 `lostland:default_damage_formula`（四节示例一）。mod 若想让自己的新武器走不同规则，注册自己命名空间下的新公式即可——命名空间隔离天然避免冲突，不需要额外机制。

**两个 mod 都想替换伤害公式怎么办**：区分「各自开一把新武器」（天然无冲突）与「争抢同一件已存在的内容」（例如都想改写 `lostland:iron_sword` 或 `lostland:default_damage_formula` 本身）。后者不是伤害公式独有的问题,是"内容注册表里一个已经被定义过的 `ContentIndex` 能不能被另一个 mod 重新 `define`"这个更通用的问题（武器/地形/公式皆然）,本文档复用项目已经在资产覆盖场景验证过的既有解法（[mod 包结构与资产 VFS](mod-package-structure.md)「覆盖冲突」一节）：**`topo_sort`（`crates/ll-mod/src/topo.rs`）确定性总序决定谁的覆盖生效，且必须可见——`LoadStatus::Warning(String)`（`crates/ll-mod/src/load_report.rs`）产出一条明确指出"被谁覆盖、当前生效谁"的诊断**,不是本文档单独发明一套解法。

**全局一套还是按类型各一套**：都不是,按内容各自声明，允许共享——本体三系默认共享同一个公式（当前数值结构同构），不是机制强制。

## 十二、公式出错怎么办

### 分类处理

| 错误类型 | 何时能发现 | 处理方式 |
|---|---|---|
| 引用了不在封闭表里的符号（含笔误、`lambda`、`define`……） | **注册期** | `ModError::UnknownFormulaSymbol`，mod 整体拒绝加载（三节已述） |
| 骰子参数越界（`N`/`S` 超出 `[1,20]`/`[2,1000]`） | 注册期 | `ModError::FormulaDiceOutOfRange`，mod 整体拒绝加载 |
| 除数是编译期常量 `0` | 注册期 | `ModError::FormulaConstantDivisionByZero`，mod 整体拒绝加载 |
| 除数是运行期才知道的操作数，恰好算出 `0` | 只能运行期发现 | 见下「运行期除零」 |
| 溢出（`i64` 运算超界） | 只能运行期发现 | 饱和运算，见下 |
| 最终结果为负数 | 只能运行期发现 | 调用方兜底，见下 |

### 运行期除零：`checked_div` 失败时落回本体默认公式，并留痕

除数是运行期才知道的操作数（例如 `Local(i)` 的结果）时,编译期无法证明恒非零,`Div` 求值必须用 `checked_div` 而不是裸 `/`（后者会 panic）。`checked_div` 返回 `None` 时：**这一下攻击改用 `lostland:default_damage_formula` 重新计算,并产出一条运行期诊断**（复用 `ScriptDiagnostic` 同一套「非致命但值得作者注意」的落点,或加载管理界面里按 mod 分组的运行期健康计数器）。理由：不能 panic（规格 §14.3）；不能静默丢弃这一下攻击（会把 bug 伪装成"没打中"，违反「不得静默失败」）；必须落回本体默认公式而不是任意兜底常数——本体默认公式（十节示例一）的除数恒为 `1000 + effective_defense ≥ 1000 > 0`,对任何合法输入不可能除零,是一个已知安全的全函数,用它兜底比用魔法常数更有意义；必须留痕,否则 mod 作者永远不会发现自己的公式有隐藏的除零路径。

### 运行期溢出：饱和运算

求值器全程使用 `saturating_*` 系列运算,结果超出 `i64` 范围时钳到边界值,不 panic、不回绕,跨平台确定（饱和运算是硬件/IEEE 无关的整数规则）。

### 负数伤害：调用方结构性兜底

`resolve` 在拿到公式求值结果后必须做 `max(0, 结果)` 才能构造 `Effect::Damage { amount }`——**这是调用方结构性保证**，不依赖任何一个具体公式的作者是否记得在表达式末尾加 `(max 0 ...)`（虽然示例二这么做了）。与 [ADR 0020](../decisions/0020-scripts-may-use-floats-internally-boundary-type-gated.md) 「`(quantize-damage x)`：取整规则固定为向下取整,下界钳制到 0」是同一条纪律在这里的复现。

## 十三、与既有系统的接口

### 与三轴战斗结算

`damage_formula: ContentIndex` 字段挂在 [三轴战斗结算](combat-three-axis.md) §四的接线点上,与 `aim_shape`/`damage_school`/`delivery` 同级。`resolve` 展开出命中目标集合后,对每个目标：按 `damage_school` 选出攻防字段,填好 `AttackPower`/`Defense`/`PenetrationFlat`/`PenetrationPermille`/`AttributeModifier`/`Crit`（六、七节已定的求值前输入准备）,若 `needs_rng` 为真则额外构造一条 `DetRng` 流,查 `damage_formula` 指向的 `FormulaDef`,跑指令数组,拿到这一下的伤害数——不改变该文档已定的「按 `EntityId` 升序逐个产出」的确定性展开顺序。

**顺带补上一节已核实的缺口**：`resolve_use_skill` 的 `SkillEffect::DealDamage` 目前完全绕过 `damage_after_defense`。本机制落地时应该改为读取该技能定义的 `damage_formula`,与 `resolve_attack` 走同一条求值路径——武器与技能只是两种不同的 `damage_formula` 载体,不该有两条独立的伤害结算代码。留给实现批次。

### 与增益/通用触发器

[增益与通用触发器](buffs-and-triggers.md) §三 `TriggerResponse::Formula(/* 占位，本文档不展开 */)` 正是本文档要填的那个占位——触发器的二档「受限公式」与本文档设计的是**同一套** `FormulaDef`/`FormulaOp` 机制、**同一套** s-表达式语法（可能需要给 `FormulaOperand` 追加一个 `TriggerDamage` 变体,代表「触发这次响应的那个 `Effect::Damage` 的数值」,是操作数枚举面向触发器场景的自然扩展,不改变核心机制)。这也是对二档定档的一次交叉验证——同一套机制既能表达"攻防到伤害"的主算式,也能表达"触发响应"的附加算式,证明这不是为伤害公式量身定做的一次性方案。

**on-hit 效果要不要也走这套**：命中判定本身不走这套（那是概率判定，本项目目前恒命中，方案甲维持这一点）。命中**之后**的数值型响应（吸血、反伤、持续伤害的单次跳字）适合走本机制，已在上一段说明。

### 与击杀记录

**`KillCause` 不需要记录用了哪套公式**——`KillCause::Melee { weapon }`/`KillCause::Skill { skill }` 已经携带武器/技能的 `ContentIndex`,而武器/技能定义本身携带 `damage_formula` 字段,「这一下用哪套公式打的」永远可以反查一步得到,在 `KillCause` 里再存一份是冗余数据。若某次击杀是「运行期除零后落回默认公式」算出来的,这个降级事实归运行期诊断/mod 健康计数器管,不归 `KillCause`——两条线服务不同的读者（mod 作者调试 vs 玩家叙事）,`kill-and-death-events.md`「克制」一节的基调同样适用于这里。

## 十四、阶段归属（规格 §15）

**机制本身（`FormulaOp`/`FormulaOperand` 类型、s-表达式编译器、求值器）归 P4**——`ll-mod` 已建立,第二档尚未实现的部分,理应与它同批。**`register-damage-formula` 这个 Steel 表面归 P4**,与既有六个 `register-*` 函数同批,注册表 API 不依赖武器系统是否已存在。**接入战斗结算（`WeaponDef.damage_formula` 字段、`resolve` 调用点）归 P6「物品与装备」**——与 [三轴战斗结算](combat-three-axis.md) 的既有归属完全一致，武器/技能定义本身也是 P6 才落地的东西。

## 十五、被否决的方案汇总

- **一档能不能凑合表达**——否决：运行期需要消费只有那一刻才存在的输入，一档物化前提不成立。
- **判成"一档+二档混合"**——否决：装载形态与运行期成本是两个独立的轴,分类判据只看后者,不存在中间态（二节详细论证）。
- **表达式在运行期照抄 `behavior.rs` 的遍历求值（逐叶子回调 Steel）**——否决：等于把伤害计算推回三档,与「一早加载成静态声明」正面冲突（二节）。
- **允许 `lambda`/高阶函数出现在表达式里**——否决：一旦允许,运行期就需要重新引入 Steel 求值上下文,「零跨界」的设计意图当场作废,正确做法是封闭表里压根不认识这些符号（三节）。
- **命中判定换成纯 AC 二元模型**——否决：推翻已测试守护的既有减伤实现,引入范围外的新机制,且「10% 下限」承诺在纯二元命中下无法直接兑现（五节）。**改为采纳"多轮判定"**：与既有减伤公式正交共存（多轮判定只负责算出送进减伤链路的攻击力数值，不改减伤链路本身），10% 下限继续有效、不冗余（五节详细论证）。
- **多轮判定里每轮伤害各自重新掷骰 / 每轮各自走完整减伤链路**——否决：前者需要真正的循环/子程序机制,复杂度不成比例；后者让防御被不必要地按轮拆分,没有对应的设计意图（五节）。
- **`adv`/`disadv` 包住任意子表达式，不限定只包骰子**——否决：「掷两次取一边」这个操作对复合表达式（含加减乘除的混合式）语义不明确（该对整个表达式重新求值两遍,还是只对表达式内的骰子部分各自取两次？），限定成只包一个 `(d N S)` 消除了这个歧义,且已经覆盖 D&D 实际用法（advantage 只作用于单次掷骰,不作用于复合算式）。
- **给公式的表达式分支加"懒惰求值"（未选中分支不消耗随机数）**——否决（暂不）：需要求值器支持真正的控制流跳过,与"扁平数组、每条指令执行一次"这个简单模型冲突,换来的收益（省一点随机流位置）不足以承担复杂度,真正需要省随机数的场景应该把判断挪到公式外（六节已给出推荐模式）。
- **伤害类型/抗性现在就设计具体字段与百分比规则**——否决：系统本身尚不存在（无数值规则、无代码），现在设计等于凭空捏造需求,只给出未来接线形状（九节）。
- **`KillCause` 记录用了哪套公式/是否发生过降级**——否决：与武器/技能字段冗余,服务对象不同,不该混进同一条记录（十三节）。
