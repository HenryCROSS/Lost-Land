# 身份与 ID 空间

**冻结于** 2026-08-17。**实现阶段** 需在[世界历史生成](world-history.md)（约 P7，[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P6 顺移为 P7）动工前定案——它是该阶段明确列出的三件「必须提前做」的事之一,但类型本身在更早的 P4（内容注册表）落地也不构成问题。

**落地状态**：纯设计,尚无代码。已核实：`crates/ll-core/src/ident.rs` 只有 `NamespacedId` 与 `ContentIndex`（见「问题的真面目」一节引用),本文档提出的 `WorldId`、`OrgInstance` 均**未落地**。`Affiliation.org: ContentIndex`（`crates/ll-world/src/entity/affiliation.rs`,已落地）正是本文档要处理的问题的现状——它把两种不同的东西用同一个类型表示,详见下文。

---

## 一、问题的真面目

[社会系统](society-and-affiliation.md)定义的 `Affiliation` 结构里,`org: ContentIndex` 这一个字段,把两种根本不同的东西混在了一起：

| | 谁创造 | 例 | 数量 |
|---|---|---|---|
| **类型（Def）** | mod 作者 | 「矮人」「铁匠」 | 几十到几百,固定 |
| **实例（Instance）** | 世界生成器 | 「卡拉克第三王朝」 | 随世界规模增长 |

`ContentIndex`（`crates/ll-core/src/ident.rs:84`）的模块文档明确写着**「不可持久化——索引依赖 mod 加载顺序」**。这条约束对「类型」是安全的：文化、职业、种族这些是 mod 作者在装载时注册的固定内容,数量小、集合封闭,`ContentIndex` 天生适合。但对「实例」是危险的：势力、家族、聚落这些是[世界历史生成](world-history.md)在**运行时**产出的,数量随世界规模增长,且**没有对应的 mod 注册条目可以在存档反序列化时重新校验**——`ContentIndex` 从设计上就没打算支撑这种用法,只是现在恰好被复用了过去。

---

## 二、定案：类型/实例分离

判据一句话：**mod 定义「种类」,世界生成造「个体」。**

| 归属 | ID |
|---|---|
| 文化、职业、种族 | `ContentIndex` |
| 势力、家族、聚落、宗教团体、历史事件 | `WorldId` |

```rust
/// 世界生成实例的持久标识。永不复用,不需要代际号——见三。
pub struct WorldId(u32);

/// 一个组织实例——势力、家族、聚落等在世界生成期间被创造出来的具体
/// 个体,与它所属的 Def（若有）分开。
pub struct OrgInstance {
    /// 一切实例都有：这是它在存档、事件日志、脚本查询里被引用的方式。
    pub id: WorldId,
    /// 源自哪个 mod 模板；纯生成（没有对应模板,例如自然形成的王国）
    /// 则为 None。
    pub def: Option<ContentIndex>,
    /// 只有 mod 直接命名定义的具体实例才有——见「mod 可以定义具体势力」。
    pub authored: Option<NamespacedId>,
}
```

`Affiliation.org` 的字段类型需要从 `ContentIndex` 改为 `WorldId`（对势力/家族/聚落这几种 `AffiliationKind`）——具体迁移方式属于实现批次的工作,本文档只定形状。

### 这个模式已经在用,不是新概念

物品系统的 `ItemDef` / `ItemStack` 分离（[物品系统](item-system.md)「定义与实例分离」）正是同一条分界线：`ItemDef` 是 mod 定义的种类（「铁剑」这个类型只有一份）,`ItemStack` 是运行时实例（世界上有一万把具体的铁剑,各自品质、耐久不同）。本方案只是把这条已经验证过的分界线,推广到组织这一类概念上——**不是新概念,是补齐了物品系统已经解决、但社会系统当初没有显式处理的同一个问题**。

## 三、`WorldId` 的两条规则

### ① 永不复用

王朝覆灭后,历史事件（[世界历史生成](world-history.md)「事件日志」一节的那约一万条记录）仍然引用它——「卡拉克第三王朝与铁血兄弟会的战争」这条事件记录,即便卡拉克第三王朝早已灭亡,这条记录里的 `WorldId` 依然要能正确解析回「那个已经不存在的王朝」,而不是解析成别的东西。

若 `WorldId` 复用（新王朝诞生时,把某个已灭亡王朝空出来的号码重新分配给它）,几百年前的战争记录会静默指向一个完全不相干的新王朝——**这类缺陷极难查**,因为它只在特定的兴亡序列（旧王朝灭亡、恰好又有新王朝在同一批次分配到同一个号）下才会触发,大多数游玩过程根本不会撞上,一旦撞上又难以定位根因。

解法很朴素：单调递增,不回收。`u32` 可容纳约 40 亿个 ID,一个 500 年的世界只会用掉两万多个——ID 空间的余量有五个数量级以上的富余,不需要考虑回收带来的复杂度。

### ② 不需要代际号

`EntityId`（`crates/ll-world/src/entity/id.rs:36`）用 `(index, generation)` 防悬垂引用——槽位被复用后,持有旧 `EntityId` 的一方因为世代号不匹配而查询失败,而不是静默指向复用后的新实体（详见[0004](../decisions/0004-two-layer-entity-storage.md)）。

`WorldId` 的需求方向**正好相反**：历史事件**故意**要指向一个已经不存在的东西,且必须永远能解析成功——`EntityId` 的代际号机制是为了让「这个引用应该失效」这件事发生,而 `WorldId` 需要的是「这个引用永远不失效,即便它指向的势力已经灭亡很久」。两者的设计目标互斥,不能共用同一套机制,`WorldId` 因此不带代际号,单纯是一个永不复用的递增整数。

## 四、mod 可以定义具体势力

已批准的用法：mod 可以直接定义一个具体的势力（比如「铁血兄弟会」这个特定组织,而不是「一种势力类型」）。

这类 mod 定义的具体势力,在世界生成时被**播种进世界**,与生成器自己产出的势力一样领取一个 `WorldId`——下游代码（关系派生、职业声望、任务发布……)完全一致,不需要为「这个势力是 mod 定义的还是生成的」写任何分支判断。区别只体现在 `OrgInstance.authored` 字段：mod 定义的实例这个字段是 `Some(namespaced_id)`,纯生成的是 `None`。

存档另需一张 `NamespacedId → WorldId` 的小映射表,只装 mod 命名过的那些实例,通常几十条——规模上与[装备栏位与占位掩码](equipment-slots.md)mod 扩展槽位、[物品系统](item-system.md)品质倍率覆盖表是同一量级,不构成新的存储压力。

## 五、脚本 API 必须是查询式,不是引用式

因为名字（见[命名、改名与本地化](naming-and-localization.md)）是随机生成的,mod 脚本**无法**按名字去引用某个具体的生成物：

```
✗ 引用：「卡拉克之战」               ← 换一个世界种子,这场战争根本不存在
✓ 查询：玩家所属家族参与过的所有战争   ← 任何世界种子下都有意义
✓ 查询：当前控制这个聚落的势力
✓ 查询：与玩家家族有世仇的家族
```

任务描述的是**关系与角色**（「玩家家族的世仇」「当前控制某聚落的势力」),不是具体的谁（「铁血兄弟会」「卡拉克王朝」）。这不只是技术限制下的退而求其次——它带来一个直接的好处：**按关系与角色写的 mod 任务,在任何世界种子下都能正常工作**;按名字硬编引用的任务,换一个世界种子后引用的对象大概率不存在,任务直接报废。

这条约束进一步支撑了「类型/实例分离」的定案：`ContentIndex` 对应的类型（文化、职业、种族）**是**可以按名字引用的——「所有信奉山地文化的 NPC」这类查询本来就是按类型走的,类型集合封闭且由 mod 装载时确定,不存在「换个种子就不存在」的问题。查询式 API 要区分清楚的正是「查类型」（稳定,可按名字）与「查实例」（不稳定,只能按关系/角色/谓词）这两类完全不同的操作。

## 六、存档与 mod 集合

总纲规格 §10.4 与 §11.2 已经要求存档头记录「启用 mod 列表与版本」「索引 ↔ 字符串映射表」，缺失 mod 时「不得崩溃」。这是底线，但离一套可用的存档—mod 兼容策略还差四块——本节只补设计，不改规格。

### ① 光有版本号不够，还需要内容哈希

mod 作者改内容却不改版本号是常态（尤其是开发中的 mod：改一个数值就发布，谁会为此升版本号）。版本号相同而内容已经变了，存档会误以为一切正常，直到某个存进去的引用（`ContentIndex`、`stat_bonuses` 里的具体加成）在读档时对不上当初生成它的定义，才在某处炸掉——而那时错误现场早已离案发点很远，极难查。

**应对**：存档头除了「mod 名 + 版本」，还要存**每个 mod 注册内容的哈希**（对该 mod 贡献的全部 `ContentIndex` 定义做一次哈希）。读档时版本号相同但哈希不同，至少能明确警告「版本号没变但内容变了」——把「静默炸在某处」变成「读档那一刻就能定位到具体是哪个 mod」。

### ② 缺失 mod 之后怎么处理，规格没定义

「不得崩溃」是底线，不是处理策略。不同内容类型缺失后合理的处理方式并不相同：

| 缺失的东西 | 合理处理 |
|---|---|
| 某个物品类型 | 丢弃该物品堆叠并提示 |
| 某个 NPC 的种族 | 降级为占位种族 |
| **玩家角色的种族** | **不能降级——降级意味着玩家失去自己的角色，这是所有处理方式里唯一不可接受的一种** |
| 世界生成用的地形生成器 | 世界已生成完毕，缺失该 mod 对已存在的世界影响有限 |

**建议再加一档只读模式**：允许打开存档查看、导出角色/物品，但不能继续游玩。这好过现在「要么想办法凑合丢数据继续玩、要么直接拒绝打开」的二选一——尤其是当缺失的东西恰好落在上表「玩家角色的种族」这一格时，只读模式是唯一不需要在「丢数据」与「打不开」之间选一个的出口。

### ③ 生成期 mod 集合 ≠ 当前 mod 集合（最要紧的一条）

世界由种子完全决定——[世界历史生成](world-history.md)「诚实警告」一节明确依赖这条性质：「由种子完全决定，结果可复现可调试……好世界可以分享种子给别人，同一个种子在同一份代码上必然生成同一个世界」。

**但这句话只在内容集合相同的前提下成立。** 种族分布场、聚落选址、势力形成全部读取 mod 注册的 `CultureDef`/`RaceDef` 等定义；同一个种子换一批 mod，生成出来的是完全不同的世界。规格 §10.4 只说存档头记录「当时启用的 mod 列表」，没有区分这份列表到底是「生成这个世界时用的那一批」还是「玩家现在开着的这一批」——这两者会在游玩过程中分道扬镳：玩家中途装卸 mod 极其常见，而世界一旦生成就不会重新生成。

**存档头必须分开记录两组 mod 集合**：

```
生成期 mod 集合   ← 这个世界是用这一批 mod 生成的，写入后永久不变
当前 mod 集合     ← 玩家现在实际开着的这一批
```

**只有「生成期 mod 集合」能用来复现世界。** 若存档只存「当前」这一组，玩家中途装了个新 mod，那个世界就再也复现不出来——**种子分享、缺陷复现、回归测试全部失效**，因为这三者都要求「同一个种子 + 同一批内容 ⇒ 同一个世界」，而「当前」这组会随时间漂移，不满足这个前提。这不是一个可以事后补救的缺口：存档格式一旦冻结（规格 §11.2 定在 P5），事后想把「当前」拆成「生成期 / 当前」两份就是一次存档迁移，而这次迁移**追不回**那些只存了一份、已经无法分辨「原始生成批次」的旧档。

### ④ schema 版本与 mod 版本是两条正交的轴，必须分开报错

- **schema 版本**变了 = 我们自己的存档格式变了 → 头部 schema 版本驱动的迁移函数链能修（规格 §11.2「迁移」一节已经安排好这条路）。
- **mod 内容**变了 = 别人的 mod 内容变了 → **迁移函数链修不了这个**，因为我们不知道对方具体改了什么、该怎么把旧数据转换成新数据。这只能由该 mod 自己提供迁移逻辑，或者干脆报错让玩家自己决定。

一个存档完全可能 schema 已经是最新版、却因为 mod 内容不兼容而打不开。**这两种失败必须分别报错**，用词也要分开——「存档版本过旧，正在迁移」与「某 mod 内容已变化，无法确认兼容性」传达的是完全不同的信息，指向完全不同的修复动作（前者等迁移跑完，后者去找 mod 作者或换回旧版本的 mod）。混在一起报「存档版本不兼容」会让玩家往错误的方向排查——他会去找存档管理器要不要更新，而不是去检查 mod 列表。

### 顺带写一句已经对上的：`WorldId` 不需要进 ID 映射表

规格 §10.4 要求的「索引 ↔ 字符串映射表」是为 `ContentIndex` 这类 mod 装载时才确定顺序的类型准备的——`ContentIndex` 的模块文档明确写着「不可持久化，索引依赖 mod 加载顺序」，所以必须存一张映射表在换mod顺序后还能对回原本的字符串 ID。

「二、定案：类型/实例分离」一节定义的 `WorldId` 不属于这个问题：它由构造保证单调递增、永不复用（见「三、`WorldId` 的两条规则」），构造过程本身就稳定，不依赖 mod 加载顺序，因此**不需要进 ID 映射表**。映射表只需要覆盖 mod 注册的 `ContentIndex` 类型——几十到几百条，见「四、mod 可以定义具体势力」一节给出的量级——而不是随世界规模增长到几万条的 `WorldId` 生成实例。这是类型/实例分离白送的又一个好处：映射表的规模天然被钉死在「mod 定义的种类数」，不随「世界生成的个体数」增长。
