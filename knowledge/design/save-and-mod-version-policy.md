# 存档兼容策略：版本不对就打不开

**状态**：已落地（本文档是把既有代码行为写成明文策略，不是新设计）。

## 一、裁决原文

项目所有者裁决：

> **新版本不兼容旧版本存档就是了，版本不对就打不开。**

这条裁决同时管两条彼此独立的版本轴——存档格式的 schema 版本，与每个 mod 自己的 `version`。两条轴各有各的判据与各自的错误，谁都不掩盖谁。

## 二、现状核实：裁决已经是代码的行为

| 轴 | 判据 | 落点 | 结果 |
|----|------|------|------|
| 存档 schema 版本 | 存档头 `schema_version` 与 `CURRENT_SCHEMA_VERSION` 不相等 | `ll_content::save_file::check_schema_version` + `ll_content::migrations` | 版本更高 → `SchemaTooNew`；版本更低且迁移链没有路径 → `SchemaMigrationGap`。当前 `CURRENT_SCHEMA_VERSION = 1`，**迁移链是空的**，所以「更低」这一档现实中还不存在 |
| mod 版本 | 存档头记的每个生成期 mod，在当前会话里**在不在**、`version` 字符串**是否原样相等** | `ll_content::load_error::check_mod_set` | 任一条不满足 → `ModSetMismatch`，在解压存档主体**之前**就拒绝 |

`check_mod_set` 是硬门禁：它排在 `check_mod_content`（内容哈希）与 `remap_world`（按内容类型细粒度降级）之前，命中就直接拒绝，不给降级机会。版本号比较是**原样字符串相等**，不做语义化版本解析——`1.2.0` 与 `1.2` 是两个不同的版本，不是"兼容"。

已经钉住这些行为的测试：

- `ll_content::load_error` 单元测试：`生成期mod在当前会话完全找不到时判定为modsetmismatch`、`生成期mod在场但版本号不一致时判定为modsetmismatch`、`生成期mod在场且版本号一致时校验通过`
- `ll_content::save_file` 端到端测试：`完全卸载的mod读档后被硬门禁拒绝而非降级为只读`、`生成期mod版本号不一致时读档被硬门禁拒绝`、`schema版本高于当前支持版本时读档返回rejected`、`schema版本低于当前版本且迁移链不认识该版本时返回迁移缺口错误`
- `ll_content::world_identity` 单元测试：`清单里的版本号原样进存档头且改一个字符就打不开`（把「清单 → 存档头 → 硬门禁」这条链一次性钉住）

**结论：不需要改代码。** 本文档存在的意义是把「这是有意的策略」写下来，因为代码本身只能告诉你"版本不等就拒绝"，说不清"那我什么时候该动版本号"。

## 三、版本号该什么时候动（本文档的正题）

### 3.1 mod 的 `version`（`mod.json5`）

**改一次 `version`，此前用这个 mod 生成的全部存档立刻打不开。** 这不是 bug，是裁决要的效果。因此：

- **发布给玩家之前**：随便改。没有别人的存档在外面。
- **发布之后**：改 `version` = 宣布「旧档作废」。只有在你**确实想要**这个效果时才改——例如内容改动大到旧档继续读下去只会变成一堆看不懂的占位物。
- **发布之后做了兼容性改动**（修一处文案、调一个数值、加一条不影响既有内容的新配方）：**不要动 `version`**。动了就是无谓地作废所有人的存档。

> 有人会想:"那我改了内容却不改版本号，存档不就悄悄坏了吗？"——不会悄悄坏。那正是**内容哈希**那道关卡管的事（`check_mod_content`，见[身份与 ID 空间](identity-and-ids.md)「六、存档与 mod 集合」）：mod 还在、版本号也对得上，但贡献的内容哈希变了，读档一样会被拒绝，并且报的是"内容变了"而不是"版本不对"。两条轴分别诚实地回答自己那部分问题，见 [mod 包结构](mod-package-structure.md)「与存档-mod 集合策略的配合」。

**本体 `mods/lostland/mod.json5` 的 `version` 同样受这条约束**——本体走的是与第三方 mod 完全相同的注册通道，它的 `version` 也逐字进存档头。在本体发布之后动它，等于宣布全体玩家的存档作废。

### 3.2 存档 schema 版本（`CURRENT_SCHEMA_VERSION`）

改 schema 版本的条件更硬：**存档结构（字段增删、语义变更）真的变了**才动。改完有两条路：

1. **写一条迁移**（`ll_content::migrations`）：旧档能升上来，旧档还能打开。
2. **不写迁移**：旧档报 `SchemaMigrationGap`，打不开。这是裁决允许的默认结局，也是当前迁移链为空时唯一可能的结局。

选哪条是产品决定，不是技术决定。**但不能不动版本号就改结构**——那会让旧档以新格式被解析，读出一堆错位的数据，是唯一真正危险的情形（比"打不开"糟得多）。

### 3.3 内容哈希算法版本（`CONTENT_HASH_ALGORITHM_VERSION`）

第三条相关的版本号，当前是 `14`。它管的不是"内容变了"，是"算哈希的方式变了"——只要动了哈希函数本身（覆盖哪些字段、怎么折叠），就必须递增它，否则旧档会拿两个不可比较的数去比，报出一条**误导性**的"你的 mod 内容变了"（见 `check_content_hash_algorithm` 文档）。递增之后旧档报的是 `ContentHashAlgorithmUpgraded`，说的是实话。

## 四、为什么不做向后兼容

裁决本身就是答案，但值得记下代价与收益：

- **代价**：玩家的存档会因为一次 mod 更新而作废。
- **收益**：不需要维护一条随版本增长的迁移链，也不需要在每处读档逻辑里写"如果是旧版本则……"。对一个还在快速变形的项目，迁移链的维护成本会迅速超过它带来的便利，而且迁移链本身是最容易写出静默错误的地方（迁移写错 = 读出一份看似正常、实则错位的世界）。
- **前提**：这条策略成立的前提是**打不开时报得清楚**。`ModSetMismatch`/`SchemaTooNew`/`SchemaMigrationGap` 都携带结构化数据与 Fluent 消息键，UI 层能告诉玩家"哪个 mod、要什么版本、现在是什么版本"，而不是一句"存档损坏"。这个前提今天成立，不能退化。
