# 种族系统

**冻结于** 2026-08-17。**实现阶段** 主体在 P9（世界历史生成产出种族分布；[2026-08-18 规格修订] 插入「物品与装备」新 P6 阶段后原 P8 顺移为 P9），但**字段形状必须在 P3 建 `Agent`/`ThinPopulation` 时就定**——与归属、钱包同样的理由：P3 加零成本，P5 存档格式冻结后再加要写迁移链。

**落地状态**：部分落地，且落地方式与本文档「存储」一节的设计有一处未对齐的实现债务，去代码核实结果如下：

- `Agent.race: ContentIndex`（`crates/ll-world/src/entity/agent.rs`）与 `Agent.luck: i32`（同文件）已落地。字段本身的形状——「种族是内容，走注册表索引，不是封闭本体枚举」——与本文档「核心形状」一节的结论一致，字段文档甚至已经预写了「未来将驱动的东西」（基础属性种族修正、专属装备槽位、随从招募同族/异族筛选、剧情分支解锁），逐条对应本文档后续各节。
- 薄层 `ThinPopulation` 也已有 `race: Vec<ContentIndex>` 列（`crates/ll-world/src/entity/thin.rs`），且是 `spawn()` 的显式参数、直接写入存储列，不是现算取值——这与本文档「存储」一节「种族完全派生、薄层零列」的结论**直接冲突**，是尚未对齐的实现债务，详见该节末尾的实现注记。
- `RaceDef` 注册表、暗视接口 `sight_radius_at`、体型 `footprint`、寿命的三条平衡手段、混血注册、种族偏见的 `race_affinity`、`birth_settlement` 列——以上均**未落地**，仍是纯设计。

所有数值一律整数，比例用千分比（见 [0002](../decisions/0002-integer-only-world-state.md)）。

## 一、核心形状：种族不是 `AffiliationKind`

[社会系统](society-and-affiliation.md)把势力、宗教、行会、文化、家族、职业统一成同一个 `Affiliation` 结构，因为它们对游戏逻辑提出的问题相同：「这个实体属于谁」「关系好到什么程度」。种族看起来也是一种「归属」，但塞进 `AffiliationKind` 会立刻露出破绽：

`Affiliation.standing` 的语义是**「你在这个组织里积累了多少」**——势力忠诚、宗教虔诚、行会资历、家族亲疏，全部是随时间、随行为变化的量。而「你有多像你的种族」这个问题本身就不成立：一个矮人不会因为常年不去矿场就变得不那么矮人。硬塞一个 `standing` 字段进去，结果只能是恒为满值（没有意义的常量）或被彻底忽略（死字段，占地方不干活）。

种族在结构上更接近[地形系统](../decisions/0005-torus-topology-and-integer-noise.md)里的 `TerrainKind`（`crates/ll-world/src/terrain.rs:43`，已落地）——一个分类标签，本身不携带「关系强度」这个维度，其余系统按标签查表取值。

**形状**：

```rust
// Agent（厚层，已落地）与 ThinPopulation（薄层，已落地）
pub race: ContentIndex,   // 指向注册表，mod 可注册新种族
```

```rust
/// 种族定义，由注册表提供，mod 可自由新增——「本体即 Mod」在种族上的
/// 应用，与 CultureDef 是同一个模式。（尚未落地）
pub struct RaceDef {
    pub id: NamespacedId,
    pub name_key: String,
    pub stat_modifiers: BaseStats,      // 见二、烘焙进 BaseStats
    pub darkvision_floor: i32,          // 见五、暗视
    pub footprint: (u8, u8),            // 见六、体型
    pub lifespan_years: u32,            // 见七、寿命
}
```

## 二、属性修正：烘焙进 `BaseStats`，创建时一次性加

种族对六维主属性的修正，在角色创建（或 NPC 生成）那一刻**一次性加进 `BaseStats`**，此后种族与属性彻底脱钩——不是每次 `derive_stats` 派生时都重新叠加一遍。

### 为什么不能走「每次派生时叠加」这条更「一致」的路

[属性系统](attribute-system.md)「衍生属性绝不进存档」这条纪律约束的是 `DerivedStats`——三系攻防、四种穿透这类由 `derive_stats(基础属性, 装备, 状态效果, 负重)` 纯函数现算的量。`BaseStats` 本身**不是**那条纪律的对象，它是存档字段，本来就该被写死。

若把种族修正也做成每次派生时叠加（`真实属性 = BaseStats + 种族修正`），`BaseStats` 的语义会从「角色的主属性」退化成「与种族无关的基底」——一个不再是「真实数值」的中间量。后果不只是命名混乱：所有读取 `stats.strength` 的地方（战斗结算、负重判定、UI 面板）都要多穿一层「先查种族再加」的查询，原本一行字段访问变成一次注册表查表 + 加法，且**必须在每一处都记得穿**，漏一处就是一个隐蔽的数值缺陷——这正是「衍生属性入存档」那类缺陷的镜像版本：不是「存了不该存的」,而是「该存却假装是派生的」。

### 代价：旧存档不随种族数值调整而变

烘焙进存档意味着，若日后调整某个种族的属性修正表（数值平衡），**已经生成的角色不会自动跟着变**——他们的 `BaseStats` 是创建那一刻算出来的死值。这是刻意接受的代价，不是遗漏。

「变形」「诅咒改变种族」这类玩法需求，**不能**通过让 `BaseStats` 变成持续依赖种族的派生量来解决（那正是上面否决的方案）。正确做法是：种族变更本身是一个 `Effect`（例如 `Effect::ChangeRace`），`apply` 阶段按新旧种族修正的差值重新烘焙一次 `BaseStats`，一次性写入，随后再次与种族脱钩，直到下一次变更事件。

## 三、数值形式：主属性用固定加减，不用千分比

种族对六维主属性的修正是**固定加减**（例如「矮人体质 +2」），不是千分比缩放。

### 为什么不学穿透的「先固定后千分比」

[属性系统](attribute-system.md)的穿透 `Penetration { flat, permille }` 用两段式设计，是因为破甲流与破防流两条装备路线需要各有用武之地——固定穿透对低护甲收益高，千分比穿透对高护甲收益高，两者制造博弈空间。种族修正不涉及这种「两条路线互相制衡」的博弈，套用同一个两段式结构是无意义的复杂化。

### 为什么不用千分比

主属性值域太小——基准 10，硬上限 30。千分比在这个值域上要么被整数除法舍成 0（`10 × 50‰ = 0.5 → 0`，向零截断后消失），要么产生不可心算的零头（`13 × 1050‰ = 13.65 → 13`，种族加成从数值上几乎观察不到）。固定加减在这个值域里心算友好、效果可预期：「矮人体质 +2」立刻知道是从 10 变 12。

**幸运是例外**：幸运本身的语义就是千分比（「每点幸运 +5‰暴击率」），种族对幸运的修正沿用它本身的记法，直接是「+N 点幸运」而非另一套换算。这不是矛盾，是幸运字段本来就不走 `(属性−10)/2` 调整值公式——**这条判断本身没有过期，但它的落点变了**：幸运并入 `AttributeKind` 批次之前，`luck` 是 `Agent` 上独立于 `BaseStats` 的字段（当时的理由见旧版 `crates/ll-world/src/entity/agent.rs` 文档「刻意放在 `Agent` 而非 `BaseStats`」，该节已被推翻并删除）；项目所有者裁定幸运并入 `AttributeKind` 之后，`luck` 现在就是 `BaseStats` 的第七个字段（`crates/ll-world/src/entity/stats.rs`），换算公式不同这条事实依旧成立——`BaseStats` 里其余六项走调整值公式、`luck` 字段走原始值语义，两者共处同一个结构体，只是「幸运沿用自己的记法」不再需要靠「不放进 `BaseStats`」来保证。

### 数值细节：调整值死区可能吃掉种族修正

调整值公式 `modifier = (属性 − 10) / 2`（整数除法，向零截断）意味着：**种族 +1 的修正可能完全不改变调整值**。例如某角色基础体质 11（调整值 0），种族 +1 后变 12（调整值 1，确实变了）；但基础体质 10（调整值 0）种族 +1 后变 11（调整值仍是 0，`(11-10)/2 = 0`）——同样是「+1」的种族修正，一个角色感受到收益，另一个完全无感。

这不是 bug，是整数除法调整值公式的固有性质，只是种族数值定稿时**必须过一遍表格**——把 10~30 每个基础值加上候选修正量，逐格看调整值是否真的变了，避免定出一批「写在设计文档上却在大多数常见基础值下不生效」的修正。

## 四、时间轴：不改公式，改数值预算

[属性系统](attribute-system.md)「与时间轴调度的接口」给出 `行动耗时 = 基础代价 × 1000 / 有效敏捷`。这是一个纯粹的反比关系：敏捷翻倍，行动耗时减半，也就是同一个时间窗口内能多行动一次。这是**这条公式的直接推论**，不是可调的旁支。

### 为什么不引入收益递减

一个自然的顾虑是：种族若能大幅提高敏捷，会不会让某个种族在时间轴上碾压其他种族？常见的补救手段是给敏捷的收益加一条递减曲线（例如超过某个阈值后每点敏捷贡献的行动频率打折）。

**本设计明确不这样做**，因为收益递减会破坏一个核心手感：「敏捷够高的角色应当能在同一个窗口内比对手多行动一次甚至多次」，这正是敏捷这个属性存在的意义（否则它和其他属性一样只是数值加成，不构成战术差异）。递减曲线会让「快角色」这个概念变得模糊——多快才算真的快，取决于一条玩家看不见的隐藏曲线。

### 改法：把种族固有敏捷修正限制在小档位

解法不在公式层，在**数值预算**层：种族给敏捷的固有修正限制在 **±2～4** 这个小区间。这个区间不足以让种族本身决定战斗节奏的量级差异，但装备与技能没有这个限制——大幅的速度成长（例如「疾风靴」「加速术」）留给装备与技能系统去提供,那里本来就该是玩家构筑的主战场。

**收益递减这类平衡手段放在数值设计准则文档里去讨论用量与阈值，不放进公式本身**——公式保持简单、确定、可心算，平衡交给数值预算去做,两者不要混在一起。

## 五、暗视：接口不碰 FOV

```rust
/// 有效可见半径：暗视只改变「算半径的输入」，不碰 FOV 算法本身。
fn sight_radius_at(base_radius: i32, light: i32, darkvision_floor: i32) -> i32 {
    let effective_light = light.max(darkvision_floor);
    // ……用 effective_light 换算出半径，具体换算公式属于视野系统，
    // 本节只约束暗视在这条链路里的介入点。
}
```

暗视的落点是「喂给半径计算的光照输入」，`compute_fov`（`crates/ll-world/src/fov.rs`）本身**完全不感知种族、不感知暗视**——它只认一个 `origin` 和一个 `radius`。

### 对称性论证（最容易被误解的一点，必须写完整）

[0007](../decisions/0007-symmetric-shadowcasting-fov.md) 用对称阴影投射保证的对称性，其精确表述是：**「同一个 `origin`、同一个 `radius`，`compute_fov` 算出的几何遮挡结论一致」**——也就是说，若把 A 换到 B 的位置、B 换到 A 的位置，且两者半径相同，两次调用互为镜像。这是 `compute_fov` 这一个函数内部的保证。

`compute_fov` **从未**保证「A 与 B 用各自不同的半径调用时结论对称」。这是两件事：

- **A 半径 10、B 半径 10** → 调用 `compute_fov` 两次，结论互为镜像，对称性成立。
- **A 半径 10、B 半径 6**（因为 B 意志更低，或 B 站在暗处而 A 有暗视）→ 两次调用的半径本来就不同,「A 看得见 B、B 看不见 A」是两次不同参数的调用各自给出正确答案,不是对称性被破坏。

跨实体的半径差异**早在暗视加入之前就已经存在**——`base_radius` 本就由[属性系统](attribute-system.md)的意志属性驱动（「视野半径」是 WIS 的次级属性之一）。两个意志值不同的角色,半径天生不同,「A 看见 B、B 看不见 A」是设计里刻意保留的机制,支撑的是潜行与伏击这类玩法价值——一个高感知的角色理应能比低感知的对手更早发现对方。

FOV 模块文档警告的「玩家会被自己看不见的敌人攻击」，语境是[0007](../decisions/0007-symmetric-shadowcasting-fov.md)描述的**单次 `compute_fov` 调用内部**的不对称（同一半径下几何算错），那是一个必须避免的 bug 类别。跨实体的、由不同半径导致的视野不对称是完全不同的另一个问题——一个是算法正确性,一个是游戏设计。种族暗视不触碰前者,只是在后者这个既有的设计维度上再加一个输入源（种族地板值）而已。

### 暗视不可做成「无视黑暗」

`darkvision_floor` 是一个**下限**，不是「黑暗对我不存在」。若做成无视黑暗，两个后果都不可接受：潜行玩法失衡（暗视种族对着潜行者毫无死角，潜行系统对这个种族形同虚设）；昼夜压迫感消失（黑夜作为一种环境压力,对暗视种族完全不起作用,削弱了昼夜系统本身的设计目的）。`effective_light = max(light, floor)` 这个写法保证了：即便环境光为零，暗视种族依然只能看到「地板值」对应的范围，而不是全图可见。

## 六、体型：只做三样，不做第四样

**做**：

1. **占位格数 `footprint`**——大型种族占 2×2 甚至更大的格子，影响碰撞与寻路。
2. **移动代价**——体型影响穿越地形的耗时（例如挤过狭窄通道）。
3. **负重上限**——已经由力量间接体现（[物品系统](item-system.md)负重分档由力量驱动），大型种族若力量基础值更高，负重上限自然更高，**不需要给体型单开一个负重系数**。

**不做**：命中率与被攻击修正——一个自然的直觉是「大目标更容易被打中、小目标更容易闪避」，但这会直接与既有的护甲穿透体系（[属性系统](attribute-system.md)四种穿透）产生数值耦合：命中判定链路里突然多出一个「体型修正」变量，需要重新设计它与穿透、闪避的相对权重,而当前完全没有证据证明这条额外维度对游戏性有不可替代的贡献。**这是 YAGNI，不是遗漏**——不需要的复杂度不提前建。

**不拆**：22 槽位掩码（`crates/`尚未落地，设计见[装备栏位与占位掩码](equipment-slots.md)）是**部位抽象**，不是尺寸抽象——`HEAD`、`ARM_L` 这些槽位描述的是「身体的哪个部位」，不是「多大」。不同体型的种族共用同一套槽位定义，一个体型巨大的种族依然只有一个 `HEAD` 槽——它戴的头盔在数值与逻辑上就是那一件头盔，只是渲染出来的贴图更大。**体型不衍生出新的槽位系统**,这是刻意的边界,避免装备系统为体型专门再长出一套平行结构。

## 七、寿命：三条自然平衡手段，不用硬编折扣

### 风险

若种族寿命差异很大（精灵活五百年，人类活八十年），而熟练度、财富都随时间线性累积（见[社会系统](society-and-affiliation.md)「职业也参与关系派生」与「真正的价值在代际」两节），长寿种族会在几个世代后碾压短寿种族——不是因为天赋更高，纯粹是活得久、攒得多。

一个常见但被否决的解法是给短寿种族的熟练度/财富增长speed硬编一个补偿系数。**本设计不采用这条路**，因为硬编折扣是在为一个自然现象打补丁，补丁的系数本身没有依据，且需要随每次数值调整反复重新校准。

### 解法：三条已有机制自然抑制线性累积

1. **熟练度增长服从边际递减**（`sqrt`/`log` 曲线而非线性）。活得越久,熟练度增长越慢——第一年学徒进步飞快,第五十年的老铁匠再练十年提升有限。长寿种族多出的年数,边际收益本就在衰减。
2. **家族传承带摩擦**（见[社会系统](society-and-affiliation.md)「真正的价值在代际」）。继承损耗、后代能力回归均值——财富与地位不会无损传递,每一代都有磨损与随机回归,长寿种族即便活得久,家族层面的优势也不会单调累积。
3. **后台推进本身带随机波动**（见[Agent 目标与经济](agent-goals-and-economy.md)钱包公式的确定性随机波动）。更多代际意味着更多次波动采样,而不是更多次确定性增益——波动的期望值不因样本数增加而系统性偏移。

### 一句话概括

**寿命提供的是更多抽奖机会，而非确定的线性增益，波动本身就是软上限。** 三条手段都是已有机制的直接复用，不需要为「种族寿命」这一个设计目标单独造一套平衡系统。

## 八、存储：薄层零列，但需要新增一列出生地

### 设计结论

种族**完全派生**，理想情况下不在薄层占任何列：

```
race(entity) = weighted_pick(
    settlement_race_weights[birth_settlement],
    hash(seed, entity_id, RACE_EVENT))
```

即：某个聚落的种族分布是一张权重表（人类聚落里偶尔生一个混血或旅居的矮人也是正常权重的一部分），个体的种族由「出生地的权重表」+「确定性哈希」现算得出——与姓名（`crates/ll-world/src/naming.rs`）走的是完全相同的模式：零存储、用时现算、同一实体每次算出来永远一样。

### 关键坑：不能用薄层现有的 `settlement` 列

`ThinPopulation` 已有的 `settlement: Vec<u16>` 列（`crates/ll-world/src/entity/thin.rs`）记录的是**当前所在地**，会随 NPC 迁徙而改变。若种族公式直接读这一列，后果是：NPC 从人类聚落迁到矮人聚落后,**下次现算种族时权重表跟着换了，同一个体的种族发生了不该发生的突变**。这不是理论风险——迁徙是[社会系统](society-and-affiliation.md)道路正反馈循环里明确存在的行为,一旦发生就会触发这个坑。

**解法**：新增一列 `birth_settlement: u16`（出生地,创建后终身不变),与 `settlement`（现居地,随迁徙更新）分开。两列 `u16`，百万 NPC 也只是 2 字节 × 2 × 百万 ≈ 4MB，可忽略。迁徙只影响**新生儿**的权重来源（新生儿的 `birth_settlement` 是父母当前所在地），不改变已生成个体的种族。

### 升格时不存 race，用同一公式重算

背景 NPC 升格为厚层 `Agent`（`ThinPopulation::promote`）时，`race` 不应作为「升格快照」的一部分被复制,而应该用同一条公式**重算**一次。这样确定性保证「降格再升格」得到同一结果，不需要专门写一致性校验去防止两次计算对不上——这是「默认派生」原则的自然收益,见[0009](../decisions/0009-derive-by-default-store-only-deviation.md)。

> **实现债务（务必对齐）**：以上是设计结论，但当前已落地的代码与此不符——`ThinPopulation::race: Vec<ContentIndex>`（`crates/ll-world/src/entity/thin.rs:42`）是一个显式存储列，`spawn()` 把种族当作调用方传入的参数直接写入，`promote()` 把这一列的值原样复制进 `Agent.race`（`thin.rs:185`），既不现算也没有 `birth_settlement` 列。这是 P3 阶段「先把字段布局搭起来」批次留下的产物,当时种族生成器与 `RaceDef` 都还不存在，用显式列占位是合理的过渡状态,但**不是本文档的最终设计**。P9（[2026-08-18 规格修订] 原 P8 顺移为 P9）世界历史生成落地、`RaceDef` 与聚落种族权重表就位后，需要一次迁移：新增 `birth_settlement` 列、把 `race` 列的存储职责替换成上面的现算公式（或者，若届时评估显式列在其他方面有价值，需另行裁定并更新本文档，而不是任由两处定义各说各话）。

## 九、混血：只在厚层，深度 1

### 薄层结构上不可能支持混血

薄层 `ThinPopulation` 只有 `family: FamilyId` 这一个血缘相关字段——一个不透明的家族号,不记录「父母具体是谁」。混血需要知道父母双方的种族才能现算出后代种族，而薄层根本没有「父母」这个概念可查。

**这条边界要显式写明，是为了避免以后有人想在薄层顺手加一个混血字段**——那会破坏薄层「定宽列式、人人一样」的设计前提（见[社会系统](society-and-affiliation.md)`Traits`一节：「定宽整数数组……完美适配薄层的列式存储」），混血需要的「父母种族」这类可变长/条件性数据不属于这个模式。

### 厚层的处理：出生时现算一次，固定存入，不递归祖父母

厚层 `Kinship`（`father`/`mother`/`spouse`/`children`，设计见[社会系统](society-and-affiliation.md)「血缘记录是极轻的」）已经记录了父母是谁。混血个体出生时,用父母双方的 `race` 现算一次混血结果,**固定写入**该个体的 `race` 字段，此后不再回头查父母——不递归到祖父母。

不递归的理由与血缘查询限深（[社会系统](society-and-affiliation.md)「谁是 X 的子女」限制在 3 代以内）同源：混血若递归查询祖辈血统比例,会退化成一次图遍历,而这里需要的只是「这个个体是什么种族」这一个离散答案,不是精确的血统分数。

### 混血是新的离散项，不是离散性的例外

混血结果注册为 `RaceDef` 的一个新条目（例如 `half_elf`），走与新增文化、新增宗教完全相同的注册路径。**混血不需要种族系统专门开一条「混合类型」的分支逻辑**——它只是「表里又多了一行」。

不支持的父母种族配对（例如两个机制上互不相容的种族），在这个模型下只是「表里没有登记对应的混血条目」，落到默认行为（沿用其中一方的种族，或走本体/mod 定义的兜底规则）即可，**不需要一套硬编的「哪些种族不能通婚」禁止规则**——不存在的东西自然不会发生,不必专门写代码去阻止它。

## 十、种族偏见：挂在文化上，且只做乘法系数

### 不做同/异种族的常量加减

一个直觉方案是给关系派生基线加一条「同种族 +X／异种族 −Y」的固定项，类似[社会系统](society-and-affiliation.md)已有的「同家族 +80」「敌对势力 −60」。**这个方案被否决**，因为常量对丢掉了不对称性——现实里种族偏见几乎从不对称（A 文化对 B 种族的态度,和 B 文化对 A 种族的态度,通常不是同一个数），一对常量只能表达「互相同等程度地喜欢/讨厌」,表达不了「一方轻蔑、另一方畏惧」这类更有戏剧张力的组合（这正是[社会系统](society-and-affiliation.md)「贵族→皮匠：轻蔑；皮匠→贵族：畏惧或怨恨」用的手法）。

### 改法：`CultureDef` 加 `race_affinity`

```rust
pub struct CultureDef {
    // …… 已有字段（building_materials、site_terrain、economy_weights……）
    /// 该文化对各种族的态度，千分比权重，可正可负。新增字段。
    pub race_affinity: Vec<(ContentIndex, i32)>,
}
```

派生基线表（见[社会系统](society-and-affiliation.md)「派生基线」）**只需加一条查表项**：`文化 X 对种族 Y 的 race_affinity[Y]`。不对称性天然成立——山地文化对精灵的 `race_affinity` 与精灵文化对山地族（假设山地族是另一个种族标签）的 `race_affinity` 是两张独立的表,各自配置,无需保持一致。

### 硬约束：种族绝不可成为职业声望表的第三个维度

这是本节最重要的一条风险，必须坚持。[社会系统](society-and-affiliation.md)「职业声望是局部的」给出的公式是：

```
本地职业声望(职业, 聚落) = 文化基准(职业) × 经济状态修正 × 本地条件修正
```

这张表的规模是「职业 × 聚落」，几千条，该文档明确标注「计算量微不足道」。**若直接把种族也塞进这张表变成第三个维度**：

```
职业 × 聚落         = 几千条      ← 可接受
职业 × 聚落 × 种族  = 几万至几十万 ← 「计算量微不足道」的前提失效
```

一旦维度膨胀到这个量级,原文档「一百个聚落 × 几十种职业 = 几千条,每次经济结算批量刷新一次即可」的性能论证直接失效,且这张三维表还要随种族数量（mod 可扩展）线性膨胀,是一个开放上限的存储量。

**必须坚持乘法分解**,而不是给原有二维表加一维：

```
本地声望(种族, 职业, 聚落) = 文化基准(职业) × 种族系数 × 经济状态 × 本地条件
```

种族系数是一个独立的、规模为「文化 × 种族」的小表（几十种文化 × 几十个种族 = 几千条，与「职业 × 聚落」同量级，可接受），乘法组合进最终结果,而不是预先展开成一张三维表存起来。**这一点必须在实现时守住,是本节唯一的硬约束。**

### 交叉歧视需要显式挂钩，不是纯涌现

态度数字本身不会自动变成经济后果。若「某文化对某种族的 `race_affinity` 很低」只是停留在关系系统的好感度数字上,玩家感觉不到任何差别——职业审计（[Agent 目标与经济](agent-goals-and-economy.md)「职业审计」）的准入判定（「有人能教」、行会名额）**必须显式读取 `race_affinity`**,种族对某职业的排斥才会转化为「这个种族在这里更难拜师、更难拿到行会名额」这类可感知的经济摩擦。这不是自动发生的——需要在职业审计判定条件里加这一处查询,是一个必须显式实现的钩子,不是关系系统接好之后自动涌现的副产品。

## 十一、美术成本：诚实结论

朝向 × 动画帧 × 装备外观 × 种族，默认是**相乘**关系。如果目标是「每个种族一套完全独立的精灵资源」，这个乘积的增长速度会压垮任何规模的美术产能——这不是需要论证的假设,是四个维度相乘的算术事实。

### 设计约束：种族能改变的东西必须是受限集合

**不是美术效率问题，是设计约束**：种族对外观的影响被限制在**肤色 + 头部 + 体型缩放**这个受限集合内，装备外观本体不因种族重绘（一件铁甲不管谁穿都是同一份贴图，只是缩放到穿戴者的体型）。这条约束必须在美术管线定稿前就写死,而不是等到资源已经开始按种族分裂制作之后才发现产能跟不上。

### 推荐的最小可行档

全种族复用同一套骨架，仅换色 + 可选 2～3 种头部；`footprint` 按种族预设（见六、体型）；数值与社会效果（属性修正、暗视、寿命、偏见系数）走完整的 `RaceDef`，不受美术精简的影响。

这样做的理由是：把「种族感」的表现力压力，从产能上限未知的美术部门，转移到数值、社会效果、脚本与文本——**这几处恰好是本项目已经证明过的强项**（[社会系统](society-and-affiliation.md)整套关系系统、职业声望、宗教戒律都是这条路径的验证）。

### 一条已知参照

Caves of Qud 用属性、社会关系、任务分支承载「种族感」，而不是堆精灵资源——身份感更多来自角色的**经历**（做过什么、被谁记住），而不是外观分类本身。这与本文档「美术成本」一节的结论同向：把差异化投入放在机制与叙事层，比投入在美术资源上更划算。**这里只引用这一条确知的方向性判断，不展开该游戏具体如何实现，以免对一个未逐条核实过的外部实现细节做出过度精确的转述。**

## 十二、待验证项（尚未核实，不要当成既定事实）

以下两项在写作本文档时**未去代码或引擎层面核实**，标注为待验证，供 P9 落地前排查（[2026-08-18 规格修订] 原 P8 顺移为 P9）：

1. **2×2 `footprint` 的碰撞与寻路是否已支持**——本文档「体型」一节假设占位格数可以直接影响碰撞体积与寻路代价，但当前寻路与碰撞系统是否已经支持大于 1×1 的实体占位，未经核实。
2. **大型精灵横跨环面接缝时贴图是否整体位移**——环面世界在接缝处的坐标处理（`TorusSize::wrap`）已经过验证,但那是针对逐格坐标的正确性,一个横跨接缝的多格精灵在渲染层是否会因为接缝两侧坐标环绕而出现视觉撕裂,未经核实。**建议补一个「2×2 精灵跨接缝」的视觉回归测试用例**,在体型系统真正落地前排查这一点。
