# 世界历史生成

**冻结于** 2026-08-17。**实现阶段** 独立一个阶段,体量上约在 P6 位置(存档格式 P5 冻结之后)。但**三件事必须提前做**（见「阶段归属」一节）。

**落地状态**：纯设计,尚无代码。已核实：`crates/` 中没有历史生成器、`Settlement` 结构、势力形成逻辑或事件日志的任何实现。地形生成（本文档流程第一步）已实现,详见[决策 0005](../decisions/0005-torus-topology-and-integer-noise.md)与 `crates/ll-world/src/terrain.rs`,本文档在此基础上叠加。

所有数值一律整数,比例用千分比（见[0002](../decisions/0002-integer-only-world-state.md)）。

---

## 一、核心架构判断：历史生成期间没有平民 NPC

这是整份文档唯一必须先立住的判断,后面的一切流程与数值都由它推出。

```
错：500 年 × 百万 NPC 逐个模拟   → 世界生成要跑十几分钟
对：500 年 × 500 聚落的聚合量更新 → 25 万次更新，秒级
```

历史生成阶段**只存在两类实体**：聚落（人口、经济、文化归属这些聚合量）与「被记住」的家族（统治家族、显赫家族——见二）。百万级平民 NPC 完全不在历史生成的模拟范围内。

### 为什么这样做是对的,而不只是为了快

百万 NPC 是**玩家落地后**、从聚落属性现算派生出来的——这是[0009](../decisions/0009-derive-by-default-store-only-deviation.md)「默认派生,只存偏差」原则在世界生成尺度上的又一次复用。矮人要塞式的「历史模拟阶段逐个体演化」之所以能产出深度传说,代价是新玩家最痛恨的漫长世界生成时间（见「诚实警告」一节）；而本项目的[社会系统](society-and-affiliation.md)与[Agent 目标与经济](agent-goals-and-economy.md)已经证明「背景 NPC 是公式不是活跃对象」这条思路能在游玩阶段撑起百万人口——历史生成阶段直接沿用同一条思路,不需要另起一套。

---

## 二、家族：只模拟「被记住」的那些

| | 历史生成期 | 数量级 |
|---|---|---|
| 统治家族 / 显赫家族 | 逐个模拟：继承、联姻、政变、绝嗣 | 几十王朝 + 几百望族 |
| 平民家族 | 完全不存在 | 玩家落地后派生 |

500 年、假设 50 个王朝更替,约产出**一万五千名历史人物**——这个规模无论存储还是计算都可以忽略不计,不需要为它单独做性能压测。

### 族谱必须有界

每一代只记录**继承线** + **做过值得记的事的人**。旁支成员默认不展开——一个王族的第五个堂弟,若他一生平平无奇,历史生成不会为他编出一条族谱记录。

只有当某个旁支成员做了值得记的事（篡位、建城、立下战功）,他才被**追认**为历史人物,补进族谱。

**这不是性能妥协,这就是真实族谱的运作方式**——现实中的族谱记录同样是「继承线 + 干过大事的旁支」,没有人会为每一代的每一个远房亲戚都写一笔,不是因为懒,而是因为「值得记录」本身就是这么筛选的。性能收益与真实性在这里同向,与[Agent 目标与经济](agent-goals-and-economy.md)「行会中介贸易」一节「省算力与真实性同向」是同一个论证结构。

---

## 三、两边必须共用同一套 `Kinship`

历史生成跑**年**粒度,游戏内跑 **tick** 粒度,但**血缘结构必须是同一个类型**——都是[社会系统](society-and-affiliation.md)已定义的 `Kinship { father, mother, spouse, children }`,不能各自定义一套。

### 为什么这条必须硬性写死

若历史生成用一套「王朝血统」结构、游戏内用另一套 `Kinship`,玩家选点落地时,「这个 NPC 是某王朝后裔」这条查询就要在两个结构之间做一次转换与对齐——转换逻辑本身就是第二个真相源,两边一旦有一处更新漏了同步,就会出现「历史记录说他是某某的后代,但游戏内 `Kinship` 查不到这条血缘」的静默不一致。

本项目已经在白昼判定上栽过一次这种跟头（[0010](../decisions/0010-single-source-of-truth-for-daylight.md)：`is_daylight()` 与光照曲线曾是两套互相矛盾的定义,四小时窗口内结论相反,根因正是「同一个概念被独立定义了两次」）。0010 的教训明确写着：「写了警告不等于警告会被遵守」——所以这里不满足于事后提醒,而是从一开始就不允许历史生成层另起一套血缘结构。

婚丧嫁娶这类事件在年粒度上产生,落到 tick 边界即可（例如「某年发生的联姻」落在那一年游戏内历总的某个固定 tick）,这只是时间粒度的映射,不是结构的分裂。

## 四、三层时间粒度

```
游戏内     tick 级    时间轴调度器
后台世界   日/周级    经济结算
历史生成   年/十年级  王朝、战争、迁徙
```

**每一层是对下一层的公式概括,不是对它的模拟。** 这是[Agent 目标与经济](agent-goals-and-economy.md)「背景层」批量公式思路在时间轴上的延伸——历史生成的一次「年」推进,不是把这一年拆成 365 个「日」再逐日跑经济结算,而是直接用一条能吞掉整年的闭式公式（人口增长率、税收累积、声望漂移）一次性算完。

**不守住这条,历史生成必然慢到不可用**——这不是性能优化的可选项,是这份文档存在的前提。若历史推进要靠逐 tick（或逐日）模拟才能算出年度结果,「25 万次更新、秒级」这个数量级论证直接不成立,退回到「500 年 × 百万 NPC」那个被否决的方案。

## 五、生成流程七步

1. **地形**（已实现,`crates/ll-world/src/terrain.rs`）
2. **种族分布场**——另开一层可平铺噪声,不同种子,手法与地形一致：可平铺、四边无缝、无边界特例（沿用[决策 0005](../decisions/0005-torus-topology-and-integer-noise.md)的整数噪声与环面处理方式）。这一层的产出正是[种族系统](race-system.md)「存储」一节里 `settlement_race_weights` 的来源。
3. **聚落播种**——地形适宜度 × 种族区域权重,决定聚落生成的位置与初始规模。
4. **文化归属**——聚落按[社会系统](society-and-affiliation.md)`CultureDef` 的选址权重（沿海/丘陵/草原等）匹配到具体文化。
5. **势力形成**——聚落聚合成国度,势力间的初始 `standing`（外交关系）在这一步定基线。
6. **历史推进 N 年**——粗粒度,王朝更替、战争、迁徙,产出「事件日志」（见六）与家族族谱（见二）。
7. **玩家选点**——从生成结果里选一处作为游戏开始位置,选点本身触发「白送的三件事」（见七）。

---

## 六、事件日志：只记「可被引用」的

矮人要塞的传说文本能到 GB 级,是因为它记录每一次出生、死亡、婚姻——一个人一生的每个节点都单独占一条记录。

**本设计只记可被引用的事件**：城市建立、战争、王朝更替、著名人物的诞生/死亡、改名。按「500 年 × 500 聚落 × 每个聚落 20 件值得记的事」估算,约 **1 万条,微不足道**。

出生、婚姻、死亡这些日常事件**不记入日志**——它们的痕迹留在家族族谱（见二）与 `Kinship` 里,需要具体查询「某人的父母是谁」时从族谱现算,不需要额外的日志条目支撑。事件日志只服务于「这件事本身值不值得被讲述」,不服务于「重建完整的人口普查记录」。

---

## 七、白送的三件事

采用「只模拟被记住的家族」这个架构判断后,以下三件事**不需要额外设计**,是架构的自然产物：

1. **玩家可以是某王朝后裔**——选点时,从当地家族池中派生一段血统,把玩家接到某个历史家族的族谱末端。
2. **世仇是继承来的**——关系系统「同家族 +80」的派生基线（[社会系统](society-and-affiliation.md)「派生基线」）已经存在,联姻天然继承双方的敌人（配偶一方的世仇,通过同家族权重自动波及另一方）,**不需要单独设计一套政治恩怨系统**——这与「杀一个土匪全家恨你」是同一个机制的不同应用场景。
3. **混血王朝自然出现**——历史人物本就属于[社会系统](society-and-affiliation.md)定义的厚层,跨种族联姻按[种族系统](race-system.md)「混血：只在厚层,深度 1」的规则自动产生混血继承人,并且因为继承人本身是「值得记的事」（王位继承),会被记进族谱与事件日志——混血王朝不是刻意设计出来的内容,是两套已有机制相交后的自然产物。

---

## 八、诚实警告：世界生成时间是最大的坑

这是矮人要塞新玩家流失最多的地方——动辄十几分钟到几十分钟的世界生成时间,劝退了大量第一次接触这款游戏的玩家。**规避手段必须现在就写进设计,不能等生成器实现完再补**：

1. **历史长度可调,默认给短的**——默认 100 年而非 500 年。500 年的深度传说是一个可选项,不是默认体验;新玩家的第一个世界应该在合理时间内生成完。
2. **生成可中断可预览**——边生成边显示地图,不是黑屏进度条。玩家能看到地形先出来、聚落陆续标出、势力边界逐渐成形,即便还没跑完全部历史年份,也能感觉到「进度在发生」而不是盯着一个不知道还要等多久的进度条。
3. **由种子完全决定,结果可复现可调试**——好世界可以分享种子给别人,同一个种子在同一份代码上必然生成同一个世界。这与[确定性重放](../../docs/superpowers/specs/2026-08-16-lostland-design.md)的整体纪律是同一件事在世界生成阶段的应用,`DetRng::for_entity` 这类确定性随机源本项目已经在钱包、姓名生成上验证过（见[0009](../decisions/0009-derive-by-default-store-only-deviation.md)）,历史生成沿用同一套工具,不另起随机源。

---

## 九、阶段归属

体量上,世界历史生成是独立的一个阶段,约在 **P6** 位置（存档格式 P5 冻结之后）。但下列**三件事必须提前做**,不能拖到 P6 才开始考虑：

1. **生成物 ID 空间选型**——势力、家族、聚落这些「世界生成器造出来的实例」用什么 ID,直接决定了历史事件如何引用它们、存档如何持久化它们。这件事定得晚,P6 落地时会被迫返工。见[身份与 ID 空间](identity-and-ids.md)。
2. **`Settlement` 结构落地**——历史生成的核心操作对象。定义拖到 P6 才做,会让 P3～P5 阶段任何提前需要引用「聚落」概念的代码（例如薄层 `settlement: Vec<u16>` 列）失去一个正式类型可以对齐,只能先用裸 `u16` 占位。
3. **事件日志 ID 空间预留**——事件日志条目（见六）需要能被查询式脚本 API（见[身份与 ID 空间](identity-and-ids.md)「脚本 API 必须是查询式」）引用,ID 空间的形状需要与势力/家族的 `WorldId` 方案一起定,不能事后另起一套。

这三件事都不依赖历史生成算法本身是否写完,可以在 P6 之前独立推进——这正是把它们提前列出来的原因。
