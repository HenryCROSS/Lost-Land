## 一、问题背景（已核实的事实）

### 1.1 脚本目前能积累跨帧状态，没有任何东西拦它

已实测确认（`crates/ll-script/src/whitelist.rs` 模块文档「白名单的定位」一节，写死的项目所有者裁定）：

> 白名单挡的是**能力**（文件系统、网络、进程、线程、墙钟、非确定性随机），放行的是**语言本身**——闭包、递归、`let`/`letrec`、`struct`、**`set!`** 都在放行之列。

`set!` 不触达六类被禁能力中的任何一类，因此**从未被拒绝过**。`(define counter 0)` 配合 `set!` 递增，或者闭包捕获一个可变单元挂在全局 `define` 上，都是纯语言特性的合法组合，白名单没有理由也没有能力拦住它们。

### 1.2 `tools/ll-datacheck` 尚不存在

规格与 [0017](../decisions/0017-tiered-declarations-materialize-columnar.md) 都提到过这个未来的静态检查工具——「顶层 `define`/`set!` 存放的值不得跨调用持续存在」原本设想靠它在加载期拦截。已核实：`ls tools` 返回「无此目录」，仓库里没有任何 `ll-datacheck` 的代码痕迹。这条防线目前是**纯纸面约定**，没有任何运行期或加载期机制真正执行它。

### 1.3 这些状态活在 VM 里，不在 `WorldState` 里

已核实：`crates/ll-world/src/state.rs` 的 `WorldState` 没有任何字段用来装脚本自己攒的数据。`ScriptEngine`（`crates/ll-script/src/host.rs`）当前的真实用法是**一次性、短生命周期**的——`crates/ll-mod/src/pipeline.rs:246` 每加载一个 mod 脚本文件就 `ScriptEngine::new()` 一个全新实例，跑完注册副作用后即弃用；P4 阶段还没有一个「跨越多个游戏 tick 持续存活、反复被调用」的长生命周期引擎实例。这一点需要**明确标注**：本文档第七节讨论的「VM 重建」问题，此刻在代码里还不真实存在——它是 P5 引入行为树/技能脚本（[0018](../decisions/0018-engine-layer-vs-gameplay-layer-scripting-boundary.md)「玩法层」清单已经把「行为树节点判断/动作」列进去）之后才会出现的真实场景。本文档提前设计，是因为**存储机制必须先于长生命周期引擎落地**——先有能存的地方，「随时重建 VM」这条纪律才谈得上「不丢东西」。

### 1.4 后果与如何被发现

脚本积累的隐式状态存在于 VM 内存里，`WorldState` 序列化时完全看不到它。存档、读档都不会报任何错——读档后世界照常运行，唯独脚本"忘了"它在做什么。这类缺陷的排查顺序几乎总是：先怀疑 AI 决策逻辑本身错了，再怀疑存档字段漏写了，最后才想到"VM 状态压根不在存档考虑范围内"——因为前两种怀疑都有明确的代码可以打断点，第三种连"这是个该被序列化的东西"这个认知都没有建立。

## 二、核心设计：状态落在 `WorldState`，脚本只经 API 读写

**给一条正路，才能理直气壮地封死歪路**——这是本文档存在的直接理由，也是与 [0019](../decisions/0019-denied-capability-needs-substitute-or-justification.md) 通则的具体呼应：VM 全局可变状态这项能力事实上无法被白名单机制禁止（1.1 节已证明——它不触达六类能力中任何一类），但脚本"记住东西"是正当需求（NPC 记得在追谁、任务进度、技能冷却）。真正的修复不是去堵一个堵不住的语言特性，而是**把这个正当需求满足在正确的地方**：数据落进 `WorldState`，脚本经明确注册的函数读写，VM 本身退化成纯粹的"求值器"，不携带任何游戏要紧的东西。

两件事同时成立之后，第三件事才能理直气壮地做：**存档/读档边界强制重建 VM**（见第七节）。重建会让"没有走正路、私自在 VM 里攒状态"的脚本立刻在下一次读档后表现异常——这不是一个需要额外检测机制的东西，是"正确用法不受影响，错误用法立刻现形"这条设计本身自带的探测器。

### 2.1 两种存储形状，不是一种

脚本要保存的状态天然分两类，混在一起会导致后文第五节（有界性）与第六节（孤儿状态）的策略互相打架，因此从一开始就分开设计（回应协调者的追问，详见第五节展开）：

```
全局命名空间存储   与任何具体实体无关的状态——教团累计声望、赛季主题、
                    某个已解锁的世界级 flag。挂在 WorldState 本身。

每实体扩展数据     依附于某一个具体实体的状态——NPC 当前在追的目标、
                    某个技能的冷却计时。挂在 Agent（厚层）本身，随实体
                    生死自动回收，不会变成孤儿。
```

两者共用同一套值类型系统（第三节）与命名空间隔离规则（第四节），但存储位置、有界性配额、mod 移除后的处理策略分别设计（第五、六节）。

## 三、值类型：整数纪律不可破

### 3.1 允许的类型

```rust
// 概念形状，非最终 Rust 类型名——具体落地时的确切类型名留给实现任务
pub enum ScriptValue {
    Int(i64),
    Bool(bool),
    Str(Box<str>),
    Ref(ContentRef),           // NamespacedId 的字符串形式，见 4.1 节
    Entity(EntityId),          // 见 3.3 节「能不能存实体引用」
    List(Vec<ScriptValue>),
    Map(std::collections::BTreeMap<Box<str>, ScriptValue>),
}
```

**明确排除 `f32`/`f64`**。这条排除现在的论证基础是 [0020](../decisions/0020-scripts-may-use-floats-internally-boundary-type-gated.md)（脚本内部允许浮点，安全边界收拢到 `register_fn` 类型签名，部分取代 0002）确立的模式,不是笼统的"浮点不可靠"：`0020` 裁定脚本**内部**计算允许使用浮点（这是语言本身的能力，白名单也从未禁止过——见 [0019](../decisions/0019-denied-capability-needs-substitute-or-justification.md) 表格「浮点」一行），真正的安全边界不在"脚本能不能算浮点"，而在"**跨过 `register_fn` 这条边界、真正写进 `WorldState` 的值，类型层面就不允许是浮点**"。`ScriptValue` 正是这条边界上的类型之一——`state-set!`/`entity-state-set!` 的 Rust 侧签名只接受 `ScriptValue`，`ScriptValue` 没有浮点变体，脚本无论内部怎么算，最终能落进 `WorldState` 的只能是整数/`Milli`——这是类型系统强制的，不依赖脚本作者自觉。

一旦浮点真的落进 `WorldState`，「同一份存档在任何机器上读出同一个世界」这条承诺当场破产：`ll_world::state` 模块文档开篇「全程禁止浮点数……浮点在不同平台/编译器/优化级别下的运算结果可能有细微差异，跨平台存档兼容性会被悄悄破坏」这条理由，对"已经写进 `WorldState` 的值"依然完全成立——`0020` 收窄的只是"脚本内部计算过程"这一层，不改变"`WorldState` 本身零浮点"这条底线（`0020` 原文明确写着这一条不在取代范围内）。脚本存的分数状态若绕过类型把关混入浮点，会在跨平台存档迁移时静默错位，这类偏差不会立刻表现成崩溃，会在几十上百个 tick 后累积成肉眼可见但无法追溯根因的偏移——这正是 `ScriptValue` 类型定义本身要杜绝的路径。

**分数用 `Milli`**：与 [脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 5.2 节 `aggregate` 的 `average` 处理方式完全同构——`ll_core::scaled::Milli` 底层就是 `i64`，没有不变式，任意整数都合法，因此不需要单独包一层 `Custom` 句柄，脚本侧存取时用整数值配合已注册的 `(milli-scale)` 常量自行换算整数部分/小数部分。`ScriptValue::Int` 直接承载 `Milli.0`，值类型系统不需要为它新增变体。

### 3.2 `Ref(ContentRef)`：为什么需要一个独立于 `Entity` 的变体

脚本状态经常需要记住"这是哪种类型的内容"而不是"这是哪个具体实例"——例如"这个 NPC 上次交付的任务需要的物品类型是 `yourmod:healing_potion`"。这类值本质是一个 `NamespacedId`，但 `ContentIndex`（`ll_core::ident` 已核实的「不可持久化」类型）不能直接存——索引依赖 mod 加载顺序，见第四节。`ContentRef` 内部就是 `NamespacedId` 的字符串形式（`namespace:path`），序列化即字符串本身，读取时经 `Interner::get` 现查当前会话的 `ContentIndex`——这与 `ll_core::ident` 模块文档「存档必须写字符串」的既有纪律完全一致，本文档没有发明新规则，只是把它套用到脚本状态这个新场景。

### 3.3 能不能存实体引用——结论：能，但只限厚层，且有一条尚未满足的前提

这是本文档除 VM 重建策略之外最需要正面回答的问题，直接决定「NPC 记得在追谁」这个真实需求能不能被满足。

**结论：允许存储 `ScriptEntityHandle`（即 `EntityId`），复用 [脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 3.1/3.4 节已经验证过的世代号失效检测——读取时若 `Arena::get` 返回 `None`（实体已死亡/世代不符），按该文档 3.4 节的约定返回一个明确哨兵值，不是错误，脚本据此自行判断"目标已经不在了"。**

**只限厚层 `Arena<Agent>`，不接受薄层 `ThinPopulation` 的实体引用**。理由：

1. `EntityId` 的世代号机制是「两层各自维护自己的 `(索引, 世代)` 分配」（`crates/ll-world/src/entity/id.rs` 模块文档原话）——同一个裸 `EntityId` 值分别喂给厚层与薄层是两次独立查询，互不相关。若值类型允许"随便一个 `EntityId`"，读取时无法判断该去查哪一层，会引入一整类新的歧义。`ScriptEntityHandle` 本身在姊妹设计文档里就只包 `EntityId` 且只在厚层场景下使用（`world.actors.get(handle.entity_id())`），本文档延续这条既有范围划分，不额外扩大。
2. 薄层是数十万到数百万个背景 NPC，设计上就不支持"个体寻址"——[0009](../decisions/0009-derive-by-default-store-only-deviation.md) 的棘轮教训（见该 ADR「棘轮问题」一节）已经证明"让大量个体各自累积一份记录"会让派生优化的收益归零。若脚本能对薄层任意实体存一份"扩展数据"，等于给了 mod 作者一条把百万级 NPC 全部升格成"有记录的个体"的隐蔽路径，重新踩中同一个坑。厚层实体数量按规格是"数百个"量级，不构成同类风险。

**为什么不是"一律不允许存任何实体引用，强制脚本改存可重新查询的条件"（这是本文档否决的另一个选项）**：

`identity-and-ids.md`「脚本 API 必须是查询式，不是引用式」一节的论证专门针对 `WorldId`——势力、家族这类**世界生成实例**，理由是名字随种子随机生成，换一个种子这个具体实例根本不存在，硬编码引用会让 mod 任务在别的种子下直接报废。**这条论证不能照搬到 `EntityId` 上**：`EntityId` 标识的是"当前这一局存档里正在被模拟的一个具体实体"，本身就是这局游戏内部的东西，不存在"换一个种子"的问题——脚本状态存储本身也只在"当前这份存档"的语境下才有意义，`WorldId` 论证的前提（"要在不同种子下都成立"）在这里根本不适用。

真正的技术反对意见只有一个：能不能安全地跨存档保存。这个问题的答案是"能，但有一条依赖"（见下面「依赖前提」），不是"不能"，因此不构成拒绝的理由。

若真的一律禁止存实体引用，代价是"NPC 记得在追谁"这类最常见的 AI 行为需求变得**表达不出来**——不存在一个能重新查询出"我三十个 tick 前锁定的那个具体敌人"的声明式条件（"距离最近的敌对实体"每次查询结果都可能不同，无法稳定指向同一个体）。禁止实体引用换来的"安全"是虚假的：它不会让 mod 作者放弃这个需求，只会逼着作者去找别的（更糟的）办法绕过限制,例如给目标挂一个自定义的、mod 自己在 `Affiliation` 或某个可查询字段上做的标记（这需要一条本文档没有设计、且会引入更多特例的旁路）。

**依赖前提，如实标注**：`crates/ll-world/src/state.rs` 里 `WorldState::actors`（即 `Arena<Agent>`）目前是 `#[serde(skip)]`——厚层实体本身还没有真正参与存档序列化，这是 `knowledge/handoff/p4-to-p5.md` 已经记录在案的 P4→P5 债务（「多处 `serde(skip)` 待还」一节）。脚本状态里存的 `EntityId` 要在读档后正确解析回原实体，**要求 `Arena<Agent>` 的序列化往返保持槽位下标与世代号逐位不变**（`Arena` 本身是 `Vec<Slot<T>>` + 空闲下标列表，直接派生 serde 不涉及任何跨字段不变式，理论上不难补齐,但**本文档不代为完成这项工作，只指出这条既有债务现在多了一个真实的下游依赖方**）。P5 落地存档格式时，若 `Arena<Agent>` 的 serde 补齐工作被安排在脚本状态存储之后，会出现一种令人困惑的过渡期现象：脚本存的 `EntityId` 保存前还能查到实体,读档后却查不到——**不是缺陷，是 3.4 节"失效返回哨兵值"约定的合法结果**,但如果开发者不知道这条依赖关系,会误以为是脚本状态存储机制本身出了 bug。**建议 P5 实现顺序把"`Arena<Agent>` 补齐 serde"排在"脚本状态存储接入存档"之前，或者两者同批完成**，避免这种过渡期困惑。

## 四、命名空间隔离

### 4.1 键的形状

复用既有 `NamespacedId`（`ll_core::ident`），键本身就是两段式：

```
全局存储：  (mod_namespace, key: String)          → ScriptValue
每实体存储：(EntityId, mod_namespace, key: String) → ScriptValue
```

`mod_namespace` 取自 `NamespacedId::namespace()`——与内容 ID 用的是同一套命名空间字符串（`lostland`、`yourmod`……），不需要为脚本状态另外发明一套命名规则。写入 API 的形状类似：

```scheme
(state-set! "grudge-target" target-handle)     ; 全局存储
(entity-state-set! actor-handle "cooldown" 5)  ; 每实体存储
```

宿主注册这两个函数时，`mod_namespace` **不是脚本传的参数**，而是宿主在注册这个函数实例时就已经固化好的上下文——这与 `ll-mod` 的既有模式（每个 mod 的脚本注册函数只能写自己命名空间下的内容，见 `crates/ll-mod/src/script_terrain_api.rs` 的 `set_active_target`/`take_active_target` 模式）同构：**mod 不需要、也没有办法在调用参数里指定"我要写哪个命名空间"，命名空间由宿主基于"当前在跑哪个 mod 的脚本"这个执行上下文决定**，脚本连伪造成别的命名空间写入的语法都没有。

### 4.2 一个 mod 能不能读另一个 mod 的状态

**结论：默认不能，但提供一个显式的只读跨 mod 查询函数，且只能查、不能写。**

正当需求确实存在——mod 互操作是"本体即 Mod"精神下的自然诉求，例如一个"声望联动"mod 想读某个基础 mod 记的教团声望值，用来驱动自己的额外规则。若完全禁止跨 mod 读取，这类互操作 mod 唯一的出路是要求基础 mod 作者专门为它开一个公开 API 函数——这在小型 mod 生态里是不现实的负担（要求每个 mod 都预判所有可能的互操作场景）。

但默认写入必须限定在自己的命名空间——**这不是靠信任约定，是 4.1 节已经描述的类型层面保证**：写入函数的命名空间由宿主注册时的执行上下文决定，脚本没有任何参数能覆盖它，天然做不到"意外或恶意地踩别的 mod 的状态"。

跨 mod**读**注册一个独立函数 `(state-get-foreign "yourmod" "reputation")`，返回值类型与 3.1 节相同，查不到（命名空间不存在，或该 mod 从未写过这个键）时返回哨兵值（沿用 `ScriptEntityHandle` 失效查询的同一套"读取型返回明确默认值，不是错误"约定，见 [脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 3.4 节）。这条查询路径本质是"公开只读接口"，与 mod 依赖拓扑（`crates/ll-mod/src/topo.rs`）已有的加载顺序保证兼容——被依赖的 mod 总是先加载、先有机会写入状态,依赖它的 mod 读到的永远是"上一个已完成 tick 的最终值"，不存在读到"写了一半"的中间态（脚本调用本身是同步的，见 `ScriptEngine::call_raw` 的调用约定）。

## 五、确定性（约束 C3）

三条具体规则，与 [脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 5.5 节的确定性规则同源，理由不重复展开：

1. **存储容器一律用 `BTreeMap`，不用 `HashMap`**——全局存储的键是 `(mod_namespace, key)` 字符串对，每实体存储的键是 `(EntityId, mod_namespace, key)`，两者都天然可比较（`String`/`EntityId` 均已 `Ord`），`BTreeMap` 给出确定的字典序遍历，满足约束 C3「禁止 `HashMap`/`HashSet` 的迭代顺序参与逻辑判断」（**这条约束在现有代码里存在编号不一致：`crates/ll-world/src/state.rs` 的 `WorldState::hash` 注释写的是「约束 C3」，`crates/ll-world/src/entity/id.rs` 同一条约束却写的是「规格 C4」——本文档沿用任务要求里使用的 C3，但如实标注这处既有的编号分歧，不代为裁定哪个编号对，见本文档末尾「发现的矛盾」**）。
2. **`Map(BTreeMap<...>)` 值类型本身也必须是 `BTreeMap`，不能是 `HashMap`**——3.1 节值类型定义已经用了 `BTreeMap`，这里重申：这不是随手选的容器，是确定性要求的直接体现，任何实现都不能为了"方便"换成 `HashMap` 再在读取时排序补救（补救本身也是一种隐藏的性能与正确性负担，不如从源头用对容器）。
3. **序列化/摘要遍历顺序固定**——若脚本状态未来需要参与 `WorldState::hash()`（`state.rs` 已有的确定性摘要函数，用于回归测试断言"同一意图流产出相同的世界哈希"），必须按 `BTreeMap` 的自然遍历顺序混入，与 `state.rs` 现有对 `actors: Arena<Agent>` 用 `iter()`（按槽位下标顺序，不依赖哈希表）混入摘要的做法保持同一套纪律。**本文档不要求脚本状态本批就接入 `hash()`**（这属于实现批次的取舍），但若接入，必须遵守这条顺序规则,不能假设"反正是 BTreeMap 应该自动没问题"就跳过显式验证——[脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 5.5 节末尾同样提醒过"这类边界需要在实现时用测试钉住"，同一条纪律。

## 六、有界性：不能让 mod 把存档撑爆

### 6.1 配额必须按 mod 静态划分，不能是共享浮动总量——这是确定性要求，不是简化选择

这是本节最容易被想当然做错的地方，值得先讲清楚为什么。若配额是"全部 mod 共享一个总量池，谁先写谁占位"，那么"某次写入是否成功"就取决于**加载顺序/执行顺序**——同一个种子、同一批 mod，只要拓扑排序在两次加载之间因为某个无关改动（比如新增一个不相关的依赖声明）而调整了顺序，原本能写入的某个 mod 可能因为"额度被前面的 mod 占满了"而写入失败，这类失败会直接体现成游戏逻辑的分叉，是确定性重放的隐患，与约束 C3 同一个精神（"结果不能依赖与逻辑无关的执行顺序"）。

因此**每个 mod 的配额必须是加载期就能确定的静态常量，与其余 mod 的实际用量无关**——A mod 用不用得完自己的配额，不影响 B mod 能不能写。

### 6.2 具体数字

- **每 mod 默认配额**：全局存储 + 每实体存储合计 **256 KB**（序列化后大小，采用与存档相同的编码，即 `postcard`，具体见 `knowledge/handoff/p4-to-p5.md` 「存档格式」相关记录提到的 `postcard`/`lz4_flex`）。这个数字按值类型系统的典型条目大小倒推：一条 `(String key, Int value)` 记录序列化后约十几到几十字节（取决于 key 长度），256 KB 能容纳上万条这个量级的记录——覆盖"教团声望表几百个组织"、"任务进度字典几十条"这类真实场景绰绰有余，同时不会让一个失控 mod（例如脚本 bug 导致每 tick 都写一个新键而不是覆盖旧键）在合理游玩时长内把存档拖到不可接受的体积。
- **每（mod × 实体）配额**：**4 KB**。厚层实体数量按规格是"数百个"量级，256 KB（单 mod 上限）÷ 数百 ≈ 每实体几百字节到 1KB 出头，4KB 是留了余量的上限（不是"平均能用到多少"，是"单个实体最多能占多少，防止某一个实体被塞爆而挤占同 mod 下其他实体的份额"——这与 6.1 节"静态划分不能互相挤占"的精神在实体粒度上的延伸：mod 内部按实体也要有硬上限，不能变成"谁的 AI 先跑就占满谁的配额"）。
- **这两个数字都是初始建议值，不是精确科学**——与 `crates/ll-script/src/host.rs` 的 `INTERRUPT_TIMEOUT`（300ms，同样标注"具体数值属于可调参数，不是精确科学，后续如有真实卡顿投诉可以再调"）同一种诚实态度。真正的调优需要等 P5 有真实 mod 内容之后用实测数据校正。

### 6.3 超限时的处理：拒绝写入，不静默截断、不报错崩溃

写操作超过配额时，`state-set!`/`entity-state-set!` **返回一个明确的失败哨兵值**（与 3.3 节「实体引用失效」用的是同一套"读取型/写入型都不用 `Result` 而用哨兵值"的既有约定，理由同 [脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 3.4 节——把"配额超限"当成"脚本出错"用 `ScriptError` 处理级别不对，这是运行时会发生的正常状况，不是异常）。**同时**产生一条 `ScriptDiagnostic::Warning`（复用 `crates/ll-script/src/api/log.rs` 已有的诊断类型），标注是哪个 mod、哪个键触发了超限——这一步是必须的：若只返回哨兵值不留痕迹，mod 作者会看到"写入好像没生效"却毫无线索,与规格反复强调的"错误必须可观测"精神相悖。

**不做"淘汰旧数据腾地方"这类自动裁剪**——这会让"哪些状态还在"变得不可预测（取决于写入顺序与淘汰算法），既破坏确定性也让调试更难。超限就是超限，靠明确的失败信号逼 mod 作者自己决定裁剪策略（比如用定容 LRU，[0009](../decisions/0009-derive-by-default-store-only-deviation.md) 的关系系统记忆槽已经是这个模式的先例，mod 作者可以在自己的存储预算内照猫画虎实现同样的策略,只是这次的"预算"由本文档的配额机制强制执行,而不是靠 mod 作者自觉）。

### 6.4 加载管理界面显示状态占用

按 [0016](../decisions/0016-mod-performance-tiers-by-declaration.md)「配套：把开销做成可见的」一节的既有精神——"代价可见，人才会去省"，加载管理界面（`ll-ui`）新增一栏，展示每个 mod 当前的状态占用（例如"某 mod：存储了 4MB 状态，占配额 1.5%"——注意这个例子数字远超 6.2 节建议的单 mod 256KB 配额，意味着这样的展示同时是一种预警：一旦某个 mod 的占用逼近或超过配额，界面上应该有醒目的视觉区分，不只是一行安静的数字）。这与 [脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 5.4 节设计的"运行期跨界调用计数器"是同一个方向的两个独立指标（一个管"存了多少"，一个管"调用了多少次"），两者都应该出现在同一个诊断面板里，但不需要合并成一个数字——它们衡量的是不同种类的代价（存储空间 vs. 计算/跨界开销）。

## 七、mod 被移除后，孤儿状态怎么办

### 7.1 结论：保留，随「生成期/当前 mod 集合」双记录一起处理，不主动清除

`identity-and-ids.md`「存档与 mod 集合」一节已经定下「生成期 mod 集合 ≠ 当前 mod 集合」的框架，`crates/ll-mod/src/mod_set.rs` 已经把这条区分落地成两个不同的类型（`GenerationModSet`/`CurrentModSet`，编译期阻止混用）。脚本状态的孤儿处理策略必须与这套记录配合，不能另起一套判断逻辑：

- **读档时**：若某个 mod 在「当前 mod 集合」里缺失，但存档的脚本状态数据里有它的命名空间残留——不删除这些数据，原样保留在 `WorldState` 里（序列化/反序列化只做数据搬运，不做"清理"这种带业务判断的操作）。
- **该 mod 重新启用时**：它的状态原样可读——因为从未被删除过，`state-get`/`entity-state-get` 立即能查到重新启用前留下的值，不需要任何"恢复"步骤,数据本来就在那。
- **该 mod 长期不再启用**：状态永久占用存档空间,直到玩家手动做"清理未使用 mod 数据"这类维护操作（本文档不设计这个维护工具本身,只是不阻止它未来存在的可能性)。

**为什么不主动清除**：

1. **对称于「缺失 mod 不得崩溃」的既有底线**（规格 §10.4，`identity-and-ids.md` 已经展开成按内容类型分级处理的具体策略）——清除数据是比"降级但保留"更激进的操作,而 `identity-and-ids.md` 表格里"玩家角色的种族缺失也不能降级"这一条已经确立了这个项目对"因为 mod 缺失就丢数据"的态度是能不丢就不丢。脚本状态虽然不像"玩家角色种族"那样性命攸关,但同一条精神适用:装卸 mod 是玩家的常规操作（`p4-to-p5.md` 已经写明"玩家中途装卸 mod 极其常见"),若每次卸载都清空该 mod 积累的所有脚本记忆,复装同一个 mod 后"记忆消失了"这种体验对玩家不友好,且不可逆——存档里原本还在的数据被清除后无法恢复。
2. **清除时机本身没有明确的触发点**——「什么时候该判定一个 mod 是真的不再需要,而不是玩家只是临时禁用」不存在一个可靠的信号（玩家可能这局不装,下局又装回来）。主动清除需要一个"确认删除"的用户交互流程,这属于存档管理 UI 的职责,不是脚本状态存储机制本身该做的决定。本文档只保证"机制不主动删,不代表玩家永远不能删",两者是不同层次的问题。
3. **存储代价有限,不构成非清除不可的压力**——6.2 节的配额已经把单 mod 上限钉在 256KB,即使若干个不再使用的 mod 各自占满配额,总量也在可控范围内（几个 mod 量级是几 MB,不是失控增长)。这与"必须清除"的紧迫性不构成同一数量级的问题。

### 7.2 与内容哈希机制的交互（一处需要留意但本文档不代为解决的边界）

`Registry::content_hash_of`（`crates/ll-mod/src/registry.rs`,已核实存在）与 `CurrentModSet`/`GenerationModSet`（`mod_set.rs`）已经提供了"同一个命名空间,内容是否变了"的检测能力。若某个 mod **版本变了、内容哈希也变了**再重新启用,它读到的脚本状态是"旧版本 mod 写下的数据"——这条数据在语义上是否还有效（例如某个键在新版本里已经被重新设计成别的含义）,本文档**不做判断**,这属于 mod 作者自己的迁移责任（与"存档 schema 版本 vs mod 版本分开报错"这条既有纪律——`identity-and-ids.md`「schema 版本与 mod 版本是两条正交的轴」一节——是同一类问题,mod 内容变化导致的数据不兼容,只能由该 mod 自己提供迁移逻辑,机制本身管不到这一层)。**如实标注**:本文档没有为"脚本状态的 mod 内迁移"设计任何专门机制,这是一个真实的开放缺口,留给后续任务视真实需求决定要不要做。

## 八、与既有原则的关系

### 8.1 ADR 0009「默认派生，只存偏差」——脚本状态是这条原则的正当例外，不是违反

[0009](../decisions/0009-derive-by-default-store-only-deviation.md) 的适用条件写得很明确（该 ADR「适用条件」一节）：这个原则要求「默认值可以从种子 + 少量固定 ID + 已知上下文确定性重算」。脚本状态**不满足**这个前提——"NPC 记得在追谁""任务进行到哪一步"这类信息**不是**可以从种子重新推导出来的公式,它是脚本执行过程中真正累积出来的、无法预先算出的决策历史。硬要套用"默认派生",唯一的"派生公式"是"重新完整模拟一遍这个 NPC 从游戏开始到现在的全部决策"——这既不是"简单的整数公式"（0009 的适用条件第一条),也违背"被记住"与"被模拟"分离的省算原则本身。

**脚本状态因此必须存,这不是对 0009 的违反,是 0009 自己写明的适用边界之外的东西**——0009 管的是"能重算就不存"的那一类数据（钱包基线、姓名、关系默认值),脚本状态从一开始就不属于这一类。两者不冲突,是互补关系:0009 减少了需要存储的数据量,脚本状态存储解决"剩下这部分真正没法省的数据该往哪存"的问题。

### 8.2 ADR 0010「单一真相源」——`WorldState` 是真相源，VM 副本是缓存，如何防止脱节

[0010](../decisions/0010-single-source-of-truth-for-daylight.md) 的教训是"写了警告不等于警告会被遵守"——一份数据的两套独立定义迟早会分裂。脚本状态的真相源必须是 `WorldState`（第二节已经定下),VM 内部**不应该、也不需要**为它维护任何"缓存副本"：

- **读**：`state-get`/`entity-state-get` 每次调用都直接查 `WorldState` 里的存储（经 `with_active_world` 同款的活跃世界指针模式,`crates/ll-script/src/api/query.rs` 已有先例),不做"VM 侧缓存一份,定期同步"这种设计——那正是 0010 教训里"另设一套定义"的现代等价物。
- **写**：`state-set!`/`entity-state-set!` 直接写穿到 `WorldState`,没有"先写 VM 本地变量,回合结束再同步"这种中间层。脚本每次读到的都是"当前 `WorldState` 里的最新值",不存在"脚本自己以为的状态"与"真实存档状态"不一致的窗口。

这个设计选择的代价是每次读写都要经过一次跨界调用（[脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 已经论证过单次跨界 326ns,纳秒级,可以放在热路径),换来的是"VM 重建"这件事在语义上完全无痛——VM 里从来没有值得保留的东西,重建前后脚本读到的 `state-get` 结果完全一致,因为读到的本来就是同一个 `WorldState`。

### 8.3 约束 C1 的修订表述

原文（[脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 3.5 节引用）：

> Steel 脚本不得持有任何跨帧的隐式状态。任务进度、技能冷却、AI 记忆、行为树当前节点，全部存放于 `WorldState`。脚本是纯函数，通过明确 API 读写世界黑板。VM 必须可随时从零重建。

「隐式」这个限定词在原文里没有实际约束力——因为当时**没有任何显式机制存在**,任何跨帧状态都只能是隐式的（活在 VM 里,没有明确 API）,「隐式」形同虚设的修饰语。本文档落地之后,「显式」有了具体所指（本文档设计的 `state-set!`/`entity-state-set!` API）,「隐式」这个词才第一次有了实际排除的对象。

**建议修订表述**：

> Steel 脚本不得持有任何跨帧的隐式状态——任何需要在下一次调用中还记得的东西，必须经由本文档定义的 `state-set!`/`entity-state-set!`（或未来同类明确注册的读写 API）显式存入 `WorldState`，不得依赖 VM 自身的 `define`/`set!`/闭包捕获来跨调用留存。任务进度、技能冷却、AI 记忆、行为树当前节点，全部经这条路径落地。脚本本身除了这条显式通道之外应被当作纯函数对待：给定相同的 `WorldState`（含脚本状态）与相同输入，必须产出相同结果。VM 必须可随时从零重建——重建不需要任何特殊的"状态迁移"步骤，因为脚本本该没有任何值得迁移的东西。

修订要点：把"脚本是纯函数"从一个笼统断言,改成"给定相同输入产出相同结果"这个可以被测试断言的具体表述（呼应约束 C3 的确定性要求本身)；把"VM 必须可随时从零重建"从单纯的能力声明,升级为"重建不需要迁移步骤"这个更强的断言——这正是本文档整套设计要保证的性质,值得写进约束本身,而不只是留在设计文档里。

## 九、配套：强制重建 VM 的策略

### 9.1 存档/读档边界：强制重建

**规则**：任何一次读档完成后，在游戏恢复正常 tick 推进之前，**丢弃当时存在的全部 `ScriptEngine` 实例，重新构造**（`ScriptEngine::new()` + 各 API 模块的 `register()` + 对每个已加载 mod 重新调用一次 `load_source`)。存档（写盘）本身不需要重建——写盘只是把 `WorldState` 序列化,VM 状态本来就不参与序列化（第二节已经论证：VM 不该有值得保留的东西),因此存档动作对 VM 没有影响,只有**读档**这个"世界状态被替换成另一个时间点的快照"的操作才需要重建 VM。

**为什么必须是强制而非可选**：若重建是可选的（例如"只有检测到需要时才重建"），就需要一种"检测"机制来判断某个 VM 实例是不是"干净的"——而这正是 1.2 节已经指出的、`tools/ll-datacheck` 尚不存在的那类静态检查工作。**强制重建绕开了"先检测再决定"这条本来就没有可靠检测手段的路**：不管 VM 里有没有脏状态,统一清空重来,天然安全,不依赖任何检测的可靠性。

**代价评估**：单次 `engine.run(源码字符串)` 实测 327~400µs（[0012](../decisions/0012-steel-capability-surface-verification.md) 表格,已核实的真实数字)。这是"重新解析并执行一份脚本源码"的成本，`load_source` 内部还会多做一次 `emit_fully_expanded_ast` 展开供白名单校验（`host.rs` 模块文档标注"多付一次解析的代价，ADR 0012 实测量级 ~百微秒"），因此单个 mod 的重新加载成本约在 **400~500µs** 量级（未精确核实这个加总值本身,是按已核实的两个分量估算的推论,不是直接测量结果）。读档本身已经涉及磁盘 I/O 与整个 `WorldState` 的反序列化,这个量级的重建成本（几十个 mod 合计可能到几十毫秒）在读档这个动作里完全不可感知——玩家对"读档需要多久"的容忍度以秒计,不是以毫秒计。

### 9.2 区块切换时是否也重建：不建议，理由是频率与代价不匹配，且没有必要性

**结论：不建议在区块切换时重建 VM。**

区块切换（`coordinate-system-and-layers.md` 设计的区块流式加载,已核实是「必须重写、且必须先于存档格式定形」的三处之一,当前尚未落地)在游玩过程中的触发频率远高于存档/读档——玩家可能每几秒到几十秒就跨越一次区块边界,这与"读档"这种以分钟到小时为间隔的动作完全不是同一个量级。若每次区块切换都重建全部 mod 的 VM,几十个 mod × 400~500µs 的重复解析成本会**反复**发生在一个玩家几乎感知不到"为什么在这个时间点"的场景里——9.1 节论证"读档时这点开销不可感知"依赖的正是"读档本身已经很重",这个前提在区块切换场景下不成立（区块切换设计上应该是尽量无感的流式加载,`coordinate-system-and-layers.md` 的整个设计动机就是避免"切换时明显卡顿"）,重建 VM 会直接违背这个设计目标。

**更重要的是,没有必要性**：区块切换不改变"当前是哪一局存档",`WorldState`（含脚本状态)本身没有被替换成另一个时间点的快照——第八节已经论证"`WorldState` 是真相源,VM 不缓存",既然 VM 从不缓存脚本状态本身的值,区块切换这个"只是玩家的可见范围变了"的事件,没有任何理由让已经加载好的脚本函数定义失效。重建的正当性来自"世界状态被替换"（读档),不来自"玩家移动了"。

若未来某个具体场景证明区块切换确实需要重建（例如某种"区块级 mod"设计,不同区块加载不同的脚本内容——**这在当前设计里不存在**,只是留一个如实标注的可能性),那应该是一个独立的、有自己论证的决定,不能用本节"存档边界重建"的论证顺手套用过去——两者触发条件完全不同,不应该被混为一谈。

### 9.3 mod API 契约需要明确声明的一句话

`crates/ll-script/src/host.rs` 的 `ScriptEngine` 类型文档,以及未来面向 mod 作者的 API 文档,都应当包含这条契约声明：

> **VM 状态是一次性的。游戏可以在任何时刻（尤其是每次读档之后）不加警告地重建整个脚本引擎，丢弃 VM 内部通过 `define`/`set!`/闭包捕获积累的一切。任何需要跨越这次重建存活的信息，必须经由 `state-set!`/`entity-state-set!` 显式写入世界状态——这是脚本与游戏世界交互的唯一持久化通道。**

这句话的作用是把"重建随时可能发生"从一个实现细节,提升为**mod 作者写脚本时必须遵守的契约**——与 [0016](../decisions/0016-mod-performance-tiers-by-declaration.md) 「配套：把开销做成可见的」一节的精神一致：约束不能只藏在实现里,必须被明确告知受约束的人。

## 十、开放问题（如实标注，不假装已解决）

1. **值类型系统是否需要支持存储 `WorldId`**——本文档 3.1 节的值类型没有纳入 `WorldId`（势力/家族等世界生成实例的标识）。协调过程中没有出现明确需要脚本"记住某个 `WorldId`"的场景（通常经由 `Agent.affiliations` 这类已持久化字段读取,不需要脚本单独复制一份),但没有充分论证"绝对不需要"。留给后续任务视真实 mod 需求决定是否补充。
2. **是否需要接入 `WorldState::hash()`**——五节已经提到,本文档不强制要求,若后续接入需要专门测试钉住遍历顺序,本文档只给出了"若接入必须怎么做"的规则,没有替实现批次做这个取舍。
3. **每 mod / 每（mod × 实体）的具体配额数字（6.2 节的 256KB / 4KB）没有经过任何真实 mod 内容的实测校准**——是按值类型典型条目大小做的理论倒推,不是基准测试结果,与 `INTERRUPT_TIMEOUT` 一样标注为"可调参数,不是精确科学"。
4. **跨 mod 读取（4.2 节）的性能特征未评估**——`state-get-foreign` 本质仍是一次跨界调用（326ns 量级),但若某个"聚合"mod 频繁读取多个基础 mod 的状态,是否需要类似 [脚本层数据句柄与批量查询](script-entity-handles-and-batch-queries.md) 5.4 节的运行期调用计数器覆盖,本文档没有展开,留给后续任务评估是否需要专门监控。
5. **脚本状态的 mod 内迁移机制**——7.2 节已标注,没有设计任何机制,完全留给后续任务或 mod 作者自行处理。
6. **`Arena<Agent>` 补齐 serde 与本文档接入存档的实现顺序**——3.3 节「依赖前提」已详细论证,本文档建议但不强制两者的先后关系,具体排期属于 P5 实现计划的职责。
