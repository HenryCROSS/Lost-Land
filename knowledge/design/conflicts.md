# 设计文档交叉核对：冲突与缺口清单

核对范围：`knowledge/design/` 下五份文档（物品、装备、属性、社会、经济）互相之间的矛盾与缺口。核对方法：逐对通读全文，重点看同一概念的命名、数据结构、数值/公式是否一致；代码相关的判断均去 `crates/` 里 grep 验证过，不是猜测。

**规则**：本清单只记录「两处说法不一致，需要人来裁定选哪个」（标「待裁定」）与「某处承诺了一个机制，但没有人把它写完整」（标「设计缺口」）。没有发现足以直接判定为笔误的地方，因此没有条目被直接改动——所有条目都保留了两边的原话，不替读者做选择。

## 待裁定（均已裁定，结论见各条目末尾）

### 1. 「近景/中景/远景」LOD 与「背景层/前景层/具名层」精度划分，是不是同一件事 —— 已裁定

**出处 A**——`society-and-affiliation.md` §六「LOD 兼容性」：势力/宗教/行会的运作按**近景 / 中景 / 远景**三档运行（引用总纲规格「决策 21」：`三档 LOD（近景/中景/远景）+ 惰性追赶`）。近景个体决策，中景按聚落+归属聚合，远景只维护组织级聚合量。

**出处 B**——`agent-goals-and-economy.md` §七之二「背景与前景：公式与模拟的分界」：NPC 个体的钱包与决策按**背景层 / 前景层 / 具名层**三档运行。背景层批量公式、前景层跑真实决策、具名层「永久高精度，数量由内容设计控制」。

同一份 `agent-goals-and-economy.md` 的 §六（职业审计）与 §八（惰性追赶的边界）又直接使用「近景」「远景」这两个词，与决策 21 的措辞一致——说明作者知道有那一套三档 LOD，但 §七之二 没有明说自己这套「背景/前景/具名」是不是它的别名。

**冲突点**：如果两套是同一件事的不同叫法，「具名层：永久高精度」这句话就与「远景：个体归属休眠、只维护组织级聚合量」字面冲突——一个身处远景区域的具名 NPC，到底遵守哪条规则？§七之二后段的「棘轮问题」小节把「被记住」与「被模拟」拆开，暗示了一种可能的调和方式（具名层只保证被记住永久保留、被模拟仍受空间距离节流），但没有回头修正前面那句「永久高精度」，也没有明说这就是化解方式。

**两种可能的裁定方向**（不代为选择）：
- (a) 明确「背景/前景/具名」就是「近景/中景/远景」在 NPC 精度维度上的别名，补一张映射表；
- (b) 明确两者是正交的两个轴（空间 LOD × 记忆/模拟精度），并把「具名层：永久高精度」改成「具名层：永久被记住，被模拟仍受空间 LOD 节流」。

**裁定：方向 (b)，但轴的名字不是「空间 LOD × 记忆/模拟精度」，而就是「被记住 / 被模拟」这一条已经在棘轮问题里定义过的轴——距离完全不参与决定精度。** 废弃「近景/中景/远景」这套词汇，统一术语为**背景层 / 前景层 / 具名层**：背景层是「被记住但不被模拟」，前景层是「被记住且被模拟（数量被玩家视野天然限界）」，具名层是「永久被记住，但是否被模拟与前景层同受被模拟的 LRU 上限约束，不因『具名』这个身份本身而豁免」。

一个具名 NPC 走到地图另一头仍然是具名的——名字、家族、恩怨都还在——按距离分层会得出「他远了所以该休眠」这个对具名 NPC 不成立的结论，这正是本条冲突的根源：把两条正交的轴压扁成一条距离轴。已落地到 `society-and-affiliation.md`「六、LOD 兼容性」一节与 `agent-goals-and-economy.md`「七之二、背景与前景」一节，两处术语与推导已对齐。

### 2. 行会定价公式是否包含买家的归属折扣 —— 已裁定

**出处 A**——`society-and-affiliation.md` §一「这个统一带来的直接回报」：Affiliation 查询同时驱动「**交易价格**——同势力/同行会打折，敌对加价或拒绝交易」，暗示价格取决于买家本人的归属状态。

**出处 B**——`agent-goals-and-economy.md` §三「行会如何定价」，给出的唯一公式：

```
本地价 = 基础价 × 库存系数 × 需求系数 × 行会政策 × 商路系数
```

五个因子全部是行会/地点级别的，不含任何「买家是谁」的项。这是全文唯一给出的定价公式，如果按字面实现，同一行会对所有买家出的是同一个价，与出处 A 的「同势力打折」矛盾。

**判断**：更可能是遗漏（「行会政策」这个因子被想象成隐含了对外来者的加价，但没有把「买家折扣」显式拆出来作为独立乘数或后处理步骤），而不是有意设计成统一定价。建议实现前先决定：要么在公式里显式加一项「买家归属系数」，要么把出处 A 的表述改得更保守（比如折扣只发生在单笔交易结算，不进入公示的「本地价」）。

**裁定：社会文档对。** 在行会定价公式外补一项，`成交价 = 本地价 × 买家归属系数`——`本地价` 保持五个因子不变、维持行会/地点级别的公示价；买家归属系数独立结算，因为它必须用买家当前的 `Affiliation.standing` 在**每笔交易**时现算，而 `本地价` 五个因子只按行会结算周期批量刷新。两者更新频率不同，不应该合并进同一个数。已落地到 `agent-goals-and-economy.md`「行会如何定价」一节，`society-and-affiliation.md`「这个统一带来的直接回报」一节已交叉引用。

### 3. 「受限转行」算法有没有把「熟练度」算进去 —— 已裁定

**出处 A**——`society-and-affiliation.md` §四之三「职业也参与关系派生」：「**转行摩擦**——熟练度即**沉没成本**——干了二十年的铁匠不会因一季度收益差就改行。这正是「受限转行」需要的阻尼器，不必再单列「转行成本」字段」。明确说熟练度是受限转行算法的输入之一，且是用来**替代**一个假想的「转行成本」字段的。

**出处 B**——`agent-goals-and-economy.md` §六「职业审计」，给出的判定条件：

```
若 收益差距 > 阈值
且 付得起学徒费
且 有人能教（同城有该职业师傅 / 行会名额）
且 年龄与属性允许
且 性格允许（保守者阈值更高）
   → 转行
```

条件列表里没有「熟练度」这一项，也没有说明「阈值」本身是否随熟练度浮动。

**判断**：这是承诺与实现清单之间的缺口，不是两个数值互相矛盾。裁定方向：要么在审计算法里显式加入熟练度对阈值的调制项，要么在出处 A 里澄清「熟练度」只是定性地体现在「性格允许」那一档判断里，不是独立变量。

**裁定：前者。** 补入判定条件——「收益差距 > 阈值」里的阈值随当前职业熟练度提高而提高，不是单列一个「熟练度」布尔条件。理由：熟练度是连续调制阈值的阻尼器（沉没成本），不是「允许/不允许」的开关，做成布尔条件会丢掉这个连续性，做成阈值的调制项则正好复用 `AffiliationKind::Profession.standing` 已有的语义，不需要新字段。已落地到 `agent-goals-and-economy.md`「六、职业审计」一节，`society-and-affiliation.md`「职业也参与关系派生」一节已交叉引用。

### 4. 「威望」（个人次级属性）与「职业声望」（聚落×职业的社会评价）是否同一个量、是否叠加 —— 已裁定

**出处 A**——`attribute-system.md` 次级属性「社交与经济」组：「议价（影响交易价格）/ **威望** / 领导力（决定可带随从数上限）」。威望挂在角色本人身上，没有给出计算方式。

**出处 B**——`society-and-affiliation.md` §四之三「职业声望是局部的，不是全局常量」：

```
本地职业声望(职业, 聚落) = 文化基准 × 经济状态修正 × 本地条件修正
```

这个「声望」挂在「职业 × 聚落」这个二元组上，是所有从事该职业的人共享的社会评价，不是角色个人的属性值。

**冲突点**：两处都用「声望/威望」这个词根，但一个是个人属性（来源未定义，大概率来自成就/等级/事件），一个是群体聚合量（来自文化与经济状况，与个人无关）。玩家实际感受到的"別人怎么看我"到底是两者相加、还是只取其一、还是两条独立的轴，两份文档都没写。

**判断**：不确定是命名撞车还是有意设计成两条轴（类似「个人声誉」与「行业地位」）。建议裁定：明确二者关系，或至少改用不同的词根区分（例如把个人次级属性改叫「声誉」，职业维度的继续叫「职业声望」）。

**裁定：改名区分，不合并。** 个人次级属性改叫**名望**（来自事迹），职业维度保留**声望**（来自当地文化与经济）。二者是否叠加仍是未来数值设计要回答的问题，但这不再是一处文档冲突——两个量现在有不会撞车的名字。已落地到 `attribute-system.md`「次级属性」一节与 `society-and-affiliation.md`「职业声望是局部的」一节，两处已互相交叉引用说明区别。

## 设计缺口（不裁定，只记录缺什么）

### 5. `StatBonus` 结构从未被定义

`item-system.md` 的 `ItemDef` 里有字段 `stat_bonuses: Vec<StatBonus>`，两份文档的「相关文档」区块都提到"`StatBonus` 如何参与派生"应该在 `attribute-system.md`。但 `attribute-system.md` 通篇没有 `StatBonus` 的字段定义，`derive_stats(基础属性, 装备, 状态效果, 负重) -> DerivedStats` 也没有说明如何读取装备的 `stat_bonuses`（加成哪个主属性/次级属性？固定值还是千分比？是否受品质倍率影响？）。两份文档都不缺这一环，只是谁都没写。

### 6. `EquipSlot` 类型从未被正式定义

`item-system.md` 的 `ItemLocation::Equipped { holder, slot: EquipSlot }` 使用了 `EquipSlot` 类型（表示物品当前占据的**单个**槽位）。`equipment-slots.md` 只定义了位掩码类型 `SlotMask`（表示一件装备**声明占用的槽位集合**）和一张槽位表（含 `MAIN_HAND` 等命名位）。这两个类型服务于不同目的（掩码 vs 单值），大概率是有意分开的，但 `equipment-slots.md` 从未显式声明一个叫 `EquipSlot` 的枚举类型，读者只能自行脑补它就是槽位表里那 22 个具名位各对应一个变体。

### 7. 品质价格倍率如何进入行会定价公式的「基础价」

`item-system.md` §五「品质」给出价格倍率表（粗糙 500‰ ~ 传说 50000‰），但没说这个倍率是乘在 `ItemDef.base_price` 上得到 `ItemStack` 的实际价格，还是别的什么基准。`agent-goals-and-economy.md` §三「行会如何定价」的公式以「基础价」为输入，但没有说明这个「基础价」是否已经包含品质倍率，还是行会公式自己还要再乘一次。两份文档语义上大概率兼容（品质决定物品实例的「基础价」，行会公式再在其上叠库存/需求/政策/商路），但没有一处把这条链路显式写出来。

## 记录但不算冲突

### 8.「默认派生，只存偏差」的复用编号不连续

`society-and-affiliation.md` 第 238 行称关系系统是「同一个思想的第三次复用」，第 404 行称背景 NPC 性格是「第五次复用」，但文中从未标注哪个是「第一次」「第二次」「第四次」。结合 `agent-goals-and-economy.md` §七之二 的钱包偏移量+重定基准机制（明显也是这一思想的实例，但该节完全没有使用「第 N 次复用」的编号语言），可以推断「第一次」大概率指钱包，但缺一个明确的「第四次」。这不影响任何实现，只是编号本身的可追溯性不完整。已在 `README.md` 的设计原则一节改为直接罗列全部已识别实例，不依赖原文编号，读者无需受这个编号困扰。

### 9. 千分比数值统一用 `Milli(i64)` 还是原生 `i32`/`i16`

[决策 0002](../decisions/0002-integer-only-world-state.md) 规定「货币、价格、比例、速率」一律用 `Milli(i64)`。五份设计文档里，价格与重量确实用了 `Milli`（`item-system.md`），但几乎所有「千分比」的比例/速率字段（`Affiliation.standing`、`Goal.progress`、`Caravan.risk_tolerance`、`Penetration.permille` 等）都直接写成裸 `i32`，`Traits` 六项更是 `i16`。五份文档在这一点上彼此一致，不构成互相矛盾，但作为一个整体，与决策 0002 的字面表述有出入。是否要紧——`Milli` 本质也是缩放整数，`i32`/`i16` 装千分比数值范围完全够用——不影响确定性，只是没有用同一个类型名字。列在这里供后续决定是否需要统一命名，不要求现在改。
