## 二、第一组：导航一致性

### 2.1 N3「返回」与「关闭」不共用一行

规格判据：**任何屏最多有其中一行**，「今天没有屏违反，这条是防将来」。

难点在于**怎么让这条判据不是一句同义反复**。今天每块屏的行都是一个枚举
（`pause_menu::MenuRow`、`menu_screen::SettingsRow`、`chargen::CharacterRow`、
`world_setup::WorldSetupRow`），行为分派是对这些枚举 `match`。如果另写一张
「哪一行算返回、哪一行算关闭」的表，那就是真相源之外的第二份副本——本仓库
反复付过代价的形状。

**做法**：新增 `crates/ll-game/src/nav_row.rs`：

```rust
pub enum NavRole { Back, Close }
pub trait NavRow: Copy { fn nav_role(self) -> Option<NavRole>; }
pub fn sole_nav_role<R: NavRow>(rows: &[R]) -> Result<Option<NavRole>, NavRoleConflict>;
```

四个行枚举各实现一次 `NavRow`，并且**把它接进真实分派**：
`pause_menu::update_menu` 对「关闭」那一行的分支改成问 `nav_role()`，
不再对 `MenuRow::Continue` 直接 `match`。这样「角色标错」不是只有门禁会红，
菜单的行为当场就变了——判据与行为共用同一份声明。

`Title` 的「离开」是 `ScreenOutcome::Quit`（退进程），**不是** `Close`；
存档列表 / 命名屏 / 选点屏 / 会话屏没有导航行（它们只有 Esc）。这些在
`nav_row.rs` 的模块文档里逐条写明，不留「漏了还是本来就没有」的歧义。

**判据**：四块屏各一条 `sole_nav_role(rows).is_ok()`；外加一条
「`MenuRow::Continue` 的角色是 `Close` 且按它真的得到 `ScreenOutcome::Close`」。
**反例**：把 `MenuRow::BackToTitle` 的角色也标成 `Close` ⇒ `sole_nav_role` 红。

### 2.2 N4 深度上限 3

**落点** `crates/ll-game/src/modal.rs`：

- `pub const MAX_DEPTH: usize = 3;`
- 一条私有判据 `fn would_exceed(&self, 目标层数: usize) -> bool`；
- 三个会加层的入口（`set_screen`、`toggle_world_map`、`with_player_menu`）
  在**动任何字段之前**先问它，超了就整个拒绝：状态字段不改、栈不压、
  `assert_paired` 因此照旧成立。
- 拒绝时 `debug_assert!(false, …)`：规格明说第 4 层意味着流程设计出了问题，
  应当在开发期就红。发布构建下退化成「拒绝但不崩」，与
  `Modal::assert_paired` 用 `debug_assert` 同一条既有取舍。

`with_player_menu` 的闭包已经把 `PlayerMenu` 改掉了才知道会不会超——因此
**先存一份旧值，超了就整个还原**。`PlayerMenu` 是 `Copy`，还原是一次赋值。

`set_screen` 的层数是 `屏(1) + 命名屏要的文本输入层(1)`，因此它要按
「换成 `next` 之后一共几层」算，不是无脑 +1（换屏、关屏都不该被上限挡住）。

**判据**：地图 + 玩家菜单 + 模态屏 = 3 层之后，再开命名屏（会要第 4 层）被拒绝，
且四个字段与栈全部原样。**反例**：把 `would_exceed` 改成恒 `false` ⇒ 该条红，
且红的原因是「深度变成 4」而不是别的。

### 2.3 N10 所有列表进入时第 0 行预选中

**落点**：`app/screen_flow.rs` 的换屏漏斗。**屏别真的变了**（按
`std::mem::discriminant` 比，不是整个 `ScreenState` 比——设置屏光标每动一格
`next != state` 就成立，用整体相等会变成「每帧重置」）时：

```rust
self.screen_focus = self.preselected_focus_for(next);
```

`preselected_focus_for` 对首页/菜单屏返回 `menu_screen::preselected_focus(ids)`
（复用批次 15 那一个函数，不新造第二套「怎么算第一项」），对 `cursor` 模型的
七块屏返回空表——它们的「第 0 行预选中」由 `cursor: 0` 表达，那是批次 21 会话屏
用的同一套，本批不改它。

**判据**：`Demo` 从首页 → 角色创建 → Esc 回首页，`screen_focus` 里第 0 项聚焦、
直接按 `Confirm` 进得了角色创建屏；再补一条覆盖真实退化路径的：玩家死亡
（`screen_focus` 被清空）→ 角色创建屏 → Esc → 首页 → `Confirm`。
**反例**：把漏斗里那一句删掉 ⇒ 后一条红，红的原因是「焦点表为空，
`focus_index` 返回 `usize::MAX`」。

### 2.4 N14 提示语在屏切换时清空

**落点**：同一个漏斗，同一条「屏别真的变了」判据。

**一处规格没裁定的取舍**：漏斗上游的六个分支会在**同一帧**里置
`self.screen_notice = update.notice`。无条件清空会把这一帧刚产生的那句话也吃掉。
因此清空的条件收紧成「这句提示不是本帧产生的」——在 `update_screen` 开头记一份
`notice_before`，漏斗里只在 `self.screen_notice == notice_before` 时清。
取这个而不是无条件清，理由是它**只删旧的、不删新的**，是两者里更保守、
更容易反转的那一个（要退回无条件清，删掉那个比较即可）。列进第九节。

**判据**：首页按「读取存档」（没有存档）得到 `NoSave` → 进设置屏 →
`screen_notice` 为 `None`。**反例**：把清空那一句删掉 ⇒ 红，红的原因是
`Some(NoSave)` 跟着进了设置屏。

## 四、第三组：文案（可裁剪，排在最后）

### 4.1 W3 `load_report_view` 的字符数截断

O-9：`PANEL_MESSAGE_MAX_CHARS = 44` 配 600px 断行宽，44 个汉字 = 616px，
加上调用点那句 `format!("    原因：{}", …)` 是 670.5px。**字符数兜不住宽度。**

**做法**：删掉 `truncate_for_panel`，改成与 W2 同一个解法——`load_report_lines`
按**实测渲染行数**推进 `cursor_y`（收一个 `&mut dyn MeasureText`），长消息在
600px 断行宽内换行、下一条不再被压住。这与规格「先伸缩、不够再换行、绝不截断」
里的「换行」那一半一致；装载报告不是居中面板，没有「伸缩」可言。

### 4.2 W4 `MAX_SAVE_NAME_CHARS`

规格给两条路，建议 (a) 按渲染宽度判。**本批取 (b)**：保留字符上限，
把注释里那句「不至于把那块居中面板撑破」删掉，改成诚实的理由。
理由：批次 19 之后模态屏面板**按内容伸缩**（`max(520, 最长行 + 2×padding)`），
「撑破面板」这个后果本身已经不存在了，(a) 要解决的问题没了；而把输入长度上限
接上字体度量，等于让「能不能再打一个字」取决于玩家选的语言与字号——那是一个
比它解决的问题更大的新问题。(b) 是两条里更保守、更容易反转的那条。列进第九节。

**判据**：24 个汉字的存档名拼成的存档列表行，在模态屏面板里仍然是一行
（面板按它伸缩），断言用真实度量。

## 八、规格没裁定、本批临时选的做法（滚动记录，收工搬进最终报告）

1. **N4 的上限落在 `Modal` 而不是 `UiModeStack::push`**（规格 N4 判据原文写的是
   后者）。理由见一节：只有同时持有状态与栈的那一层能做到「拒绝时两边都不动」。
2. **N14 的清空条件收紧成「不是本帧产生的提示」**（规格写的是无条件在
   `next != state` 时清）。
3. **「屏切换」按 `discriminant` 判，不按整个 `ScreenState` 相等判**。
   设置屏光标每动一格 `next != state` 都成立，用整体相等会退化成每帧重置。
4. **W4 取 (b) 保留字符上限、只改理由**（规格建议 (a) 按宽度判）。
5. **F6 的提示行落 `UiLayer::Hud`，不是 `Notice`**（规格只写「Hud 层底部」，
   没说层；这里明确它与反馈行分层）。
6. **F6 的新键在溢出门禁里归「参数化」**，整行宽度另由 `ll-game` 侧断言覆盖。
7. **F6 只在「有世界且没有模态屏」时显示**（规格只说「世界里」，没说模态屏开着
   算不算）。玩家菜单（背包/制作/交互）开着时**仍然显示世界那一条**——那三块
   弹窗跑在 `InputContext::Gameplay` 上，世界那一行说的键此刻全部仍然有效。
8. **F6 地图那一条里「方向键 平移」的「方向键」三个字写在 `.ftl` 文案里**，不像
   缩放/关闭那样现查键名。四个方向键的键名全排出来会让这一行长过世界那一行两倍，
   而它要说的只有「方向键」一个概念。代价：玩家重绑方向键之后这三个字不跟着变。
9. **F4 的门槛按帧数（30）而不是墙钟半秒**。主循环是 60 帧每秒，两者今天等价；
   取帧数是因为它不需要回答「暂停时算不算」「掉帧时补不补」。
10. **F4 的计数只在 `Acted`/`Nothing` 时归零，`Idle`（玩家没提交任何意图）不清**
    ——那一帧世界并没有回答玩家什么，清零会让「按住方向键」与「松一下再按住」
    走出两种不同的提示时机。
11. **N4 的「拒绝是原子的」这一半在 debug 构建下观察不到**（`reject_push` 当场
    panic）。守它的是 `Modal::would_exceed` 这个纯判据本身与那条 `#[should_panic]`；
    发布构建下的静默拒绝没有直接断言。
