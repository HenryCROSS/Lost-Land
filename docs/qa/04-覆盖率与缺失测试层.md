## 1. 覆盖率：跑不了，如实说明

**实测命令与结果**：
```
$ cargo llvm-cov --version
error: no such command: `llvm-cov`
help: view all installed commands with `cargo --list`
help: find a package to install `llvm-cov` with `cargo search cargo-llvm-cov`
```
`cargo-llvm-cov` 在本机（本次冻结所用的开发环境）**未安装**，且已确认不尝试
自行安装（任务明确要求：没装就不要装，如实说明跑不了）。

`cargo --list` 输出里能找到的相关工具只有 `deny`（对应 `.github/workflows/ci.yml`
的 `licenses` job）；没有 `llvm-cov`、没有 `mutants`、没有 `fuzz`、没有
`udeps`/`machete`/`shear`。

**规格 §14.5 要求"行覆盖率 ≥ 80%，核心 crate（`ll-core`、`ll-sim`、`ll-world`）
≥ 90%"，这个要求核实结果是：从项目启动到本次冻结，从未被实际测量过一次**。
不是"曾经达标、后来退化"，是这个数字**从来没有存在过**。`.github/workflows/ci.yml`
的 `test` job 只跑 `cargo fmt --check` / `cargo clippy` / `cargo test --workspace`，
没有任何一步生成覆盖率报告；`licenses` job 只跑 `cargo deny check`。整个 CI
历史上没有任何一次运行计算过覆盖率。

**308 个测试全部通过，不能作为覆盖率的替代证据**。测试数量、通过率、覆盖率是
三件独立的事——`01-测试清单与覆盖分布.md` 已经指出至少 `ll-core/src/error.rs`
（`CoreError` 的 `Display` 实现）没有任何测试触达，这一小段代码在实际覆盖率
报告里必然是 0%；如果 `error.rs` 这种显眼的空白都能存在到现在都没被发现，
更隐蔽的"分支覆盖但没被断言"的空转路径大概率也存在，只是同样没有工具能
把它们照出来。

**下一步该怎么做**：见 `03-CI门禁对照与补齐方案.md` 第 3.1 节的具体
`cargo-llvm-cov` CI 步骤方案。在装上这个工具之前，"是否达到 80%/90%"是一个
**没有答案的问题**，不是"接近但没到"，是"不知道"。

## 2. 还缺哪几层测试

规格 §14.1 定义了 L1-L8 共 8 层。结合 `01`/`02` 文档已经确认的现状，
这里逐层盘点哪些是空白、为什么空白、该在哪个阶段补。

## 3. 另外三项规格 §14.4 点名、但代码里尚不存在的"关键专项测试"

规格 §14.4 除了确定性回归、跨平台一致性（这两项已落地，见 `02` 文档第 3 节）
外，还点名了三项，实测结果：

- **经济收敛**（`ll-econsim` 空跑 100 年）——`ll-econsim` crate **不存在**
  （`ls crates` 只有 `ll-core`/`ll-platform`/`ll-render`/`ll-sim`/`ll-world`
  五个），经济系统尚未进入实现阶段，这项测试自然也不存在。**不是欠债，是
  还没到该有它的阶段**。
- **脚本沙箱**（Steel 脚本死循环/无限分配/深递归/畸形语法各一例）——脚本
  加载路径本身不存在（`grep -rn "econsim\|steel" crates` 未找到相关代码），
  同上，未到实现阶段。
- **大量实体压力**——见上表 L8 行，存储层已具备，压测对象（批量驱动逻辑）
  未具备。

这三项连同 L5 模糊测试里"mod 清单/脚本/`.ftl`"三个入口，共同指向同一个
事实：**规格 §14 的测试分层是"全项目终态"的蓝图，本项目当前处于 P2→P3
过渡阶段（`knowledge/handoff/p2-to-p3.md` 是最新的阶段交接记录），大量测试
类型的"空白"本质上是"对象还不存在"，不是"该测的东西没测"**。这个区分很
重要：不该现在就为不存在的功能写空壳测试，但也不该把"阶段性正常空白"和
"阶段内真实的测试债务"混为一谈——本系列文档的 `01`/`02`/`03` 已经把当前
阶段内真实存在的债务（覆盖率从未测量、4 项 CI 门禁缺失、L5/L7/L8 的
"已有对象但无自动化防线"部分）单独列出，不与这里的"阶段性空白"混淆。

## 4. 存档往返测试的现状澄清

任务清单里专门问到"有没有存档往返测试"。实测结果需要拆成两层说清楚：

- **有**：`serde` 结构体级别的往返——`ll-core/tests/torus_blackbox.rs` 的
  `serde_tests` 子模块、`ll-world/src/state.rs` 的
  "尺寸一致的存档可以正常往返"、`ll-sim` 相关类型的序列化往返测试，验证的是
  "`deserialize(serialize(x)) == x`"这个属性测试点名的不变量（规格 §14.2
  表格第二行），**在内存里**用 `serde_json` 完成，已确认落地。
- **没有**：真正意义上"写一个文件到磁盘、重启进程、从磁盘读回"的端到端存档
  测试。目前没有找到任何测试涉及真实文件 I/O（`std::fs::write`/`std::fs::read`
  配合存档路径），也没有找到"损坏/截断的存档文件"场景的测试——后者正是
  L5 模糊测试要覆盖的对象，见上表。这两者是不同的风险面：内存里的 serde
  往返测的是"数据结构设计得对不对"，真实文件 I/O 测的是"路径处理、权限、
  跨平台换行/编码"这类操作系统层面的问题，目前只有前者。

## 5. 总结：优先级排序建议

结合本文档与 `03-CI门禁对照与补齐方案.md` 的分析，如果只能选一件事优先做，
建议顺序如下（详细理由见对应章节，此处只列结论）：

1. **补"无手写欧氏距离"CI 检查**（`03` 文档 3.3 节）——成本最低（今天就能
   零违规通过）、收益最高（防止一类"极难定位"的缺陷，规格自己都点名）、
   且是规格文档白纸黑字承诺"由 CI 静态检查强制"却完全没兑现的一条，兑现
   成本几乎为零。
2. **跑一次 `cargo-llvm-cov` 拿到真实覆盖率基线**（本文档第 1 节 + `03` 文档
   3.1 节）——不是为了立刻卡 80%/90% 的阻断线，而是把"从未测量"变成"至少
   知道现在在哪"，这是后续所有覆盖率相关讨论的前提。
3. **存档反序列化的模糊测试**（本文档 L5 行）——存档格式已经存在，玩家会
   真的拿到损坏文件，这是规格 §14.3 五个入口里唯一"对象已存在、只是还没
   测"的一个，其余四个（mod 清单/脚本/`.ftl`/资产元数据）目前对象都还不
   存在，做了也是空转。

这三项加起来的共同点：**它们都是"补上去立刻有真实收益，而不是为了凑规格
条目数"的选择**——这也是本系列 QA 文档想传达的核心态度：诚实盘点现状，
而不是把"文档写了"和"防线真的在挡"混为一谈。
