# 测试类型与它们各自的局限

> **冻结时间**：2026-08-17 21:00（本地时间，UTC-4）
> **对应提交**：`4bdd87dd8834c79fb52f73ea5a744a60cf27a812`
> **写作目的**：本项目用到四种测试手段。每种"能抓什么"容易讲，"抓不到什么"
> 才是决定还需要哪一层防线的关键，本文档刻意把篇幅偏向后者。

## 1. 单元测试（L1，`#[cfg(test)]` 内联模块）

**能抓什么**：私有函数的具体分支、边界值（零、负数、溢出临界）、显式的
`Err` 路径。本项目里最典型的例子是 `ll-core/src/scaled.rs` 的
"按比例缩放在溢出时返回空值而非回绕"——这种"某个特定输入必须产出特定
结果"的断言，正是单元测试的强项，proptest 反而不适合表达（属性测试擅长
断言"所有输入满足某关系"，不擅长断言"输入 X 必须恰好等于 Y"这种钉死具体
数值的场景）。

**抓不到什么**：
- **写测试的人和写实现的人是同一个人、同一次思考**——如果对某个边界条件的
  理解本身就是错的，单元测试和实现会一起错，测试不会报警。`fov.rs` 的对称性
  缺陷正是这一类：如果只靠开发者手写用例，两次真实缺陷（见第 3 节）里的
  几何配置几乎不可能被人工想到去写成用例。
- **组合爆炸**。环面坐标涉及"跨接缝""贴边""半周精确重合"等多个维度的组合，
  单元测试只能覆盖开发者能想到的组合，覆盖不到的组合就是盲区，而这类盲区
  往往恰好就是缺陷藏身的地方。
- **不测试"合约"**。单元测试直接调用私有函数，重构内部实现（哪怕外部行为
  完全不变）也可能让测试跟着变红或变得不再有意义，这也是为什么本项目在
  L1 之上还要 L3 黑箱测试。

## 2. 属性测试（L2，`proptest`）——本项目实测抓到过 2 个真实缺陷

**它验证的是"不变量"，不是"某个输入的某个输出"**：给定随机输入，断言某个
关系恒成立（对称、往返、单调、有界）。

### 2.1 真实战绩：FOV 对称性

`crates/ll-world/src/fov.rs` 的对称阴影投射视野算法，由
`crates/ll-world/tests/fov_blackbox.rs` 的属性测试守护（核心断言：
`compute_fov(&grid, a, r).contains(b) == compute_fov(&grid, b, r).contains(a)`，
随机地形 + 随机两点 + 随机半径）。

提交 `2d909d8`（"feat: 对称阴影投射视野"）的提交信息原文记录了两次真实反例：

> 对称性由属性测试守护（随机地形上随机取两点，断言互相可见性一致），因为这条
> 性质靠手写用例几乎不可能覆盖到真正出问题的那些几何配置——开发过程中先后
> 两个随机反例都靠这条测试揪出来的：一个源于紧贴原点的格子近角公式选错分母，
> 另一个源于挡光格的角落恰好落在正对角线上，都是手写用例不可能想到的几何配置。

这两个缺陷的共同点：**都是几何边界情况**（紧贴原点、恰好落在对角线上），
**都不是开发者会主动去写的手写用例**——这正是属性测试相对单元测试的不可替代性：
它不依赖人预先猜到"哪里可能出错"，而是靠随机采样撞见"哪里真的出错了"。

> **关于具体用例数的说明**：本任务背景资料提到"20 万组用例下抓出过 2 个真实
> 缺陷"，但仓库内（提交信息、`knowledge/handoff/p2-to-p3.md`、测试源码）都没有
> 找到"20 万"这个具体数字的记录，因此**这个数字未经核实，不采信为事实**。
> 可核实的是：`proptest` 未设自定义配置，默认每个属性单次运行 256 组随机用例
> （已用 `find . -iname proptest.toml` 确认仓库无自定义配置文件）；`fov_blackbox.rs`
> 有 4 个属性测试函数，开发过程中历经多次 `cargo test` 运行（每次 commit 前、
> CI 每次 push/PR 都会重跑），累计执行的随机用例数远超单次的量级，但没有任何
> 地方记录过精确的累计次数。真正能确认的事实只有"两个反例被这条测试抓到过"，
> 这一点有提交信息为证。

另有 `knowledge/handoff/p2-to-p3.md` 记录的相关裁定（P2-5）：把墙格可见性
规则从"扇区有重叠即可见"改为"墙也遵循中心点规则"时，**实测 1500 组随机地图
中有 12 例不对称**，这是**决策讨论阶段的对比实验**，不是 CI 里跑的测试，
用来证明"扇区重叠"方案会破坏对称性、"中心点"方案不会——这也是属性测试的
一种用法：不只是回归防线，也是方案选型阶段快速证伪的工具。

### 2.2 属性测试抓不到什么

- **它只验证"关系"，不验证"值本身对不对"**。`compute_fov` 就算返回的可见集
  完全对称，也可能整体上"看得太远"或"看得太近"——对称性测试对这类整体偏差
  完全不敏感，必须靠 `可见格恒在半径之内` 这样额外的属性、以及具体的单元测试
  钉住半径边界的数值。
- **它验证不了"跨平台一致"**。同一份 Rust 代码在不同 CPU/OS 上跑同一组
  proptest 用例，只要每次生成的随机输入相同、算法本身跨平台确定，断言就该
  一致地通过或一致地失败——但 proptest 本身不比较"Windows 跑出的哈希"和
  "Linux 跑出的哈希"是否逐位相同，这是下一节"确定性/跨平台一致性测试"的职责，
  两者互补而非互相替代。
- **收缩（shrinking）不保证找到最小反例，也不保证收敛到人能一眼看懂的用例**。
  本项目用 `DetRng` 而非 `proptest` 自带随机源生成地形（`fov_blackbox.rs` 里
  `random_grid(wall_seed)` 的做法），这是为了让收缩后的失败用例可复现同一张
  地图，但复现出来的地图仍然可能是几十乘几十的随机墙体分布，人工排查成本不低。
- **默认 256 组用例是"够用"而非"穷尽"**。用例数越多，抓到的边界情况越多，
  但没有任何数字能保证"零遗漏"——这是概率性防线，不是形式化证明。真正需要
  强保证的核心不变量（比如环面距离对称性）理论上应配合形式化验证或详尽边界
  枚举，本项目目前完全依赖 proptest 的随机覆盖。

## 3. 确定性 / 跨平台一致性测试（L4 变体，`ll-core/tests/determinism.rs`、
`ll-world/tests/determinism.rs`）

**能抓什么**：这是本项目**优先级最高**的专项测试（规格 §14.4 原文），因为
「同一种子在不同平台产出不同世界」是这类游戏最致命也最难事后修复的缺陷类型
——它不会崩溃、不会报错，只会让联机/分享种子/回放这些功能悄悄产出错误结果。
做法是把固定种子 + 固定操作序列跑出的 `WorldState` 哈希写死成"黄金基准"常量
（如 `EXPECTED_TORUS_DIGEST`），CI 的 Windows + Linux 双平台矩阵各自重新计算
一遍这个哈希，只要有一个平台算出的值和黄金基准不一致就直接测试失败。

**实测现状**：本任务背景提到"已实测 Windows 与 Arch Linux 产出逐位相同"。
仓库内可核实的部分是：`.github/workflows/ci.yml` 的双平台矩阵用的是
`windows-latest` 与 `ubuntu-latest`（GitHub 官方镜像），**不是** Arch Linux；
"Windows 与 Arch Linux 逐位相同"这一具体表述，仓库内没有找到对应的 CI 记录或
测试日志能直接证实，可能是开发者在本机之外单独用 Arch 机器人工验证过、未留痕迹，
**本文档不采信为已核实事实，只记录"CI 矩阵覆盖 Windows + Ubuntu 双平台，且截至
本次冻结两者的黄金基准全部通过"这一可核实的事实**。逐位相同的判定逻辑对
Linux 发行版无感（比较的是应用层计算出的 `u64` 哈希，不涉及任何发行版特定
行为），所以 Ubuntu 通过大概率能代表 Arch 也会通过，但"大概率"不等于"已验证"。

**抓不到什么**：
- **它只在"哈希不匹配"时报警，完全不告诉你哪里不匹配**。`determinism.rs`
  的注释也承认这一点："绝不允许「测试挂了就把期望值改成实际值」"——因为
  失败后唯一的信息是"这个 `u64` 变了"，排查具体是哪个字段、哪次计算引入了
  平台差异，需要额外的人工二分排查，测试本身不提供定位能力。
- **只覆盖被显式纳入黄金基准的路径**。`ll-core/tests/determinism.rs` 目前
  钉住的是 RNG、环面坐标、时间三条摘要；`ll-world/tests/determinism.rs`
  钉住的是"六十四乘六十四世界摘要""随机序列""季节推进""环面距离序列"。
  任何**没有**被纳入某条摘要计算路径的新逻辑（比如未来加入的战斗结算、
  经济模拟），在被显式加入某个黄金基准之前，**跨平台不确定性可以自由潜入
  而不会被这层防线发现**——这是一个持续性风险，每次新增会影响世界哈希的逻辑
  都必须记得同步扩展摘要覆盖范围，规格本身也没有自动化机制强制这一点。
- **不能替代属性测试**。它验证的是"同一份代码在不同平台算出相同结果"，而不是
  "这份代码的逻辑本身是对的"——一个从一开始就算错但两个平台算出同样错误结果
  的实现，会通过确定性测试，但逻辑仍然是错的。

## 4. 基准测试（L8，`criterion`）

**能抓什么**：`ll-core/benches/torus.rs` 衡量环面坐标运算（距离、位移、
绕回）的实际执行耗时，理论上能发现"改动引入了 O(n²) 或不必要的堆分配"这类
性能回归——但仅限于人手动运行 `cargo bench` 并**主动去比较**前后两次结果的
场景。

**抓不到什么**——这是本项目当前基准测试能力最大的短板：
- **CI 完全不运行它**。`ll-core/Cargo.toml` 显式给这个基准声明了
  `test = false`，`cargo test --workspace` 因此永远不会触碰它；
  `.github/workflows/ci.yml` 里也没有任何一步调用 `cargo bench`。这意味着
  一次把某个热路径从 O(n) 改成 O(n²) 的提交，**merge 到 main 完全不会被
  任何自动化手段拦截**，只有人恰好手动跑了 `cargo bench` 并且恰好记得和
  历史结果比较,才会发现。
- **没有基准结果的持久化与比较机制**。`criterion` 本身支持
  `target/criterion/` 下的历史结果对比（"变化超过 X% 就报警"），但本项目
  没有把这份历史结果提交进版本控制或接入任何 CI 产物存档，所以即便手动跑，
  也只能和"上一次在这台机器上跑的结果"比，换一台机器、换一次 CI 运行，
  历史基线就丢了。
- **只有 `ll-core` 一个 crate 有基准**。`ll-sim`（时间轴调度、Effect 应用）、
  `ll-world`（地形生成、FOV 计算，规格里明确点名"大量实体压力测试"要用到）
  完全没有基准测试，规格 §14.4 提到的"大量实体压力测试，记录帧时间曲线，
  防止 O(n²) 悄悄溜进来"这一条**目前在代码层面完全不存在**，见
  `04-覆盖率与缺失测试层.md` 的"性能回归守护"一节。

## 5. 小结：四种手段的互补关系，以及共同的盲区

| 手段 | 回答的问题 | 典型失败信号 |
|---|---|---|
| 单元测试 | "这个具体输入，输出对不对？" | 断言失败，定位精确到函数 |
| 属性测试 | "所有输入，某个关系是否恒成立？" | 收缩后的最小反例 |
| 确定性/跨平台测试 | "同一段代码在不同环境下算出的结果一致吗？" | 哈希不匹配，无定位信息 |
| 基准测试 | "这段代码跑得够快吗，有没有变慢？" | 耗时数字变化（若被比较的话） |

四者叠加也留有共同盲区：**没有一种手段验证"这个功能本身是不是玩家想要的
行为"**——这需要 L6 端到端测试与人工验收；**没有一种手段验证"画面看起来对
不对"**——这需要 L7 视觉回归；**没有一种手段验证"崩溃的存档文件不会让游戏
panic"**——这需要 L5 模糊测试。这三层目前在本项目里的真实状态，见
`04-覆盖率与缺失测试层.md`。
