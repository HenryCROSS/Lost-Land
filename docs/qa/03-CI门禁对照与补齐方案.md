## 1. 逐项对照表

规格 §14.7 原文措辞是**"合并到 `main` 前必须全部通过，任一项失败即阻断"**，
列出 9 项。实测 `.github/workflows/ci.yml` 只有两个 job：`test`
（`cargo fmt --check` → `cargo clippy --all-targets -- -D warnings` →
`cargo test --workspace`，跑在 `windows-latest` + `ubuntu-latest` 矩阵）
与 `licenses`（`cargo deny check`）。

| # | 规格声称的门禁 | CI 里有没有 | 若没有，具体漏掉什么类型的问题 |
|---|---|---|---|
| 1 | 编译无警告（`cargo clippy -- -D warnings`） | **有**。`test` job 第二步，`--all-targets -- -D warnings` | — |
| 2 | 格式统一（`cargo fmt --check`） | **有**。`test` job 第一步 | — |
| 3 | 全部测试通过（`cargo test --workspace`） | **有**。`test` job 第三步 | — |
| 4 | 覆盖率达标（`cargo-llvm-cov`） | **没有**。CI 全文搜不到 `llvm-cov` 字样 | 一段代码"被调用过但没有任何断言"的空转测试可以无限混进代码库而不被发现——见 `04-覆盖率与缺失测试层.md`，本项目的覆盖率**从未被测量过**，不是"曾经达标过后来退化"，是从 P0 到现在都不知道数字 |
| 5 | 许可证合规（`cargo-deny`） | **有**。独立的 `licenses` job | — |
| 6 | 无硬编码用户可见字符串（自研检查，规格 §11.3） | **没有** | 项目目前甚至还没有 i18n 基础设施（`find . -iname "*.ftl"` 结果为空，规格提到的 Fluent `.ftl` 本地化文件一个都不存在）——这一条现在**无法检查也无法违反**，因为面向玩家的字符串目前本来就还没被 UI 层大规模引入。风险会在 `ll-ui` 落地、菜单文案开始写进代码那一刻突然出现，届时如果这条门禁还不存在，第一批硬编码字符串会在无人察觉的情况下进入代码库，往后每一条新字符串都要靠人眼在 review 里揪，而 review 恰恰是最容易漏掉字符串字面量的场景（它们不像逻辑错误那样会导致测试变红） |
| 7 | 无手写欧氏距离（自研检查，规格 §7.1） | **没有** | 规格原文："遗漏一处就会产生「小地图上很近但寻路绕半个世界」这类极难定位的缺陷。此项由 CI 静态检查强制。"——目前这句话是空头支票。已用 `grep -rn "sqrt\|powi(2)\|hypot" crates` 核实：目前仓库里**唯一**命中的是 `ll-world/src/noise.rs` 里一行注释文字提到 `sqrt`（描述"+ - * / sqrt 必须逐位精确"），**没有任何实际代码手写欧氏距离**——说明这条约束到目前为止靠人的自律守住了，但正因为守住了才更值得现在就补上机械检查，而不是等第一次真的漏写之后才追悔莫及 |
| 8 | 无死代码与过时文档（自研检查，规格 §13） | **没有** | 未使用的 `pub` 项、过时的模块文档描述与实际代码不符，这类问题**不会**被 `clippy -D warnings` 全部抓到（`clippy` 的死代码检测默认对 `pub` 项失效，因为无法确定外部 crate 是否使用），也不会导致任何测试失败——只能靠 review 时人恰好注意到，规模变大后必然会漏 |
| 9 | 跨平台世界哈希一致 | **有，且是唯一被规格点名却确实做到了的"专项"门禁**。`test` job 的双平台矩阵天然覆盖，`ll-core`/`ll-world` 的 `determinism.rs` 在 Windows 和 Ubuntu 上各跑一遍，任一平台哈希不匹配就是测试失败，直接阻断 | — |

## 2. 数字结论

**规格声称 9 项门禁，CI 实际落地 5 项**（clippy、fmt、test、cargo-deny、跨平台
哈希一致——注意"跨平台哈希一致"不是独立 job，而是"测试"这一项在双平台矩阵下
运行的自然结果，如果拆开算，"独立配置的检查步骤"是 4 个：fmt、clippy、test、
deny）。**缺失 4 项：覆盖率、硬编码字符串检查、手写欧氏距离检查、死代码与过时
文档检查**，全部符合任务背景给出的历史信息，本次实测确认无误、数字未变。

另外，`cargo doc --workspace --no-deps` 在 CI 中**同样搜索不到**——规格全文
没有一处把它列进 §14.7 的门禁表，但它对"文档断链"这类问题有独特价值（见第 4
节），不在规格声称的 9 项之内，单独作为第 10 条候选补充。

## 3. 每项缺失门禁的可执行补齐方案

以下每条都给出：装什么工具、跑什么命令、阈值定多少、预计增加多少 CI 时长。
时长估算基于本项目当前规模（5 个 crate、308 个测试、纯 Rust 无重型依赖）与
GitHub Actions `ubuntu-latest`/`windows-latest` 标准 runner 的经验值，非实测
（实测需要真正把步骤加进 CI 并跑一次，本任务不允许改 `.github/workflows/ci.yml`）。

### 3.1 覆盖率达标（`cargo-llvm-cov`）

**当前状态**：本机未安装 `cargo-llvm-cov`（`cargo llvm-cov --version` 返回
`error: no such command`），且已确认不尝试自行安装（任务要求：没装就不要装）。
**从未在本项目任何环境测量过覆盖率数字**，规格 §14.5 的"行覆盖率 ≥ 80%，
核心 crate ≥ 90%"目前是完全未经验证的目标，见 `04-覆盖率与缺失测试层.md`。

**方案**：
```yaml
coverage:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: dtolnay/rust-toolchain@stable
      with:
        components: llvm-tools-preview
    - uses: taiki-e/install-action@cargo-llvm-cov
    - uses: Swatinem/rust-cache@v2
    - name: 覆盖率（workspace 80%，核心 crate 90%）
      run: |
        cargo llvm-cov --workspace --lcov --output-path lcov.info
        cargo llvm-cov report --fail-under-lines 80
        cargo llvm-cov report -p ll-core -p ll-sim -p ll-world --fail-under-lines 90
    - uses: actions/upload-artifact@v4
      with:
        name: coverage
        path: lcov.info
```
- **工具**：`taiki-e/install-action@cargo-llvm-cov`（预编译二进制安装，比
  `cargo install` 快得多），需要 `llvm-tools-preview` rustup 组件。
- **阈值**：workspace 整体 80%、`ll-core`/`ll-sim`/`ll-world` 各 90%，直接照抄
  规格 §14.5 的数字——**但务必先跑一次拿到真实基线再决定是否真的按这个阈值
  阻断**，见第 4 节的务实建议，不要在不知道当前实际覆盖率的情况下就把 90%
  设成阻断线。
- **预计增加 CI 时长**：单平台运行（覆盖率工具与双平台矩阵重复运行的意义不大，
  建议只在 `ubuntu-latest` 跑一次），`cargo llvm-cov` 需要用插桩模式重新编译
  整个 workspace 再跑一遍测试，经验值约为普通 `cargo test` 耗时的 2-3 倍。
  以本项目当前 308 个测试、纯 CPU 逻辑（无重型依赖如 `wgpu` 需要在 `ll-render`/
  `ll-world` 的测试路径里初始化，实测这些测试本身 debug 模式下运行仅需
  0.01-1.47 秒），预计**新增 3-6 分钟**。

### 3.2 无硬编码用户可见字符串（规格 §11.3）

**先决条件**：这条门禁在 i18n 基础设施（`ll-core` 或专门 crate 提供的
`t!("key")` 风格宏、`.ftl` 资源文件）真正落地之前**没有意义**——现在检查会
是"全项目零命中"的空转，false negative 不是因为守住了，是因为规则还没东西可查。
**建议**：把这条门禁的落地时间点和 `ll-ui`/i18n 基础设施的落地时间点绑定，
不要现在就加一个查不出任何东西的步骤误导人以为这条防线已经生效。

**真正落地时的方案**（等 i18n 宏/机制确定后套用）：
```yaml
- name: 无硬编码用户可见字符串
  run: |
    # 假设约定：面向玩家的字符串必须经由 `ll_core::i18n::t!()` 宏或等价机制，
    # 直接扫描裸露的中文/英文字符串字面量出现在非 t!() 调用、非注释、非测试代码里。
    # 具体规则需与实际选定的 i18n 宏签名对齐，此处给出可行思路而非最终脚本：
    grep -rnP '"[^"]*[\x{4e00}-\x{9fff}][^"]*"' crates/ll-ui/src crates/*/src \
      --include="*.rs" \
      | grep -v '^\s*//' \
      | grep -v 't!(' \
      && exit 1 || exit 0
```
- **工具**：不需要额外安装工具，`grep -P`（PCRE，GitHub Actions 的 ubuntu 镜像
  自带）配合一份"允许出现裸字符串的例外清单"（日志文案、`tracing::error!` 里
  面向开发者的诊断信息本就不受这条约束，规格原文已明确"此文案面向开发者与
  日志，不面向玩家，故不走 i18n"——`ll-core/src/error.rs` 的注释就是这么写的）。
  比正则更稳妥的做法是写一个几十行的小工具（放进 `xtask/` 或 `tools/`），
  用 `syn` 解析 AST 找字符串字面量再按调用上下文过滤，正则容易漏报或误报。
- **阈值**：零容忍（一处命中即失败），因为这本来就是"不该存在"的模式。
- **预计增加 CI 时长**：若用 `grep`，几乎为零（几秒）；若用 `syn` 写专门检查
  工具，需要先编译该工具，增加 10-30 秒。

### 3.3 无手写欧氏距离（规格 §7.1，最具体、最该优先补的一条）

**为什么这条最重要**：这不是风格问题，是正确性问题——环面世界里
`sqrt((x1-x2)^2 + (y1-y2)^2)` 这种教科书欧氏距离公式**在数学上就是错的**，
因为它不知道坐标会在世界边缘绕回，算出来的"很远"实际上可能贴脸。规格要求
"必须"用 `ll_core::torus::TorusSize` 提供的方法（`chebyshev`、`delta` 等），
这些方法内部处理了绕回。这类缺陷极难在测试里主动发现——除非恰好写了跨接缝
场景的用例，否则功能"看起来正确"（不跨接缝时两种算法结果一样），只在特定
坐标组合下才会暴露，正是规格原文说的"极难定位"。

**具体怎么查（静态检查，不依赖运行时）**：

方案 A——`grep` 快速版（立即可用，误报需人工复核，但作为第一道防线成本极低）：
```yaml
- name: 无手写欧氏距离
  shell: bash
  run: |
    # 匹配典型欧氏距离手写模式：
    #   (a - b).powi(2) / (a-b)*(a-b) 相加后 .sqrt()
    #   hypot(...)
    # 排除 ll-core/src/torus.rs 自身的实现，以及 benches/ 里对比用的参照实现
    PATTERN='\.sqrt\(\)|\.hypot\(|powi\(2\)'
    HITS=$(grep -rnE "$PATTERN" crates/*/src crates/*/examples \
      --include="*.rs" \
      | grep -v 'crates/ll-core/src/torus.rs' \
      | grep -v 'crates/ll-world/src/noise.rs')  # noise.rs 当前命中的是注释，见下方说明
    if [ -n "$HITS" ]; then
      echo "疑似手写欧氏距离，请改用 TorusSize 的方法，或若确认安全（如非坐标运算）加入白名单："
      echo "$HITS"
      exit 1
    fi
```
已用当前代码库实测这个模式：`grep -rn "sqrt|powi(2)|hypot" crates` 目前只命中
`ll-world/src/noise.rs` 第 6 行的**注释文字**（"规定 `+ - * / sqrt` 必须逐位
精确"），不是代码。也就是说**这条规则加上去，今天就能直接通过，不会有任何
待修复的存量问题**——这是补这条门禁成本最低的时候，越晚补，存量违规可能
越多，修复成本越高。

方案 B——更精确但成本更高的版本：写一个基于 `syn` 遍历 AST 的小工具，专门
检查"两个坐标类型相减后调用 `.sqrt()`"这一结构性模式，而不是广撒网匹配
`.sqrt()` 关键字（`.sqrt()` 在非坐标场景，比如光照曲线插值、噪声算法，
也会合法出现——`ll-core/src/light.rs`、`ll-world/src/noise.rs` 未来若真的
用到 `sqrt` 做插值，方案 A 的粗粒度 grep 会持续产生需要人工白名单的噪音）。
成本是要多维护一个小工具，收益是精确度更高、后续维护噪音更小。

- **建议起步方案**：先上方案 A（grep 版），配合一份显式白名单注释约定
  （比如要求"确认这不是坐标欧氏距离"的代码在同一行加 `// euclid-ok:` 标记，
  检查脚本对带标记的行放行），成本最低、今天就能落地生效；等项目规模变大、
  `.sqrt()` 的合法用途变多导致白名单维护成本上升，再升级到方案 B。
- **预计增加 CI 时长**：方案 A 几秒，方案 B（含编译一个小工具）10-30 秒。

### 3.4 无死代码与过时文档（规格 §13）

**死代码部分**：
```yaml
- name: 未使用的依赖
  run: |
    cargo install cargo-udeps --locked
    cargo +nightly udeps --workspace
```
`cargo-udeps` 需要 nightly 工具链（它依赖的 unstable 编译器接口），这与本项目
"CI 用 `dtolnay/rust-toolchain@stable`"的现状不完全兼容，需要额外装一条
nightly 工具链专门跑这一步，或改用不需要 nightly 的替代品——`cargo machete`
（只做依赖使用扫描，不需要 nightly，更轻量）：
```yaml
- name: 未使用的依赖（无需 nightly）
  run: |
    cargo install cargo-machete --locked
    cargo machete
```
对"未使用的 `pub` 函数/类型"这类死代码，`cargo-udeps` 不管这个，需要
`cargo +nightly build -Z unpretty` 类工具或干脆依赖 `#[warn(dead_code)]`
在**私有**项上已经生效（`clippy -D warnings` 已经在管私有死代码），
**真正的缺口是"未被任何地方使用的 `pub` 项"**——这类项因为"理论上外部 crate
可能用到"而被 `dead_code` lint 放过。若要检查这个，`cargo-shear` 是目前
（据公开信息）相对成熟的选择，同样不需要 nightly：
```yaml
- name: 未使用的 pub 项
  run: |
    cargo install cargo-shear --locked
    cargo shear
```

**过时文档部分**：`cargo doc --workspace --no-deps` 本身不检查"文档内容是否
与代码语义一致"（这需要人工判断），但能检查**断链**（文档注释里
`[SomeType]` 这类 intra-doc link 指向不存在的项）与语法错误：
```yaml
- name: 文档构建与断链检查
  env:
    RUSTDOCFLAGS: -D warnings
  run: cargo doc --workspace --no-deps --document-private-items
```
`RUSTDOCFLAGS=-D warnings` 让 `rustdoc` 把断链警告（`rustdoc::broken_intra_doc_links`）
当错误处理，直接失败退出——这是"文档与代码不一致"里机器能查的那一小部分
（链接是否指向存在的项），"描述是否还准确"仍然要靠人。

- **预计增加 CI 时长**：`cargo machete`/`cargo shear` 各自几秒到十几秒（纯静态
  分析，不编译）；`cargo doc --workspace --no-deps` 需要真正生成文档，
  经验值 30 秒-2 分钟（取决于依赖数量，本项目依赖不重，预计接近下限）。

### 3.5 `cargo doc --workspace --no-deps`（规格未列入 §14.7，但建议补充为第 10 条）

这条**从来不在门禁里**，后果是文档断链可以在整个项目周期里累积而无人发现——
这本身不是规格声称的门禁缺失（规格 §14.7 表里根本没有这一行），但鉴于它成本
极低（见上方 3.4 的命令与耗时估算，可以和"过时文档"检查合并成同一步），
建议直接把 `cargo doc --workspace --no-deps --document-private-items`
（配 `RUSTDOCFLAGS=-D warnings`）作为独立一步加入 `test` job，成本几乎为零，
收益是立刻能拦住"重命名了一个类型但忘记改所有引用它的文档注释"这类问题。

## 4. 务实的取舍建议

不是每一项都值得无条件按规格原文的强度补齐，以下是需要拿出来公开讨论、
而不是闷头硬补的地方：

- **覆盖率阈值先测量、再决定要不要卡死**。规格 §14.5 的"核心 crate ≥ 90%"
  是一个没有经过任何实测验证的数字。建议第一步只加 `cargo-llvm-cov` 生成
  报告并上传为 CI 产物（不设 `--fail-under-lines`），跑几次拿到真实基线后，
  再决定阈值定多少、要不要真的拿它阻断合并——**直接照抄规格数字设成阻断线，
  如果现状离 90% 很远，会让 CI 在补齐当天就全线变红，逼着团队为了让 CI 变绿
  而突击写"调用了但没断言"的空转测试，这恰好是规格 §14.5 自己都点名警惕的
  反模式**。
- **变异测试（`cargo-mutants`）成本高、见效慢，规格已经把它降级为"夜间任务，
  不阻断合并"（§14.7 末尾原文），这个安排是合理的，不需要现在改**。本次
  盘点确认仓库内目前**没有**任何 `cargo-mutants` 相关配置或历史运行记录，
  这条"夜间任务"目前也是空头支票，但由于它本就不在"任一项失败即阻断"的
  9 项列表内，不属于本文档"补齐阻断门禁"的范围，只在此提醒：如果规格希望
  它真的作为夜间任务跑起来，需要单独的 CI workflow（`on: schedule`），
  这也不在本文档权限范围内（不改 `.github/workflows/`）。
- **硬编码字符串检查现在加是空转，不如先不加，等 i18n 落地那一刻和它一起加**。
  见 3.2 节。现在加一个"永远通过"的步骤，除了给人"这条防线已经生效"的
  错觉外没有实质收益，反而会在 i18n 真正落地、字符串开始大批量进入代码库
  时，因为团队以为"CI 会拦"而放松警惕，实际这条检查规则很可能还没跟上
  真实的 i18n 机制签名。
- **规格 §14.7 的措辞"任一项失败即阻断"与现实的落差，本身违反项目 §13
  代码卫生要求（"文档与代码不一致即视为缺陷"）**——这不是本文档编造的
  引申，是规格自己第 364 行的原话。因此这里的建议不只是"补齐 4 项"，
  也包括：**规格文档本身应该同步更新**，要么把 §14.7 改成如实反映当前
  CI 真实门禁数（5 项）+ 明确标注"待补"的另外几项及其目标日期，要么
  真的按第 3 节的方案把 CI 补齐到 9 项——两者选一个，但不能让规格继续
  用"任一项失败即阻断"这种确定性极强的措辞描述一个只有 5 项真正在挡的现实，
  这会误导后来者以为覆盖率、死代码检测等防线已经在生效。
