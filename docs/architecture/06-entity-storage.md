# 两层实体存储

**冻结时间**：2026-08-17，核对提交 `7a126f5`。
代码位置：`crates/ll-world/src/entity.rs` 及其子模块（`crates/ll-world/src/entity/*.rs`）。

## 概览

| | 薄层 `ThinPopulation` | 厚层 `Arena<Agent>` |
|---|---|---|
| 规模 | 数十万～数百万 | 数百，有界 |
| 内存排布 | 列式（SoA，Struct of Arrays） | 行式（AoS，Array of Structs） |
| 驱动方式 | 批量公式 | 逐实体模拟 |
| 典型访问模式 | 批量遍历单一字段（"把所有人的钱包都加 10"） | 随机访问单个实体、一次读它全部字段 |
| 代码 | `crates/ll-world/src/entity/thin.rs` | `crates/ll-world/src/entity/arena.rs`、`agent.rs` |

两者都定义在 `ll-world`（不是 `ll-sim`），因为它们是**世界状态的一部分**——`WorldState` 直接
持有 `population: ThinPopulation` 与 `actors: Arena<Agent>`（`crates/ll-world/src/state.rs:62-79`），
和地形、时钟一样是"世界现在长什么样"的数据，详见 [`01-crate-layering.md`](01-crate-layering.md)
关于 `ll-world`/`ll-sim` 边界的讨论。

## 为什么两层用不同排布不是不一致

`crates/ll-world/src/entity.rs` 顶部的模块文档直接回答了这个问题，值得完整摘录其论证：

> 薄层要容纳数十万到数百万 NPC，靠批量公式驱动。批量算一百万个钱包是一次列式操作——若 `Agent`
> 是十来个字段的结构体存在 `Vec<Agent>`（行式/AoS），只读 `wallet` 一个字段也会把整条缓存行
> 拉进来，浪费十倍内存带宽。厚层反过来：数量少、按实体随机访问、一次要读它的全部字段，行式
> 排布更优。**两层用不同排布不是不一致，是各自匹配访问模式。**

这是理解这个设计的关键：判断"该用哪种排布"不是看"实体"这个概念本身，而是看**这一批数据将
如何被访问**。薄层的典型操作是"遍历全体 NPC，只碰钱包这一列"（`ThinPopulation::batch_update_wallets`，
`thin.rs:152-156`）——如果用行式排布，CPU 从内存取一个 `Agent` 时会连带取出它的其余全部字段
（哪怕这次只关心钱包），缓存行的大部分带宽被浪费在读了用不上的数据上。厚层的典型操作是"取出
某个具体实体，读它的位置、属性、目标栈等全部字段来跑一次行为决策"——这种场景下行式排布把
一个实体的全部数据放在连续内存里，一次缓存行命中就能拿到它的大部分状态，反而是列式排布会
让"凑齐一个实体的全部字段"变成多次分散的内存访问。

## 薄层：`ThinPopulation`

`crates/ll-world/src/entity/thin.rs:36-47`：

```rust
pub struct ThinPopulation {
    generation: Vec<u32>,
    settlement: Vec<u16>,
    profession: Vec<ContentIndex>,
    family: Vec<FamilyId>,
    wallet_rebase: Vec<i64>,
    wallet_delta: Vec<i64>,
    rebase_at: Vec<Tick>,
}
```

七个字段各是一个 `Vec`，同一下标对应同一个 NPC——这就是 SoA 的字面含义。

### 列式存储最容易犯的错：`spawn` 必须一次性 push 全部七列

`ThinPopulation::spawn`（`thin.rs:89-106`）的文档专门警告了这一点：

> 七个列必须在这一处、且只在这一处一起 push——分散到多处各自 push 正是列式存储最容易出的错：
> 某一列忘了同步，各列长度就此错位，后续任何按下标读取都会读到别的 NPC 的数据。

这是 SoA 排布相对 AoS 的一个真实代价：AoS 里"忘记初始化某个字段"是编译器能帮忙抓的错误
（结构体字段缺失编译不过），而 SoA 里"忘记 push 某一列"是运行时才会暴露的错误（各列长度
不再一致，且不一定立刻崩溃——只有当读到那个错位的下标时才会返回错误数据），而且发生后
定位起来相当困难。测试 `薄层各列的长度恒相等`（`thin.rs:252-274`）就是专门为了守住这条不变式。

### 钱包不直接存值，而是"基准值 + 偏移量"（棘轮问题）

`ThinPopulation::wallet_of`（`thin.rs:138-146`）不是简单地读一个存好的余额，而是：

```rust
公式(种子, id, 距 rebase_at 的时长) + wallet_rebase + wallet_delta
```

`wallet_of` 文档解释了这个设计要解决的问题——"棘轮问题"：

> 被玩家动过的 NPC 只多存一个偏移量，仍能立刻回到批量公式，不必永久占用昂贵的模拟槽位。

也就是说，绝大多数背景 NPC 的钱包从不需要被真正"存储"——`wallet_of` 每次查询时用确定性公式
（`wallet_formula`，`thin.rs:220-228`，靠 `DetRng::for_entity` 派生，见约束 C3）现算。只有当
玩家真的与某个 NPC 交互（给钱、抢劫）时，才往 `wallet_delta` 这一列记一个偏移量。`rebase`
（`thin.rs:183-194`）把当前公式值"冻结"成新的基准、偏移量归零，让长期未交互的 NPC 能重新
回到纯公式驱动，不需要永久占用一份显式存储——这正是"薄层"这个名字的字面含义：大多数字段是
按需计算，不是按需存储。

## 厚层：`Arena<Agent>`

`crates/ll-world/src/entity/arena.rs:33-39` 是一个带世代索引的泛型对象池，`Agent` 只是它当前
存的类型（`crates/ll-world/src/entity/agent.rs:58-83`）：

```rust
pub struct Agent {
    pub pos: TorusPos,
    pub stats: BaseStats,
    pub next_action_at: Tick,
    pub health: i32,
    pub affiliations: Vec<Affiliation>,
    pub wallet: i64,
    pub profession: ContentIndex,
    pub goals: Vec<Goal>,
}
```

一个 `Agent` 值就是连续内存里的一整块——查询一个具体实体时，一次内存访问基本能拿到它全部
字段，这正是随机访问、按实体读全部字段这类场景需要的排布。

### 世代索引：为什么需要，解决什么问题

`EntityId`（`crates/ll-world/src/entity/id.rs:36-39`）是 `(index, generation)` 一对整数。
`Arena::despawn`（`arena.rs:107-126`）销毁一个实体后，下标会被 `spawn` 复用，但世代号递增——
旧的 `EntityId` 因世代号不匹配而查询失败（`Arena::get`，`arena.rs:76-81`），而不是静默指向
复用后的新实体。`id.rs` 模块文档给出了这为什么在回合制里尤其重要：

> 时间轴队列可能残留已死实体的条目，若查询悬垂 ID 静默返回复用后的新实体，一个本该失效的
> 旧行动会打在完全无关的对象上。

这不是抽象风险——`apply.rs` 的测试 `对已销毁实体施加效果不会崩溃`（`apply.rs:166-189`）就是
在验证这条链路：时间轴队列里对一个已经 `despawn` 的实体发来的 `Effect`，必须被安全忽略而不是
崩溃或误伤复用后的新实体。

### 世代索引之外的教训：旁挂表与孤儿记录

`Agent::health` 现在是厚层实体自己的字段（`crates/ll-world/src/entity/agent.rs:69`），但它
**曾经**是 `WorldState` 上一张独立的 `BTreeMap<EntityId, i32>` 旁挂表——用 `BTreeMap` 而不是
`HashMap` 是为了满足确定性遍历的要求（见 [`07-determinism.md`](07-determinism.md)），这个
选择本身没有错。但这张表还是被替换掉了，原因记在 `agent.rs:24-45` 的模块文档里，值得完整
搬过来，因为它揭示的问题和"该用哪种 Map"完全无关，是另一类风险：

> 旁挂表不受 `Arena` 的世代号管辖：实体被 `despawn` 之后，`Arena` 里对应的槽位立刻变成
> `Vacant`，但旁挂表里的条目不会跟着消失，除非另外手动清理——一旦某次 `Effect` 忘了同步
> 删除，旁挂表就会攒下一批指向不存在实体的孤儿记录。这不是假设的风险：这正是上一批实现里
> `WorldState::health` 字段被发现的真实缺陷（该字段存档可见但 `Arena` 的生死不参与序列化，
> 往返后孤儿记录会一直累积）。

这条教训值得和"世代索引解决悬垂 ID"放在一起理解，因为它们其实是同一个问题的两个方向：

- **悬垂 ID**：`EntityId` 已经失效（世代号不符），但代码还拿着旧 `EntityId` 去查询——`Arena`
  用世代号让这类查询安全地返回 `None`，不会误伤复用后的新实体。
- **孤儿记录**（本节）：`EntityId` 已经失效，`Arena` 本身已经正确地把槽位标记为空闲，但**另一处
  存储**（旁挂表）不知道这件事，继续保留着那个失效 ID 的数据。这不是查询安全性问题，是"两份
  存储各自维护生死状态，谁都不保证跟对方同步"的问题。

修法是让实体的全部逐实体状态都进 `Agent` 本体，不额外开旁挂表——这样任何字段的生死都自动
跟随 `Arena::despawn` 一起收走，不需要"记得同步清理"这个人工步骤。`agent.rs` 的文档结尾专门
留了一句给未来的维护者："如果日后又想把它挪回 `WorldState` 的旁挂表——不要。"

### 世代号溢出：一个容易被忽略的边界情形

`Arena::despawn` 文档（`arena.rs:97-106`）处理了一个非常边缘但真实存在的问题：世代号是
`u32`，如果某个下标被反复复用到世代号打满 `u32::MAX`，正常做法（`generation + 1`）会回绕到
`0`——而 `0` 正是这个下标第一次被占用时发出的世代号。若那个最早的 `EntityId` 仍残留在某处
（时间轴队列、玩家的旧引用），回绕后它会被误判为"世代吻合"，静默复活成完全无关的新实体。
代码的处理方式是世代号到达上限时把槽位标记为 `Slot::Retired` 并永久排除在复用之外——用少量
下标的永久闲置换取"世代号一旦分配就绝不会与另一个更早的实体重合"这条更重要的保证。测试
`世代号溢出时槽位被弃用而非回绕`（`arena.rs:319-341`）直接构造了这个边界情形（不真的循环
`u32::MAX` 次）来验证。

## 薄层与厚层之间的迁移：`promote`

`ThinPopulation::promote`（`thin.rs:164-177`）把一个背景 NPC 升格为一份 `Agent` 快照——玩家
靠近某个背景 NPC 所在的聚落时，这个 NPC 需要开始被逐格模拟（有位置、能寻路、能参与战斗），
这时才从薄层"升格"到厚层。文档说明了这是单向快照，不是持续同步：

> 返回的 `Agent` 是升格那一刻的快照，此后不再与薄层的公式挂钩；调用方需要自行决定何时（以及
> 是否）通过 `rebase` 把它交还给薄层。

这条迁移路径目前只有升格（薄→厚），"厚层实体离开玩家视野后重新压回薄层"这个反方向的操作
在规格 §9.2（E2 薄个体+厚群体）里有描述，但截至本次核对，代码里还没有找到对应实现——`Agent`
升格后的位置、属性等状态如何折算回薄层的公式参数，是尚未实现的部分。

## 为什么不引入 ECS 框架

`crates/ll-world/src/entity.rs` 模块文档与规格 §3 技术栈表都给出了理由，核心是"拿不到 ECS
框架想解决的那个问题"：

> `hecs` 的原型动态分组是为组件动态增删设计的，薄层字段是固定模式，人人一样，动态分组只有
> 开销没有收益；也不做"找出同时具备 A 与 B 组件的实体"这类稀疏组件查询；系统调度由已有的
> 时间轴与 Intent 管线负责，不需要额外的调度器。

换句话说，ECS 框架的核心价值——**运行时动态的组件组合与稀疏查询**——本项目用不上：薄层
的七个字段对所有背景 NPC 都存在，不会有的实体有 `wallet` 有的没有；厚层的字段同理。既然
不需要"运行时决定这个实体有哪些组件"，就不需要为此付出 ECS 框架的原型管理开销。而 ECS 框架
通常依赖的迭代顺序、内部调度往往不是显式可控的确定性来源——这与自由读档和确定性重放的地基
直接冲突（详见 [`07-determinism.md`](07-determinism.md)）。当前的两层设计是"借用 ECS 的 SoA
思想（薄层），但自己写存储结构"，规格里称之为"自研列式实体存储"。
