# 五条不可让步的约束

**冻结时间**：2026-08-17，核对提交 `7a126f5`（C1–C4 各节与代码现状核对均以此为准）。**C5 一节于
2026-08-18 补充**，依据规格修订提交 `2f4cc26` 与工单提交 `5b47c39`（`knowledge/audit/worklist.md`
W-05）核对，不影响 C1–C4 各节此前的核对结论。

规格 §4 给这五条约束编了号（C1–C5）。它们不是风格建议，是**违反了会导致确定性重放与自由读档
直接失效**的硬约束。本文档逐条给出：约束是什么、代码里目前如何体现、以及——这是规格原文没写清楚
的部分——**违反了具体会发生什么**，而不只是"不要这样做"。

## C1 — 单向数据流，`apply` 是唯一写入口

**约束原文**：整个游戏逻辑是一条严格的单向数据流，`apply` 是全局唯一能修改世界的地方。

**代码现状**：`crates/ll-sim/src/apply.rs:54-83` 是当前仓库里**唯一**一处同时具备"拿到
`&mut WorldState`"与"据此给字段赋值"两个动作的函数。它的文档写了三条纪律（不含逻辑、极短、
唯一入口），细节见 [`02-core-data-flow.md`](02-core-data-flow.md)。

**这条约束靠什么守住**：不是编译器。`WorldState` 的字段全部公开（`crates/ll-world/src/state.rs:62-79`，
存档格式即结构体本身，多一层私有化封装就多一层可能与本体字段漂移的地方），Rust 的可见性系统
管不住"谁能拿到 `&mut WorldState` 后直接赋值"。守住这条约束靠的是**约定加评审**：`apply.rs`
自己的文档写明了这一点——"评审时若在本文件之外看到 `&mut WorldState` 紧跟着字段赋值，就是这条
纪律被打破的信号"。

**违反了会怎样**：

- 一旦有第二处代码能写 `WorldState`，"记录 `Intent` 流即可重放"这个前提就不成立了——重放引擎
  只重演 `Intent`，如果某处旁路直接改了世界状态而没有经过 `Intent → resolve → Effect`，重放出的
  世界会和原局分叉，且**分叉的原因不会出现在 `Intent` 日志里**，几乎无法排查。
- 模式 3（自由读档）的"存档 = 序列化 `WorldState`，无隐藏状态"这条承诺会被打破：如果某个旁路
  写入依赖了不在 `WorldState` 里的额外状态（例如一个全局计数器），读档后这部分状态会丢失或错位。
- 脚本沙箱（P4）的安全边界依赖"脚本只能产出 `Effect`，物理上摸不到 `&mut WorldState`"。若这条
  约束在 Rust 侧已经被打破，脚本沙箱的隔离承诺无从谈起——沙箱挡不住比它更底层就已经破防的东西。

## C2 — 时间轴队列只装朴素数据

**约束原文**：时间轴队列中只能存放纯数据（actor id + 行动类型 id + 参数），禁止闭包与裸指针。

**代码现状**：`crates/ll-sim/src/timeline.rs:40-46`

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Serialize, Deserialize)]
pub struct TimelineEntry {
    pub at: Tick,
    pub actor: EntityId,
}
```

`Timeline` 内部用 `BinaryHeap<Reverse<TimelineEntry>>`，且**自己实现了 `Serialize`/`Deserialize`**
（`timeline.rs:115-143`），而不是直接派生——原因同样值得记住：`BinaryHeap` 的内部数组顺序是堆
结构的实现细节，依赖插入历史，不是弹出顺序本身。若直接序列化内部数组，同一逻辑状态在不同插入
顺序下会产出不同的存档字节。`Timeline` 的做法是序列化前先排序成 `Vec<TimelineEntry>`（模块文档：
"保证同一逻辑状态恒产出同一份存档字节"），反序列化时再逐条 `schedule` 重新入堆。

**为什么必须是"朴素数据"而不能是闭包**：`TimelineEntry` 只装 `(Tick, EntityId)`，不装"这个
实体到时候要做什么"的可执行内容。模块文档写得直接：

> 真正"弹出后要做什么"（读取该实体的意图、跑 `resolve`）由调用方在拿到 `TimelineEntry` 之后
> 另行决定，不是这个类型的职责。

**违反了会怎样**：

- 闭包与函数指针**在结构上就不可序列化**——`serde` 没有办法把一段捕获了环境变量的可执行代码
  写成字节流再读回来（哪怕用 `Box<dyn Fn>` 这类类型擦除，反序列化时也无法凭空重建出"当初捕获的
  是哪些变量"）。一旦时间轴队列里混进了闭包，存档格式当场失效——不是"需要多写一点代码"级别的
  问题，是这条路径根本走不通。
- 即使勉强用某种自定义协议序列化了"要执行的代码"，跨版本兼容性也会立刻崩溃：游戏更新后重新编译，
  旧存档里记录的"代码"（哪怕是某种函数 ID）可能已经对应到完全不同的逻辑，读档后的行为会和存档
  时的意图不符，而这类错位往往要等到具体某个实体触发那条队列项时才会暴露。

## C3 — 一切随机来自 `hash(种子, 实体 id, 事件计数)`

**约束原文**：所有随机性必须来自按实体 ID 派生的确定性流，禁止使用全局 RNG 流。

**代码现状**：`crates/ll-core/src/rng.rs:45-50`

```rust
pub const fn for_entity(world_seed: u64, entity_id: u64, event_counter: u64) -> Self {
    let a = splitmix64(world_seed);
    let b = splitmix64(entity_id ^ a);
    let c = splitmix64(event_counter ^ b);
    DetRng { state: c }
}
```

三个输入逐级混合而非简单异或——模块文档解释了为什么：直接异或会让 `(种子=1, 实体=2)` 与
`(种子=2, 实体=1)` 得到同一条流，造成不同实体之间出现可察觉的行为关联。这条性质由
`rng.rs` 里的 `交换种子与实体号得到不同序列` 测试守护。

薄层人口的钱包公式（`crates/ll-world/src/entity/thin.rs:220-228`）是这条约束在实际业务代码
里的一个具体应用：

```rust
fn wallet_formula(seed: u64, id: EntityId, elapsed_ticks: i64) -> i64 {
    ...
    let mut rng = DetRng::for_entity(seed, id.as_u64(), days as u64);
    ...
}
```

**违反了会怎样**（`rng.rs` 模块文档已经点明，这里展开一层）：

- **并行结算直接不安全**。若 `resolve` 内部用一个全局 RNG（例如线程局部的 `rand::thread_rng()`），
  两个 `resolve` 调用在 `rayon` 任务池里并行执行时，谁先拿到随机数完全取决于线程调度——这次跑
  出来的世界和下次跑出来的世界会不同，即使输入的 `Intent` 序列完全一致。
- **读档后世界会分叉**。全局流的当前状态是运行时的隐藏变量，不在 `WorldState` 里，读档后无法
  恢复到存档那一刻全局流所在的确切位置——哪怕存档本身完整保存了世界的其余状态。
- **确定性重放失效**。这是最根本的后果：C3 的存在理由就是让"同一个 `(种子, 实体, 事件计数)`
  三元组在任何时候、任何线程、任何平台上得到相同结果"，全局流从定义上做不到这一点。

## C4 — 后台推进必须推到确定的 tick

**约束原文**：后台推进离屏世界时，必须推进到一个确定的世界时刻 T，不得"能跑多少跑多少"。

**代码现状：尚未实现**。当前仓库里没有找到离屏世界后台推进（规格 §9 的三档 LOD、惰性追赶）
相关的代码——`WorldState::advance(&mut self, ticks: i64)`（`crates/ll-world/src/state.rs:146-148`）
只是"把时钟推进 `ticks` 格"这一个基础操作，调用方目前只有测试代码，还没有"利用玩家思考间隙在
后台推进离屏世界"这层逻辑（规格 §9.1/§9.2，属于 P8 阶段）。

这条约束目前是**给未来实现者的红线**，不是"检查现有代码是否遵守"的问题。记在这里是因为它和
C1–C3 同属"一次违反就会摧毁确定性"的同一类风险，值得在骨架文档里提前立好标准，而不是等 P8
真正写这部分代码时才第一次讨论。**C5（见下）同样属于这一类**，区别只在于发作速度——C1–C4
违反后通常在第一次并行结算、第一次读档重放或首次触及后台推进逻辑时就能观察到分叉；C5 违反后
未必如此，同一进程内哈希表迭代顺序可能连续多次保持稳定，测试照样全绿，分叉往往要等到几百 tick
后、甚至换一次进程或平台才会暴露成状态哈希对不上——不是风险类别不同，是同一类风险里最难被
当场抓到的一种。

**为什么"能跑多少跑多少"是错的**：如果后台推进的量取决于玩家这一回合思考了多久（墙钟时间），
那么同一个存档、同一串操作，在不同玩家（思考速度不同）或不同机器（帧率不同）上会把离屏世界
推进到不同的世界时刻——这直接违反了"同一种子加同一串操作在任何机器上产出逐位相同的世界状态"
这条全项目的根本承诺（ADR 0002）。正确做法是：无论墙钟用了多久，后台推进的目标永远是一个由
游戏逻辑（例如"玩家下一次行动预计花费的世界时间"）算出的确定 tick 数，墙钟时间只决定"有没有
时间跑完这次推进"，不决定"要推进到哪"。

## C5 — 禁止让 `HashMap`/`HashSet` 的迭代顺序参与逻辑判断

**约束原文**：禁止让 `HashMap`/`HashSet` 的迭代顺序参与任何逻辑判断。无序容器的迭代顺序在不同
运行、不同平台之间不保证一致，甚至同一进程内两次构造内容相同的容器也可能产出不同的键序（**P4
期间已实测确认**：两个内容相同的 `HashMap` 给出了不同的迭代顺序）。需要顺序参与逻辑时改用
`BTreeMap`/`BTreeSet`，或对键先显式排序再遍历；`HashMap`/`HashSet` 只允许用于 O(1) 单键查找，
禁止遍历其产出的顺序去影响世界状态。

**代码现状**：这条规则在代码里**已经生效了一整个阶段**，只是没有统一编号。正面例子有两处：
`ll_core::ident::Interner`（`crates/ll-core/src/ident.rs:99-103`）的模块文档明确写着"内部的哈希表
永远不得被遍历"，只用 `to_id`（一个按插入顺序排列的 `Vec`）提供遍历；`EntityId` 专门派生了 `Ord`
（`crates/ll-world/src/entity/id.rs:33-39`），就是为了让需要确定性遍历的场景走 `BTreeMap<EntityId, _>`
的键序而不是 `HashMap` 的哈希桶序（详见 [`07-determinism.md`](07-determinism.md)"`EntityId` 派生
`Ord`"一节）。

但反面例子同样真实：`knowledge/audit/worklist.md` 的 W-05 号工单核实到，代码注释里引用这条规则的
五处地方**标号三比二分裂**——`crates/ll-world/src/state.rs:196`、
`crates/ll-sim/examples/p3_acceptance/turn.rs:356` 标成了 C3，`crates/ll-mod/src/registry.rs:66`、
`crates/ll-mod/src/topo.rs:5`、`crates/ll-world/src/entity/id.rs:30` 标成了 C4——没有一处对得上
规格原文：C3 字面只讲"随机性/RNG 流"，C4 字面只讲"后台推进到确定 tick"，都不是"容器迭代顺序"。
同一批核对还发现一处方向相反的独立错误：`crates/ll-sim/src/intent.rs:9` 把"`DetRng::for_entity`
派生的随机数序列在重放时必然相同"错标成了 C4，而这恰好就是 C3 的字面定义——两类错误方向相反，
凑在一起让读者更难从代码里猜出规律。这些错标不是笔误的巧合，是**症状**：一条规则如果不在真相源
里有自己的编号，贡献者就只能各自猜一个看起来最接近的现成编号去套。

**这条约束的来历值得记一笔**：C5 此前是一条被反复引用、被当作硬约束执行、却从未进入规格 §4
这份唯一真相源的口头约定——上述五处引用就是证据。它能够生效，只是因为每次派任务时被人手写进
指令里；漏写一次，它在那次任务里就等于没发生过，约束是否真的被执行，取决于派活者当时是否想起来
写这一句。这与 [ADR 0013](../../../knowledge/decisions/0013-ledger-vs-adr-discipline.md) 记录的
失败模式同源：重要决定只存在于会被 git 忽略、不参与评审、没有版本历史的地方，看起来"一直在
起作用"，实际上没有任何机制保证它不会被漏掉。2026-08-18 的规格修订（提交 `2f4cc26`）把这条规则
正式收编进 §4，本节随之补上——这是"约束必须进真相源"这条纪律的一次具体验证，不是抽象道理。

**违反了会怎样**：

- 与 C3 同一条失败链路，只是隐藏输入源不同：C3 是全局 RNG 流的调度顺序被卷进了 `resolve`/`apply`
  链路，C5 是哈希表的桶序被卷了进去——两者都是把一个**非确定性的隐藏输入**带进本该纯粹由
  `Intent` 与 `WorldState` 决定的计算里，后果同样是确定性重放失效、跨平台/跨进程结果不一致。
- **发作比 C1–C4 更慢，排查也更难**。违反 C1–C4 通常在第一次并行结算或第一次读档重放时就能
  观察到明显分叉；违反 C5 未必——如果代码路径恰好在同一次进程运行内反复使用同一个已构造好的
  `HashMap` 实例，它在这次运行内的迭代顺序可能保持稳定，测试因此全绿。分叉往往要等到重放发生在
  不同进程、不同平台，或哈希表被重新构造出不同桶序的时机，才会暴露为几百 tick 之后**状态哈希
  对不上**——不是某个测试突然变红，而是某天黄金基准或跨平台断言悄悄不再吻合，且没有一个明确的
  "第一次出错的地方"可供定位。
- 违反的判定标准很具体：这个值会不会被用来决定处理顺序、比较大小、拼接输出、或以任何方式影响
  `WorldState` 的最终内容？会，就是错的；只用来做一次 O(1) 查找、从不遍历、结果不依赖桶序，
  是安全的（`Interner::to_index` 即是这类安全用法）。
