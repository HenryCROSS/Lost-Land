# 规格 / 交接清单 与真实代码的不一致清单

**冻结时间**：2026-08-17，核对提交 `7a126f5`。

本清单按"先读代码，再读规格，冲突时以代码为准"的方法核对得出。每条格式统一：规格/交接清单
怎么说、代码实际怎样、判断哪个是对的、建议怎么处理。**存疑但未能完全确认的条目也列出，标注
为存疑**，不因为"可能是我理解错了"而略过。

部分条目是延续 `knowledge/handoff/p2-to-p3.md` 已经记录的发现——这些不是本次新发现，而是
"本次核对确认它们截至 `7a126f5` 仍然成立、尚未被后续阶段处理"，会明确标注延续来源。

---

## 1. 【最要紧】规格 §14.7 声称的 9 项 CI 门禁，实际只有约 5 项落地

**规格怎么说**：§14.7 列了 9 行门禁表格，措辞是"合并到 `main` 前必须全部通过，**任一项失败
即阻断**"。

**代码实际怎样**：核对 `.github/workflows/ci.yml`（写作时读取，未修改），实际存在的检查是：

- `cargo fmt --all --check`（对应"格式统一"）
- `cargo clippy --workspace --all-targets -- -D warnings`（对应"编译无警告"）
- `cargo test --workspace`，在 `ubuntu-latest` 与 `windows-latest` 双平台矩阵下跑（对应
  "全部测试通过"，双平台矩阵间接覆盖了"跨平台世界哈希一致"，因为
  `crates/*/tests/determinism.rs` 的黄金基准断言会在两个平台上各跑一次）
- `cargo deny check`（对应"许可证合规"）

**缺失的四项**：`cargo-llvm-cov` 覆盖率检查、无硬编码用户可见字符串检查（规格 §11.3）、
无手写欧氏距离检查（规格 §7.1 明确写"此项由 CI 静态检查强制"）、无死代码与过时文档检查
（规格 §13）。

**判断**：代码为准，规格措辞失实。这条延续自 `knowledge/handoff/p2-to-p3.md` 第五节的发现，
本次核对确认**截至 `7a126f5` 依然未修复**——不是"尚未来得及"，是已经被明确记录了一整个阶段
却仍未处理。

**为什么这是最要紧的一条**：这四项缺口不是孤立的文档问题，每一项都直接对应本文档组里反复
强调的某条硬约束的自动化防线——无手写欧氏距离对应环面拓扑的核心心智模型
（[`04-torus-topology.md`](04-torus-topology.md)），覆盖率与死代码检查对应规格 §13 的代码卫生
要求，而这些约束目前**只能靠人工评审拦截**。人工评审是本项目已经证明会失手的防线——
"精灵批处理支持最多 4 份偏移副本"那条错误在规格里躺了一整个阶段、经过五轮评审都没被发现，
正是靠"反向核对规格"这条纪律才被抓出来。CI 门禁的价值就在于它不依赖评审者当时是否想起来
检查——这四项缺口意味着对应的四条纪律目前完全依赖人的记性。

**建议**：`knowledge/handoff/p2-to-p3.md` 已经给出了建议方向："P3 应当要么补上，要么把规格
措辞改成实情——两者留着不一致，本身就违反 §13"。本次核对结果是**这个建议至今没有被采纳**，
应当继续作为 P3（或更早）收尾前的必办项，而不是被后续阶段继续延后。

## 2. 规格 §5 的 crate 职责描述遗漏了实体存储的归属

**规格怎么说**：§5 的 crate 列表里，`ll-world` 一行的职责描述是：

> `ll-world      WorldState、环面地形、FOV、世界时钟、昼夜四季、分区`

**代码实际怎样**：`crates/ll-world/src/lib.rs` 实际导出的模块包含 `entity`（实体存储：
`Agent`/`Arena`/`ThinPopulation` 等，见 [`06-entity-storage.md`](06-entity-storage.md)）与
`naming`（名字生成）。这两个模块是在 `cc0552e refactor: 实体存储迁回 ll-world，修正对
ll-sim 的反向依赖` 这次提交里确定归属 `ll-world` 的（详见
[`01-crate-layering.md`](01-crate-layering.md) 的"历史教训"一节），但规格 §5 的这行职责
描述**从未随这次架构调整更新**。

**判断**：代码为准。实体存储确实应该在 `ll-world`（详细论证见
[`01-crate-layering.md`](01-crate-layering.md) 关于 `ll-world`/`ll-sim` 边界的部分），这不是
代码错了，是规格文字没跟上已经做出的决定。

**建议**：把 §5 表格里 `ll-world` 一行的描述补上"居民实体存储（薄层/厚层）、名字生成"，
避免读者依据这行文字误判两个模块该放在哪个 crate。

## 3. 规格 §5 的依赖顺序文字简化了 `ll-sim` 对 `ll-platform` 的依赖关系

**规格怎么说**：§5 原文"依赖顺序：`ll-core` ← `ll-platform`/`ll-render`/... ← `ll-world` ←
`ll-sim` ← ..."，字面读法容易让人以为 `ll-sim` 只经由 `ll-world` 间接接触 `ll-platform`。

**代码实际怎样**：`crates/ll-sim/Cargo.toml` 的 `[dependencies]` 里 `ll-platform` 是与
`ll-world` 并列的**直接**依赖，用于 `intent_from_input` 把 `ll_platform::input::InputState`
映射成 `Intent`（`crates/ll-sim/src/intent.rs`）。`Cargo.toml` 里的注释已经解释了这条依赖
"不成环"，是有意添加。

**判断**：不算规格错误，是文字表达的精度不够——它描述的是一条主干顺序，没打算穷举每个 crate
的全部直接依赖。**标注为轻微/存疑**：是否值得因此修改规格文字，取决于团队认为这份"依赖顺序"
一行该有多精确；至少值得在骨架文档（本组文档已经做了）里把真实依赖图列清楚，供读者核对。

## 5. 规格 §7.2「季节更替是时间轴上的一个定时事件」——当前是纯函数派生（延续记录）

**规格怎么说**：§7.2「季节更替是时间轴上的一个定时事件，其 `Effect` 修改各城镇生产速率、
地形通行性与野怪分布表。」

**代码实际怎样**：`Tick::season()`（`crates/ll-core/src/time.rs`）是纯函数，由 `day_of_year()`
直接计算得出，不经过时间轴，也没有对应的 `Effect` 变体（`crates/ll-sim/src/effect.rs` 现有
六个 `Effect` 变体里没有"季节切换"相关的一项）。

**判断**：`p2-to-p3.md` 已记录此项，并指出"P3 要建时间轴调度器，届时必须决定：季节到底是
纯函数派生（当前实现）还是时间轴事件（规格原文）？两者不能都留着"。本次核对发现
`docs/superpowers/plans/2026-08-17-p3-turn-combat.md`（Task 8）已经提出了折中方案——
"保留纯函数派生作为『现在是什么季节』的查询，同时在时间轴上放一个季节切换事件用于触发
`Effect`"，理由是"查询必须是纯函数……而『切换那一刻要改各城镇生产速率』是一次性状态变更，
天然是 `Effect`。两者不矛盾"。**但截至本次核对，这个方案尚未在代码里实现**——`effect.rs`
里没有季节相关的 `Effect` 变体，时间轴里也没有季节事件。

**建议**：延续 P3 计划已经给出的方向即可，只是需要有人真正落地并同步更新规格 §7.2 的措辞
（把"是"改成实际的"查询纯函数 + 切换时刻的 Effect"两段式描述）。

## 7. `resolve` 未实现：代码现状与规格 §4 描述的完整管线之间有实质差距

**规格怎么说**：§4 完整描述了 `Intent → resolve → Effect → apply` 四段管线，读起来像是
一个已经完整存在的架构。

**代码实际怎样**：截至本次核对，`crates/ll-sim/src/` 下有 `intent.rs`、`effect.rs`、
`apply.rs`、`timeline.rs`，**没有 `resolve.rs`**。`lib.rs` 顶部模块文档明确写着 `resolve`
"是批次 C 的内容"，尚未实现。

**判断**：这不是规格与代码的冲突——规格描述的本来就是终态架构图，不是"当前进度快照"。列在
这里是提醒读者：**读规格 §4 时容易把它当成"代码已经这样运作"，实际上这条管线目前只有后三分
之二落地**。详见 [`02-core-data-flow.md`](02-core-data-flow.md) 的完整说明。

**注意**：由于另有代理在并行实现 `ll-sim`，这条差距随时可能已经被填上——请以
`crates/ll-sim/src/` 目录下是否存在 `resolve.rs` 为准，不要依赖本文档的时间快照判断。

## 8. 存疑：`TerrainKind` 的反序列化校验口径与"本体即 Mod"原则的阶段性冲突

**规格怎么说**：§15「本体即 Mod」原则要求本体内容与 mod 内容走完全相同的注册表 API，本体
不享有特权通道。

**代码实际怎样**：`crates/ll-world/src/terrain.rs` 的 `TerrainKind` 反序列化校验（`is_known`）
目前只接受本体内置的常量 ID，任何其他 ID（包括未来 mod 注册的自定义地形）都会被拒绝反序列化。
代码注释里**已经自己承认**这是刻意的阶段性取舍，并标注为"P4 迁移债务"：mod 注册表落地前，
拒绝未知 ID 比静默接受更安全。

**判断**：这不算隐藏的不一致——代码注释已经明确记录了这个限制、原因与后续动作，规格 §15
的阶段表 P4 行也确实认领了"注册表落地"这项工作。**标注为存疑但不列为需要处理的缺口**：
放进本清单只是为了完整性，这是我核对 §15"本体即 Mod"原则时顺带发现的关联点，不是本次核对
的重点区域（那需要检查整个内容注册表/mod 加载链路，本文档组的核对范围不含此项）。
