# 整数纪律

**冻结时间**：2026-08-17，核对提交 `7a126f5`。
背景决策见 [ADR 0002 — 世界状态一律用整数，禁止浮点](../../knowledge/decisions/0002-integer-only-world-state.md)。

## 规则

**世界状态中不出现任何浮点数。** 浮点只允许出现在渲染层、音频层、脚本内部计算三处（[ADR 0020](../../knowledge/decisions/0020-scripts-may-use-floats-internally-boundary-type-gated.md)），且结果绝不得回流入世界状态。判据统一为「结果最终会不会变成世界状态的一部分」，不按模块列举清单。脚本浮点的安全边界收拢在 `register_fn` 的类型签名处——`ScriptValue` 排除浮点变体，跨越 FFI 边界的值只能是整数/字符串等类型，完整判据与残余风险见 ADR 0020，不在此重复。

| 世界量 | 表示 | 代码 |
|---|---|---|
| 位置 | 瓦片坐标 `i32`（`TorusPos`） | `crates/ll-core/src/torus.rs:73-76` |
| 时间 | 刻度 `i64`（`Tick`，一刻度 = 一游戏秒） | `crates/ll-core/src/time.rs:46` |
| 货币、价格、比例、速率 | 千分之一定标整数 `Milli(i64)` | `crates/ll-core/src/scaled.rs:21` |
| 属性 | `i32`（`BaseStats` 等） | `crates/ll-world/src/entity/stats.rs` |
| 距离 | 只提供平方值 `squared_euclidean`，不开方 | `crates/ll-core/src/torus.rs:174-179` |

## 为什么：跨平台确定性，不是"性能更好"

这是最容易被误解的一点——整数纪律**不是**为了性能（虽然整数运算通常也更快），核心理由是
**跨平台确定性**。ADR 0002 的表述：

> 同一段 `f64` 表达式在不同平台、不同优化等级、不同指令集扩展（x87 与 SSE 的中间精度差异、
> FMA 融合与否）下可能产出不同的最低位。差一位，世界就分叉。

这条原理有一个容易被忽略的推论：**不是所有浮点运算都不确定**。`crates/ll-world/src/noise.rs`
模块文档专门澄清过这一点——IEEE 754 规定 `+ - * / sqrt` 必须逐位精确，Rust 不开 fast-math、
LLVM 也不会重排浮点运算（浮点加法不满足结合律），所以只用四则运算的浮点本身是跨平台确定的。
真正不确定的是 `sin`/`cos`/`exp`/`pow` 这类**超越函数**——IEEE 754 没有规定它们的精度，不同
`libm` 实现结果不同。

这个区分解释了地形生成为什么选"模格点"方案而不是"4D 噪声投影"（规格 §7.1 记录的另一次修正）：
4D 投影需要 `sin`/`cos` 才能把 2D 环面坐标嵌入 4D 空间，这才是真正的风险来源，而不是"用了浮点"
本身。但即便四则运算浮点在理论上是确定的，本项目仍然选择在世界状态里**完全**禁用浮点而不是
"只禁用超越函数"——这是工程上的简化：一旦允许"某些浮点用法是安全的"，就需要每个开发者在写
代码时判断"我这里用的运算算不算安全"，这个判断成本比"世界状态里看到 `f32`/`f64` 就是错的"
这条零判断成本的规则要高得多，也更容易在评审中漏判。

## `Milli`：为什么用千分制定标整数而不是定点数库

`crates/ll-core/src/scaled.rs:21`：

```rust
pub struct Milli(pub i64);
```

`Milli(1_500)` 表示 1.5。ADR 0002 记录了被否决的选项：

> **定点数库（如 `fixed` crate）**：能表达小数且跨平台确定，但引入一个运行时依赖，而 `ll-core`
> 必须保持零依赖……本项目绝大多数世界量本来就是整数，只有价格与比例需要小数精度，一个千分之一
> 定标的 `i64` 就够，不值得为此背一个库。

`SCALE = 1_000`（而不是 100，即"到分"）的取舍理由在 `scaled.rs:11-14`：经济系统的价格需要到
"厘"的精度，若只到"分"，大宗商品按百分比抽税时的舍入误差会在长期模拟中累积成可观偏差——这是
针对规格 §9.3"必须内置稳定器"（价格软上下限、防止通胀通缩螺旋）这个长期风险预先做的精度选择。

`Milli::whole()`（`scaled.rs:51-53`）取整数部分时**向零截断**而非向下取整，理由是让正负方向
对称：

> 向下取整会使 `-1.5` 变成 `-2` 而 `1.5` 变成 `1`，经济结算中的盈亏就会产生系统性偏移。

比例运算（`checked_mul_ratio`/`mul_ratio`，`scaled.rs:59-77`）用分数（`numerator`/`denominator`）
而不是小数表达，中间乘积用 `i128` 承接，避免"先乘后除"时的假溢出——这也是全项目"比例用分数而
非小数"这条更广泛纪律（ADR 0002 提到的"距离只提供平方值，比例运算用分数而非小数"）的具体实现。

## 浮点边界：哪些地方允许浮点，为什么危险不在"用没用浮点"而在"有没有回流"

`ll-render`、`ll-platform` 的输入/渲染层允许浮点（wgpu 本身要求 `f32`，见
`crates/ll-render/src/lib.rs:10-13`）。真正的红线不是"渲染层不许出现浮点"，而是：

> 这些值绝不可回流入世界状态或被存档序列化。

`knowledge/handoff/p0-to-p1.md`（第二节）与 `p1-to-p2.md`（第一节）**逐字重复**了同一条警告，
说明这是一条被反复验证过、每个阶段交接都要重申的高风险点：

```
错误：world.entity_pos = lerp(from, to, t)   // t 是浮点，世界状态被污染
正确：world.entity_pos 始终是整数格坐标
      渲染层自己算插值，结果只用于本帧绘制，不写回
```

`p1-to-p2.md` 给出的判断标准最实用：**这个浮点值会不会被 `serde` 写进存档？会，就是错的。**

这条警告被反复强调的原因是它"看起来完全无害"——子格插值（角色在两格之间平滑移动的视觉效果）
是渲染层的正常需求，写 `lerp(from, to, t)` 这行代码本身没有任何编译错误或运行时错误，污染是
**渐进的、无声的**。ADR 0002 的原话：

> 等黄金基准跨平台对不上时，已经无从追溯是哪次改动。

截至本次核对，`ll-world`/`ll-sim` 的实体位置（`Agent::pos: TorusPos`）全部是整数格坐标，
子格插值这类效果尚未实现（P3 阶段还在做地格对齐的移动），这条红线暂时没有被真正考验过——
但正因为如此，它更需要被明确写进骨架文档：**一旦开始做子格移动动画，这是最该第一时间检查的
地方，不要等到跨平台哈希对不上才回头排查。**

## `WorldState::hash` 是这条纪律生效与否的度量

`crates/ll-world/src/state.rs:150-170` 的 `hash()` 方法把整个世界状态归约成一个 64 位摘要
（用 `ll_core::hashing::StateHasher`，FNV-1a，理由见 [`07-determinism.md`](07-determinism.md)）。
`crates/ll-core/tests/determinism.rs` 与 `crates/ll-world/tests/determinism.rs` 里的黄金基准
测试就是靠比对这类摘要来发现"某次改动是否意外引入了平台相关行为"——浮点回流是这类意外最常见
的成因之一，测试文档顶部专门写了"绝不允许测试挂了就把期望值改成实际值"，见
[`07-determinism.md`](07-determinism.md) 的完整讨论。
