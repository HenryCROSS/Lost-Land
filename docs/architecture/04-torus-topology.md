# 环面世界拓扑

**冻结时间**：2026-08-17，核对提交 `7a126f5`。

## 适用范围

环面拓扑**仅适用于大陆世界地图层**（规格 §7.1）。进入具体区域后的分区场景是有界局部地图，
四周由地形自然收边，不做环绕。当前仓库（`ll-world`）还没有分区场景的实现，`WorldState` 里的
`terrain: ChunkGrid` 就是那张环面大陆图本身，本文档讨论的全部是这一层。

## `TorusSize::delta`：为什么返回"最短带符号偏移"

代码：`crates/ll-core/src/torus.rs:137-154`

```rust
pub fn delta(&self, from: TorusPos, to: TorusPos) -> (i32, i32) {
    (
        Self::shortest_offset(to.x - from.x, self.width as i32),
        Self::shortest_offset(to.y - from.y, self.height as i32),
    )
}

fn shortest_offset(raw: i32, extent: i32) -> i32 {
    let forward = raw.rem_euclid(extent);
    if forward * 2 > extent {
        forward - extent
    } else {
        forward
    }
}
```

环面上任意两点之间**存在四条候选路径**（沿 x 轴正向/反向、沿 y 轴正向/反向的组合），朴素的
`to - from` 只算出其中一条（不绕接缝的那条），完全可能不是最短的。`delta` 的职责就是在两条
候选（沿该轴正向绕、反向绕）里选更短的一条，逐轴独立计算。

**为什么必须有稳定的打破平局规则**：`shortest_offset` 用 `forward * 2 > extent`（严格大于）
而不是 `>=`，模块文档写明这是刻意的：

> 若正向距离超过半周，则反向更近。用 `>` 而非 `>=` 使恰好半周时取正方向，即打破平局规则。

当两个方向等长时（例如世界宽 10、目标恰好在正对面 5 格处），如果没有固定规则，两次调用可能
一次返回 `+5` 一次返回 `-5`——这在单次调用里看不出问题，但一旦这个值参与了任何需要跨调用/跨
平台一致的计算（寻路方向选择、AI 决策的随机种子输入等），"恰好半周"这个边界情形就会成为
确定性重放偶发分叉的根源。这条规则本身也是环面坐标模块被要求"必须提供"（不允许在别处手写距离，
规格 §7.1 并由 CI 静态检查禁止手写欧氏距离）的原因之一：手写的距离计算几乎不会想到去处理这个
平局情形。

## 距离与位移是"尺寸的方法"而不是"坐标的方法"

`TorusSize::delta`/`chebyshev`/`manhattan`/`squared_euclidean` 全部定义在 `TorusSize` 上，
不是 `TorusPos` 上。模块文档给出的理由：

> 脱离世界尺寸，两个环面坐标之间的距离根本无法定义。这个 API 形状让"忘记传尺寸"变成编译错误，
> 而不是运行时的错误答案。

这不只是 API 品味问题：如果 `TorusPos::distance_to(&self, other: &TorusPos) -> u32` 这样设计，
调用点看起来完全正常，但对于同一对坐标，在宽 100 的世界和宽 10 的世界里"最短路径"是不同的——
方法签名本身给不出这个信息，只能靠调用者自己记得传对世界尺寸（或者悄悄假设了一个全局唯一的
世界尺寸，这在多世界/测试场景下会出错）。现在的设计把"没有世界尺寸就无法回答距离"这件事焊进
类型系统：你物理上拿不到一个脱离 `TorusSize` 的距离值。

## 为什么跨接缝绘制不需要画多份拷贝

`Camera::world_to_screen`（`crates/ll-render/src/camera.rs:29-35`）：

```rust
pub fn world_to_screen(&self, pos: TorusPos) -> (i32, i32) {
    let (dx, dy) = self.world.delta(self.center, pos);
    (
        offset_screen(LOGICAL_WIDTH as i32 / 2, dx),
        offset_screen(LOGICAL_HEIGHT as i32 / 2, dy),
    )
}
```

模块文档解释了这里的设计取舍：

> 环面世界里，相机附近的目标可能"绕过接缝"才最近。常见做法是把整个场景画 2~4 份偏移拷贝以
> 覆盖接缝，那既慢又容易出边界错误。这里直接用 `TorusSize::delta` 求出目标相对相机的最短带
> 符号位移——绕接缝的情形已经被它处理掉了，每个目标仍然只画一次。

`camera.rs` 的测试 `跨接缝的目标按最短方向绘制而非绕远`（`camera.rs:132-146`）验证了这一点：
相机在 `x=1`、目标在 `x=31`（世界宽 32），期望目标画在相机左侧 2 格处（向西绕），而不是右侧
30 格处（向东走到底再绕回来）。

这正是规格 §7.1 记录的一次真实教训：

> 原方案为"精灵批处理支持最多 4 份偏移副本"。P1 实施时发现不必要：`TorusSize::delta` 返回的
> 已是最短位移，多副本方案既慢又容易出边界错误。

规格里这条错误的历史意义比表面看起来更大——`knowledge/handoff/p2-to-p3.md` 把它作为整个项目
"必须反向核对规格"这条方法论纪律的起源案例："精灵批处理需支持最多 4 份偏移副本"这条错误在规格
里躺了整整一个阶段、经过五轮评审都没被发现，因为所有评审都在问"实现是否满足规格"，没人反过来
问"规格是否已经被实现淘汰"。

## 教训案例：`DrawOrder` 的排序键曾经用错坐标系

这是本文档要重点记录的一处"位置修好了，但排序键没跟上"的真实缺陷，值得完整讲清楚因果链。

### 缺陷是什么

`DrawOrder`（`crates/ll-render/src/sprite.rs:87-114`）是精灵的绘制顺序键，字段是
`(layer, foot_y, entity)`。`foot_y` **曾经**被定义成"世界纵坐标"——`ll-render::sprite`
最初的实现直接传世界 y 值。P2 阶段的验收 demo 也是这么传的，而且没有暴露问题。

但环面世界里 `y = 世界高度 - 1` 与 `y = 0` **在屏幕上相邻**、在世界坐标数值上却相差整个世界
高度。如果排序键用世界坐标，站在南北接缝两侧、屏幕上明明紧挨着的两个单位，排序键会相差一个
巨大的数——排序完全不对，站在接缝北侧的单位会被南侧的单位错误遮挡。

### 为什么 P2 没发现

`knowledge/handoff/p2-to-p3.md` 记录得很直接：

> P1 用 `TorusSize::delta` 解决了跨接缝的**位置**，但**排序键没跟上**。P2 只有一个实体、地形
> 又平铺，所以看不出来。

这是这类缺陷最危险的特征：修位置的那次改动（`Camera::world_to_screen` 用 `delta` 算最短偏移）
是完全正确的，也确实解决了"画在哪"的问题。但"按什么顺序画"是另一套独立的计算，没有人在改
位置的时候想起来同步检查排序键用的是哪个坐标系——两者概念上很接近（都叫"Y 坐标"），代码上
却是完全独立的两处，没有类型系统或测试把它们绑在一起。P2 阶段世界只有一个实体，不存在"谁挡住
谁"的问题，这个缺陷因此完全不可见，直到 P3 引入第二个实体才会真正表现出来。

### 现在的修法

`crates/ll-render/src/sprite.rs:96-104`（`DrawOrder::new` 文档）现在写得很明确：

> `foot_y` 应为精灵脚底（而非图像原点）的**屏幕**纵坐标（相机相对），不是世界纵坐标。
> 必须用屏幕坐标：环面世界里 `y = 世界高度 − 1` 与 `y = 0` 在屏幕上相邻却相差整个世界高度，
> 用世界坐标会让跨南北接缝的排序反转，接缝北侧的单位被南侧的错误遮挡。屏幕坐标由
> `Camera::world_to_screen` 得出，它已处理环面最短位移，因此接缝两侧的相邻格在屏幕上也相邻。

对应的测试 `跨接缝的两个实体按屏幕纵坐标排序`（`sprite.rs:143-152`）直接用注释写明了这条修复
的验证逻辑：屏幕坐标下北侧单位 y 更小（更靠上，应先绘制），断言 `north_on_screen < south_on_screen`。

git 历史上对应的提交是 `c0768af fix: DrawOrder 的排序键改用屏幕纵坐标`。

### 这条教训真正想说明什么

**"位置对了"不等于"依赖同一份位置信息的其余计算也对了"。** 环面世界里几乎任何涉及"两个坐标
谁在前/谁更近/谁挡住谁"的计算，都需要经过环面感知的换算（`delta` 或 `world_to_screen`），而不
能直接比较原始坐标数值。修复一处（相机定位）之后，习惯性地假设"环面问题已经解决"是这类缺陷
反复出现的根源——真正安全的做法是每次引入新的"比较/排序/距离"逻辑时都问一次："这个值是原始
世界坐标，还是已经过环面换算的相对值？"

## 气候周期性条带：规格写了，代码里没有

规格 §7.1 提到"气候为周期性条带：两条赤道 + 两条极圈"。`knowledge/handoff/p2-to-p3.md` 的
反向核对已经记录过这一点：**全仓零实现，无阶段认领**。核对本文档时依然如此——`ll-world` 里
没有任何气候/纬度带相关的代码。这条不算"发现的新问题"，只是延续记录，避免读者以为漏查了。
